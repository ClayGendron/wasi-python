## The facts

**What fails.** A static CPython links every Rust extension module into one Rust static library, so one dependency graph holds them all. orjson 3.13.0 requires `pyo3-ffi = "0.29"` and pydantic-core 2.50.4 requires `pyo3 = "0.30.1"`. Each `pyo3-ffi` declares `links = "python"`, and cargo admits one package per `links` value in a graph: "package `pyo3-ffi` links to the native library `python`, but it conflicts with a previous package which links to `python` as well" (EXECUTED, cargo 1.97.0, specification 190, Decision 3). A `[patch.crates-io]` cannot cross a semver line, so only orjson's requirement can move.

**The change.** In `Cargo.toml`, `pyo3-ffi = { version = "0.30", … }` and, under `[build-dependencies]`, `pyo3-build-config = { version = "0.30" }`, each from `"0.29"`. No source file changes.

**Checked.** With 0001, this patch and 0003, orjson 3.13.0 built for `wasm32-wasip1` on Rust 1.97.0 in one library with pydantic-core 2.50.4 and the build's own probe module, one `pyo3-ffi` (0.30.1) in the graph, and `PyInit_orjson` defined (EXECUTED, 2026-11-15, in scratch; built, not linked into CPython or run). orjson's suite and golden job in the guest are the proof that its behaviour is unchanged.
