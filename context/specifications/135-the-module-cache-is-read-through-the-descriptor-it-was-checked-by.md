## The problem

A `.cwasm` is native code wasmtime runs as it finds it. Spec 113 made the grant judge the guard (no guest reaches any cache a process of this user could use) and the modes a filter (a folder at 0700, a file at 0600 with one name), and it narrowed the window between the check and the load with a second `lstat` after `Module.deserialize_file` (`_engines.py:233-237`). What is left is a check and a load that are not of the same file:

- `private()` (`_platform.py:556-577`) takes `os.lstat(path)` of the **leaf**: the cache folder, then the file. `Module.deserialize_file` then opens the **path** itself (it takes no descriptor). Between the two, whoever can write the folder, or any ancestor of it, can replace the file or the folder. The second `lstat` catches a swap that changes the stamp, not one that restores it, and not one timed after it.
- **No ancestor is checked.** The default cache is `~/Library/Caches/wasi_python`, `~/.cache/wasi_python` or `%LOCALAPPDATA%\wasi_python\cache`, from `$HOME` (`_engines.py:85`, `_platform.py:534`). Nothing says who owns `~`, `~/Library`, `~/.cache` or the folder `$XDG_CACHE_HOME` names. The judge refuses a guest a grant there; it does not ask whether another **user** owns the way to it.

**Reproduced for one user** (EXECUTED, h04, v01, r02): a swap by this user between the check and the open loaded the planted module (deterministic, with a stand-in that swaps inside `deserialize_file`; and a blind race, 3 hits in 5,000). **Not observed:** another user owning an ancestor. The audit would not run as another account on the owner's machine.

**Who it would reach.** Only a deployment where the runner runs as one user with a cache under a folder another, lower-trust user owns or can write: root under `sudo` keeping `HOME`, a container or CI step with a mapped or shared home, a home on a shared folder, or `$XDG_CACHE_HOME` or `$WASI_PYTHON_CACHE` pointed under `/tmp`. Whether that is supported is the owner's to say.

**Three notes of the same unit** (h04, EXECUTED):
- macOS extended ACLs are invisible to `private()`, which reads `st_mode` alone: an allow entry granting everyone write and `file_inherit` on the cache folder passes, and every new `.cwasm` inherits it (`acl_run.log`).
- A set given through `artifacts=` (not held by its checked digest) is hashed by `_artifacts._digest(binary)` and then compiled by `Module.from_file` (`_engines.py:155`, `195`): two reads, so a file changed between them is compiled and cached under a digest it does not have, and a later call that checked its set against `SHA256SUMS` loads that entry (`unheld_run.log`). The `want` path already reads once and hashes those bytes.
- `cache_dir=""` is `Path("")`, which is `Path(".")`, the working folder (`_engines.py:80`): not refused.

## Decisions

### 1. The owner's answer of 2026-10-25, and what follows from it

**Question 112** asked: is running the runner as root or as another user with a different user's `$HOME`, `$XDG_CACHE_HOME` or `$WASI_PYTHON_CACHE` (sudo keeping `HOME`, a container or CI step with a mapped home, a home on a shared or world-writable folder) a configuration wasi_python supports, or one the security model declares the embedder's own risk, as it declares `cache_dir` trusted input today?

**The answer** (the owner, 2026-10-25, `../decisions.md`): not supported, on the condition that no real use a developer may want breaks. Nothing in this specification refuses a call, except an empty `cache_dir`, which names no folder (Decision 4): a cache whose path passes through a folder another user can write is **not used**, the module is compiled and kept in memory, and one warning says to set `$WASI_PYTHON_CACHE`; a developer under `sudo -E` loses the cache for that process, never the run. So the condition holds, this specification is **defence in depth**, it lands after 0.1.0 when a slot is free, and the security model's cache bullet says in one sentence that the runner trusts every folder on the way to its cache to be this user's ("run it with your own home, or set `$WASI_PYTHON_CACHE` to a folder of yours").

### 2. The cache is opened once, by descriptor, and what is read is what was checked

On POSIX, `_load` opens the cache folder with `os.open(cache, O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC)`, checks that descriptor with `os.fstat` (a directory, this user's, no bit for group or other), then opens the file **relative to that descriptor** with `os.open(name, O_RDONLY | O_NOFOLLOW | O_CLOEXEC, dir_fd=folder_fd)`, checks it with `os.fstat` (a regular file, this user's, mode 0600 or stricter, one name), and hands wasmtime **that descriptor**: `Module.deserialize_file(engine, f"/dev/fd/{fd}")` (Linux: `/proc/self/fd/{fd}` where `/dev/fd` is absent), the same device spec 129 uses to give wasmtime a pipe. wasmtime opens that name with a plain open and maps the file it gets. On macOS opening `/dev/fd/N` duplicates the descriptor (the same open file, EXECUTED by the review); on Linux it reopens the same inode with a new open file description; either way the file mapped is the file checked, whatever the path now names, so the stamp re-check after the load goes: the file loaded is the file checked, by construction. That is identity, not content: wasmtime maps the file lazily, so what it runs still rests on the `fstat` check that no one but this user can write that inode (this user's, 0600, one name, no access list). The runner opens `/dev/fd/{fd}` itself first; if that fails, it loads by path with the stamp re-check, as on Windows, and never replaces the file for that reason, so a system without `/proc` (some sandboxes and chroots) keeps its cache and never compiles and rewrites it every process. `_file_stamp` stays for that fallback and for Windows (below). Both descriptors are closed in a `finally`. Which name wasmtime is given and how the file is opened are the platform's (one method on `_Posix`, one on `_Windows`), so `_load` has no platform branch. **The builder measures** that `deserialize_file` through `/dev/fd/N` maps the file as it does by path (wasmtime `mmap`s a `.cwasm`); if a platform reads it whole instead, the landing notes record the cost and the build review decides whether the plain path with the stamp re-check stays there.

`private()` keeps its signature for the other callers and gains a sibling that takes a descriptor (`private_fd(fd, *, is_dir)`), so the judge's `test_runner_module_caches.py` rows hold unchanged. The folder is still made with `mkdir(mode=0o700)` first, as today.

**On Windows** there is no descriptor name wasmtime can open, so the load stays by path, and the window from the check to wasmtime's open is closed with a held handle. The runner holds a read descriptor of the `.cwasm` (`os.open(path, os.O_RDONLY | os.O_NOINHERIT)`) from its check until `deserialize_file` returns, and compares `os.fstat` of it with the `lstat` it checked; Python's `os.open` there shares read and write but not delete, so while it is open the name cannot be renamed or removed, and wasmtime's own open (read and execute access, read sharing) is compatible with it. The stamp re-check after the load stays. The builder's Windows leg is the evidence; if wasmtime's open fails while the handle is held, the handle is dropped, the stamp re-check alone stays, and the landing notes say so. `_Windows.private` keeps its reparse-point and one-name checks, and the README says the grant rule is the guard there, as 113 said.

### 3. Every ancestor of the cache folder is this user's or root's, and not writable by others

On POSIX, before the cache is used, each ancestor of the resolved cache folder (`os.path.realpath`, then every prefix up to `/`) is `lstat`ed and must be a directory owned by this user or by root (uid 0), and either no one but its owner can write it (`st_mode & 0o022 == 0`) or it carries the sticky bit (`st_mode & stat.S_ISVTX`), as `/tmp` does, where no one but an entry's owner, the folder's owner and root can rename the entry. The rule is `sshd`'s `StrictModes` for `~/.ssh`, which the same deployments already live under. A cache that fails is **not used**: the module is compiled and kept in memory, and one `RuntimeWarning` names the ancestor and why (the existing `_cache_warning`). It is raised inside `_module_miss` once per flavor per process (a later call finds the module in memory), under the compile lock of that module only, never the cache lock, as 113's warnings are; a warning filter of `error` makes it an exception, which is the embedder's choice. Nothing is refused: a call still runs. A swap between this walk and the open needs a folder another user can write, and the walk has just shown there is none on the way; root is trusted. `O_NOFOLLOW` guards the cache folder itself (it applies to the last name only), and Decision 2's `fstat` checks what was opened. The walk reads owners and mode bits only; an access list on an ancestor is not read (Scope, Out). The walk takes the `lstat` it calls as a parameter, `os.lstat` by default, so the judge can stand in a foreign owner (Decision 6, row 2).

`/Users/<me>` and `/home/<me>` are the user's; `/Users`, `/home`, `/Library`, `/var` are root's at 0755; `$XDG_CACHE_HOME=/tmp/x` passes only because `/tmp` is root's and sticky and `/tmp/x` must be this user's; a sticky folder another user owns is refused, since its owner can rename this user's entries in it. A cache under a folder another user owns, the F4 case, is not used, and the warning says to set `$WASI_PYTHON_CACHE`.

### 4. Access lists, the two reads, and the empty `cache_dir`

- **Access lists on the cache folder and file:** `_Darwin.private_fd` refuses a folder or file for which `acl_get_fd_np(fd, ACL_TYPE_EXTENDED)` (in `libSystem`, through ctypes, as `_Darwin` already calls `sysctlbyname`) returns an access list, any entry, allow or deny, and frees what it returns with `acl_free`; NULL with `errno` `ENOENT` is no list and passes, and NULL with any other `errno` is an `OSError`, so the cache is not used, with the warning. The runner's own folder and files carry none (EXECUTED by the review, the default cache folder). The system's `listxattr` does not list access lists on macOS, and `os.listxattr` is not built there (EXECUTED by the review), so there is no cheaper test. On Linux, `os.listxattr(fd)` naming `system.posix_acl_access` or, on the folder, `system.posix_acl_default` refuses the same way (`ENOTSUP` from a file system without extended attributes is no list). Any list on the folder, an inheritable one included, means the folder is not used and nothing is written into it, so an inheritable list cannot make every process write a `.cwasm` the next one refuses. A refused folder or file is the cache not used, with Decision 3's warning, never a refused call. Access lists on the ancestors are not read: a macOS home carries a `deny delete` entry for everyone (EXECUTED by the review), so a presence test there would refuse every default cache (Scope, Out).
- **One read for every compile:** `_module_miss` reads the binary's bytes once, hashes them, compares with the digest the key was made from and compiles from those bytes, for the `want` path (as today) **and** the `artifacts=` path, so a `.cwasm` under a digest always holds that digest's code; `Module.from_file` is no longer used. This costs no new read: wasmtime-py's `Module.from_file` reads the whole file into memory too, so the compile's read stays one read, now hashed and compared, for one SHA-256 pass over bytes already in memory; recorded. For a set given through `artifacts=`, the `ArtifactsMissing` message says the binary changed while it was read, not that it failed its `SHA256SUMS`.
- **`cache_dir=""`** is refused with `ValueError` in the argument checks ("cache_dir must be a folder, True, False or None; an empty string names none"), since it can only be a mistake (an unset variable read as `""`). **A relative `cache_dir`** keeps working, as it does today: it is made absolute with `os.path.abspath` at the call's argument check, against the process's current folder read once at that call, so the folder judged is the folder used, and a later `chdir` in the embedder does not move it; `$WASI_PYTHON_CACHE` is made absolute the same way.

### 5. The security model and the README

The security model's cache bullet gains the answer to question 112 (Decision 1) and one sentence: "On POSIX the runner uses a cache only when every folder on the way to it is yours or root's and no one else can write it, and it loads a compiled module through the descriptor it checked; on Windows the grant rule is the guard, and the file is held open from its check until it is loaded." The pages that say what the runner loads and what `cache_dir` takes say the same (Design). The README's cache paragraph says the same in one line. The CHANGELOG line: "A compiled module is loaded through the descriptor it was checked by, so the file read is the file checked; a cache whose path passes through a folder another user can write is not used, with a warning; a set given through `artifacts=` is hashed and compiled from one read; a cache folder or compiled module with an access list (macOS, Linux) is not used; on Windows the file is held open from its check to its load; `cache_dir=''` is refused, and a relative `cache_dir` is made absolute at the call."

### 6. The checks first

One unit file, `tests/unit/test_runner_module_cache_read.py`, in `own-runner`:

1. **The swap inside the load is impossible, not caught:** the stand-in for wasmtime-py (113's L9 row's shape) swaps a 0644 module in **and restores the original's stamp** inside `deserialize_file`; today the restored stamp passes and the swapped module is loaded (red); after, the stand-in receives a `/dev/fd/N` path and the module loaded is the checked file's (green). POSIX only. Where `/dev/fd/{fd}` cannot be opened (a failing open passed as the load's parameter), an existing `.cwasm` still loads by path, compiled 0 loaded 1, and is not rewritten. On Windows, an `os.replace` over the `.cwasm` inside the stand-in's `deserialize_file` raises `PermissionError` (the held handle), and the stamp re-check still runs.
2. **An ancestor another user owns or can write is not used:** the refused and passing modes are real folders under `tmp_path` (0777, 1777) and `/`; the foreign owner alone uses a stand-in, passed as the ancestor walk's `lstat` parameter (as `trap_handlers_ready` takes `handler_base`), never a field of the process object or a module global. 3. **An access list on the cache is refused** (macOS: `chmod +a "everyone allow write" <folder>` in the row; Linux: `setfacl` where it is installed and the file system takes it; skipped with its reason elsewhere): the folder is not used; a `.cwasm` with an access list in a folder without one is compiled around and replaced; a folder whose list is only inheritable is not used and no `.cwasm` is written into it.
4. **One read:** an `artifacts=` set whose binary is swapped between the digest and the compile (a stand-in for the file reads) raises `ArtifactsMissing` saying the binary changed while it was read, never caches.

## Intent

After this specification, the file wasmtime deserializes is the file the runner checked, because both are the one open file behind one descriptor; the way to the cache is judged as `sshd` judges the way to a key, so a cache under another user's folder is not used and the embedder is told why; a compiled module always holds the code of the digest it is filed under; the two inputs that could silently widen the cache, an access list and an empty `cache_dir`, are refused, and a relative `cache_dir` is the folder it names at the call. On Windows the grant rule stays the guard and the file is held open from its check to its load, said plainly.
