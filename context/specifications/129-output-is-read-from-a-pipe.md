## The problem

A guest that writes 32 MiB to stdout in 64 KiB pieces costs the product **156 to 242 ms** where bare wasmtime-py writing the same bytes to a file costs **35 to 42 ms**, in the same windows. The spike called it 210 µs a write. It is not one write: wasmtime's preview1 `fd_write` hands a stream its bytes in pieces of at most **4,096 bytes**, so 512 writes of 64 KiB are **8,192 callbacks**, and a `print` of one line is one callback too. The cost is per piece, about 14 µs, whatever the guest's write size.

Per piece, three parts, none of them the copy. About **3.4 µs** is wasmtime's own stream worker: the C API wraps a custom stdout in an `AsyncWriteStream` whose task runs on wasmtime-wasi's tokio thread, so each piece is a hand-off to that thread and back, paid even when the callback is libc's `write`. About **4.7 µs** is the ctypes crossing onto that thread, which has no Python thread state: Python makes one and destroys it on every callback (the memo saw a fresh `Dummy-N` thread name on each). About **2.8 µs** is the Python body: the lock, the table lookup, `string_at`, `_Stream.write`. The copies are two or three of those microseconds. Five cheaper callbacks saved 12 ms of 120 at best. The two parts a callback cannot touch are the two largest.

For 10,000 writes of 100 bytes, the shape `print` makes, the product costs **305 ms** where a file costs 48: about 25 µs a line.

The way out that keeps every promise: wasmtime writes each stream into a **pipe** the runner opened, through the public `stdout_file` setter and a `/dev/fd/N` path, and one runner thread reads both pipes into the two capped streams. wasmtime's file path writes on the guest thread with no worker, no second thread and no Python per piece. Prototyped on the real runner by monkeypatching: 32 MiB in **36 to 48 ms** (the file floor), 10,000 small writes in **35 ms**, the cap exact at the byte, `truncated` named, 1,000 interleaved stdout and stderr writes kept apart, nothing added to the empty call.

What a pipe does not give on Windows: a path to an anonymous pipe, or `poll` on one. A named pipe has a path, but whether wasmtime's `File::create` opens its client end was not established, and no Windows host was in the session. So this specification moves **macOS and Linux** and leaves **Windows on today's callback**, behind one platform operation, with the Windows move reserved as its own specification.

### 2. Two captures behind one platform operation

`_platform._Platform` gains `output_channel(self) -> tuple[str, int, int] | None`: a path wasmtime can open for writing, the descriptor the runner reads the same bytes from, and the runner's own write descriptor to close once wasmtime has opened the path; or `None` when the platform offers no such channel.

- `_Posix.output_channel`: `r, w = os.pipe()`; returns `(f"/dev/fd/{w}", r, w)`. macOS's `/dev/fd` is the descriptor file system; Linux's is a link to `/proc/self/fd`, through which a pipe is reopened (INFERRED in the memo, §6; the Linux runners of the builder's release run are the check). `wasi_config_set_stdout_file` opens the path before it returns (READ, the memo §5.3), so the runner closes `w` right after the two setters and the only write end is wasmtime's.
- `_Windows.output_channel`: returns `None`.
- `_outputs.py` holds the two captures with one shape: `open(wasi)`, `retarget(out, err)`, `settle()`, `close()`, and the kind it reports through `on_capture`. `_PipeCapture` is Decisions 3 and 4. `_CallbackCapture` is today's code moved whole: `_Stream`, `_write_output`, `_free_output`, the two C function objects, `_send_outputs`'s body, the keys in `process().outputs`; its `settle` is a no-op (the callback is synchronous) and its `close` pops the keys as `_instance`'s release does today. `_capture(wasi, out, err)` picks by `PLATFORM.output_channel()`, and falls back to the callback, with every descriptor the pipe capture made closed, when wasmtime cannot open the channel's path: a POSIX host whose `/dev/fd` does not reach a pipe (Linux without `/proc`: a chroot, a minimal container) runs every call as before (the pull request's review, Medium 1; the row `test_a_path_that_does_not_open_falls_back_to_the_callback`).
- Why not every system: the memo's §6. A named pipe's client end under wasmtime's `File::create` (`CREATE_ALWAYS`) is unverified, `poll` does not take Windows pipes, and a turn's settle would need `PeekNamedPipe`. Reserved as **130**, the Windows move, for a builder with a Windows host; the roadmap carries it.
- Why not a FIFO under the private scratch: it works on both POSIX systems too, but it is a file-system object to make and remove and an open order to get right (the reader first, non-blocking). `/dev/fd` needs neither. The builder may fall back to a FIFO in `_Posix` if a Linux runner refuses the reopen, and says so in the landing notes.

### 3. The pipe capture: one reader thread per store

`_PipeCapture.open(wasi)`: two channels (stdout, stderr), `wasi.stdout_file` and `wasi.stderr_file` set to the two paths, the runner's write ends closed, a wake pipe of its own made, and one thread started, `wasi-python-output`, daemon, that runs `_drain`:

- **`select.poll`**, not `select.select`: a `poll` object registered on the two read ends and the wake pipe's read end, waited on with no timeout. `select.select` refuses any descriptor at or above `FD_SETSIZE` (1,024) on macOS and Linux (the review, EXECUTED: a pipe end at descriptor 1,100 raised `ValueError`), and an embedder that holds that many, or the command line, which raises its own soft limit to 10,240, would give the reader such descriptors on its first call. `poll` has no descriptor ceiling, every POSIX Python has it, and watching three descriptors needs no kqueue or epoll object per store, which is why it is chosen over `selectors.DefaultSelector` (which would also do: kqueue on macOS, epoll on Linux, neither bounded by `FD_SETSIZE`). A ready stream end (`POLLIN` or `POLLHUP`) is read with `os.read(fd, 65536)` and the bytes go to that stream's current target through `_Stream.write`, which keeps to the cap and sets `dropped`; an empty read is EOF: the end is closed and unregistered.
- **When the reader ends.** The loop ends in exactly two ways: when `close()` tells it to stop, after the store is closed (below), or earlier when both stream ends have reached EOF, which is a shortcut and never the condition. Nothing else ends it. An exception from a read or a write of one piece (a `MemoryError`, an `OSError`, anything) drops that piece, marks the target `dropped` so the result names the stream, and the loop continues, as `_write_output`'s `except BaseException` keeps the callback alive today; an exception from `poll` itself, or from a read, which a valid set never raises, moves the reader to a slow loop that reads every end without blocking, with a millisecond's sleep when none had bytes, until `close()` asks, and answers a settle the failure interrupted. The reader never closes an end the guest may still write to: that write would refuse the guest, and in a host that restored `SIGPIPE`'s default action the signal would end the host process (the pull request's review, Low 2; the row `test_a_reader_whose_wait_fails_still_reads_every_byte`). As built first, this path closed the read ends; the review's probe ended such a host with -13. Two follow-ups, written 2026-10-26 from the review's second pass (Lows 9 and 10), for a change of their own, since this one is signed on its head: the fall to the slow loop is reported, through an observer on the process object as `on_capture` is, and `test_output_arrives_above_descriptor_1024` asserts it never happened, so that row tells `poll` from a `select.select` reader again; and a read that fails sets no `dropped`, since a failed `os.read` takes nothing from the pipe and the slow loop reads the end again, so `dropped` is set only where a piece is lost (the stream's `write` failing). Until then, as built, a failed read names its stream as truncated though no byte was lost, which errs to the safe side of spec 006's promise. A guest blocked in `write(2)` is in a host call the epoch deadline, `cancel` and Ctrl-C cannot interrupt, so the one thing the reader must never do is die with a pipe open. And on every exit path, the exception path included, the reader's last act (`finally`) sets `settled` and whatever else a waiter holds on it, so a session's `settle()` or a `close()` never waits on a reader that has ended: the reader ends only after `close()` asks or both streams reach end of file, so a `settle()` after it has ended returns at once with nothing lost.
- The targets are read under the capture's own lock (an instance attribute, not module level), set by `retarget`.
- What the host holds: the stream's bytes, at most the cap, plus the pipe's kernel buffer (64 KiB on macOS and Linux) and one `os.read` in flight. Past the cap the reader keeps draining and drops; the guest is never blocked for longer than a buffer's fill. The promise an embedder sees, `len(stdout) <= output_bytes`, is unchanged.
- What the call holds open: six descriptors on POSIX while it runs (the two read ends, wasmtime's two write ends, the wake pipe), where today's callback holds none. The library never changes the process's limits, so under macOS's default soft limit of 256 twenty concurrent calls take 120 of them. An `OSError` from `os.pipe()` or a failure to start the reader is raised before any guest code, with every descriptor the capture opened closed: the host's failure, not the guest's, as a failed `_Private` is today.
- `close()`: called after `store.close()`, which drops wasmtime's write ends, so nothing more can arrive. It writes the stop byte to the wake pipe; the reader settles (a `poll` with a timeout of zero on the open stream ends, each ready end read into its target, until none is ready: Decision 4's drain), closes the stream read ends it still holds, and ends; `close()` joins it and closes the wake pipe. EOF is never waited for: a forked child of the embedder holds a copy of wasmtime's write ends (a fork copies the table; `O_CLOEXEC` acts at `exec`), so an EOF wait would hold the parent's call for as long as the child lives (the review's Medium 2). `_instance`'s result is built from the streams after `close()`, as it is built after the release today. Every ending goes through `release()`: a normal exit, a trap, a deadline, a cancel, a hard `os._exit`, an exception raised into the home; each closes the store first and the capture second.
- `Completed.stdout` stays `bytes(out.data)`; `truncated` stays the names of the streams whose `dropped` is set.

### 4. A session's turn settles its pipe

A session opens its capture once with its store and keeps it until the session ends. Each turn calls `retarget(out, err)` with its two fresh streams before the guest runs, as `_session_call` sets the table's streams today, and `settle()` after the guest thread has returned the turn, before the turn's result is built.

`settle()` writes one byte to the wake pipe and waits on the capture's `settled` event. The reader, woken, drains: `poll` with a timeout of zero on the open stream ends, reading each ready end into its target, until none is ready, then sets `settled` and clears the wake byte. The guest is parked between turns and writes nothing, so a pipe seen empty stays empty: every byte written before the turn ended is in the turn's streams when `settle` returns, and nothing the next turn writes can be in them. This rests on wasmtime-wasi's `OutputFile` writing on the guest thread (`write_all` in its `cli/file.rs`): a write has reached the pipe when `fd_write` returns. The engine-upgrade note in `_wasmtime_ffi.py`'s docstring names that fact, so a pin bump re-reads it. The callback capture's `settle` is a no-op.

## Intent

A guest that prints a lot, or prints a line per row, costs the product what it costs wasmtime: on macOS and Linux, 32 MiB of output in about 40 ms rather than 160 to 240, ten thousand lines in about 35 rather than 300. Nothing an embedder can observe changes: not the cap, not `truncated`, not the API, not a default; Windows is as it was until its own specification.

## Design

- `src/wasi_python/_outputs.py` (new): `_Stream` (moved from `_call.py`, unchanged), `_PipeCapture` (Decisions 3 and 4: `open`, `retarget`, `settle`, `close`, `_drain`, each under 80 lines, the drain about 35), `_CallbackCapture` (today's `_write_output`, `_free_output`, the two C function objects at module level as today, since wasmtime may call them for as long as the process lives, and the keys), `_capture(wasi, out, err)` (picks by `_platform.PLATFORM.output_channel()`, reports the kind to `process().observers.on_capture`). The module docstring gives the reason in words: wasmtime hands a custom stream its bytes 4 KiB at a time on a thread of its own, a Python callback there costs a thread state per piece, and a pipe wasmtime writes as a file costs one kernel write per piece and nothing in Python.
- `src/wasi_python/_call.py`: `_instance` makes the two streams, calls `_capture`, and in `release` calls `capture.close()` right after `store.close()`; the result is built as today. `_Stream` is imported from `_outputs` for `_sessions.py` and `_process.py`, or they import it from `_outputs` directly (the builder picks the one that keeps `test_the_filesystem_imports_only_itself_and_the_engine_seam` and the package's import graph green).
- `src/wasi_python/_sessions.py`: the open makes the capture with two placeholder streams of cap 0 (as the keys are made today) and keeps it on the session's state; `_session_call` calls `retarget`; the turn's end calls `settle` before the result; the session's end calls `close` after `store.close()`.
- `src/wasi_python/_platform.py`: `output_channel` on the protocol, `_Posix` and `_Windows` (Decision 2).
- `src/wasi_python/_process.py`: `_Observers.on_capture`; its type-checking import of `_Stream` moves from `._call` to `._outputs`.
- `tests/unit/test_runner_outputs.py` (new), `tests/unit/test_runner_sessions.py`, `tests/unit/test_runner_cancel.py`, `tests/unit/test_wasmtime_ffi.py`, `tests/release_shards.toml` (the new file under `own-runner`): Decisions 1 and 6.
- `CHANGELOG.md`, under the unreleased section: one line (below).
- `docs/`, `README.md`: unchanged (Decision 7).

### The CHANGELOG line

- **A guest's output is read from a pipe on macOS and Linux** (spec 129). wasmtime hands a custom output its bytes 4 KiB at a time on a thread of its own, and the runner's callback there cost about 14 µs a piece, most of it the hand-off and a Python thread state made and destroyed per piece: 32 MiB of output took 160 to 240 ms, ten thousand printed lines 300 ms. wasmtime now writes each stream into a pipe the runner reads on one thread of its own per call: about 40 ms and 35 ms. ## One line

On macOS and Linux wasmtime writes each of the guest's two streams into a pipe the runner opened through the public `stdout_file` setter and reads on one thread of its own, with the cap kept to the byte and a session's turn settling its pipe before its result; the 4 KiB-piece callback, its tokio hand-off and its per-piece Python thread state are gone, and 32 MiB of output costs about 40 ms rather than 160 to 240.
