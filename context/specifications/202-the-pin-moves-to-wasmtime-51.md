## The problem

The published pin is `wasmtime>=50,<51`. The only wasmtime-py in that range is 50.0.1, which bundles wasmtime 50.0.0. wasmtime has since fixed nine advisories in 50.0.2 and 50.0.3, but wasmtime-py published neither, so no 0.1.5 user can reach those fixes by pinning.

One of them is High and very likely reaches **every call on Windows**. GHSA-f2pq-268w-886c lets a guest escape a host folder with a name such as `./C:foo`, which Windows reads relative to drive C's current folder. Every call preopens host folders of the runner's own, through wasmtime: the stdlib folder (read-only, at `/usr/local/lib`), matplotlib's data beside it, and, when there is no writable `/tmp`, an empty read-only HOME (READ: `_call._preopens`, `_call.py:227-251`; `_guest_home`, `:332-343`; the review's finding 1). `root=True` adds a writable private root. The runner forwards every path call on such a folder to wasmtime unchanged, and its own rule against a `:` serves only its mounts. So on 0.1.5 a call with no grants at all can read outside its folders. One with a writable grant or `root=True` can also write outside them (INFERRED; 3a is the evidence).

Of the other eight, none reaches the runner. GHSA-5m8g-xhq4-4h93 (empty writes to the custom output grow host memory) names a stream the runner uses on Windows, but WASIp1's `fd_write` skips every empty buffer before it calls the stream (READ: `first_non_empty_ciovec` and the write loop, `crates/wasi/src/p1.rs` at `v50.0.1` and `v51.0.0`; the review's finding 3). The fix is carried, and 0.1.5 was not exposed to it.

wasmtime-py 51.0.0, on PyPI since 2026-11-20, bundles wasmtime 51.0.0, which carries every one of those fixes, the Windows one included, though 51's notes do not list it. The seam's private names all resolve on it, and 0.1.5's binaries validate under it.

### 5. The runner adds no colon rule of its own

wasmtime 51 refuses a `:` in every path on Windows, which covers the forwarded calls. A rule of the runner's on forwarded calls would refuse colons on macOS and Linux too, where they are legal names that guests use (`12:00.log`), or it would be a platform branch. So the engine's rule is the fix, and 3a holds it against the installed engine, as 127 held the rename fix.

### 6. The GC proposal is off

Both engines set `cfg.wasm_gc = False` in `_engines.py`, next to `consume_fuel`. A comment gives the reason in words: the guest uses exceptions but no GC types, and an engine that refuses GC types keeps that code out of a guest's reach. Exceptions stay on. The judge's own engines mirror the runner's, so they set it too: the guest driver's `engine()` in `tests/harness/guest.py`, and the two engines in `tests/harness/files.py`. Without them, most checks would not see the switch (EXECUTED by the probe). That list is complete for engines that run the artifacts. The other `Config()` sites compile toy modules or only validate (EXECUTED by the reviewer, grep). The owner approved the switch on the condition that a probe show no impact on wasi-python and no change in performance (`decisions.md`, "0.1.6 is a security release"). The probe found none (EXECUTED, `../research/2026-11-22-the-gc-proposal-off-under-wasmtime-51.md`):

- **Verdicts:** in 2,290 checks and unit rows run with GC on and with it off on wasmtime-py 51.0.0, no status differs.
- **Fuel:** 430 of 437 metered checks are equal to the instruction. The other 7 differ by 17 to 34 instructions, the same wobble seen between two GC-on runs. Twelve programs that throw C++ exceptions, `longjmp`, panic in Rust or raise `RecursionError`, run through the judge's seeded driver, give identical results and fuel.
- **Machine code:** the compiled modules are byte-identical except one feature bit in the `.wasmtime.engine` section.
- **Speed:** every measure, from compiling each binary to a run of 10,000 caught exceptions, is within noise. Peak memory is the same.

The probe ran 2,290 of the fast tier's 4,998 items, on one x86_64 Linux machine, with no release tier (READ). **The remaining evidence** is the branch's run on three systems and the release pull request's release tier. The switch is its own commit. If either run shows a difference the switch explains, that one line is reverted and the question goes back to the owner, as the owner's decision provides.

What changes for users:

- **A guest or embedder.** A module that declares a GC struct, array or heap type is refused when compiled, with wasmtime's "… not supported without the gc feature" error. The artifact set declares none (EXECUTED: both binaries validate with GC off). wasmtime keeps its small heap for exception objects either way, so this hardens. It closes no open advisory, and the documents say exactly that.
- **The module cache.** The cache file's name does not carry the engine's features. A GC-off engine refuses a GC-on `.cwasm` with wasmtime's feature check, and the runner recompiles and overwrites the entry, about 26 s per binary and engine kind, with no warning. A GC-on engine loads a GC-off entry, so a shared cache settles and does not flip (EXECUTED). Users meet no extra cost: the move from wasmtime 50 to 51 already makes every cached entry stale, so the first run after upgrading recompiles once whatever the GC setting. No change to the cache key is made here. That the key leaves out the engine's features is a finding for a later specification (For the lane).

## Intent

A `pip install wasi-python` user on Windows can no longer reach host files outside a guest's folders with a drive-prefixed name, whether or not they grant any. The engine also stops accepting a WebAssembly feature the artifacts never use. What else an embedder can observe: fuel figures, a slash-named `rmdir` on a mount that now succeeds as on a grant, and the four `pread` rows where a grant answers EINTR and a mount EINVAL.

### The CHANGELOG lines

Under **Security**:

- **A guest on Windows can no longer reach host files through a drive letter.** The runner moves to wasmtime 51, which refuses a `:` in any path on Windows. Before, any guest on Windows could name a file such as `/usr/local/lib/C:secret`, which Windows reads relative to the current folder of drive C. Every call could read outside its folders this way, even with none granted, and a call with a writable folder or `root=True` could write there too (GHSA-f2pq-268w-886c, High). Your own wasmtime needs 51.0.0, 50.0.3, 49.0.7, 48.0.10 or 36.0.22 to have the fix. [Security model](https://claygendron.github.io/wasi-python/explanation/security-model/)
- **wasmtime's other fixes since 50.0.0 are carried.** None of them reached the runner. A guest's empty writes, for one, never reach the output stream that one of them is about. [Security model](https://claygendron.github.io/wasi-python/explanation/security-model/)
- **The engine refuses WebAssembly GC types.** The runtime uses exceptions but none of the GC proposal's structs and arrays, so the runner now turns that proposal off. A module that declares one is refused. [Security model](https://claygendron.github.io/wasi-python/explanation/security-model/)

Under **Fixed**:

- **Removing a folder named with a trailing slash works on a mount.** `os.rmdir("logs/")` now removes an empty `logs` on a mount, as it does on a granted folder under wasmtime 51 and on Linux. It answered EINVAL before. [The guest's files](https://claygendron.github.io/wasi-python/reference/guest-filesystem/)

Under **Upgrading**:

- **wasmtime 51 is required.** The wheel requires `wasmtime>=51,<52`. Fuel figures change slightly, since fuel is counted by the new engine. [Support and versioning](https://claygendron.github.io/wasi-python/reference/support-and-versioning/)

The builder adjusts the first line to what 3a found. If 3a showed no reach on 50.0.1, it says the fix is carried, not that 0.1.5 was exposed.
