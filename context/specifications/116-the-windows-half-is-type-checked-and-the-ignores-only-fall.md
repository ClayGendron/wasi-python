## The problem

The type checker reads one platform. `pyproject.toml` sets `platform = "linux"` (`pyproject.toml:111`), so one verdict holds on every host. That choice has three costs today.

- **The Windows half is read as Linux** (EXECUTED). Under Linux's stubs `ctypes.WinDLL`, `ctypes.WinError`, `ctypes.get_last_error`, `ctypes.WINFUNCTYPE`, `msvcrt.locking` and its constants, and `winreg` do not exist. So each of the 14 lines of `_platform_windows.py` that uses one carries `# type: ignore[attr-defined]` (`:101`, `:122`, `:123`, `:126`, `:128`, `:279`, `:293`, `:310`, `:312`, `:313`, `:318`, `:352`, `:354`, `:357`). An ignore silences the whole line. A planted mistake shows it: `ctypes.WinDLL("kernel32", use_last_error="yes")` at `:101` passes today's `uv run mypy`, exit 0; the same line under `--platform win32` is `error: Argument "use_last_error" to "WinDLL" has incompatible type "str"; expected "bool"  [arg-type]`. The code that runs only on Windows is the code the checker does not read.
- **No class but `_Linux` is held to the platform protocol** (EXECUTED). `_select` returns `_Windows()`, `_Darwin()`, `_Linux()` or `_Posix()` as a `_Platform` (`_platform.py:1054-1066`). Under Linux's narrowing mypy reads the `win32` and `darwin` branches, and the fall-through after the `linux` one, as unreachable, and checks nothing in them. A member planted in the `_Platform` protocol, and in no class, gives exactly one error today: `_platform.py:1063: … "_Linux" is missing following "_Platform" protocol member`. `_Windows`, `_Darwin` and `_Posix` could each lose a member and the checker would pass.
- **The count of escapes moves with nothing to hold it** (READ). 106 counted `type: ignore` as a fact and set no ratchet. It was 12 before 106, 14 at its base, 25 by 0.1.0, and 25 at `aad3a059` (EXECUTED: `grep -rc 'type: ignore' src/wasi_python`, 14 in `_platform_windows.py`, 4 in `_wasmtime_ffi.py`, 3 in `tools.py`, one each in `_call.py`, `_fs_memory.py`, `_fs_paths.py` and `runner.py`). Of those, 21 give no reason on their line, and the next Windows-only call would add one more by the same pattern.

## Decisions

### 1. Two passes, and each module is read by exactly one

The **Linux pass** is `mypy` as `pyproject.toml` configures it, with three lines added to `[tool.mypy]`: `exclude = ['_platform_windows\.py$']`; `enable_error_code = ["ignore-without-code"]` (Decision 5); and one override, `[[tool.mypy.overrides]] module = "wasi_python._platform_windows"`, `follow_imports = "silent"`. It reads every module of the package but `_platform_windows.py`, and reads that one's signatures, silently, where `_platform.py` imports it. Its flags are `--no-error-summary` alone, as today's row passes.

The **Windows pass** is `mypy --platform win32 --follow-imports silent --cache-dir build/.mypy_cache_win32 --no-error-summary src/wasi_python/_platform_windows.py`. Everything else comes from the same `[tool.mypy]`: `--strict`, Python 3.11. A file named on the command line is read whatever `exclude` and the override say (EXECUTED: "no issues found in 1 source file"). `--follow-imports silent` lets it read `_platform_common.py`, `_process.py` and, under `TYPE_CHECKING`, `_platform.py` for their types while reporting none of their errors, which under `win32` are the POSIX calls (`os.getuid`, `fcntl.flock`, `pwd.getpwuid`; 131's measurement). Its own cache folder keeps the two passes from evicting each other's cache entries; both are under `build/`, which git ignores.

Reason. This is 131's measured design, unchanged. Each module has one platform it is read under, so no error is reported twice and no line needs an ignore that the other platform would call unused. The passes' verdicts do not depend on the host: both name their platform, so Linux, macOS and Windows hosts give one answer, as 106 required.

### 2. One list of passes, read by the rules row and by a local command

`tests/harness/typecheck.py` (new, standard library only) holds `PASSES`, the two argument tuples of Decision 1, and `run(root: Path) -> list[str]`, which runs `sys.executable -m mypy` with each tuple in `root` and returns every `error:` line, each prefixed by its pass's name (`linux` or `win32`), plus one finding for an exit of 2 (a crash or a configuration error). Run as a script, `uv run python tests/harness/typecheck.py` prints the findings and exits 1 when there is one. `tests/checks/test_rules.py::test_src_type_checks_under_mypy_strict` calls `typecheck.run(paths.REPO)` in place of its own one `subprocess.run`; `UNTYPED` (empty) and its rules read the findings of both passes. The module docstring says that the list is the one place the passes are named. `uv run mypy` alone stays the Linux pass, as `pyproject.toml` alone describes it.

`quick`'s `mypy` step (`.github/workflows/release.yml:158-159`) is not changed. The Windows pass runs in `quick` all the same: the rules step runs `tests/checks/test_rules.py` whole, and the type-checking row with it. The same row runs in `own-rest` on Linux and macOS (`tests/release_shards.toml`, "rest runs on macOS and Linux").

Reason. One list is what keeps the step and the row from drifting. The workflow stays unchanged for two reasons. A change under `.github/` makes the pull request's plan the whole workflow (`release/ci_plan.py:346-348`), every upstream group and the build on three systems, for a one-line command. And the row already runs the Windows pass on every run that runs `quick`, so the step's second copy would add a readable log and no verdict. The next specification that edits the workflow for its own reason may switch the step to the script; this one does not need it.

### 3. Each platform class is held to the protocol in the pass that reads it

`_platform_windows.py` gains, at its end, under `if TYPE_CHECKING:`, an import of `_Platform` from `._platform` and one function, `def _conforms(windows: _Windows) -> _Platform: return windows`. `_platform.py` gains, at its end, under `if TYPE_CHECKING:`, `def _conforms(darwin: _Darwin, posix: _Posix) -> tuple[_Platform, _Platform]: return darwin, posix`. A comment on each says in words what it is for: the checker reads the platform choice as one platform, so the classes it skips are held to the protocol here. Neither runs: `TYPE_CHECKING` is false at run time, so the import cycle the Windows half's import would make never forms.

Reason. Without it the Windows pass reads `_Windows`'s body but not its use as a `_Platform`, and the Linux pass skips `_Darwin` and `_Posix` the same way. Measured: with both functions, both passes exit 0 today; with a member planted in `_Platform`, the Windows pass names `_Windows` at its function, and the Linux pass names `_Linux` at `_select` and the pair `tuple[_Darwin, _Posix]` at its function. This is the smallest form: no assignment at module level (so the mutable rule has nothing to read), no runtime cost, no platform branch.

### 5. Every ignore that stays names its code and gives its reason on its line

The shape is `# type: ignore[<code>, …]  # <reason>`: one or more error codes in brackets, then a second comment with at least one word. `tests/checks/test_rules.py::test_every_type_ignore_names_its_code_and_reason` (new) reads every ignore found by Decision 6's scan and names each that lacks either part, by path and line. Today it names 21 lines: the 14 Windows ones, the three `Context` ones, `_fs_memory.py:158`, `_fs_paths.py:621`, `_call.py:585` and `runner.py:1015` (whose reason is on the line above, not on its own). After the build the three in `tools.py` pass it. mypy's own `ignore-without-code` error code is turned on in `[tool.mypy]` too, so `uv run mypy` alone refuses a bare ignore on a line with an error. `warn_unused_ignores` is already on under `strict = true` and stays so: every pass reports a stale ignore as `[unused-ignore]`, which is how the Windows pass finds the 14 today.

Reason. A reason left for the reader to see in the line itself, with no comment, was weighed and refused: no scan can check it, and every rule here is one a scan can hold. A reason on the line is checkable, short, and is what the three survivors and `_wasmtime_ffi.py:334` already do. A reason on the line above (`runner.py:1013-1014`) is the one form that fails; it goes with its line in Decision 4.

### 6. The count is a metric the ratchet holds: a rise is red without a claim, a fall is kept

`scan.type_ignores(files, root) -> list[str]` (new) reads every `.py` file under `src/` with `tokenize`, takes each `COMMENT` token, and returns `path:line: text` for each that matches `type:\s*ignore` anywhere in it: bare or coded, any spacing, after other comment text or not. No file, line or code is excluded. Strings and docstrings are not comments, so a docstring that mentions the phrase is not counted; today the scan and the rubric's `grep -rc 'type: ignore' src/wasi_python` agree, 25. `tests/checks/test_rules.py::test_the_type_checkers_escapes_are_counted` (new) records the scan's length as `metric("ignores", n)` and passes.

The metric is named `ignores` and joins `bytes` everywhere `bytes` is named as an exact count: `tests/harness/plugin.py`'s `METRIC_NAMES`, `tests/harness/sameness.py`'s `EXACT_METRICS` and its claim kinds (`"ignores": ("grows",)`, beside `"bytes"` at `:403`), and `tests/harness/accept_from.py`'s `COUNTS` (`:60`). Nothing else changes in the ratchet: the scoreboard already treats a metric that is not `fuel` or `passes` as one where a rise is growth and a fall is kept as the lower value (`tests/harness/scoreboard.py:197-198`, `:311-312`). So the accepted value lives in `context/progress/accepted.json`, per platform, beside each check's `bytes`. A rise is listed under `GROWTH` and is red unless a news file's claim names the row: `grows = ["tests/checks/test_rules.py::test_the_type_checkers_escapes_are_counted"]` with its `growth` reason, the shape of `../changes/README.md`. A fall needs no claim and is accepted at the next acceptance, the new lower value replacing the old.

Reason. This is "a ratchet on the count that only falls", in the machinery every other ratchet uses, so a rise is explained in the same place a fuel or byte growth is, and reaches the reviewer under `GROWTH`. A constant in `test_rules.py`, the form of `ALLOWED` and `UNTYPED`, was weighed and refused: raising it is a judge edit that needs no claim, and its reason would live only in a commit message. `COUNTS` is needed: without it `--accept-from` applies a Linux record's metrics over darwin's accepted ones and keeps the old, higher count, so a fall measured on Linux would never be accepted (`tests/harness/accept_from.py:183-192`). `EXACT_METRICS` holds it equal across systems, which it is, being a count of source text. The first acceptance after the merge records the row's first value; it is new, so there is nothing to compare it with.

## Intent

After this specification the type checker reads the Windows half as Windows, on every run, whatever system runs it. Each platform class is held to the protocol the runner uses it through. The escapes from the checker are 3, each with its code and its reason on its line, and the count is a ratcheted number: it can fall freely, and it can rise only with a reason a reviewer reads.
