## The problem

The owner wants Rust packages in the set: orjson now, pydantic-core next, then rpds-py and python-calamine. Each is a PyO3 module: Rust code that speaks CPython's C API. The build has no Rust today. It compiles C, C++ and Cython with wasi-sdk's clang and links every module into `python.wasm` as a builtin, through CPython's inittab.

Rust brings five hazards the C path does not have. The spikes found each one.

1. **Two Rust libraries cannot share one binary.** Each Rust static library carries its own copy of Rust's standard library, so two collide on `rust_eh_personality` and `std::panicking::EMPTY_PANIC` (EXECUTED, 2026-10-31). Every Rust module must go into one library.
2. **A Rust library carries its own math.** Rust's static library holds 263 objects of Rust's `compiler_builtins` and 35 of compiler-rt's C. Linked as cargo writes it, its weak `round`, `sqrt`, `fma`, `cbrt` and the 128-bit float helpers replace wasi-libc's for the whole interpreter, with no warning (EXECUTED, 2026-10-31; the pydantic-core spike found `round` the same way, its record's "checked"). The weak-duplicate gate does not see it: it compares the packages' archives with each other, not with the SDK's runtime.
3. **Rust reads entropy past the build's wrap.** The reactor's link wraps `__wasi_random_get`, so entropy is pinned while a starting image is prepared (`recipes/reactor_main.c`, "pinned"). Rust's standard library and the `getrandom` crate import `wasi_snapshot_preview1.random_get` directly and skip the wrap (pydantic-core spike, "checked"). Their clock reads go through wasi-libc's `clock_gettime`, which is wrapped (same record, "checked").
4. **A Rust panic ends the run.** Rust's shipped standard library for `wasm32-wasip1` only aborts, so a panic is the trap `unreachable` (EXECUTED, 2026-10-31). Natively, PyO3 turns a panic into `PanicException`, a Python exception a program can catch.
5. **New inputs.** A Rust toolchain and crates are build inputs from two hosts the build has never fetched from.

### 2. Every crate is a pin from crates.io

Rust's standard library's own dependencies are `rust-src`'s `library/vendor/` crates (READ), but cargo resolves them through crates-io under build-std, so the source replacement below sends them to `build/rust/vendor/` too. The spikes' cargo downloaded exactly rust-src's vendored versions from crates.io during their build-std runs (EXECUTED: the registry cache, written during those runs; the cause INFERRED). So step 52 copies `rust-src`'s `library/vendor/*` into `build/rust/vendor/`, the same directory source. They are pinned by `rust-src`'s SHA-256 and carry their own per-file `.cargo-checksum.json` (EXECUTED, 1.97), so they need no pins of their own. The crate rule (Decision 14) reads `recipes/rust/Cargo.lock` only, not `library/Cargo.lock`, and a name and version found in both folders must hold identical bytes, or step 52 stops.

Every other crate is a file from crates.io: one pin per package in `recipes/rust/Cargo.lock` that is not a path crate, named `<name>-<version>.crate`, fetched from `https://static.crates.io/crates/<name>/<name>-<version>.crate`, its SHA-256 the lock's `checksum`. orjson's own vendored copies in its sdist are not used, so there is one source of crates and one rule. The bytes are the same either way: a vendored crate is the `.crate` file unpacked.

The lock is written once by the build session, with network, from orjson's own `Cargo.lock` plus the probe's additions (Decision 9). That one online resolution reads `index.crates.io`, the sparse index; every later build is offline, and the lock's checksums are the crates' trust root. Every crate orjson's lock names keeps orjson's version; a rule (Decision 14) holds that. The crate pins are `TBD` until then: about 22 of orjson's and 5 of PyO3's macros.

Step 52 unpacks each crate pin into `build/rust/vendor/<name>-<version>/` with a `.cargo-checksum.json` whose `"package"` is the pin's SHA-256 and whose `"files"` holds each file's SHA-256, read from the verified `.crate` archive's members, as `cargo vendor` writes it. So cargo refuses a file changed after unpacking. An empty `"files"` would turn that check off. `$CARGO_HOME/config.toml` replaces crates-io with that folder (Decision 5). Cargo checks each package's checksum against the lock (INFERRED from cargo's directory-source rules; the build's `--frozen` holds it). The crate trees under `build/rust/vendor/` also join the judge's tree check (`tests/harness/pins.py`, `SOURCE_PATTERNS`), so a changed file there is seen as orjson's would be.

Rust's dist server and crates.io are new download hosts, as the owner decided. The rule on third-party hosts holds for both: no retry on a timer, and an outage is the owner's to hear about.

### 4. One workspace, one umbrella library

One workspace, its manifest at `build/Cargo.toml`, copied from `recipes/rust/Cargo.toml` with its lock. It has one member that matters, the umbrella `recipes/rust/modules/` (package `wasi_python_rust`, `crate-type = ["staticlib"]`). Its `src/lib.rs` links each module crate, `extern crate orjson as _;` and `extern crate rust_probe as _;`, and holds nothing else. It is our code. The workspace's release profile is `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `debug = false` and `incremental = false`, orjson's own, and it sets no `panic` (Decision 8).

**Why the workspace root is `build/`.** Cargo hashes a path crate into its symbol names by its path relative to the workspace root, and by its absolute path when it lies outside it (INFERRED from cargo's source, not read here). orjson's tree must sit at `build/orjson-3.13.0` for the judge. With the root at `build/`, every path crate is inside it, so the symbols do not depend on where the repository is checked out.

`recipes/rust/modules.txt` lists each module: its dotted import name and its init function, `orjson.orjson PyInit_orjson` and `_rust_probe PyInit__rust_probe`. A later Rust package adds a dependency, a line here and its pins, and nothing else.

**One PyO3.** cargo admits one `pyo3-ffi`, so every module in the umbrella uses the same PyO3 line: 0.29 while orjson 3.13.0 is on it. pydantic-core needs 0.30.1, so its specification brings orjson onto 0.30 by an orjson release, or by a carried patch, before the two can share the umbrella.

### 6. Only each crate's own objects are kept

With fat LTO the static library holds one object for all the Rust code (named after the umbrella crate), the C objects that module crates compile through the `cc` crate (yyjson's), and `compiler_builtins`' objects, which LTO never merges: its Rust objects and the compiler-rt C files its build script compiles (EXECUTED, 2026-10-31: 1 + 1 + 263 + 35 members, with the shipped standard library). Under build-std the layout is smaller: Ask 4's library held 2 members, the crate's object and one `compiler_builtins` object, with no compiler-rt C (EXECUTED by the review). `keep` handles both layouts by the same rule.

`scripts/rust_objects.py keep` writes the new archive with the umbrella's object and each object found under a module crate's own `build/*/out/` folder, by `llvm-ar rcsD` (no timestamps). It stops on any dropped member that is not `compiler_builtins`': a Rust object of that crate, or an object under its `out/` folder. So nothing else is dropped without a word. `round`, `sqrt` and their kin then come from wasi-libc and the 128-bit helpers from `libclang_rt.builtins.a`, as for every C module (EXECUTED, both spikes).

### 7. The entropy shim

`scripts/rust_objects.py imports` reads each kept object's import entries exactly, module and field, with `harness.wasm` (EXECUTED by the review on the spike's object: its only non-`env` import is `wasi_snapshot_preview1.random_get`). It fails on any import outside `env` but `wasi_snapshot_preview1.random_get`. It also drops the names wasm-ld defines itself: `__stack_pointer`, `__indirect_function_table`, `__memory_base`, `__table_base` and `__c_longjmp`. What is left is what would become an import of its own.

Each such name whose demangled form (`llvm-cxxfilt`, which reads Rust's v0 mangling) ends in `::random_get` gets one definition, and the count of names shimmed must equal the count of `random_get` import entries in `build/rust/entropy_shim.c`, by its mangled name (`__asm__`), calling `__wasi_random_get` with its two arguments. The reactor's link wraps that call, so Rust's entropy is pinned while an image is prepared, as C's is. The spike's two names were `getrandom::backends::wasi_p1::random_get` and `wasip1::lib_generated::wasi_snapshot_preview1::random_get` (checked, Ask 3). Any other name left fails the step: "a direct WASI import the shim does not route: <mangled> (<demangled>)". A new direct `clock_time_get` or `poll_oneoff` is then reviewed before it ships, not found later. This gate alone sees an import that bypasses a wrap: wasm-ld merges imports with the same module, field and type (INFERRED), so a direct `random_get` adds no new line to `python.wasm`'s imports, and Decision 10's gate 5 sees only new fields.

For orjson alone the list may be empty: the October spike's archive needed only wasi-libc's names (READ, the memo's list). PyO3's runtime in the probe may bring std's `random_get` through a hash map (INFERRED). The shim file is written either way, and the step's line counts it.

`RandomState`'s and `ahash`'s keys are drawn once and kept in a static. A session checkpoint taken after they are drawn carries them into every resume, the same class as CPython's own hash secret (INFERRED in Ask 3). This specification changes none of that.

### 8. Panics unwind, with one switch to abort

`RUST_PANIC=unwind`, the owner's decision. The standard library is rebuilt with `-Zbuild-std=std,panic_unwind` on the pinned stable compiler, which `RUSTC_BOOTSTRAP=1` lets take that flag. The target's panic flag is `-Cpanic=unwind` alone, as Ask 4 built (EXECUTED by the review: its cargo fingerprints). That turned on `exception-handling` and gave the standard form (`try_table`, `throw_ref`) with C++'s tag, matching `python.wasm`'s own `-fwasm-exceptions -mllvm -wasm-use-legacy-eh=false` (checked, Ask 4). No `-Ctarget-feature=+exception-handling` and no `-Cllvm-args=-wasm-use-legacy-eh=false`: nothing needed them, and the spikes' notes tie the open compiler crash rust-lang/rust#156469 to the second. The binary's standard-form check and its tag count (Decision 10) gate the form. If the explicit flags are wanted, the builder tries them once beside the plain form and records which built. `RUSTC_BOOTSTRAP=1` reaches every crate's build probes too (proc-macro2's among them), on every host alike, so a probe that reads the compiler as nightly does so everywhere (INFERRED). Nothing new on the C side: `python.wasm` already links `-lunwind -lc++abi` from the `eh` sysroot and the snapshot step already runs with exceptions on (READ, `scripts/steps/60_link.sh`, `80_snapshot.sh`).

`RUST_PANIC=abort` is the fallback the owner accepts. It is one line in `line.conf`: the build passes `-Zbuild-std=std,panic_abort`, `CARGO_PROFILE_RELEASE_PANIC=abort` and no exception flags. Every input stays the same. A rule holds that `RUST_PANIC` is `unwind` or `abort`, and that nothing else under `recipes/rust/` or `scripts/` sets a panic strategy.

**The gate before it ships.** The pull request's run (with `ci:full`, so the release tier runs) links the unwinding build into both binaries, runs orjson's suite in the sandbox, and runs Decision 13's panic checks on Linux and Windows. That is the first half of the gate the owner set ("0.1.5's scope": both pydantic suites in the sandbox and a deliberate panic). orjson's entry points are raw `extern "C"`, so its suite never unwinds; here only `_rust_probe` exercises unwinding. pydantic-core's specification runs both suites on `panic=unwind`, and the abort switch stays open until then. If it fails on the unwinding, the builder records why in the landing notes, tries once more (two strikes), then sets `RUST_PANIC=abort` in a commit of its own. That commit turns `test_a_rust_panic_raises_panicexception` into a known gap closing with the specification that brings unwinding back, and says on the limitations page that a Rust panic ends the run. The owner is told in the pull request.

MANIFEST gains `x-rust 1.100.0 panic=<strategy>`, so a reader and the checks know which build they hold.

### 9. A probe module, for the panic checks

The owner's decision, 2026-11-14, in the project chat, answering whether every `python.wasm` should carry a tiny private Rust module that panics on purpose, for the panic tests and not part of the public API: "And yes, we can ship a private rust module that panics" (`../decisions.md`, "The Rust crates' licences").

orjson cannot show `PanicException`: its entry points are raw `extern "C"`, so its panics abort under either strategy. The checks need a PyO3 function. `recipes/rust/modules/probe/` is a crate of ours, `rust_probe`, on `pyo3` 0.29.3 with its macros (the same `pyo3-ffi` as orjson). It makes the builtin module `_rust_probe` with three functions:

- `panic(message)`, a `#[pyfunction]` that panics with the message. PyO3 catches the unwind at its boundary and raises `PanicException`.
- `panic_in_c(message)`, a raw `extern "C"` method registered through `pyo3::ffi`, as orjson's are, which panics. It aborts under both strategies, as orjson's code would.
- `hashed(keys)`, which builds a `std` `HashMap` from the keys and returns its iteration order, for the entropy check (Decision 13).

It ships in both binaries, a few kilobytes. It adds no import and no power: it panics or it aborts the guest's own run. Its name starts with an underscore and the packages page calls it the build's own check, not an API. It also proves PyO3's macros, which pydantic-core uses, before pydantic-core arrives. Its licence is the project's.
