## The problem

Seven places where the build or the release trusts a little more than it checks. None is a finding: no current input collides, and the judge or a later step catches each today. Each is a check that should hold on its own.

1. **`pinned()` matches by regular expression.** `scripts/steps/common.sh:52` selects the pin line with `grep "  $1\$"`, so `.` in a name matches any character. On a fixture, `pinned foo.tar.gz` accepted an unpinned `foo.tar.gz` because `fooXtar.gz` was pinned (EXECUTED, h11). `scripts/steps/10_tools.sh:207,226` and `scripts/make_openblas_void_patch.sh:38` do the same with `grep "  $wheel\$" | cut -c1-64`. No pinned pair collides today, and every literal name has an exact line.
2. **The same-bytes step compares the index, not the files.** `release.yml:448-457` unpacks the tarball and `cmp`s its inner `SHA256SUMS` with each rebuild's; it never runs the inner `SHA256SUMS` against the inner files (EXECUTED on a dummy, `same_bytes_fixture.log`). The judge legs' runner-integrity check binds `MANIFEST`, the binaries and the zip; the licence files inside the tarball are bound by nothing on a tag (the `save-set` job, which does check them, runs only on a branch run that built its set).
3. **Meson may download a subproject.** No `meson setup` in `scripts/steps/` passes `--wrap-mode`. There are eight: `37_plot_libs.sh:39`, `40_numpy.sh:34` (numpy's vendored meson, `"$HOSTPY" "$MESON" setup`), `50_pandas.sh:21`, `55_matplotlib.sh:118,169`, `57_scipy.sh:75`, `58_sklearn.sh:55`, `59_statsmodels.sh:61`; and no cross file sets `wrap_mode`. The pinned libraqm 0.10.5 carries `subprojects/sheenbidi.wrap`, an unhashed `[wrap-git]` at `revision=master`, behind `dependency('sheenbidi', fallback: …)`. The recorded build resolved it through pkg-config to step 37's own SheenBidi; had pkg-config failed, meson would have cloned `master` over the network and built it in, and the zero-patch judge (`tests/harness/pins.py`, "files the build adds are not judged") would not have seen the added folder.
4. **Some licence inputs are read without their pin.** `scripts/assemble_artifacts.py` reads some downloads through `pinned_bytes()` (line 521; tqdm, reportlab, the MPL and MIT texts, the scikit-learn and statsmodels extras) and others with a plain read: the wheels `wheel_licences()` opens with `zipfile.ZipFile(d / …)` (`:832`), the sympy wheel's nested licence (`:853`), the wasi-libc and LLVM notices (`:844-845`), the Unicode terms (`:790`). `00_download.sh` verified them in a full build; a step run alone from a named step skips that.
5. **curl may leave HTTPS on a redirect.** `scripts/00_download.sh:35` has `-fsSL --retry 3` and no `--proto '=https' --proto-redir '=https'`, and names no TLS floor. Integrity holds through the in-repo SHA-256, so this matters only with a wrong pin. A present-but-mismatched file is never refetched and fails every later run until someone deletes it (fails closed; a lasting red).
6. **The verify note hard-codes the repository's name.** On origin/main since `5b2689b9`, the verify note (`release/version.py:301-303`) and the docs page (`docs/how-to/verify-a-download.md`) name `ClayGendron/wasi-python`, and the page says 0.1.0 and the alphas verify under the old name, `ClayGendron/wasi_python`, since an attestation names the repository it was signed in (the published v0.1.0 attestation's signer is `https://github.com/ClayGendron/wasi_python/.github/workflows/release.yml@refs/tags/v0.1.0`, READ in h10's `attestation_identity_v0.1.0.txt`). So the link fix is done, and the old name stays right for 0.1.0. What remains is the signer identity for new releases: the note still writes the name as a literal, while the attest job verifies with `$GITHUB_REPOSITORY` (`release.yml:2484-2485`), and nothing holds the two equal. The next rename, or an edit to either side, would make the documented command fail closed for every new release, which teaches users to drop the check.
7. **`.gitignore` names no secret-file pattern** (`.env`, `*.pem`, `*.key`, `.claude/settings.local.json`); none is tracked, and the untracked `test_app/`, `.agents/` and `skills-lock.json` show how a broad `git add` would carry a stray file.

## Decisions

### 1. Pins are selected by exact field, and exactly one

`pinned()` in `common.sh` selects its line with `awk -v n="$1" '$2 "" == n ""' "$D/SHA256SUMS"` into the check file (the empty strings force a string comparison, since `awk` compares two numeric-looking fields as numbers), and dies unless the result is exactly one line ("`$1` is not pinned" for none, "`$1` is pinned twice" for more). The three `grep … | cut` lookups in `10_tools.sh` and `make_openblas_void_patch.sh` call a shared `pin_of()` in `common.sh` with the same selection and the same one-line rule. A rules check in `tests/checks/test_rules.py` greps `scripts/` for `grep "  \$` against `SHA256SUMS` and fails on any.

### 2. The same-bytes step checks every inner file

`release.yml`'s same-bytes step gains, after the `cmp` loop, inside `set/wasi-python-*`: `sha256sum --strict -c SHA256SUMS`; then `listed=$(awk '{print $2}' SHA256SUMS | LC_ALL=C sort)` and `present=$(find . -mindepth 1 ! -type d ! -path ./SHA256SUMS | sed 's#^\./##' | LC_ALL=C sort)`, which must be equal, so a nested file named `SHA256SUMS` or a symlink cannot hide; `find . -type l` prints nothing, since `sha256sum -c` follows a symlink (`release/set_key.py verify` refuses one for the same reason); and each published artifact, `python.wasm`, `python-snapshot.wasm`, `python-stdlib.zip` and `MANIFEST`, is among the listed names with at least one `LICENSES/` file, so a set that dropped a file from both the index and the tarball still fails. The wheel step beside it already checks the wheel's copy this way. The build job's "Release assets" step runs `release/set_key.py verify build/artifacts` as its first command, after the zero-patch pytest step and before it packs, so the producer's handoff is tight after the wheel copy (`release.yml:176-198`). Two release-scan rules in `tests/harness/scan.py` hold both after landing, each with a good and a bad fixture in `tests/unit/test_scan.py` and a row in `tests/checks/test_rules.py` on the real workflow: (i) the same-bytes step runs `sha256sum --strict -c SHA256SUMS` in the unpacked set, compares listed with present, refuses a symlink, and names every file of `tests/harness/paths.py`'s `ARTIFACT_FILES` but `SHA256SUMS` itself (the rule reads the tuple, so a new artifact name added there fails the rule until the step names it); (ii) the build job's "Release assets" step runs `release/set_key.py verify build/artifacts` before its packing command, and comes after the zero-patch step.

### 3. Meson never downloads

Every `meson setup` in `scripts/steps/` passes `--wrap-mode=nodownload`, through one variable `MESON_WRAP="--wrap-mode=nodownload"` in `common.sh`, so a wrap that pkg-config does not satisfy fails the build instead of cloning; numpy's `"$HOSTPY" "$MESON" setup` (`40_numpy.sh:34`) is one of them. Step 37's `build()` passes `${wrap:-$MESON_WRAP}`, and HarfBuzz's call sets `wrap=--wrap-mode=nofallback`: that is HarfBuzz's own project default (`default_options`, `wrap_mode=nofallback`), which refuses every fallback, local or fetched, and is stricter than `nodownload`, which would allow a local subproject folder; so one mode reaches meson and HarfBuzz is not loosened. Contourpy's configure (`55_matplotlib.sh:169`) does not pass `$MESON_WRAP`, for two reasons, both written in words in a comment there. It has nothing to fetch: its sdist ships no `.wrap` file and no `subprojects/` folder (`tar -tzf downloads/contourpy-1.4.0.tar.gz | grep -E '\.wrap$|subprojects'` prints nothing, EXECUTED 2026-10-25, 262 entries), and a grep of its four meson files (`meson.build`, `src/meson.build`, `lib/contourpy/meson.build`, `lib/contourpy/util/meson.build`) for `subproject`, `fallback` and `wrap` finds only `src/meson.build:20`, the source file `wrap.cpp` (EXECUTED); its one `dependency('pybind11', …)` names no fallback, and meson consults no subproject without a wrap file or a `subprojects/` folder. And it ships its configure line: `lib/contourpy/util/meson.build:48` writes `meson.build_options()` into `_build_config.py`, which ships in `python-stdlib.zip` (the review read `-Dbuildtype=release … --cross-file=…` in the zip's `contourpy/util/_build_config.pyc`), so `--wrap-mode=nodownload` there would change the zip by one line. The rules check reads every line under `scripts/steps/` that runs `meson setup` or `"$MESON" setup` and requires `$MESON_WRAP` on it (step 37's `${wrap:-$MESON_WRAP}` counts), and every `wrap=` assignment under `scripts/steps/` to be `--wrap-mode=nofallback` or `--wrap-mode=nodownload`. Its one exemption is contourpy's line, and it holds only while step 55 unpacks `contourpy-1.4.0`, so a bump of contourpy's pin fails the rule until the new sdist is checked again the same way. The zero-patch judge (`tests/harness/pins.py`) gains a rule: a `subprojects/*/` folder that the pinned tarball did not ship, inside any build tree, is a difference (the files the build adds are still not judged elsewhere; this one folder shape is the exception, with the reason in words); it covers contourpy's tree too.

### 4. Every download is read through its pin

`assemble_artifacts.py` routes every read of a file under `downloads/` through `pinned_bytes()`: the wheels (`wheel_licences` takes bytes, or a path it has checked), the sympy wheel, the wasi-libc and LLVM notices, the Unicode terms. A file under `build/` (an unpacked tree) is the step's own output, verified at unpacking, and stays a plain read. `d / "SHA256SUMS"` is the pin list itself, read by `pinned_bytes()` and by MANIFEST's `pin` lines, and stays a plain read. A unit row hands the function a fixture `downloads/` with one mismatched file and expects the failure to name it.

### 5. curl keeps HTTPS, and a mismatch is said once

`00_download.sh`'s curl becomes `curl -fsSL --proto '=https' --proto-redir '=https' --tlsv1.2 --retry 3`. A present file whose hash does not match is reported with the one-line fix ("delete downloads/<name> and run again") instead of a bare mismatch; it is still never refetched on its own (a poisoned cache must be seen, not silently replaced). A rules row in `tests/checks/test_rules.py` reads every `curl` command line in `scripts/` and `.github/workflows/` (comments and `curl --version` aside) and requires `--proto '=https'`, `--proto-redir '=https'` and `--tlsv1.2` on each.

### 6. The verify note is built from the repository's name, and held equal to attest's

`release/version.py`'s `verify_note()` takes the repository name as a parameter (`$GITHUB_REPOSITORY`, passed as an argument by the `notes` command, which `release.yml:2547` calls), with a default of `ClayGendron/wasi-python` for a local run; `tests/unit/test_release_version.py`'s two verify rows follow. The attest job is unchanged: it has no checkout, runs before `notes.md` exists, runs only on a pushed tag, and the release attestation scan (`tests/harness/scan.py`, "attest runs setup-uv or uv") keeps uv out of the one job that holds `id-token: write`. A unit row in `tests/unit/test_release_version.py` reads attest's `gh attestation verify` line from `release.yml` (its `\`-continued lines joined, whitespace collapsed) and holds it equal to `verify_note(version, repository)`'s command, with `"$GITHUB_REPOSITORY"` read as the repository, `$GITHUB_REF` as `refs/tags/v<version>` and `"$asset"` as `<asset>`, the quotes dropped; so the documented command is the one attest runs, and an edit to either side fails the row. `docs/how-to/verify-a-download.md` already names `ClayGendron/wasi-python` and the old name for 0.1.0 and the alphas on origin/main (`5b2689b9`); this specification does not touch it, nor `tests/harness/coverage.py`.

### 7. `.gitignore`

Five lines under a comment that says why: `.env`, `.env.*`, `*.pem`, `*.key`, and `.claude/settings.local.json`. `test_app/`, `.agents/` and `skills-lock.json` are the owner's to ignore or commit; this specification does not touch them.

## Intent

After this specification, a pin is found by its exact name and never by a pattern; the release's same-bytes check binds every file in the tarball, not only its index; no build step can reach the network through a build system's fallback; every byte read from `downloads/` is checked against its pin in the step that reads it; the download keeps HTTPS at TLS 1.2 or later; and the command users are told to run is held equal to the one the release's attest job runs, under the repository's current name.
