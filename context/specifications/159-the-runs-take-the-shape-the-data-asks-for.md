## The problem

The 0.1.2 release pull request's run took 97.5 minutes: a 42-minute macOS compile gated every judge, then 229 release legs ran 18 at a time for 52 minutes (EXECUTED, the memo §2.3). A pull request's run took a median 18.6 minutes when green and 46.6 at the ninetieth percentile, and in 13 of 17 runs with three systems the last leg to finish was a macOS leg that had waited a median 11 minutes for one of the account's five macOS runners (EXECUTED, §2.2). Every judge waits 2.5 minutes for `quick`. Fifty of the 74 red jobs in ten days were `ci-status` red by design, waiting for a review file (EXECUTED, §2.1). Every post-merge run's longest job is a 23-minute compile whose only consumer is the build shard. The owner wants the full Linux run, build and both tiers, at or under one hour.

## Decisions

### 1. The build and the judges run beside `quick`

The `build` job needs `plan` and `inputs`; `quick` leaves its needs. `ci-status` keeps `quick` in its needs, so a lint-red tree still cannot merge. A docs-only pull request still runs `quick` alone (the plan's `judge` output is false there). The cost is a few job-minutes on a tree that fails lint; the saving is 2.5 minutes on every run.

### 2. A macOS leg on a pull request only where macOS code changed

`select()` takes an own shard on macOS when the run is `full` (the merge-grade set: a push to `dev`, the `ci:full` label, a `citest:full` commit line, the workflow changed, the release pull request) or when the plan's new flag `platform` is set: a changed path under `src/wasi_python/` whose name begins `_platform`, or `uv.lock`, where the engine's pin lives. The `runner`, `set` and `harness` flags alone no longer add macOS on a pull request. The `upstream-macos` shard follows the same rule. A macOS-only defect in any other file reaches `dev` and is found by the post-merge run within the hour, and fixed forward or reverted under specification 160's rule; the memo's run data cannot show what macOS legs caught on pull requests before they reached `dev`, which is why the platform module and the engine pin keep their macOS legs (INFERRED: that is where the host-specific code lives).

### 3. The own shards are split so no leg runs past seven minutes on Windows

`own-guest` (461 checks, 11.3 minutes on Linux and 13.7 on Windows) becomes `own-guest-a`, `own-guest-b` and `own-guest-c`, its files divided so the three legs are within two minutes of each other, read from the pull request's run. `own-hostile` (218 checks in one file, 9.1 minutes on Windows), `own-embedding` (133 checks, 8.2) and `own-embedding-a` (65 checks, 8.8) are each divided in two by `file::function` entries under `nodes`, as `own-embedding-a` was cut from `own-embedding`. The shard plan's invariants (`tests/unit/test_shards.py`: every item in exactly one shard per system, every product file in a files shard on all three systems, a node taken from its file's shard) hold unchanged; a check's node id does not move, so the ratchet sees no retirement. `COVERAGE_SHARDS` in `release/ci_plan.py` names the new shards. The builder divides by the leg times of the pull request's own run and records the times in the landing notes. The budget: no own leg over seven minutes on Windows and over six on Linux.

### 4. The review file has its own check

A new job `review` (name `review`), needing `plan` alone, runs on every pull request into `dev`, gated on the event alone and never on `judge` or `docs_only`, so it runs on the push that carries the review file too; it fails when the plan's new output `review_refusals` is not empty, and that output is empty on a documentation-only pull request, which needs no review. `ci_plan.py` splits what `refusals()` returns into the refusals `ci-status` keeps (accepted state written by a pull request, a missing news file, a skip word, the release preparation's ledger move) and `review_refusals` (everything `review_refusals()` returns today). Until the repository ruleset requires `review`, `ci-status` keeps reading the review refusals too, so no pull request can merge unreviewed in between; specification 160 removes them from `ci-status` in the same change that records the ruleset read back with `review` required, pinned by the GitHub Actions app's `integration_id` as `ci-status` is. `find_reusable` and `reusable_after_edit` treat `review` as they treat `ci-status`: a green run whose only red jobs are those two is re-used by the review file's push (138's Decision 2 otherwise unchanged). The rule in `tests/harness/scan.py` that `ci-status` needs every job excepts `review`, the one job whose verdict is not the code's. The display is the point: `gh pr checks` shows one check for the code and one for the review, and no agent reads a red run to find the code passed.

### 5. The build shard runs where the pins are compiled, and the gather expects it only there

The `build-shard` job goes. The build shard's checks (the trees of every component, the compile records, the zlib tarball, the nodes that need the build host's unpacked tools and sdists) run in `rebuild-linux-x86-64` after its compile and its zero-patch check and before its wheel step, so the record is of a clean tree, which exists exactly when the plan's `rebuild` is true and always compiles from the pins, cached set or not; that job checks out with `fetch-depth: 0`, since the build shard's rules read the history, and uploads the record and hands on its id and SHA-256 as `build-shard` did, and the gather downloads it from there. `select()` sets `build` true when `rebuild` is true and the run judges (the release pull request, the weekly run, a dispatch; a tag too until specification 155 takes the tag's judge away), never on a push to `dev` or a pull request. After a merge the gather is told the plan's `build` output (`BUILD` in its env, beside `PLAN`), `expected_keys` omits `build/build` when it is false, and goals G3 and G5 treat the build shard's checks as not selected, as they treat the release tier on a normal-tier run today; `--accept-from` keeps the accepted rows of checks the record did not select, as it keeps the release tier's. The weekly run keeps its check of the cached set against two fresh rebuilds, since the `build` job still reuses there and both rebuild jobs still compile. The post-merge run loses its 23-minute compile and ends when its last judge leg does. The build shard's file's sixteen checks that read no build tree (the pins, the download script and its mirrors, the recipes' paths, the toolchain and pure-Python pins, two workflow rules) are taken from it by `nodes` into `own-pins`, on Linux and macOS, so they still run on every merge.

### 6. The build is arm64 Linux; macOS rebuilds and votes

The `build` job runs on `ubuntu-24.04-arm` whenever it compiles (it keeps `ubuntu-24.04` when it reuses a cached set); it never runs on `macos-15`. The macOS compile becomes a rebuild job, `rebuild-macos-arm64`, on `macos-15`, in the shape of `rebuild-linux-x86-64`: it compiles from the pins, runs the zero-patch check, uploads its `SHA256SUMS` and wheel, and runs only when `rebuild` is true. `same-bytes` needs `build`, `rebuild-linux-x86-64` and `rebuild-macos-arm64`, and compares both rebuilds with the build's bytes; the three-host vote stays three hosts and `REBUILD_JOBS` in `tests/harness/scan.py` names the two. The published bytes are the build job's, now made on arm64 Linux, which `docs/reference/artifacts.md` and the CHANGELOG line say; `set-cache.yml` already compiles on `ubuntu-24.04-arm`, so the cached set and the release's set come from the same host.

### 7. same-bytes gates publishing, not the gather

`gather` needs `plan`, `build`, `rebuild-linux-x86-64` (for the build shard's record, when the plan asks for it) and the four judge jobs. `same-bytes` stays in the needs of `ci-status`, `save-set`, `attest` and `publish`, so nothing is signed, published or cached that the three hosts did not agree on, and a release pull request is still red when they disagree. The gather no longer waits for the macOS rebuild before reading records that were complete.

### 8. The judges run at the plan's parallelism, and the release legs are repacked

The `max-parallel: 18` lines leave the four judge jobs; GitHub's plan limit throttles a run that asks for more, and a release-shape run then takes the account's slots for about 25 minutes, during which a pull request's legs queue behind it; nothing merges while a release pull request runs in any case, and the weekly run is at 06:00 on Monday. The release shards in `tests/release_shards.toml` are repacked from the judge-step minutes measured per existing shard in the 0.1.2 release pull request's run (`../research/2026-10-30-where-the-time-goes-since-0-1-1/release-leg-minutes.json`, the second number of each pair): whole existing shards are combined into shards whose minutes sum to at most 12, which gives about 65 shards and 13.7 job-hours against 229 and 14.4 (INFERRED from the measured legs). The measured minutes are per present shard (199 of 229 hold several groups), so the unit packed is the present shard, by its judge step, not its leg time (73 shards by leg time, over criterion 8's cap); shards of one family are packed together where they fit, so a leg fetches fewer source trees. Each release shard gains a `minutes` key holding its measured sum, data the rules read, and keeps its fuel comment. The one shard past the cap, `upstream-pure-r-001` at 18 minutes, stays as it is and is a standing `lint` warning until sympy's group is split, a change to sympy's groups and out of scope. The repacking is a judge change: the shards' names change, the groups and their checks do not, and the plan's rules (`test_release_shards_hold_the_release_groups_alone`, `test_every_item_is_in_one_shard_per_system`) hold it.

### 9. The two times are read from runs, not asserted by tests

No run is dispatched for this specification. Its own pull request changes the workflow, so its run is the merge-grade shape without the rebuilds, and the macOS rebuild, the build shard on x86-64 and the new `same-bytes` first run at the weekly run or the next release pull request, which is safe since `same-bytes` and the gather still gate signing and publishing; the landing notes record the first weekly run's id and, for the times, record the wall time of the first pull request after the merge that changes `src/` and not the workflow, and of the next release pull request's run, each EXECUTED with its run id, and the owner's one-hour target is read there. The first weekly run after the merge is read before the next release pull request opens; when it is red, the fix lands first. No test measures time (constitution §4.9); the `lint` step's budget warnings gain one line for a release shard whose `minutes` exceeds 12, a warning and never a failure.

## Intent

A pull request's run ends when its Linux and Windows legs do, about twelve minutes; the release pull request's run ends about fifty minutes after it starts; the post-merge run ends when its last judge leg does; and a green run means the code is green.

## Design

Files: `.github/workflows/release.yml` (Decisions 1, 4, 5, 6, 7, 8), `release/ci_plan.py` (2, 3, 4, 5: `classify`, `select`, `refusals`, `outputs`, `COVERAGE_SHARDS`, `find_reusable`, `reusable_after_edit`), `tests/harness/gather.py` and `tests/harness/accept_from.py` (5: `expected_keys`, G3, G5, the kept rows), `tests/harness/scan.py` (4, 6: the rule that `ci-status` needs every job, R3, R4, rule 7, `REBUILD_JOBS`, the shard rules), `tests/release_shards.toml` (3, 8), `tests/harness/budget.py` and `tests/lint/` (9), `tests/unit/test_ci_plan.py`, `tests/unit/test_shards.py`, `tests/unit/test_gather.py`, `tests/unit/test_accept_from.py`, `tests/unit/test_scan.py` and `tests/checks/test_rules.py` (the rows), `docs/contributing/review-and-landing.md`, `docs/contributing/release-process.md` and `docs/reference/artifacts.md` (what runs where, the build host), `AGENTS.md` step 6 and `context/reviews/README.md` (the two sentences that say `ci-status` holds the review now name `review`), `context/changes/159-the-runs-take-the-shape-the-data-asks-for.md`.

The workflow after the change, by event:

| event | build | rebuilds and same-bytes | judges | gather needs |
|---|---|---|---|---|
| pull request into dev | cached set, or one compile on arm64 Linux | none | own shards on Linux and Windows, macOS when the platform module or the engine pin changed; upstream groups on Linux when their inputs changed; verify on Linux | plan, build, the judges |
| push to dev | cached set | none | the normal tier on three systems, verify on three | plan, build, the judges |
| release pull request, weekly, dispatch | compile on arm64 Linux, or the cached set where it is trusted | x86-64 Linux with the build shard, arm64 macOS, same-bytes | both tiers on their systems | plan, build, the x86-64 rebuild, the judges |

The `review` job and `ci-status` are two checks on a pull request; the ruleset requires both once 160 lands. The new rows in the unit files are seen failing before the workflow changes (the plan's outputs, the needs lists, the absence of `max-parallel` and of `macos-15` in the build job's `runs-on`, the `minutes` keys).

## Scope

In: the nine decisions. Out: splitting sympy's long group; test-impact selection of own shards; larger runners; a per-component build cache; the ruleset change itself and the removal of the review refusals from `ci-status` (160); the tag's run (155).

## Acceptance criteria

1. On a pull request into `dev` that changes `src/wasi_python/runner.py`, the plan's `macos` output is `[]`; one that changes `src/wasi_python/_platform.py` or `uv.lock` names the own shards on macOS; a push to `dev` and the `ci:full` label name every own shard. Unit rows.
2. `build.needs` holds `plan` and `inputs` and not `quick`; `ci-status.needs` holds `quick`. A rules row.
3. The `review` job exists, gated on the event alone, with `review_refusals` as a plan output; `ci-status` still reads them until 160; `find_reusable` skips `review` as it skips `ci-status`; the every-job rule excepts `review`. Unit rows.
4. On a push to `dev` and a pull request the plan's `build` output is false; on the release pull request, the weekly run and a dispatch it is true, and on a tag too until specification 155 changes that row. Unit rows.
5. The `build` job's `runs-on` names no macOS runner; `rebuild-macos-arm64` exists, runs on `macos-15` only when `rebuild` is true, and is in `same-bytes`'s needs; `build-shard` is no job; `rebuild-linux-x86-64` runs the build shard and hands on its record. Rules rows.
6. `gather.needs` is `plan`, `build`, `rebuild-linux-x86-64` and the four judge jobs; `same-bytes` is in the needs of `ci-status`, `save-set`, `attest` and `publish`. A rules row.
7. After a merge the gather expects no `build/build` record and G3 and G5 hold with the build shard's checks not selected; `--accept-from` keeps their accepted rows. Unit rows, seen failing first.
8. No `max-parallel` line in the workflow; every release shard has a `minutes` key; there are at most 80 release shards; `lint` warns on a shard above 12 minutes and fails on nothing. Rules and unit rows.
9. No own shard's leg in the pull request's run exceeds seven minutes on Windows or six on Linux, and the three `own-guest` legs are within two minutes of each other (EXECUTED in the landing notes from the run's job times).
10. The first pull request after the merge that changes `src/` and not the workflow ends within 15 minutes of its creation, and the next release pull request's run within 60 (EXECUTED in the landing notes, run ids named, when those runs exist).
11. The fast tier, `tests/lint` and the pull request's `ci-status` are green; the news file names the shard plan and the gather under `judge` with their reasons, and its CHANGELOG line says the published set is built on arm64 Linux.
