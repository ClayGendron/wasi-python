## The problem

A `.cwasm` is native code wasmtime runs as it finds it, so the runner loads one only from a folder no one but this user, and those who already control the tree, could swap. On POSIX, `_Posix.cache_folder` (`_platform.py:497-518`) walks the way to the cache with `_way` (`_platform.py:562-585`): every folder from `/` down that exists must be a folder, owned by uid 0 or `os.getuid()` (`:576`), and closed to other writers unless sticky (`:578`). A failure raises `PermissionError`, which `_module_miss` (`_engines.py:212-214`) turns into one `RuntimeWarning` through `_cache_warning` (`_engines.py:298-302`); the module is compiled in memory and the call runs. Five things are wrong with it.

- **A host where another uid owns `/` never caches** (the memo, EXECUTED, `:14`, `:22-29`). On Cloudflare Containers the container's `/` is owned by uid 2346 while the runner runs as uid 10001 with every folder of its cache at `700 runner:runner`. `/` is on the way to every path, so no cache folder can pass, and every container start compiles: 323 s and 295 s on a 1/2-vCPU instance, against about 0.3 s for a load. The same image under Docker Desktop, where `/` is root's, loads its baked `.cwasm` (`:32`).
- **The warning's advice cannot be followed there** (the memo, `:17`, `:29`). It ends "set $WASI_PYTHON_CACHE to a folder of yours" (`_platform.py:583`), and every folder is below `/`.
- **Two owner tests disagree** (the security review's L3; 139's "Beside 135"). The folders the runner makes and the sweep ask `_platform_common._this_users` (`_platform_common.py:181-189`): the effective uid, the one a made file is owned by, with the observers' `owner_of` (`_process.py:89`) standing in for the owner in the rows. The cache asks `os.getuid()`, the real uid, in `_as_made` (`_platform.py:485`) and `_way` (`:576`), and reads the password entry of the real uid in `default_cache_dirs` (`:460`). Where the two uids differ, which question 112 places outside what is supported, the runner's own `.cwasm` fails `_as_made` and is compiled around (fails closed), but `_way` trusts the real user's folders on the way to a cache the effective user loads native code from. And no cache row can stand in for an owner, since `owner_of` is not asked.
- **135's three deferred Lows** (`135-…md:120-123`). 113's swap row (`tests/unit/test_runner_module_caches.py:432-463`) passes because its stand-in's `os.replace` onto `/dev/fd/N` fails, so nothing on POSIX tests the by-path fallback's stamp re-check (`_engines.py:282`). `_module_miss`'s `held` defaults to None (`_engines.py:195`), the branch that compiles without comparing the digest, which only the judge's direct calls take. And `cache_folder`'s `mkdir` loop (`_platform.py:507-511`) passes over `FileExistsError`, so a folder another user makes between the walk and the `mkdir` is adopted unjudged in this process.
- **`$WASI_PYTHON_CACHE` is read in three places in three forms** (the structural review's L5): made absolute when the call is made (`_engines.py:85-86`), read again when the cache is resolved if it was unset at the call (`:102-103`), and read raw, possibly relative, for the other caches the grant judge must keep from the guest (`:115-116`). And the form "absolute" is `os.path.abspath`, which collapses `..` by its spelling: on POSIX the system climbs from where a link leads, so `granted/link/../c` and `granted/c` are different folders, as `test_a_cache_reached_through_a_link_then_dotdot_in_a_writable_grant_is_refused` (`tests/unit/test_runner_module_caches.py:229-251`) holds for the raw value today.

## Decisions

### 1. The owner of `/` is trusted on the way to the cache as root is

**The predicate.** `_way` walks `[*reversed(folder.parents), folder]`, `/` first, through the `lstat` it is given. Let `owner(st)` be `_platform_common._owner(st)` (Decision 3: the observers' `owner_of(st)` when set, else `st.st_uid`), `e` the effective uid, and `r` the owner of `/`, read as `owner(lstat("/"))` from the walk's own first step. An existing entry `here` with stat `st` is refused, in this order, when:

1. it is not a folder (`not S_ISDIR(st.st_mode)`), "is not a folder", as today;
2. it is another user's: `here` is not `/`, and `owner(st)` is neither `e` nor `0`, nor `r` on a folder whose `st_dev` is `/`'s, where `r != 65534`; the words "is another user's (uid N)", as today;
3. others may write it and it is not sticky (`st.st_mode & 0o022 and not st.st_mode & S_ISVTX`), "may be written by others (mode NNN) and is not sticky", as today, for every folder, `/` included.

Written as code, with `root_dev` read from the walk's first step beside `r`: refused for its owner when `here != here.parent and not _this_users(st) and owner(st) != 0 and not (owner(st) == r != _OVERFLOW_UID and st.st_dev == root_dev)`, where `_OVERFLOW_UID = 65534` is a module constant of `_platform.py` with a comment giving its reason. The cache folder itself and its `.cwasm` are untouched by this: `_as_made` still requires them to be this user's, at 0700 and 0600, with one name and no access list. `/`'s owner is trusted on the way, never as the owner of the cache.

**The reason.** The check's promise is that no one but this user and those who already control the tree can swap the folder a `.cwasm` is read from. Whoever owns `/` already controls the tree: they may `chmod` `/` and then rename any entry of it that is not a mount point, `/home` and the cache's own way included, and they may replace `/etc`, which makes them root wherever a setuid program is installed (the memo, `:65`, INFERRED; `python:3.14-slim` carries setuid `su`, `mount` and `passwd`). Root is trusted on every folder already. So trusting `/`'s owner adds no one the check was keeping out, and it needs no embedder action and no new public surface (the memo's option 1, `:47-49`); the memo's option 2, an opt-in that vouches for a path, is a new public surface that is easy to give carelessly, and option 3, words alone, leaves the cache off on such hosts. The trust is read from the walk's first step through the same `lstat` and the same owner function, so it costs no system call and a stand-in `lstat` decides it in the rows.

**The edge cases, each decided.**

- **`/` itself always passes the owner test.** Its owner is by definition `/`'s owner. So `/` is refused only for its kind or its mode, and Decision 2's words are the only words `/` can produce.
- **`/` writable by its group or by others, without the sticky bit, still refuses**, whoever owns it: anyone in that group, or anyone at all, could rename `/home` away. A sticky `/` passes, as a sticky `/tmp` does: no one but an entry's owner, the folder's owner and root may rename an entry in it. The mode rule is unchanged for every folder.
- **An overflow or unmapped owner (65534).** Under a user namespace, a file whose owner has no mapping in the namespace shows the kernel's overflow uid, 65534 by default (`/proc/sys/kernel/overflowuid`; INFERRED from `user_namespaces(7)`, not run here). No process in the namespace has owner rights over such a file, so a `/` showing 65534 passes for its owner, like any `/`. But the number is ambiguous below `/`: a folder that really belongs to a mapped uid 65534 (the namespace's `nobody`) shows the same number as an unmapped one, and that user, often the least trusted on the host, could rename what is in it. So when `r` is 65534 it is trusted on `/` alone, and a folder below `/` owned by 65534 is refused as another user's, as today; the warning then names that folder and its advice (another folder of yours) can be followed. Reason: trusting a number that stands for two different owners would add one of them, and the one it could add is `nobody`. A host that changed `overflowuid` from its default is not chased: reading the sysctl would add a file read and a Linux branch for a value almost never changed, and the gap it leaves needs both an unmapped `/` and a folder below it really owned by a mapped uid equal to the changed value.
- **Below a mount point.** The owner of `/` cannot rename a mount point (`EBUSY`), and on a read-only `/` it can neither rename an entry nor replace `/etc`, so past a mount its only power over a folder is owning it. So it is trusted below `/` only on a folder on `/`'s own device (`st_dev`, from the stat the walk already holds); a folder on another device that it owns is refused as another user's, as today. A bind mount of `/`'s own file system keeps `/`'s device and is not told apart: that remainder is named, not closed.
- **A chroot or a container's own root.** The walk sees the process's `/`; the folders above it are the host's, outside every check before and after, as today.
- **`/` owned by this user or by root.** No change: `r` is already trusted.
- **The process runs as 65534 and `/` is unmapped.** A folder showing 65534 passes as this user's through `_this_users`, as it does today with `os.getuid()`; this specification neither adds nor closes that collision.
- **What the embedder's host still needs.** `/` closed to other writers, and every folder below it this user's, root's or `/`'s owner's and closed to other writers. The memo did not read `/`'s mode or `/home`'s owner on Cloudflare (`:69`); if either fails, the cache is still not used, and Decision 2's words, or the existing ones, say which folder and why.

### 2. When `/` is what fails, the warning says no folder can help

`_way` builds its message as `f"{here}, on the way to it, {why}; {advice}"`. The advice is "set $WASI_PYTHON_CACHE to a folder of yours" for every folder below `/`, as today, and for `/` itself (`here == here.parent`) it is: **"no folder can hold the cache while it is, so have its owner run chmod go-w /, or pass cache_dir=False to compile in memory without this warning"**. So the whole warning on a `/` at 0777 reads: "wasi_python: not using the module cache at /home/runner/.cache/wasi_python: /, on the way to it, may be written by others (mode 777) and is not sticky; no folder can hold the cache while it is, so have its owner run chmod go-w /, or pass cache_dir=False to compile in memory without this warning". Reason: every cache folder is below `/`, so `$WASI_PYTHON_CACHE` cannot help; the two things an embedder can do are close `/` (in its image, as `/`'s owner) or say it keeps no cache, and `cache_dir=False` keeps the module in memory with no walk and so no warning. After Decision 1, the mode is the only reason `/` can fail, so the advice names the mode's fix.

### 3. One owner test, by the effective uid, for the cache too

`_platform_common` gains `_owner(st) -> int`, the owner the runner compares: the observers' `owner_of(st)` when set, else `st.st_uid`; `_this_users` calls it in place of its inline expression, unchanged in behaviour. `_Posix._as_made` asks `_platform_common._this_users(st)` in place of `st.st_uid == os.getuid()`; `_way` asks `_this_users(st)` for this user and `_owner(st)` for root and `/`'s owner (Decision 1). `_Posix.default_cache_dirs` lists the defaults under the password entries of both the real and the effective uid, deduplicated, where it lists the real uid's alone (`_platform.py:460`). Reasons: the effective uid owns what this process makes, so it is the uid to compare, as 139 decided for the made folders and the sweep; one owner function means one place for the owner and one stand-in for every row that needs another owner, and the cache rows gain the `owner_of` stand-in (Decision 6, row 5); `default_cache_dirs` is the list of caches the grant judge keeps every guest from, so a wider list only refuses more, and a process with no `$HOME` resolves its own default under the real uid's entry (`Path.home()`), so both entries stay. The real uid and the effective uid are the same in every row; that they differ is read in review, not run, as 139's was.

**Beside 149.** The 0.1.1 structural review's L4 asks that `_this_users` take its owner source as a parameter rather than from the observers. 149 leaves that half to the next structural review (its Scope). This specification builds on `dev` as it stands, with `owner_of` on the observers, and puts every owner test of the cache through `_owner` and `_this_users`, so whoever later moves the owner source moves one function, and these rows move with the grants and sweep rows. After this specification the judge-only branch L4 names is asked by the cache's checks too, which the next structural review reads. Reason: 147 is the embedder's blocker and should not wait on a structural Low; routing through the one function is what makes that later move one move.

### 4. 135's three Lows, with the reviewer's fix text

- **The swap row tests the by-path fallback again.** `tests/unit/test_runner_module_caches.py::test_a_cwasm_swapped_between_its_check_and_its_load_is_discarded` is rewritten, not retired: on POSIX it passes `_module_miss` a `reopen=` open that fails, so wasmtime is given the path, the stand-in's `os.replace` at that path succeeds, and the stamp re-check is what discards the swapped file (compiled 1, loaded 0, written 1, the file 0600 after); on Windows it is skipped, naming `test_on_windows_the_cwasm_is_held_open_from_its_check_to_its_load`; its docstring says "where wasmtime is given the path". A judge change, with that reason, in the news file's claim.
- **`held` has no default.** `_module_miss(wt, engine, metered, binary, cache, digest, held, *, lstat=…, reopen=…)`: `held` is required, so a later caller cannot reach the compile without the digest compare by forgetting it. 113's rows that call `_module_miss` with a digest of their own (`tests/unit/test_runner_module_caches.py:338`, `:458`) and 135's helper (`tests/unit/test_runner_module_cache_read.py:79`) pass `held=None` by name. `_compile`'s docstring says None is "a key the caller names itself, never the binary's". `_module` passes True or False positionally as today, so `tests/unit/test_runner_sets.py`'s positional stand-in still works.
- **The way is walked once more after the `mkdir` loop.** In `_Posix.cache_folder`, after the loop, `_way(folder.parent, lstat)` runs again, so a folder another user made between the walk and the `mkdir`, which the loop passed over as `FileExistsError`, is judged as an existing one is: one that fails raises the walk's `PermissionError`, and the cache is not used, with the warning. If the second walk finds a folder missing (one removed between its `mkdir` and the second walk), `cache_folder` raises `FileNotFoundError(errno.ENOENT, "<folder>, on the way to it, went away while it was made")`, and the cache is not used, with the warning: a folder that vanishes there means someone else is changing the way, and the cache is never worth a failure. The second walk costs one `lstat` per folder on the way, once per flavor per process; the landing notes record the count.

### 5. `$WASI_PYTHON_CACHE` is read once, at the call, and made absolute as the system reads it

`_cache_given(given)` reads the variable once and returns a record, `_Cache(folder, named)` (a `NamedTuple` in `_engines.py`): `folder` is the cache folder this call uses, absolute, or None for none; `named` is the folder the variable names at the call, absolute, or None when it is unset or empty. `folder` is the given folder; or, for `None` and `True`, `named` when set, else the platform's default under `_home()`, else None; or None for `False`. An empty `cache_dir` still raises `ValueError` before any work. `_cache_dir` is folded into `_cache_given` and removed; `_call._run_checked` and `_sessions._open_session` read `chosen.folder`; `_caches(chosen)` takes the record and names `chosen.named`, never reading the variable itself. The runner's entry points keep their public `cache_dir` parameter and bind the record to a new local name. Reason: one read means the folder judged, the folder used and the folders kept from the guest are all as the variable stood when the call was made, as `_cache_given`'s docstring already promises.

**Absolute, not collapsed.** A relative value is made absolute by a new platform method, `PLATFORM.absolute(path)`: on POSIX `os.path.join(os.getcwd(), path)`, joined without normalising, as the walk joins (`_platform.py:218-220`); on Windows `os.path.abspath(path)`. The same method makes a relative `cache_dir` absolute. Reasons: on POSIX the kernel takes `..` after it follows the link before it, so collapsing `link/../c` to `c` names another folder, and an `os.path.abspath` here would turn the link-then-`..` guard row red, a guard lost; on Windows, Win32 collapses `..` by its spelling before it opens anything, so `abspath` is the system's own reading, and it also resolves a drive-relative `D:rel`, which a plain join leaves relative. That is a platform difference, so it is a method of the platform object, not a branch in `_engines.py`. `_caches` drops a repeat only when two absolute spellings are equal, never by a collapsed form: listing one folder twice costs one more walk, and dropping a different folder as a repeat would drop a guard.

**What stays.** `_caches` still reads `_home()` and the platform's defaults itself: the call's own folder is passed to the grant judge by name beside the others, so a `$HOME` read twice leaves no folder unjudged. An embedder that changes `$WASI_PYTHON_CACHE` while a call runs changes it for the calls made after; the running call judged its grants as the variable stood at its start, and today's late read leaves the same kind of window after the walk. Both are the embedder's own race, outside what any read order closes.

## Intent

After this specification, a runner on a host whose `/` belongs to a uid of its own, such as a container runtime that maps ids, keeps its compiled module between starts, because the one owner who could already swap anything below `/` is trusted on the way as root is; nothing else is trusted that was not, the mode rule holds for every folder, and the ambiguous overflow uid is trusted on `/` alone. Where `/` itself is what fails, the embedder is told the two things that help. The cache asks the same owner test, by the effective uid, as every other folder the runner makes, so the rows can stand in for any owner on the way. And the carried Lows close: the by-path fallback is tested again, the unsafe default is gone, a folder made on the way is judged, and `$WASI_PYTHON_CACHE` is read once and kept in the form the system reads it. The embedder confirms it on its own host when it pins the release: its warm-up reports `loaded`, or the new words name what is left.
