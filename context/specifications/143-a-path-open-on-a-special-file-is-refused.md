## The problem

A FIFO is a named pipe: a file-system object whose `open` waits in the kernel until its other end is opened. A guest cannot make one, but a folder the embedder grants may hold one, left there by the host or by another local process that can write the folder. M1 found that a guest's `open('/g/fifo', 'rb')` with `deadline_s=2`, its `O_NONBLOCK` variant, and `open('/g/fifo', 'wb')` on a writable grant were each still waiting at 25 s, with or without a `cancel` set at 2 s, and that `Session.close()` on a session whose turn is blocked so had not returned at 25 s (EXECUTED by the review, `:180-191`). The guest's `O_NONBLOCK` does not reach the host's open (`:189`).

Why: the deadline, `cancel` and Ctrl-C stop wasm code at its next epoch check (READ, `_call.py:425`, `:706`, `:778`; `_fs_table.py:292-305`, "an interrupt at the next entry"). A guest inside a host call is beyond them until the call returns. `_outputs.py`'s docstring states this rule for a full pipe (`_outputs.py:25-26`), and the reader is built around it; nothing applies it to `path_open`. Since 0.1.1 the security model and the grants guide say so (`docs/explanation/security-model.md:80`, `docs/how-to/grants.md:119`), but nothing refuses the open.

The forwarded open is wasmtime's. On a grant, `_path_open` finds no entry in the call's table for the descriptor and forwards the call unchanged (`_fs_paths.py:107-113`). wasmtime's `open_at` hands the open to the host and only then asks what it opened (READ, `crates/wasi/src/filesystem.rs:1020-1029` in both trees): `O_DIRECTORY` is not passed to the host, so an `O_DIRECTORY` open of a FIFO waits too (EXECUTED, `build/143/opens.log`: "fifo, O_DIRECTORY: still waiting in the open after 5 s").

## Decisions

### 1. The look goes through wasmtime, on the same descriptor; the runner records no host path

Before a `path_open` on a grant is forwarded, the runner forwards wasmtime's own `path_filestat_get` with the open's descriptor, lookup flags, path pointer and path length, and reads the filetype it answers. The runner does not learn the host path of the descriptor, and does not need it.

What the runner knows today (READ): the table's `held` is a `set[int]` of the numbers wasmtime gave the guest (`_fs_table.py:132`, `_hold` at `:587`), with no kind and no path, as 140 found; `preopens` is only a count (`:134`); `others` is the preopens' guest paths (`_call.py:484`); the preopens' host folders exist only as `_run`'s locals (`_call.py:473-475`, `p.walked.path`), and a session's table is built the same way (`_sessions.py:1024`); a folder the guest opens below a preopen is known by its number alone. A look by host path would need the preopens' host folders handed to the table and, at every successful forward, the guest's path joined onto its base's host path and recorded per number, with that record kept through `fd_renumber` and `fd_close`.

Reason: that record would be wrong in three ways the forwarded look is not. It goes stale when the guest or the host renames a folder the guest holds open. It resolves `..` and links on the host's terms, not inside wasmtime's sandbox, so `os.lstat` of a joined path could look outside the grant and tell the guest whether a name there is a special file, a probe of the host it does not have today. And it needs Windows path translation. The forwarded look resolves the path exactly as the open will: the same descriptor, the same bytes, the same lookup flags, the same sandbox. It tells the guest nothing its own `path_filestat_get` does not already tell it. Its cost is one more forwarded call and wasmtime's two host stats (`stat_at` and `metadata_hash_at`, `crates/wasi/src/p1.rs:2064-2076`) per open on a grant, and 64 bytes saved and restored in the guest's memory (Decision 4); it records nothing.

### 2. Look before the forward; opening non-blocking is not open to the runner

The review named a second fix: open the special file non-blocking. The runner cannot. The open is wasmtime's `open_at`, which takes no non-blocking flag from preview1 (READ, `filesystem.rs:934-1029`), and the guest's `O_NONBLOCK` does not reach it (EXECUTED by the review, `:189`). The runner could open the file itself, but wasmtime-py offers no public way to put a host descriptor into the store's WASI table, so the guest could not use what it opened. Reason: the look is the only fix inside the runner; a non-blocking open is a change to wasmtime itself, out of scope here.

### 3. The answers

The look is made only for an open that wasmtime would take to its host open: the path and the look's window (Decision 4) are in the guest's memory; `oflags` holds only wasmtime's four bits, and not both `O_CREAT` and `O_EXCL`; `fdflags` holds only wasmtime's five bits and none of `SYNC`, `DSYNC`, `RSYNC`; both rights words are within `RIGHTS`; and `O_DIRECTORY` comes without `O_CREAT`, `O_EXCL` and `O_TRUNC`. Any other open is forwarded unchanged, as today, and wasmtime refuses it before any host open (READ: an undefined flag bit is `EINVAL` from wiggle's conversion, `p1.rs:1114-1119`; the sync flags, `O_DIRECTORY` with a create and a read-only grant's write are refused in `open_at`, `filesystem.rs:987-1009`). An open past the cap answers `EMFILE` first, as today, with no look.

- The look answers an errno: the open is forwarded, and the guest gets wasmtime's own answer. A missing name an `O_CREAT` open will create is this case.
- The look ends in a wasmtime error: the guest gets `ENXIO`, no stop is recorded, and the run goes on. Preview1 ends a `path_filestat_get` that meets a socket of wasmtime's `Socket` type (READ, `p1.rs:1013-1016`, `:2079`); wasmtime's POSIX code names no socket so today (READ, `filesystem/unix.rs:150-158`, so a socket answers `Unknown`; EXECUTED, `probe.log`: a socket answers filetype 0 on macOS), so this case is for a later wasmtime. The store stays usable after a wasmtime error in a nested call (EXECUTED, `probe.log`: after a nested `path_filestat_get` ended on a path past memory, the guest's own call answered 0 with filetype 4).
- The filetype is a folder (3), a regular file (4) or a link (7): the open is forwarded.
- Any other filetype (0 unknown, which is a FIFO or a socket; 1 block device; 2 character device; 5 and 6 sockets): `ENOTDIR` when the open has `O_DIRECTORY`, else `ENXIO`. Nothing is forwarded and no number is held.

Reason: `ENXIO` is what a POSIX host answers for a FIFO opened non-blocking to write with no reader, and what Linux answers for an open of a socket, so it is "no such device or address" as a sealed host would say it. `ENOTDIR` for `O_DIRECTORY` is wasmtime's own answer for any non-folder (`filesystem.rs:1024-1027`, `:1055`), so a guest asking for a folder sees no change. `O_CREAT` with `O_EXCL` gets no look: the host refuses an existing name with `EEXIST` before it opens anything (EXECUTED, `opens.log`: "fifo, O_CREAT|O_EXCL: errno 20"), so the look would only cost a call. The other arguments are left to wasmtime so that every errno it gives before its host open stays its own, in its own order.

One answer differs from wasmtime's, kept and named: an open that asks to write a special file on a read-only grant answers `ENXIO`, where wasmtime answers `EPERM` from its permission check before the host open. The runner does not record which grant a held folder came from, and both answers refuse with nothing opened. `_forwarded_open`'s docstring names it, and a row asserts it.

### 4. The look's 64 bytes, at address 0, saved and restored

wasmtime writes `path_filestat_get`'s 64-byte answer into the guest's memory. The runner saves the 64 bytes at address 0, makes the look with its answer there, reads the filetype at offset 16, and writes the 64 bytes back in a `finally`, before the open is forwarded. Reason: address 0 is in bounds and 8-aligned for any memory of one page or more, so no address has to be chosen. A path that overlaps it is harmless: wasmtime copies the path before it stats it and writes the answer after (READ, `p1.rs:2063`, `:225-228`), and the bytes are restored before the open reads the path again. The guest cannot see the window: it is inside its own host call, on its one thread, and its memory is not shared (wasm32-wasip1 without threads). No look is made when the memory is smaller than the window or does not hold the path (Decision 3).

### 5. The look follows links exactly as the open will

The look is made with the open's own lookup flags. When the open follows links (wasi-libc sets `SYMLINK_FOLLOW` unless `O_NOFOLLOW`; READ, `context/prior_art/wasi-libc/libc-bottom-half/cloudlibc/src/libc/fcntl/openat.c:73-75`), the look follows them, and a link that names a FIFO answers the FIFO's filetype, refused. When the open does not follow, the look does not, a link answers filetype 7 and is forwarded, and wasmtime refuses to open the link itself with `ELOOP`, without waiting (EXECUTED, `opens.log`: "link, nofollow, read: errno 32").

Reason: a look that never follows would let a link through to an open that follows it, and that open waits (EXECUTED, `opens.log`: "link, follow, read: still waiting in the open after 5 s"; `probe.log`: a link to a FIFO answers 7 without following, 0 with). A guest can make that link itself on a writable grant with `path_symlink`, which is wasmtime's own, so a look that never follows would let the guest step around the refusal. The approved wording, "looks at the target without following links", is kept where it binds: the look never opens the target, and an open that does not follow is looked at without following.

### 6. What a look cannot close, said in the docs

Between the look and wasmtime's open, the name can change. The guest that made the look cannot change it: it is inside its own host call. A host process can, and so can another call or session that writes the same grant at the same moment, by renaming a link to a FIFO already in the grant over the name. Reason: closing that window needs the open itself to refuse a special file, which is wasmtime's open (Decision 2); the window needs a special file the embedder left in a granted folder and a writer racing one open; the docs say so in one sentence each (Design).

### 7. A mount is out of scope

A mount's `path_open` is served by the runner from its provider's answers, not forwarded (`_fs_paths.py:114-169`). A provider answers `stat`, `list` and `read` with values: a `Stat` whose kind is `"file"` or `"dir"`, pairs whose kind is the same, and bytes (READ, `mounts.py:7-13`, `:64-118`; the runner refuses any other kind, `_fs_table.py:643-644`). The runner owns every descriptor and the provider sees only paths, so a provider cannot hand back a special file's descriptor. Reason: there is no special file on a mount to refuse. A provider whose own `read` waits on a host FIFO is the embedder's code running on the call's home thread, which the gate checks before each provider call; bounding a provider's call is a different change, out of scope.

### 8. Windows

Windows has no FIFO in a folder: its named pipes live in the `\\.\pipe\` namespace, which no grant can name (INFERRED). wasmtime's Windows `descriptor_type` names one special file, the `NUL` device, a character device, and every other one `Unknown` (READ, `filesystem/windows.rs:150-170`); an open that reaches `NUL` through a grant answers `ENXIO` now, as a device does on POSIX. The look runs on Windows as everywhere, for every open on a grant. The unit rows that plant a FIFO or a socket skip on Windows with `@pytest.mark.skipif(not POSIX, reason="no FIFOs on Windows")`, as `tests/unit/test_runner_sweep.py:173` does; the unit suite counts a skip, it does not judge it. The goal-check rows in `tests/checks/` may not skip without a known need (READ, `tests/harness/plugin.py:510-523`), so on Windows they run the same guest against a regular file at the same name and assert the open succeeds and `Session.close()` returns, as `test_v1_2_hostile_guest.py:1225` runs a different child there. Reason: the Windows legs then read the look's common path, a regular file let through, on every row; no named pipe is planted, since none can sit in a grant.

### 9. Fuel and bytes do not change

The look is a forward, and a forward is fuel-neutral: the guest's fuel is read, raised by the allowance and set back in a `finally` (READ, `_fs_table.py:234-265`); the look's own error path sets it back the same way and records no stop. The guest's code and the artifact set do not change. Reason: no check's fuel can move, so there is no fuel row; the ratchet's fuel lines are the check, and the post-merge acceptance refuses an unclaimed growth. The claim says fuel none.

## Intent

After this specification, a guest that opens a FIFO, a socket or a device file in a granted folder is refused at once with `ENXIO`, as a sealed host would answer, so the open cannot hold its call past the deadline and `cancel`, and `Session.close()` does not wait on it. The look that decides it resolves the name as the open will, through wasmtime, on the same descriptor, and records nothing. What it cannot close, a host or another writer swapping a name during the open, is said in the docs.
