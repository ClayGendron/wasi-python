## The problem

Six Lows on the release path. None lets a change reach `main` or PyPI unreviewed, since only the owner's account merges and a release builds from source at the release pull request and at the tag. Each weakens a check that should hold on its own.

1. **The agents' own files count as documentation (L2).** `classify` puts `.claude/` and `AGENTS.md` in the `docs` row (`release/ci_plan.py:130`, and `DOCS_FILES` at `:96`). A pull request that changes only them is `docs_only`: it runs `quick` alone and needs neither a news file nor a review (`refusals`, `:454-460`). `.claude/settings.json` is tracked and can carry hooks, shell commands that run on the machine of every agent that opens the repository, and the agents' permission lists. EXECUTED while drafting: `classify` gives `{"docs"}` for `.claude/settings.json`, `.claude/hooks/x.sh` and `AGENTS.md`, and `docs_only` is true for each alone. The release's preparation, also judged as documentation, may carry such a change too (`is_release_preparation`, `:150-168`).
2. **GitHub's `skip-checks: true` trailer is not refused (DL1).** `refusals` refuses the five bracketed skip words in a pull request's title or description (`SKIP_WORDS`, `:95`; the loop at `:462-470`), since the squash merge's message is the title and description and GitHub starts no run for a commit whose message carries one. GitHub's documentation names a second form beside them, a message that ends with a trailer line `skip-checks:true` or `skip-checks: true` (INFERRED, the review's reading; not re-checked here, by the rule against probing a third-party host). EXECUTED while drafting: a description ending in a blank line and `skip-checks: true`, or `skip-checks:true`, gives no refusal. Such a merge would start no post-merge run, so `dev` would go unjudged and unaccepted until the next merge.
3. **The plan misreads a path that git quotes (L4).** `_diff` (`:821-823`), `read_pull_request`'s per-commit list (`:840`) and the preparation's `--name-status` pairs (`:890-891`) read `git diff --name-only` and `git diff-tree --name-only` as lines. Git quotes a path with a byte above `0x7f`, a double quote, a backslash or a control character, and escapes it. EXECUTED while drafting, in a throwaway repository: `.github/workflows/é.yml` and `src/wasi_python/é.py` come back as `".github/workflows/\303\251.yml"` and `"src/wasi_python/\303\251.py"`, which `classify` maps to `[]`; read with `git -c core.quotePath=false … -z`, they map to `workflow` and `runner`. So a new workflow with such a name does not force the merge-grade set, and a runner file with one does not run macOS. The review check and the preparation fail closed on `[]`, since it is not documentation.
4. **A retargeted pull request is not judged again (L5).** `types: [opened, synchronize, reopened, labeled]` (`release.yml:29`) has no `edited`. A pull request retargeted from `dev` to `main` keeps the narrow green `ci-status` of its run into `dev`, and an edit of the title or description that adds a skip word or changes the `Author:` line is never read. The tag still builds from source, so the assets stay safe. The review's second half, that the first tag run's `attest`, `publish` and `pypi` be read before anything else, is done: 0.1.1's tag run 40501356433 attested and published the GitHub release in its first attempt, and its `pypi` job failed four times with `invalid-publisher`, the token's claims being repository `ClayGendron/wasi-python`, workflow `release.yml`, environment `pypi`, because PyPI's publisher still held the repository's old name; the owner re-registered the publisher and the fifth attempt published, and PyPI's digest of the wheel equals the release's (READ, 138's landing notes, "The release of 0.1.1").
5. **The release token reaches the notes step (L6, 0.1.0's L5a).** In `publish`, `GH_TOKEN` (`contents: write`) is in the environment of the one step that runs `uv run --no-project python release/version.py notes` and then `gh release create` (`release.yml:1479-1488`). `notes` reads `CHANGELOG.md` and prints (`release/version.py:227-231`, `:466-468`); it needs no token.
6. **PyPI's upload runs a container named by tag while it holds `id-token` (L6, 0.1.0's L5b).** `pypi` ends with `pypa/gh-action-pypi-publish@dc37677b…` (`release.yml:1515`): the action is pinned by commit, but the container it runs is named by a mutable tag, so the bytes that hold `id-token: write` are not pinned. The review's fix is `uv publish --trusted-publishing always` with the pinned uv, which every other uv job already installs: `UV_VERSION: "0.9.22"` (`release.yml:61`) through `astral-sh/setup-uv` pinned by commit.
7. **Three documents (L6 and L1).** `SECURITY.md` names the three advisories wasmtime 50 carries but not wasmtime's batch of 2026-10-19 (`SECURITY.md:22-28`). The install page says a `.cwasm` "made any other way is compiled around and never loaded" (`docs/get-started/install.md:58`), which a umask of `077` makes untrue for a guest's file in a cache this process cannot know (0.1.0's D1). And `ci-status` and the review check are computed by `release/ci_plan.py` and the workflow, run from the pull request's own head and merge ref (`release.yml:101-130`), so a pull request that edits them can give itself a green check; only the reviewer stands there, and the reviewer's checklist does not say so (`context/reviews/README.md:20-31`).

## Decisions

### 1. The agents' files get a row of their own: `quick` alone, but not documentation (L2)

`classify` gives `agents` to a path that has a folder named `.claude` or `.agents` anywhere on it, or whose file name is `AGENTS.md`, `CLAUDE.md` or `CLAUDE.local.md` at any depth, in any case, since the owner's file system ignores it (the names compared by `casefold`); such a path takes no other row. So `.claude/` leaves the `docs` row's prefixes at `:130`, `AGENTS.md` leaves `DOCS_FILES`, and `context/CLAUDE.md` or `docs/AGENTS.md`, documentation today, is no longer. These are the names an agent's tool loads by itself, at the root or in the folder it works in: its settings, hooks and permissions, its skills, its instructions and an author's local instructions. Only `.claude/settings.json` and `AGENTS.md` are tracked today; the rest are in the row so that adding one is reviewed from the first commit. `FLAGS` gains `agents`, `Decision` gains `agents: bool`, `outputs` writes it, and the `plan` job's `outputs:` hands it on beside the others; no job gates on it. A change whose every path is `docs` or `agents` runs `quick` alone: `Decision.judge` becomes `not self.quiet and (self.full or not (self.docs_only or self.agents_only))`, with `agents_only` set in `decide` when every changed path's classes are within `{"docs", "agents"}` and one is `agents`. It is not `docs_only`, so `refusals` asks it for a news file and a review file as for any change, a commit to one of these paths after the review is refused as a code commit is, the re-use of a green run does not cross it (`reuse_rule` admits `docs_only` alone), and the release's preparation that carries one is no preparation (`is_release_preparation` admits `docs` alone). Reason for a row and not the review's other option, setting nothing: a path in no row runs the own shards on Linux and Windows, which judge nothing in these files; what the finding asks for is the review, and the row gives it without the shards. `SECURITY.md`, `.gitignore`, `mkdocs.yml` and the rest of `DOCS_FILES` stay documentation: none is loaded or run by an agent's tool, and `mkdocs.yml` is built by the docs workflow's own required check. The knowledge tree under `context/` stays documentation too: agents read it by instruction, not by a tool's own loading, and it is the reviewers' medium, so a review per change there would end documentation-only pull requests. The cost, accepted: a change to these files alone carries a news file, and a news file holds at least one CHANGELOG line (`tests/harness/news.py` refuses one with no heading), so it is named in the next release's CHANGELOG; one pull request since 138 changed `AGENTS.md` with `context/` alone (#22, 2026-10-26).

### 2. GitHub's skip trailer is refused beside the skip words (DL1)

`release/ci_plan.py` gains `SKIP_TRAILER = re.compile(r"^[ \t]*skip-checks[ \t]*:[ \t]*true[ \t]*$", re.I | re.M)`, and `refusals`, where it reads the skip words (a pull request into `dev` whose title and description it has), also searches the title and the description, each with `\r\n` and `\r` turned into `\n` first, and refuses a match: "the pull request's title or description holds a line skip-checks: true: it would end the squash merge's message, and GitHub would skip the run that judges and accepts the merge; quote it another way". Reason for the pattern: it is the review's, with spaces or tabs allowed around each part and any case, so both spellings and their near variants are refused, and a line ending with a carriage return, as a description edited in a browser often has, cannot slip past `$`. It matches a whole line only, as a trailer is a line; a sentence that mentions the trailer, or `skip-checks: false`, is not refused. The release pull request into `main` is not read for it, as it is not for the skip words: `main` moves by a fast-forward, never by a message built from the description.

### 3. A path git would quote is read by its name (L4)

`release/ci_plan.py` gains one reader, `git_paths(repo: Path, subcommand: str, *rest: str) -> list[str]`, that runs `git -c core.quotePath=false -C <repo> <subcommand> -z <rest>`, with `-z` right after the subcommand so a `--` in the rest can never make it a pathspec, reads bytes (`capture_output=True`, no `text=True`), decodes them with `.decode("utf-8", "surrogateescape")`, so a name reads the same on every host and a name that is not UTF-8 still classifies by its prefix, and splits on NUL, dropping the empty last field. Every list of paths the plan reads from git goes through it: `_diff(a, b, repo=REPO)` (`diff --name-only --no-renames`), `read_pull_request`'s per-commit list (`diff-tree --no-commit-id --name-only -r --no-renames`), and a new `status_pairs(base, head, repo=REPO) -> list[tuple[str, str]]` (`diff --name-status --no-renames`, whose NUL-split output alternates status and path) in place of the split by tab at `:890-891`. Reason for `-z` as well as `core.quotePath=false`: `quotePath=false` stops the escape of bytes above `0x7f` only, and git still quotes a path holding a double quote, a backslash, a tab or a newline unless `-z` is given; with `-z` no path is ever quoted. The `--files` option of the command line keeps reading one path a line: it is a person's input for a local run, never git's. `tests/harness/accept_from.py:390`'s list of news files changed since an acceptance is left as it is: it keeps a name only when `news.NAME` matches it, whose grammar is lowercase ASCII, so a quoted name can never be a news file there.

### 4. An edited pull request is judged again (L5)

`release.yml`'s `pull_request` trigger reads `types: [opened, synchronize, reopened, labeled, edited]`, with a comment beside it that an edit is judged again: a new base runs the selection again (a pull request retargeted to `main` runs the release shape), and a new title or description is read anew (the skip words, the trailer of Decision 2, the `Author:` line and the review check). An edit that leaves the base alone re-uses the run before it, through the mechanism 138's Decision 2 gives a documentation-only push onto a green head (`find_reusable`, `release/ci_plan.py:646-678`): every output false, nothing judged, the refusals read anew from the edited title and description and the pull request's commits, and the run re-used named in the summary's "Why". The run before it is the newest run of this pull request's branch other than this one (`GITHUB_RUN_ID`), read from the one list of runs the plan already makes (`green_runs`), and it is re-used only when it is completed, on this head, and every job of it but `ci-status` succeeded or was skipped (`run_jobs`, one `gh run view`); otherwise, and always on a base change, the edit runs the plan's selection anew, as a push does. `green_runs` reads `gh api repos/$GITHUB_REPOSITORY/actions/workflows/release.yml/runs?branch=<head_ref>&event=pull_request&per_page=20` in place of `gh run list` and keeps only the runs whose `head_repository.full_name` is `$GITHUB_REPOSITORY`, each as the `databaseId`, `headSha`, `status` and `conclusion` `find_reusable` already reads (a pure `runs_of(payload, repository)` does the keeping, so a row can hold it). Reason: `gh run list` filters by branch name and event alone, so a fork's branch of the same name at the same head could lend a quiet green run to a re-use; the run's head repository is the one field that tells them apart. The workflow's own endpoint is read rather than the repository's, `actions/runs`, since the docs workflow also runs on every pull request and would crowd the twenty; `find_reusable`, for a documentation-only push, reads the same list and gains the same guard. The plan learns of the edit from two new variables on its step, `PLAN_ACTION: ${{ github.event.action }}` and `PLAN_OLD_BASE: ${{ github.event.changes.base.ref.from }}`, which is empty unless the base changed; `Event` gains `edited`, true when the action is `edited` and `PLAN_OLD_BASE` is empty; a new `reusable_after_edit(head, runs, this_run, jobs_of) -> tuple[int | None, str]` holds the rule; and `from_runner` calls it, on such an event, before `find_reusable`. Reasons. Re-using only the newest earlier run, never an older green one, is what keeps a base change honest: a retarget starts a run of its own, so the run before a later edit is the retarget's, and if that edit cancelled it (the concurrency group cancels a pull request's run in progress, `release.yml:55-57`), the cancelled run is not re-used and the edit runs the release shape whole; an older green run into `dev` is never lent to it. A run that was itself a re-use may be re-used, since its jobs succeeded or were skipped and no base change came between (a base change starts a newer run). `ci-status` on the head is the newest run's, and here it is computed from this run's own refusals over jobs it skips, never from an earlier `ci-status`, so an edit that adds a skip word turns it red. The selection depends on the head, the base, the labels and the commits' lines; a label starts a run of its own (`labeled`), so an edit that leaves the base alone would choose what the run before it chose. The cost, accepted: an edit after a red, cancelled or unfinished run runs the selection again, and an edit during a run cancels it. The self-check's boxes are ticked after the first run, so the template's Windows box and the contributing page say to read the newest run on the head and to tick every box in one edit (Decision 8). The tag run's three jobs were read at 0.1.1 (*The problem*, 4), so the review's second fix is done and is recorded here; the `pypi` job in its new form (Decision 6) is read first at the 0.1.2 tag (Decision 7).

### 5. The release token is set on `gh release create` alone (L6, 0.1.0's L5a)

`publish`'s one step becomes two. "Write the release notes" runs `version="${GITHUB_REF_NAME#v}"` and the `uv run --no-project python release/version.py notes "$version" --repository "$GITHUB_REPOSITORY" > notes.md` line, with no `env:`. "Create the release" alone sets `GH_TOKEN: ${{ github.token }}`, and runs `version="${GITHUB_REF_NAME#v}"`, the `prerelease` case and the `gh release create` command exactly as today. The two steps share a runner, so this keeps the token out of the environment that `uv`, Python and `version.py` see, which closes an accidental read (a process that prints or forwards its environment); it does not wall the token off from a hostile earlier step, which the job bounds by running only the tagged commit's reviewed code under the pinned uv, as it does today. A rule holds it (Decision 9, rule 19), for every job that can write, not for `publish` alone: in a job whose `permissions:` grant any `write` (or `write-all`), no job-level `env:` names `github.token` or `secrets.`; a step whose `env:` names `github.token` or any `secrets.` value (`secrets.GITHUB_TOKEN` is the same token) runs `gh` and no `uv`, `uvx`, `python`, `pip` or path under `release/`, each matched as a command word (`\b(uvx?|python[0-9.]*|pip[0-9.]*)\b`, and `release/` only at the start of a word, so `release-assets/` and `release.yml` are not it); and in `publish` exactly one step names the token, and its script runs `gh release create`. Today `attest`'s verify step and `weekly-issue`'s step already meet it; `publish` does not.

### 6. PyPI is published by the pinned uv (L6, 0.1.0's L5b)

`pypi`'s last step, `pypa/gh-action-pypi-publish`, is replaced, and the job reads, its `if:`, `needs:`, `environment: pypi` and `permissions:` (`contents: read`, `id-token: write`) unchanged:

```yaml
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
          sparse-checkout: .github/actions
          persist-credentials: false
      - uses: astral-sh/setup-uv@1c37ad07a6a961277cf70c0d37d6f313000f5884 # v10.3.0
        with:
          version: ${{ env.UV_VERSION }}
          enable-cache: false
      - name: The build's files
        uses: ./.github/actions/verify-artifact
        with:
          assets-id: ${{ needs.build.outputs.assets-id }}
          sums-sha256: ${{ needs.build.outputs.sums-sha256 }}
      - name: Only the wheel goes to PyPI
        run: mkdir dist && mv release-assets/*.whl dist/
      - name: Upload the wheel through trusted publishing
        run: uv publish --no-config --trusted-publishing always dist/*.whl
```

What uv's own text in the repository establishes, and what it does not. READ, the clone's `PublishArgs` (`crates/uv-cli/src/lib.rs:7504-7511`): `--trusted-publishing` "configure[s] trusted publishing", uv "checks for trusted publishing when running in a supported environment", and "uv's supported environments for trusted publishing include GitHub Actions"; `crates/uv-static/src/env_vars.rs:1116-1121`: `GITHUB_ACTIONS` "indicates that the current process is running in GitHub Actions" and "`uv publish` may attempt trusted publishing flows when set to `true`", added in 0.4.16, as are `UV_PUBLISH_URL` and `UV_PUBLISH_TOKEN` (`:351-356`), so the pinned 0.9.22 has the command and the flow; with no URL given, the upload goes to "PyPI's publish URL" (`lib.rs:7527`). EXECUTED with the local uv 0.13.6, `uv publish --help`: `--trusted-publishing` takes `automatic`, `always` or `never`; `always` is the value that makes the flow required rather than tried, so a missing token fails the step instead of falling back to a password prompt (INFERRED from the three values and the flag's text; the enum's own documentation, in `crates/uv-configuration`, is outside the sparse clone). Not in the repository: the exchange's code, `crates/uv-publish`, which the clone does not check out and which is not fetched here, since the clone is read-only prior art. What the exchange needs from the job is set by GitHub, not by the client: `id-token: write` is the only way a step gets an OIDC token, and the token's claims (repository, workflow file, environment) come from the job's repository, file and `environment:` key, which are the ones PyPI's publisher accepted at 0.1.1's fifth attempt (READ, *The problem*, 4). So the client changes and the claims do not. Reason for `--no-config`: the sparse checkout still holds the root `pyproject.toml`, and with the flag uv reads no project or user configuration (`UV_NO_CONFIG`, `env_vars.rs:203-207`, since 0.2.30; `crates/uv/src/lib.rs:322-323`), so where the one job holding `id-token` uploads, and with what, comes from its command line and the runner's own variables, since the job sets none (rule 20). The order of `setup-uv` before the build's files is deliberate: no byte arrives after the files are checked, as rule 16 asks of a job that holds them.

One consequence, decided here. The action made a PEP 740 attestation for each file it uploaded, and PyPI showed it as the file's provenance (READ, the whole-surface review read a7's provenance and its publisher binding, `:80`; INFERRED for 0.1.1, the same action at v1.14.2 with its default on). `uv publish` uploads an attestation it finds beside a file but makes none (READ, `lib.rs:7435-7436`, "selects only wheels and source distributions and their attestations", and `:7559-7560`, "uv attempts to upload matching PEP 740 attestations"; the upload of attestations was added in 0.9.12, `env_vars.rs:378-381`). So from 0.1.2 the wheel on PyPI carries no PyPI-side provenance object. The project's proof of origin is unchanged: the GitHub attestation the `attest` job signs over the same wheel bytes, which `docs/how-to/verify-a-download.md` documents and no page claims PyPI's provenance for. Reason: making a PEP 740 attestation needs a second signing tool in the one job that holds `id-token`, which is the very surface this finding removes. This is decided; the owner may reverse it at the pre-build review, and the Scope names what reversing it would add.

A rule holds the job (Decision 9, rule 20): in `pypi`, every `uses:` is `actions/checkout@<40 hex>`, `astral-sh/setup-uv@<40 hex>` with `version: ${{ env.UV_VERSION }}` and `enable-cache: false`, or the local action; no job of the workflow has a `container:` or `services:` key; exactly one step runs `uv publish`, its command carries `--no-config` and `--trusted-publishing always`, names files under `dist/` alone, and carries no `--token`, `--username`, `--password`, `--publish-url`, `--index` or `--check-url`; and `pypi` has no `env:`, at the job or on any step, and no `run:` of `pypi` writes `$GITHUB_ENV` or `$GITHUB_PATH`; the workflow's top-level `env:` is already held to the five names `release/set_key.py`'s `ENV` lists. ### 7. How the new `pypi` job is exercised before the 0.1.2 tag: it is not, and the tag is its first run

The 0.1.2 tag's run is the first run of `pypi` in its new form, with the owner's PyPI publisher unchanged: it binds the repository `ClayGendron/wasi-python`, the workflow `release.yml` and the environment `pypi`, and this specification changes none of the three. No earlier exercise is added, for three reasons. The exchange can only succeed where the publisher's claims hold, in the `pypi` environment, whose deployment policy admits tags; a dispatch, or a branch or pull request job given `id-token`, to rehearse it would reopen the whole-surface review's S1, a dry run that can publish, which rule 18 (`pypi` runs only on a pushed tag with `PYPI_PUBLISH`) and the attestation scan's ban on `id-token` elsewhere (`scan.py:648-652`) close. `uv publish --dry-run` "will not upload any files" (`lib.rs:7550-7555`), and nothing in the repository says it performs the exchange, so a dry run would show that the command parses and nothing about the token. One rehearsal holds no token, and the builder runs it as a step of the build, before the pull request is opened: `uv publish --dry-run --no-config --trusted-publishing always <wheel>` with uv 0.9.22 (`uv tool run --from uv==0.9.22 uv …`, a tool run from uv's cache), outside GitHub Actions, on the 0.1.1 wheel taken from its GitHub release and checked against that release's `SHA256SUMS`; its output goes into the landing notes, labelled EXECUTED. Either uv refuses because trusted publishing cannot run there, which shows `always` fails closed instead of asking for a password, or the dry run checks the one wheel without a token; either way the pinned uv parses the step's command and selects the file. And a failure there is one of availability, not integrity: `pypi` needs `publish`, so the GitHub release, its attestation and its `SHA256SUMS` are out before it runs, as at 0.1.1. What the tag run settles is read first, before anything else in it: the `pypi` job's log (the trusted-publishing exchange, the upload of the one wheel) and PyPI's digest of the wheel against the release's `SHA256SUMS`, recorded in this specification's landing notes. If the job fails at the 0.1.2 tag on PyPI's side (a publisher setting), the owner fixes the setting and the failed job is re-run, as at 0.1.1. If it fails in its own step, a re-run cannot help, since the tag's run reads the tagged commit's workflow: the fix lands as a pull request into `dev`, and the wheel reaches PyPI with the next patch release, tagged once the fix is merged. That tag is the owner's to push or to delegate: the delegation of 2026-10-27 covers 0.1.2 alone (`../decisions.md`), and constitution §7 forbids an upload to PyPI without the owner's instruction. The wheel is never uploaded by hand, which would need a long-lived PyPI token, the thing trusted publishing exists to avoid.

## Intent

After this specification, a change to the files an agent's tool loads by itself is reviewed like code while running only what it needs; no pull request can merge with a message that stops `dev`'s post-merge run, in either of GitHub's two forms; the plan reads every path by its real name; a pull request retargeted is judged again in its new shape, and one re-described has its description read again at the cost of the plan alone when the run before it is green; the release token is in no environment but the step that creates the release; and the one job that holds PyPI's `id-token` runs a uv named by an exact version instead of a container named by a tag. The reviewer is told that a change to the workflow or the plan is code whatever it claims to be, `SECURITY.md` accounts for every wasmtime advisory up to the pinned engine, and the install page no longer promises more than the umask allows.
