## The problem

The judge is good and the process runs it far too often, in the wrong places, and makes its colour mean nothing (READ, the memo §1 and §2; every number EXECUTED there).

- The release workflow ran 177 times in seven days; 53% failed; in the sampled failures most spec-branch reds were by design: growth lines, or the gather's G7, which is red on every branch by construction because a branch's set is never the accepted one.
- Every dispatch compiles the artifact set three or four times and runs every judge leg with no path filter. A change to `context/` alone costs 52 jobs and 36 minutes on a branch, 281 jobs and 80 minutes on `main`.
- The workflow has no `pull_request` trigger. The only way to test a change is to dispatch the whole release pipeline by hand.
- One specification costs about 2.7 branch runs, two to five review files with confirmation rounds, a share of a wave's integration review and dry run, a local full judge by the lane, and 15 to 30 commits, 64% of all commits since 2026-10-16 touching only `context/` and docs.
- Only the lane accepts, locally, in the main tree, on a detached HEAD, after a full judge. That is the structural reason no pull request can merge on its own; waves, `build/lane.lock` and the integration review exist to amortise that step.
- The fast tier doubled to about nine minutes at six cores; `AGENTS.md` says four. `--accept-judge` was given on 96 of 97 landings. The documented `uv run pytest --tier release` fails to parse. A writing rule turned a research branch's fast tier red.

What has earned its keep and stays (READ, the two earlier memos; EXECUTED, the run history): Windows on every code change (14 of 24 real red runs were Windows alone); one full three-system run at one integration point (three wave dry runs caught what branches missed); the ratchet that counts passes by name and refuses a lost pass; fuel as a deterministic operation count; pinned inputs and the zero-patch rule; a fresh reader for every change; same-bytes and the attestation at a release; the release tier whole before a tag; set reuse by the hash of the build inputs.

## Decisions

### 1. The branches

- **`main`** holds released states only and carries the `v*` tags, made by the owner. It moves only when the owner fast-forwards it to the release acceptance commit (Decision 6). Its ruleset `25363090` today targets `~DEFAULT_BRANCH` with the rules `deletion`, `non_fast_forward` and `update`, no `pull_request` and no `required_linear_history` rule, and one bypass actor, the admin role (`RepositoryRole` 5) in `bypass_mode: always` (EXECUTED, the review's `gh api` read). Before `dev` becomes the default, it is retargeted to `refs/heads/main` (`include: ["refs/heads/main"]`), keeps `deletion`, `non_fast_forward` and `update`, and gains `required_linear_history` and the required check `ci-status`, so moving the default neither unprotects `main` nor puts the `update` rule on `dev`. Its admin bypass stays in `bypass_mode: always`, not `pull_request`: GitHub has no fast-forward merge for a pull request, so in `pull_request` mode no one could put on `main` the commit its release pull request judged. That bypass has one use, the owner's push of Decision 6; `AGENTS.md` and §7 forbid an agent to push `main`. The tag ruleset `25363091` is unchanged.
- **`dev`** was made from `main`'s tip (`e0b89c9c`) and becomes the repository's default and integration branch. Its own new ruleset targets `refs/heads/dev`: `deletion`; `non_fast_forward`; `pull_request` with zero required approving reviews and squash the only allowed merge method; `required_linear_history`; `required_status_checks`, strict (up to date before merging), with `ci-status` and the docs workflow's `build the site strictly`. It has no admin bypass. Its one bypass actor is the accept identity (Decision 4), for the push of an acceptance commit. GitHub never lets an author approve its own pull request, and every agent acts through the owner's account, the repository's one collaborator (EXECUTED, the review), so the one-review rule is held by `ci-status` itself (Decision 9). Squash merge: one pull request, one commit on `dev`, its message the pull request's title and body; the owner may switch to rebase merge later without a specification. A branch is brought up to date by rebase (`gh pr update-branch --rebase`), never by a merge commit: the head is what the judge reads (Decision 3), and `test_main_is_linear` refuses a merge commit reachable from it.
- **Topic branches** branch from `dev`, carry one to three specifications, and are deleted at merge (`delete_branch_on_merge` on). Their names are free; `spec/NNN-slug` stays the convention. A worktree is the builder's convenience, not a rule.
- **No `wave/*` branches, no lane, no `build/lane.lock`.** `handoff.md` keeps state between sessions as it does now.

### 2. One decision job picks the run

A script, `release/ci_plan.py`, with unit tests in `tests/unit/test_ci_plan.py`, reads the pull request's changed files (`git diff --name-only <merge-base>...<head>`; on a push, from the previous tip) and writes GitHub outputs. It is the project's own code: no third-party changed-files action (the `tj-actions/changed-files` compromise of 2025 is why numpy's release repository forbids one).

| output | true when |
|---|---|
| `set` | a changed path is `downloads/SHA256SUMS`, under `scripts/` or `recipes/`, `release/set_key.py`, `release/build-constraints.txt` or `tests/harness/constructors*`, or any change that moves the key: the decision job runs `set_key.py key` at the head and at the merge base with the workflow's env and sets `set` when they differ, so the `ENV` values in `release.yml` and `set-cache.yml` count too |
| `runner` | `src/**`, `pyproject.toml`, `uv.lock` |
| `harness` | `tests/harness/**`, `tests/conftest.py`, `tests/release_shards.toml`, `tests/known_gaps.toml`, and the judge's data outside `tests/`: `context/embedders.txt`, `context/release-tier-claims.toml`, `context/upstream/**`, `.gitattributes` |
| `upstream` | `tests/upstream/**`, `tests/checks/test_v1_3_upstream_suites.py` |
| `workflow` | `.github/**`, `release/**`; it runs as `full` |
| `progress` | `context/progress/accepted.json` or a history volume (`context/progress/history*.jsonl`), the files the accept job writes; any other file there, its README, is a document; `ci-status` fails a pull request that sets it: only the accept job writes accepted state (amended 2026-10-25, step 2's review, Medium 1) |
| `news` | a news file (`context/changes/*.md`, Decision 7) is among the changed paths |
| `docs_only` | every changed path is under `docs/` or `.claude/`, or under `context/` and in no row above, or is `README.md`, `CHANGELOG.md`, `AGENTS.md`, `SECURITY.md`, `LICENSE*`, `mkdocs.yml`, `.gitignore` |
| `full` | the pull request carries the label `ci:full`, or a commit in it has a line `citest:full`, or the event is a push to `dev` |

A path under `tests/` in no row above (`tests/unit/`, `tests/checks/`, `tests/jobs/`, `tests/public_api.txt`, `tests/lint/`) or under `fixtures/` sets no output of its own: it is not `docs_only`, so the own shards run (Decision 3). A unit row holds that every tracked path maps to an output or to `docs_only`. Two pushes set every output false: a push to `dev` whose changed paths are exactly `context/progress/accepted.json` and the newest history volume (the acceptance commit, Decision 4), and a push to a pull request that adds only `docs_only` paths onto a head whose run was green (the review file, Decision 9): the decision job finds that run with `gh run list` (with `actions: read`), checks that `git diff --name-only` from its head to this one is all `docs_only`, and names it in the job summary.

The job runs on `ubuntu-24.04` in under a minute. Every later job gates on these outputs with `if:`, never with a workflow-level `paths:` filter, so a skipped job reports success and the required check is always reported.

### 3. What a pull request runs

Two stages, the second gated on the first, superseded runs cancelled (`concurrency: pr-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`). Every job of a pull request's run checks out `github.event.pull_request.head.sha`, never `refs/pull/N/merge`: the merge ref is a merge commit nobody will merge and `test_main_is_linear` refuses, and the up-to-date rule makes the head contain `dev`'s tip, so the head's tree is the tree the squash puts on `dev`.

**`quick`** (ubuntu-24.04, always): `ruff check`, `ruff format --check`, `mypy`, the pure-Python unit tests (everything under `tests/unit` and `tests/checks` that needs no artifact: the harness's own tests, the build-tooling tests, the public-API rows), and **`lint`**, the writing-convention rules of Decision 8. About 5 to 8 minutes (INFERRED from own-rest's 4m42s on Linux).

**`judge`**, from the cached set (the pull request's own cache scope (`refs/pull/N/merge`), else `dev`'s; on a miss with `set` true, one compile on `ubuntu-24.04-arm`, saved to the pull request's scope, about 20 minutes; on a miss with `set` false, the same one compile as for `set` true, with a line saying `dev`'s cache did not hold the key):

| shards | when | systems |
|---|---|---|
| own-runner, own-embedding, own-guest, own-hostile, own-rest (the normal tier's product checks) | unless `docs_only` | Linux and Windows always; macOS when `runner`, `set`, `harness` or `full` |
| the upstream normal-tier groups | when `set`, `upstream`, `harness` or `full` | Linux |
| `verify` (install the wheel fresh, run pandas and the CLI) | unless `docs_only` | Linux; three systems when `full` |
| `build-shard`, the two rebuilds, `same-bytes`, the release tier, the macOS publish build, the assets | never on a pull request into `dev` | — |

A `docs_only` pull request runs `quick` alone and `ci-status` passes on it. `full` runs the merge-grade set of Decision 4 on the pull request.

**The verdict on a pull request** is the gather's, narrowed to what the plan ran, and the record says so (`meta.event: pull_request`; `meta.selected`, the (system, shard) pairs that ran). The decision job writes the pairs as an output, computed by `ci_plan.py` from the shard plan and its outputs, and the gather reads them as `PLAN` in its env. On a pull request `expected_keys(plan, tier, selected)` returns exactly the selected pairs, never `build`. G1 expects one record for each and no other file. G2 compares `artifact` and `set_sums` with the `wasm-sha256` and `set-sums-sha256` the set step hands on after `set_key.py verify` of the restored set, in place of the build job's. G3 holds each selected shard to its share, and evaluates "collected, run in no record" over the goal checks of the selected shards only. G4 is unchanged. G5's lost-pass and absent rows are red; its "ran in no record" is evaluated over the accepted checks of the selected shards only; the rows an acceptance needs a reason for (growth, fewer passes, a tier move) are listed under a `GROWTH` heading, each with the reason its news file gives (Decision 7) or the word `unclaimed`, and are not red. G6 requires the probe to pass on every system among the selected pairs. **G7 is not evaluated.** On every other event `PLAN` is absent and G1 to G6 are whole. A unit row in `tests/unit/test_gather.py` holds that a pull-request gather with macOS and the upstream groups unselected is green, and that the same records without `PLAN` are red. The gather's summary is posted as the job summary, so a reviewer reads it without opening logs.

**`ci-status`** is one job with `if: always()` that passes when every job in `needs` is `success` or `skipped` and the decision job's own refusals are empty (`progress`, a missing news file, a missing review file: Decisions 2, 7 and 9), as Wasmtime's aggregate does. The job is `ci-status:` with `name: ci-status`, and the ruleset's required check names it with the GitHub Actions app's `integration_id`, so no other app's status can satisfy it; `docs.yml`'s check is required beside it.

### 4. What a merge to `dev` runs, and the accept jobs

A push to `dev` (the squash merge) runs, from `dev`'s cached set (`set-cache.yml` builds and saves it first when the key misses, once, on `ubuntu-24.04-arm`; the judge waits on it):

- the full normal tier on three systems: every own-* shard on macOS, Linux and Windows, every upstream normal-tier group, `verify` on three systems, `build-shard` on arm64 Linux;
- the gather with G1 to G6 in full. G7 is not evaluated after a merge either: this run is the one that makes the acceptance G7 would compare with, so its artifact clause is true by construction. G7 holds at the release pull request and at the tag (Decision 6);
- **`accept-record`**, gated on a green gather, with `contents: read`, no secret and no environment: in a fresh checkout of the judged commit, `uv run pytest --accept-from build/ci/record.json --claims context/changes/` (Decision 5) writes `context/progress/accepted.json` and the newest history volume, and the job uploads the two files as one artifact;
- **`accept-push`**, after it, in the `accept` environment, whose deployment branch policy is `dev` alone, so no pull request's run can reach its secret. It downloads the two files into a checkout of the judged commit made with the accept identity, runs no script or module of the repository (inline `git` steps only), checks that `git status --porcelain` names exactly those two files, and checks that `dev`'s tip (`git ls-remote origin refs/heads/dev`) is still the judged commit. Then it commits, the message `Accepted: <pull request title> (#<n>) [skip ci]` with the reasons the news files gave, and pushes. When `dev`'s tip is not the judged commit, it pushes nothing, writes one line naming the newer merge, and succeeds: the newer merge's run accepts everything since the last acceptance (Decision 5). `[skip ci]` keeps GitHub from starting a run for the acceptance commit; the decision job's rule (Decision 2) is the second guard, so an acceptance never starts another.

The accept identity is a deploy key with write access held as a secret in the `accept` environment, the bypass actor of `dev`'s ruleset, so its push passes the pull-request rule; the owner creates it or authorises the agent to. A `DeployKey` bypass covers every deploy key of the repository (INFERRED, read back with `gh api` at the build), so the repository holds this one deploy key with write access and no other.

A red post-merge run means `dev` is broken. The rule, written into `AGENTS.md`: no new merge to `dev` while its last post-merge run is red, except the fix or a revert; the author of the merged change fixes forward the same day or reverts. The accept jobs never run on a red gather, so `accepted.json` never records a red state. Amended 2026-10-25 (step 2's review, Medium 2): a pull request lists its growth, fewer passes and tier moves under `GROWTH`, but step 2's post-merge gather holds G1 to G6 whole, so the same rows are red after the merge. Until step 3, a red post-merge run whose only red rows are those its local acceptance recorded: a growth (`--accept-growth`), fewer passes (`--accept-fewer-passes`), a tier move (`--accept-tier-move`), an absent check (`--retire`), or an upstream pass count that rose, does not count as `dev` broken and blocks no merge; the local acceptance's commit carries `[skip ci]`, so no run turns `dev` green again before the next merge's run, which compares with that acceptance. Step 3 makes the post-merge gather read the news files' claims, so those rows list under `GROWTH` after the merge as they did on the pull request, and `--accept-from` refuses an unclaimed one (Decision 5).

**What a cached set is trusted for.** A cached set is judged on pull requests and on `dev` without a rebuild, and the acceptance is written from it. It is rebuilt from the pins and compared byte for byte at the weekly run, at the release pull request and at the tag, so a stale set or a planted cache entry is caught before any release and never published. This replaces the per-run rebuild that `release/set_key.py`'s docstring and the 0.1.0 security audit's h10 note (`../reviews/0.1.0-security-audit-2026-10-25.md`) rest on ("a planted entry would end red today"); the docstring is changed to say this, and `test_the_release_reuses_a_set_only_on_a_branch` and the reuse decision admit a pull request into `dev` and a push to `dev` and refuse a pull request into `main`, a run on `main` and a tag.

A scheduled run on `dev`, weekly (`schedule: cron "0 6 * * 1"`, dispatched on `dev` explicitly as Wasmtime's cron does), runs the release tier and the two rebuilds with `same-bytes`, compares the rebuilds' `SHA256SUMS` with `dev`'s cached set's by `cmp`, and opens or updates one issue when red. It never accepts. `workflow_dispatch` gains an input `weekly` that selects this shape, the job that opens the issue has `issues: write`, and a public repository's schedule is disabled after 60 days without activity, which a weekly push to `dev` prevents. The owner chose this against the standing rule that slow tests run only to publish (`../decisions.md`, 2026-10-25).

### 5. Acceptance from CI's record

The plugin gains `--accept-from <record.json>`: the record is a gather's merged record (spec 092's reader) from a run whose every job was green, for the commit checked out, from a push to `dev` or a release pull request (`meta.event`), with `meta.set_source` naming `dev`'s cache key or `built`. It applies the record's statuses and metrics as a local run's would. The record's platform key is the shard's `meta.platform`, never the accept job's host, so darwin fuel stays keyed `darwin-arm64` though the job runs on Linux. The `three systems` need (G6) is met by the record, as spec 092 arranged. Reasons come from the news files of the pull requests merged since the last acceptance (`--claims context/changes/`, Decision 7); an unclaimed row refuses the acceptance with the row named, the run is red, and the fix is a one-line news-file pull request whose merge re-runs the accept.

Each of today's refusals (`tests/harness/plugin.py`, `tests/harness/scoreboard.py`) and its form under `--accept-from`, each with a unit row in `tests/unit/test_accept_from.py`:

- **a linked worktree**: dropped for `--accept-from`, since CI's checkout is a fresh clone and the record, not the tree, carries what was judged; kept for the local `--accept`, its message no longer naming the lane.
- **a dirty tree**, before collection and at the write: kept; the checkout is clean at both.
- **HEAD moved during the run**: becomes "the record's `meta.commit` and every shard's are the checkout's HEAD".
- **no goal check collected**: kept; the job collects the judge at the commit and refuses an empty collection, or a record whose checks are not that collection.
- **`--shard`**: refused with `--accept-from`.
- **a run that is not green** (pytest's verdict, `PYTEST_ADDOPTS`, a foreign plugin): becomes "the gather's verdict has no red line, every record's `foreign` is empty and its only override is `--progress-latest`".
- **a lost pass**: refused; no claim clears it.
- **an absent check not retired**: cleared by the claim block's `retired` list; a `retired` name that is not absent refuses, as `--retire` does.
- **blocked accepted passes, or accepted upstream rows unrun** (today's `--partial`): always refused for CI's record, since a merge-grade run that blocks an accepted pass is a broken run; no claim key clears it.
- **growth**: cleared by `grows` with its `growth` reason.
- **pass counts fell**: cleared by `passes` with its reason.
- **a verdict-bearing judge file changed** (Decision 8): cleared by `judge`.
- **a check moved between tiers**: cleared by the new `moved` key.
- **a history that does not replay**, or breaks its chain or its volume rule: refused.

The local `--accept` stays, unchanged but for the worktree message, for a machine that must accept without CI; it is not part of the normal flow and `AGENTS.md` says so.

This is the choice the owner deferred on 2026-10-22 ("not yet, after three G5-clean waves"); three full runs since 2026-10-22 were green, so G5-clean: the main dry runs `39790261668` and `39943021050` and the tag run `39957192055` (EXECUTED, `gh run list`); wave 12 had no wave run and wave 13's `39891594258` was red on an absent check. The owner agreed on 2026-10-25.

### 6. A release is a pull request from `dev` to `main`

The pull request's title is the version; its branch is `dev` itself (or a `release/<version>` branch cut from `dev` when fixes must not wait for `dev`). Its jobs check out `github.event.pull_request.head.sha`. `gather.py`'s release run (`is_release_run`) is a tag, a run on `main`, or a `pull_request` whose base is `main` (`GITHUB_EVENT_NAME` is `pull_request` and `GITHUB_BASE_REF` is `main`, both set by the runner), so G1 requires the release tier on it, and the reuse decision refuses it a cached set, so it builds its own. Its check is today's whole workflow: the macOS `build`, both rebuilds, `build-shard`, `same-bytes`, every normal-tier shard on three systems, the release tier (229 legs), `verify` on three systems, `quick`, and the gather with every goal.

The release pull request's G7 requires the newest acceptance to be on its set (`artifact` and `set_sums` equal to its own build's), clean and not partial, and does not require the release tier. When its run is green, the accept jobs accept its release-tier record onto `dev` as one acceptance commit (context only, as today's rule 6b allows after a dry run), and the owner moves `main` by `git push origin <that commit>:main`, a fast-forward the `update` rule's admin bypass allows, after which GitHub marks the pull request merged. The tag's run requires the release tier in the newest acceptance, as G7 does today. `dev` takes no merge while its release pull request runs (`AGENTS.md` says so); if one lands, `accept-push` pushes nothing and the release pull request runs again on the new tip.

The security review and the structural review (constitution §5.6) are its review, written under `../reviews/` as today and merged into `dev` by their own `docs_only` pull request before the release pull request opens, so its head carries them; the owner's push to `main` is the release's approval. The owner tags; the tag's run is today's tag run (build, judge both tiers, attest, publish, PyPI) and gains `quick`. "Tag only what a dry run passed" holds by construction: the release pull request's run is the dry run on the exact commit, and the commit tagged is that commit plus one acceptance commit. The two local release acceptances of about 1.5 hours each go.

A later specification may let the tag's run promote the release pull request's built assets instead of rebuilding, as Wasmtime publishes what CI built; this one keeps the rebuild.

### 7. News files

`context/changes/NNN-<slug>.md`, one per specification (or per pull request when a pull request carries no specification), holding: the CHANGELOG line under its heading (`### Added`, `### Changed`, `### Fixed`, `### Security`, as the CHANGELOG uses), the README package rows the change adds or moves, and a `claims` TOML block in spec 092's shape (`new`, `retired`, `changed`, `passes`, `grows` with `growth`, `units`), with two new keys: `judge`, each verdict-bearing judge file changed with its reason, and `moved`, each check moved between tiers with its reason. `release/version.py bump` assembles the news files into `CHANGELOG.md` and the README rows at a release and deletes them. The decision job sets `news`, and `ci-status` fails a pull request that is not `docs_only` and carries no news file; a unit row holds it. The CHANGELOG's unreleased section is no longer edited by hand; the specification's "For the lane" section becomes one line naming its news file.

### 8. The judge's diet

- **`lint`.** Eight writing-convention rules leave `tests/checks/test_rules.py` and the goal count for `tests/lint/`: `test_specifications_have_their_header_and_sections`, `test_specifications_have_no_open_question`, `test_markdown_paragraphs_are_one_line_each`, `test_executed_memos_label_their_claims`, `test_readme_carries_the_codecov_badge`, `test_code_outside_src_names_no_context_document`, `test_no_string_names_a_context_document` and `test_src_names_no_context_document`. They run in `quick` as the `lint` step, which gates `ci-status` but is not a goal check and is not ratcheted. `quick` runs on every pull request, the release pull request into `main` included, and in the tag's run, so a writing rule broken on `dev` stops a release. Four rules that hold more than writing stay goal checks: `test_no_embedder_name_in_code` (constitution §4.5, a hard constraint), `test_a_release_has_its_structural_review` (the judge's refusal of a release without one), `test_landed_specifications_cite_an_existing_review` ("nothing lands unreviewed") and `test_built_structural_specifications_cite_their_pre_build_review` (the structural review the judge holds, `reviews/README.md`). The release and supply-chain rules, the code-shape rules and the judge-integrity rules stay too. Each moved check is absent at the next acceptance, so this specification's news file lists the eight under `retired`.
- **`--accept-judge`** is required only when a **verdict-bearing judge file** changed since the last acceptance: `tests/known_gaps.toml`, `tests/upstream/*.toml`, `tests/upstream/expected/**`, `tests/upstream/python/**`, `tests/release_shards.toml`, `tests/public_api.txt`, `context/release-tier-claims.toml`. Every other judge change is recorded by the judge-hash line in the history, unflagged. The list lives in `tests/harness/paths.py` beside `JUDGE_PATHS` and a rules check holds it.

### 9. Reviews

- **One review per pull request** that is not `docs_only`, by a fresh agent or a person who did not write the change, written under `../reviews/NNN-<slug>-pr-YYYY-MM-DD.md` in the build review's template (criteria against evidence, findings ranked, constitution checks, verdict). No confirmation round: the author answers in the pull request, a code fix is a new commit on the same pull request, and the reviewer reads it and signs again. The reviewer reads the pull request's run (`ci-status`, the gather's summary) and never dispatches one; a Low that touches only `context/` the reviewer may commit to the pull request's branch.
- **`ci-status` holds the review** (Decision 1). The decision job finds, among the pull request's changed paths, a file matching `context/reviews/NNN-<slug>-pr-YYYY-MM-DD.md` whose `NNN-<slug>` is one of the pull request's news files' names. It fails the pull request when there is none, when the newest commit that changed it is followed by a commit touching a path that is not `docs_only`, when its `Reviewer:` header line is empty or names the author, or when the first line of its `## Verdict` section does not begin with "Lands". The review file is committed to the pull request's branch as its last context-only commit, after the final code commit; `ci-status` runs `quick` on it and re-uses the green run of the head it follows (Decision 2), and the merge follows.
- **"Not the author"**: every agent commits through the owner's GitHub account, so the author is read from words, not accounts. The `Reviewer:` line names the reviewer's session (`https://claude.ai/code/session_…`) or a person; the pull request's self-check (its template, below) names the author's session or name, and so does each code commit's `Claude-Session:` trailer. The review fails when the `Reviewer:` line equals the self-check's author or any trailer on the pull request's code commits. A reviewer that runs as a sub-agent of the author's session, given only the specification and the diff, names itself so (`an agent (Claude), a fresh sub-agent of <session>; not the author`); the check refuses a `Reviewer:` line that is the author's session URL alone (the first pull-request review, `../reviews/138-pull-requests-into-dev-and-the-judge-runs-where-it-is-needed-pr-2026-10-25.md`, Low 6). This is a process guard, not an identity guard: an agent that writes a false `Reviewer:` line defeats it, as a false review file would today. What it holds is that nothing merges without a review file a session other than the author's signed, after the last code. A second identity, a reviewer GitHub App whose approval the ruleset requires, is a later choice for the owner.
- The pre-build review stays for the classes §5.6 names (the guest's imports or exports, the artifact set, the build recipe) and for structural specifications, as a review of the specification before the branch has code; a parallel-safe runner change no longer needs one unless its Kind line says structural, since its pull request review reads the code with the specification (the owner's "review follows risk", 2026-10-19, kept).
- The security review and the structural review stay per release (Decision 6).
- The integration review, the wave's review, the lane's addendum and the self-check list go; the self-check's substance (the author named, checks seen failing first, Windows read, every gap names its closer, a news file present) becomes the pull request template under `.github/PULL_REQUEST_TEMPLATE.md`.

## Intent

After this specification, a change is a pull request into `dev` that runs what its paths need, in minutes, on Linux and Windows from a cached set, and merges when its check is green and a fresh reader's review file says it lands; every merge is judged once in full on three systems and accepted by a job, so `context/progress/` is written by CI, not by a person on a laptop; a release is a pull request from `dev` to `main` whose check is the whole workflow, both tiers, the rebuilds and the attestation's goals, and whose acceptance is the commit the owner puts on `main` and tags. The judge keeps every check and every ratchet; what changes is where and how often it runs, and that its colour means something: red is broken, on a pull request as on `dev`.
