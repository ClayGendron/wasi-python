## The problem

The judge is good and the process runs it far too often, in the wrong places, and makes its colour mean nothing (READ, the memo §1 and §2; every number EXECUTED there).

- The release workflow ran 177 times in seven days; 53% failed; in the sampled failures most spec-branch reds were by design: growth lines, or the gather's G7, which is red on every branch by construction because a branch's set is never the accepted one.
- Every dispatch compiles the artifact set three or four times and runs every judge leg with no path filter. A change to `context/` alone costs 52 jobs and 36 minutes on a branch, 281 jobs and 80 minutes on `main`.
- The workflow has no `pull_request` trigger. The only way to test a change is to dispatch the whole release pipeline by hand.
- One specification costs about 2.7 branch runs, two to five review files with confirmation rounds, a share of a wave's integration review and dry run, a local full judge by the lane, and 15 to 30 commits, 64% of all commits since 2026-10-16 touching only `context/` and docs.
- Only the lane accepts, locally, in the main tree, on a detached HEAD, after a full judge. That is the structural reason no pull request can merge on its own; waves, `build/lane.lock` and the integration review exist to amortise that step.
- The fast tier doubled to about nine minutes at six cores; `AGENTS.md` says four. `--accept-judge` was given on 96 of 97 landings. The documented `uv run pytest --tier release` fails to parse. A writing rule turned a research branch's fast tier red.

What has earned its keep and stays (READ, the two earlier memos; EXECUTED, the run history): Windows on every code change (14 of 24 real red runs were Windows alone); one full three-system run at one integration point (three wave dry runs caught what branches missed); the ratchet that counts passes by name and refuses a lost pass; fuel as a deterministic operation count; pinned inputs and the zero-patch rule; a fresh reader for every change; same-bytes and the attestation at a release; the release tier whole before a tag; set reuse by the hash of the build inputs.

## Decisions

### 1. The branches

- **`main`** holds released states only and carries the `v*` tags, made by the owner. It moves only when the owner fast-forwards it to the release acceptance commit (Decision 6). Its ruleset `25363090` today targets `~DEFAULT_BRANCH` with the rules `deletion`, `non_fast_forward` and `update`, no `pull_request` and no `required_linear_history` rule, and one bypass actor, the admin role (`RepositoryRole` 5) in `bypass_mode: always` (EXECUTED, the review's `gh api` read). Before `dev` becomes the default, it is retargeted to `refs/heads/main` (`include: ["refs/heads/main"]`), keeps `deletion`, `non_fast_forward` and `update`, and gains `required_linear_history` and the required check `ci-status`, so moving the default neither unprotects `main` nor puts the `update` rule on `dev`. Its admin bypass stays in `bypass_mode: always`, not `pull_request`: GitHub has no fast-forward merge for a pull request, so in `pull_request` mode no one could put on `main` the commit its release pull request judged. That bypass has one use, the owner's push of Decision 6; `AGENTS.md` and §7 forbid an agent to push `main`. The tag ruleset `25363091` is unchanged.
- **`dev`** was made from `main`'s tip (`e0b89c9c`) and becomes the repository's default and integration branch. Its own new ruleset targets `refs/heads/dev`: `deletion`; `non_fast_forward`; `pull_request` with zero required approving reviews and squash the only allowed merge method; `required_linear_history`; `required_status_checks`, strict (up to date before merging), with `ci-status` and the docs workflow's `build the site strictly`. It has no admin bypass. Its one bypass actor is the accept identity (Decision 4), for the push of an acceptance commit. GitHub never lets an author approve its own pull request, and every agent acts through the owner's account, the repository's one collaborator (EXECUTED, the review), so the one-review rule is held by `ci-status` itself (Decision 9). Squash merge: one pull request, one commit on `dev`, its message the pull request's title and body; the owner may switch to rebase merge later without a specification. A branch is brought up to date by rebase (`gh pr update-branch --rebase`), never by a merge commit: the head is what the judge reads (Decision 3), and `test_main_is_linear` refuses a merge commit reachable from it.
- **Topic branches** branch from `dev`, carry one to three specifications, and are deleted at merge (`delete_branch_on_merge` on). Their names are free; `spec/NNN-slug` stays the convention. A worktree is the builder's convenience, not a rule.
- **No `wave/*` branches, no lane, no `build/lane.lock`.** `handoff.md` keeps state between sessions as it does now.

### 2. One decision job picks the run

A script, `release/ci_plan.py`, with unit tests in `tests/unit/test_ci_plan.py`, reads the pull request's changed files (`git diff --name-only <merge-base>...<head>`; on a push, from the previous tip) and writes GitHub outputs. It is the project's own code: no third-party changed-files action (the `tj-actions/changed-files` compromise of 2025 is why numpy's release repository forbids one).

| output | true when |
|---|---|
| `set` | a changed path is `downloads/SHA256SUMS`, under `scripts/` or `recipes/`, `release/set_key.py`, `release/build-constraints.txt` or `tests/harness/constructors*`, or any change that moves the key: the decision job runs `set_key.py key` at the head and at the merge base with the workflow's env and sets `set` when they differ, so the `ENV` values in `release.yml` and `set-cache.yml` count too |
| `runner` | `src/**`, `pyproject.toml`, `uv.lock` |
| `harness` | `tests/harness/**`, `tests/conftest.py`, `tests/release_shards.toml`, `tests/known_gaps.toml`, and the judge's data outside `tests/`: `context/embedders.txt`, `context/release-tier-claims.toml`, `context/upstream/**`, `.gitattributes` |
| `upstream` | `tests/upstream/**`, `tests/checks/test_v1_3_upstream_suites.py` |
| `workflow` | `.github/**`, `release/**`; it runs as `full` |
| `progress` | `context/progress/accepted.json` or a history volume (`context/progress/history*.jsonl`), the files the accept job writes; any other file there, its README, is a document; `ci-status` fails a pull request that sets it: only the accept job writes accepted state (amended 2026-10-25, step 2's review, Medium 1) |
| `news` | a news file (`context/changes/*.md`, Decision 7) is among the changed paths |
| `docs_only` | every changed path is under `docs/` or `.claude/`, or under `context/` and in no row above, or is `README.md`, `CHANGELOG.md`, `AGENTS.md`, `SECURITY.md`, `LICENSE*`, `mkdocs.yml`, `.gitignore` |
| `full` | the pull request carries the label `ci:full`, or a commit in it has a line `citest:full`, or the event is a push to `dev` |

A path under `tests/` in no row above (`tests/unit/`, `tests/checks/`, `tests/jobs/`, `tests/public_api.txt`, `tests/lint/`) or under `fixtures/` sets no output of its own: it is not `docs_only`, so the own shards run (Decision 3). A unit row holds that every tracked path maps to an output or to `docs_only`. Two pushes set every output false: a push to `dev` whose changed paths are exactly `context/progress/accepted.json` and the newest history volume (the acceptance commit, Decision 4), which sets one output of its own, `acceptance`, so that `quick` is skipped too and its run is `plan` and `ci-status` alone (amended 2026-10-25, Decision 4), and a push to a pull request that adds only `docs_only` paths onto a head whose run was green (the review file, Decision 9), or, on the release pull request, only its own acceptance pair (Decision 6): the decision job finds that run with `gh run list` (with `actions: read`), checks that `git diff --name-only` from its head to this one is all `docs_only`, and names it in the job summary.

The job runs on `ubuntu-24.04` in under a minute. Every later job gates on these outputs with `if:`, never with a workflow-level `paths:` filter, so a skipped job reports success and the required check is always reported.

### 3. What a pull request runs

Two stages, the second gated on the first, superseded runs cancelled (`concurrency: pr-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`). Every job of a pull request's run checks out `github.event.pull_request.head.sha`, never `refs/pull/N/merge`: the merge ref is a merge commit nobody will merge and `test_main_is_linear` refuses, and the up-to-date rule makes the head contain `dev`'s tip, so the head's tree is the tree the squash puts on `dev`.

**`quick`** (ubuntu-24.04, always): `ruff check`, `ruff format --check`, `mypy`, the pure-Python unit tests (everything under `tests/unit` and `tests/checks` that needs no artifact: the harness's own tests, the build-tooling tests, the public-API rows), and **`lint`**, the writing-convention rules of Decision 8. About 5 to 8 minutes (INFERRED from own-rest's 4m42s on Linux).

**`judge`**, from the cached set (the pull request's own cache scope (`refs/pull/N/merge`), else `dev`'s; on a miss with `set` true, one compile on `ubuntu-24.04-arm`, saved to the pull request's scope, about 20 minutes; on a miss with `set` false, the same one compile as for `set` true, with a line saying `dev`'s cache did not hold the key):

| shards | when | systems |
|---|---|---|
| own-runner, own-embedding, own-guest, own-hostile, own-rest (the normal tier's product checks) | unless `docs_only` | Linux and Windows always; macOS when `runner`, `set`, `harness` or `full` |
| the upstream normal-tier groups | when `set`, `upstream`, `harness` or `full` | Linux |
| `verify` (install the wheel fresh, run pandas and the CLI) | unless `docs_only` | Linux; three systems when `full` |
| `build-shard`, the two rebuilds, `same-bytes`, the release tier, the macOS publish build, the assets | never on a pull request into `dev` | — |

A `docs_only` pull request runs `quick` alone and `ci-status` passes on it. `full` runs the merge-grade set of Decision 4 on the pull request.

**The verdict on a pull request** is the gather's, narrowed to what the plan ran, and the record says so (`meta.event: pull_request`; `meta.selected`, the (system, shard) pairs that ran). The decision job writes the pairs as an output, computed by `ci_plan.py` from the shard plan and its outputs, and the gather reads them as `PLAN` in its env. On a pull request `expected_keys(plan, tier, selected)` returns exactly the selected pairs, never `build`. G1 expects one record for each and no other file. G2 compares `artifact` and `set_sums` with the `wasm-sha256` and `set-sums-sha256` the set step hands on after `set_key.py verify` of the restored set, in place of the build job's. G3 holds each selected shard to its share, and evaluates "collected, run in no record" over the goal checks of the selected shards only. G4 is unchanged. G5's lost-pass rows are red, and so are its absent rows that no news file's `retired` names; an absent row a news file retires is listed beside the `GROWTH` rows with that claim's reason, on a pull request and after a merge, and so is it in each shard's ratchet and the quick job's rules step, since `--accept-from` consumes the claim (amended 2026-10-25 at step 3's review: a removed check must reach its acceptance); after a merge into `dev`, a growth, a fall in `passes` or a tier move a news file's claim gives a reason for (`grows` with `growth`, `passes` with `fewer`, `moved`) is listed under `GROWTH` with that reason, as on the pull request, and so is it in each shard's ratchet and the quick job's rules step, while an unclaimed one is red there, named, since the accept job would have nothing to consume (amended 2026-10-25 at step 2's review, Medium 2: otherwise a red shard or gather stops `accept-record` before it can consume a claim); its "ran in no record" is evaluated over the accepted checks of the selected shards only; the rows an acceptance needs a reason for (growth, fewer passes, a tier move) are listed under a `GROWTH` heading, each with the reason its news file gives (Decision 7) or the word `unclaimed`, and are not red at the gather; one no news file explains is red, named, in the shard whose ratchet saw it, as after the merge (amended 2026-10-25 at step 3's review, Low 8: every run's ratchet reads the news files' claims, so a pull request that merged green with an unclaimed growth would turn `dev` red). Follow-up, for a later specification (step 3's review, Low 7): the ratchet's and the gather's claims should be the news files changed since the commit the newest history line judged, as `--accept-from`'s are (`news_since`; every judging job checks out with `fetch-depth: 0`), so a claim an earlier acceptance consumed no longer clears a later growth of the same check; until then such a pull request is green and its merge red at `accept-record`, named, and fixed forward by a one-line news-file pull request. G6 requires the probe to pass on every system among the selected pairs. **G7 is not evaluated.** On every other event `PLAN` is absent and G1 to G6 are whole. A unit row in `tests/unit/test_gather.py` holds that a pull-request gather with macOS and the upstream groups unselected is green, and that the same records without `PLAN` are red. The gather's summary is posted as the job summary, so a reviewer reads it without opening logs.

**`ci-status`** is one job with `if: always()` that passes when every job in `needs` is `success` or `skipped` and the decision job's own refusals are empty (`progress`, a missing news file, a missing review file: Decisions 2, 7 and 9), as Wasmtime's aggregate does. The job is `ci-status:` with `name: ci-status`, and the ruleset's required check names it with the GitHub Actions app's `integration_id`, so no other app's status can satisfy it; `docs.yml`'s check is required beside it.

### 4. What a merge to `dev` runs, and the accept jobs

A push to `dev` (the squash merge) runs, from `dev`'s cached set (`set-cache.yml` builds and saves it first when the key misses, once, on `ubuntu-24.04-arm`; the judge waits on it):

- the full normal tier on three systems: every own-* shard on macOS, Linux and Windows, every upstream normal-tier group, `verify` on three systems, `build-shard` on arm64 Linux;
- the gather with G1 to G6 in full. G7 is not evaluated after a merge either: this run is the one that makes the acceptance G7 would compare with, so its artifact clause is true by construction. G7 holds at the release pull request and at the tag (Decision 6);
- **`accept-record`**, gated on a green gather, with `contents: read`, no secret and no environment: in a fresh checkout of the judged commit, `uv run pytest --accept-from build/ci/record.json --claims context/changes/` (Decision 5) writes `context/progress/accepted.json` and the newest history volume, and the job uploads the two files as one artifact;
- **`accept-push`**, after it, in the `accept` environment, whose deployment branch policy is `dev` alone, so no pull request's run can reach its secret. It downloads the two files into a checkout of the judged commit made with the accept identity, runs no script or module of the repository (inline `git` steps only), checks that `git status --porcelain` names exactly those two files, and checks that `dev`'s tip (`git ls-remote origin refs/heads/dev`) is still the judged commit. Then it commits, the message `Accepted: <pull request title> (#<n>) [skip ci]` with the reasons the news files gave, and pushes. When `dev`'s tip is not the judged commit, it pushes nothing, writes one line naming the newer merge, and succeeds: the newer merge's run accepts everything since the last acceptance (Decision 5). `[skip ci]` keeps GitHub from starting a run for the acceptance commit; the decision job's rule (Decision 2) is the second guard, so an acceptance never starts another. Amended 2026-10-25 at step 3's review: the acceptance commit carries no skip word, since GitHub skips a `pull_request` run whose head commit holds one and a release pull request from `dev` usually has an acceptance commit as its head; the decision job's rule is the guard alone, widened to any push whose paths are the accepted state alone (`accepted.json` and history volumes), on which `quick` waits and nothing that judges runs; and the plan refuses a pull request into `dev` whose title or description holds a skip word, which would land in the squash merge's message. Amended 2026-10-25 at step 2's review, Medium 2: the post-merge gather and every shard's ratchet list a claimed growth, fall in `passes` or tier move with its reason and stay green, so `accept-record` runs and consumes the claim; an unclaimed one is red at the gather, named, and the fix is still the one-line news-file pull request.

The accept identity is a deploy key with write access held as a secret in the `accept` environment, the bypass actor of `dev`'s ruleset, so its push passes the pull-request rule; the owner creates it or authorises the agent to. A `DeployKey` bypass covers every deploy key of the repository (INFERRED, read back with `gh api` at the build), so the repository holds this one deploy key with write access and no other.

A red post-merge run means `dev` is broken. The rule, written into `AGENTS.md`: no new merge to `dev` while its last post-merge run is red, except the fix or a revert; the author of the merged change fixes forward the same day or reverts. The accept jobs never run on a red gather, so `accepted.json` never records a red state. Amended 2026-10-25 (step 2's review, Medium 2): a pull request lists its growth, fewer passes and tier moves under `GROWTH`, but step 2's post-merge gather holds G1 to G6 whole, so the same rows are red after the merge. Until step 3, a red post-merge run whose only red rows are those its local acceptance recorded: a growth (`--accept-growth`), fewer passes (`--accept-fewer-passes`), a tier move (`--accept-tier-move`), an absent check (`--retire`), or an upstream pass count that rose, does not count as `dev` broken and blocks no merge; the local acceptance's commit carries `[skip ci]`, so no run turns `dev` green again before the next merge's run, which compares with that acceptance. Step 3 makes the post-merge gather read the news files' claims, so those rows list under `GROWTH` after the merge as they did on the pull request, and `--accept-from` refuses an unclaimed one (Decision 5). Built so at step 3 (2026-10-25): after the merge a row a news file's claim gives its reason for lists under `GROWTH` with that reason, in the gather and in every shard's ratchet, and `--accept-from` consumes the claim; an unclaimed row is red at the gather itself, named, so the run is red before `--accept-from`, which would refuse it too, is reached (Decision 3's G5 sentence, amended the same day).

**What a cached set is trusted for.** A cached set is judged on pull requests and on `dev` without a rebuild, and the acceptance is written from it. It is rebuilt from the pins and compared byte for byte at the weekly run, at the release pull request and at the tag, so a stale set or a planted cache entry is caught before any release and never published. This replaces the per-run rebuild that `release/set_key.py`'s docstring and the 0.1.0 security audit's h10 note (`../reviews/0.1.0-security-audit-2026-10-25.md`) rest on ("a planted entry would end red today"); the docstring is changed to say this, and `test_the_release_reuses_a_set_only_on_a_branch` and the reuse decision admit a pull request into `dev` and a push to `dev` and refuse a pull request into `main`, a run on `main` and a tag.

A scheduled run on `dev`, weekly (`schedule: cron "0 6 * * 1"`, dispatched on `dev` explicitly as Wasmtime's cron does), runs the release tier and the two rebuilds with `same-bytes`, compares the rebuilds' `SHA256SUMS` with `dev`'s cached set's by `cmp`, and opens or updates one issue when red. It never accepts. `workflow_dispatch` gains an input `weekly` that selects this shape, the job that opens the issue has `issues: write`, and a public repository's schedule is disabled after 60 days without activity, which a weekly push to `dev` prevents. The owner chose this against the standing rule that slow tests run only to publish (`../decisions.md`, 2026-10-25).

### 5. Acceptance from CI's record

The plugin gains `--accept-from <record.json>`: the record is a gather's merged record (spec 092's reader) from a run whose every job was green, for the commit checked out, from a push to `dev` or a release pull request (`meta.event`), with `meta.set_source` naming `dev`'s cache key or `built`. It applies the record's statuses and metrics as a local run's would. The record's platform key is the shard's `meta.platform`, never the accept job's host, so darwin fuel stays keyed `darwin-arm64` though the job runs on Linux. The `three systems` need (G6) is met by the record, as spec 092 arranged. Reasons come from the news files of the pull requests merged since the last acceptance (`--claims context/changes/`, Decision 7); an unclaimed row refuses the acceptance with the row named, the run is red, and the fix is a one-line news-file pull request whose merge re-runs the accept.

## Intent

After this specification, a change is a pull request into `dev` that runs what its paths need, in minutes, on Linux and Windows from a cached set, and merges when its check is green and a fresh reader's review file says it lands; every merge is judged once in full on three systems and accepted by a job, so `context/progress/` is written by CI, not by a person on a laptop; a release is a pull request from `dev` to `main` whose check is the whole workflow, both tiers, the rebuilds and the attestation's goals, and whose acceptance is the commit the owner puts on `main` and tags. The judge keeps every check and every ratchet; what changes is where and how often it runs, and that its colour means something: red is broken, on a pull request as on `dev`.
