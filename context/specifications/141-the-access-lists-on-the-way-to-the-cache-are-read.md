## The problem

`_way` (`src/wasi_python/_platform.py:593-621`) judges every folder from `/` down to the folder that holds the cache by its kind, its owner and its mode bits. On macOS the mode bits are not the whole answer: an extended access list is evaluated before them, and an entry such as `group:everyone allow add_file,delete_child` lets every user put, remove and rename entries in a folder whose mode reads 0755 (EXECUTED above, `0x44` on a 0755 folder). So a folder on the way that passes the walk can still be one another user may change, and whoever can change it can put another folder at the cache's name between the check and the load. The access list is read today only on the cache folder and on the `.cwasm` (`_Posix.private_fd`, `_Darwin._access_list`, `_platform.py:498-503`, `:998-1018`), where any list at all refuses, since the runner's own folder and file carry none. That presence test cannot move up the way: every macOS home and its `Library` carry a `deny delete` entry for everyone (EXECUTED above and in 135's review), so a folder with a list is the normal case there, and only reading each entry tells a grant from a denial.

On Linux the question is different. A POSIX access list that names a user or group other than the owner has a mask entry, and the mode's group bits show that mask; no named entry is granted a right the mask lacks. So a named entry that lets another user write shows as a group-writable folder, which the walk already refuses unless it is sticky (Decision 3).

This is defence in depth. Question 112 placed a cache under a folder another user may change outside what is supported, and nothing here refuses a call: a cache whose way fails is not used, the module is compiled in memory, and one warning names the folder, as since 135.

## Decisions

### 1. On macOS, an allow entry that lets anyone but this user or root change a folder on the way means the cache is not used

For each folder the walk finds (every folder from `/` down to the folder that holds the cache, the same folders `_way` already judges, in the same order), after its kind, owner and mode pass, the platform reads its extended access list. The folder fails when the list holds an entry that is all of these:

- **an allow entry**: tag `ACL_EXTENDED_ALLOW` (1). A deny entry (`ACL_EXTENDED_DENY`, 2) never refuses, so the home's `group:everyone deny delete` passes. A deny entry never excuses either: an allow entry counts even when a deny entry before it takes the same right from the same principal. Reason: whether a deny shadows an allow depends on the entries' order and on group membership, which the kernel evaluates and the runner would have to model; judging every allow entry on its own fails closed, and costs a cache only on a folder whose list both grants and takes away the same right, which no default way carries (EXECUTED above).
- **one that applies to the folder itself**: the flag `ACL_ENTRY_ONLY_INHERIT` (`1<<8`) is not set. An only-inherit entry grants nothing on the folder it sits on. An entry marked inherited (`ACL_ENTRY_INHERITED`) without only-inherit applies like any other and counts. Reason: an inheritable entry shows where it lands, so a folder the runner makes below one (the missing folders `cache_folder` makes at 0700) inherits it as an applying entry (EXECUTED above: `[inherited, dir_inh]`), and 147's second walk refuses that folder by this rule; the cache folder itself, made below such an entry, is already refused by 135's presence test.
- **one that grants a right that changes what the folder holds or who may change it**: any of `add_file` (`ACL_ADD_FILE`, `1<<2`), `add_subdirectory` (`ACL_ADD_SUBDIRECTORY`, `1<<5`), `delete_child` (`ACL_DELETE_CHILD`, `1<<6`), `delete` (`ACL_DELETE`, `1<<4`), `writesecurity` (`ACL_WRITE_SECURITY`, `1<<12`) and `chown` (`ACL_CHANGE_OWNER`, `1<<13`), the names `chmod +a` takes for a folder. Not counted: `list`, `search`, `readattr`, `writeattr`, `readextattr`, `writeextattr`, `readsecurity` and `synchronize`, none of which adds, removes or renames an entry or changes who may. Reasons, right by right: `delete_child` removes or renames any entry in the folder, which is the swap itself; `delete` on the folder lets its holder rename the folder away, and in a parent anyone may add to (a sticky folder such as `/tmp`) put another in its place; `writesecurity` and `chown` let their holder give itself every other right; and `add_file` and `add_subdirectory` are counted though alone they replace nothing, because the mode rule counts the `w` bit, which on a folder is adding and removing together, and macOS splits it in two: the walk refuses either half, as it refuses `w`, and the rule stays one sentence. A folder another user could add to but not remove from is the sticky case, which the mode rule allows by its bit; an access list has no such bit, so it is not copied. An entry whose mask holds the kernel's generic write or generic all bit (`1<<23`, `1<<21`), which the kernel expands to every write right, counts as granting the five it expands to (`add_file`, `add_subdirectory`, `delete_child`, `delete`, `writesecurity`), and the warning names them. Reason: libc refuses to set either bit (EXECUTED by the pre-build review: `acl_set_permset_mask_np` with `1<<23` answers `EINVAL`), but a list a network file system translates from its server can carry one, and the kernel's `KAUTH_VNODE_GENERIC_WRITE_BITS` (`sys/kauth.h`) then grants every write right with none of the six specific bits set.
- **for a principal that is not this user or root**: an entry for a user whose uid is the effective uid (the uid `_this_users` compares, 147's Decision 3) or 0 passes. Every group entry counts, whatever the group, `everyone` (gid 12) included, as the mode rule counts the group's `w` bit whoever is in the group. An entry whose principal the system cannot name as a uid or a gid (its qualifier missing, or `mbr_uuid_to_id` failing, as for a deleted account) counts. Reason: the walk trusts exactly whom the mode rule trusts, and a principal it cannot name it cannot trust. The owner of `/`, whom 147 trusts on `/`'s own device, gains no entry here: on macOS `/` is the sealed system volume, root's (EXECUTED above), so that owner is root, and an entry for any other uid on macOS fails closed and is named.

The first entry that counts, in the list's own order, is the one the warning names (Decision 6). The cache folder and the `.cwasm` keep 135's presence test unchanged: any list there, an inheritable one included, means they are not used.

### 2. The reads, and what an unreadable list means

`_Darwin.access_entries(path)` reads the list by path, without following a last link, with `acl_get_link_np(path, ACL_TYPE_EXTENDED)`, and returns one `_Entry(allow, kind, id, rights, inherit_only)` per entry: `allow` from `acl_get_tag_type`; `rights` the whole mask from `acl_get_permset_mask_np`, which fills an `acl_permset_mask_t`, a 64-bit integer (`ctypes.c_uint64`) (one call where `acl_get_permset` and `acl_get_perm_np` would take one per right; available since macOS 10.7); `inherit_only` from `acl_get_flagset_np` and `acl_get_flag_np`; `kind` `"user"` or `"group"` and `id` from `acl_get_qualifier` and `mbr_uuid_to_id` (id type 0 a uid, 1 a gid), or `kind` `""` for a principal it cannot name. It walks the entries with `acl_get_entry`, first `ACL_FIRST_ENTRY` (0) and then `ACL_NEXT_ENTRY` (-1), stopping at the first nonzero answer (macOS answers -1 with `EINVAL` past the last, EXECUTED above) and after at most `ACL_MAX_ENTRIES` (128). Each qualifier and the list are freed with `acl_free`, the list in a `finally`. The calls are resolved once into the platform's one access-list table, `acl_api`, which `_Darwin._access_list` already fills with `acl_get_fd_np` and `acl_free`: one fill resolves all ten calls and publishes the table whole, as 149's Decision 1 asks of every resolve-once table.

**Why by path and not by descriptor.** The walk `lstat`s each folder by path, top down; once every folder above a folder has passed, no one but this user, root (or, on Linux, `/`'s trusted owner) can rename it, so its path names the folder the `lstat` saw when its list is read. A folder whose list is read through a path that changed would need a folder above it that fails, and that folder was judged first. `acl_get_link_np` needs only search permission on the way, as `lstat` does (EXECUTED above: two root folders this user cannot list read as no list, not `EACCES`); opening each folder for `acl_get_fd_np` would need read permission and one more descriptor per folder.

**The answers.**

- `acl_get_link_np` returns NULL with `ENOENT`: **no list**. It is macOS's answer for a folder without one (EXECUTED above). The same `errno` for a folder that went away between its `lstat` and the read is taken as no list too: only a principal the walk trusts could have removed it, and the walk's next `lstat`, or 147's second walk, sees it missing.
- NULL with `ENOTSUP` or `EOPNOTSUPP`: **no list**. The file system keeps none, so none can grant.
- NULL with any other `errno` (`EACCES`, `EPERM`, `EIO`, `ENOMEM` and the rest), and a nonzero answer from `acl_get_tag_type`, `acl_get_permset_mask_np` or `acl_get_flagset_np`: an `OSError`, which `_way` turns into the walk's `PermissionError` naming the folder, so **the cache is not used**, with the warning (Decision 6). Reason: the check cannot vouch for a folder whose list it cannot read, and the cost of failing closed is a compile; `EACCES` is not expected where the folder can be searched (EXECUTED above), so a host that answers it is told so in words.
- `ENODATA` is Linux's answer for a missing attribute; Linux reads no list here (Decision 3), so it does not arise.

`_Posix.access_entries(path)` returns `()`: a POSIX host the runner does not know by name has no way it reads (as `_Posix._access_list` answers today), and Linux's reason is Decision 3. `_Linux` inherits it.

### 3. Linux reads no list on the way, because the group bits are its mask

The reserved line says each ancestor's list is read "through `system.posix_acl_access` on Linux". This specification reads none there, and adds a row that holds the reason on the Linux leg. **The reason** (INFERRED from the POSIX.1e access-list model as Linux implements it, the `acl(5)` manual's section on the correspondence between entries and permission bits; the pre-build review reads it again, and row 9 runs it): a list holding a named user or named group entry must hold a mask entry (`ACL_MASK`), the kernel refuses one without; the rights a named user, a named group or the owning group is given are its entry's rights limited by the mask; and the mode's group bits are the mask's rights while a mask exists. So any entry that lets another user add, remove or rename in a folder puts `w` in the mask and therefore in the group bits, and the walk already refuses a folder whose group bits hold `w` unless it is sticky; under the sticky bit, a named user with `w` can rename only its own entries, as anyone in `/tmp` can. The `other` entry is the mode's other bits, which the walk reads. A list cannot widen write past what `st_mode` shows, so parsing `system.posix_acl_access` could refuse nothing the walk does not refuse already: code no row could see refuse, which is worse than none. `system.posix_acl_default` on a folder on the way grants nothing on that folder; a folder the runner makes inside takes the default list with its mask cut to the `mkdir` mode's group bits, which are none at 0700, and the cache folder is held to 135's presence test.

**What stays outside.** A list that names only this user or root with `w` still sets the mask's `w`, so the folder is refused by the mode rule, as today: that strictness is the mode rule's, and the exception for a group that holds only its user was left to the owner by 135's review (Low 5). Access lists the kernel does not show in the mode bits (NFSv4's `system.nfs4_acl` on an NFS home, `system.cifs_acl` on an SMB mount) are not read: a home on a shared folder is the configuration question 112 placed outside what is supported, and those lists are the server's to evaluate, not the client's.

### 4. Windows is out of this walk

`_Windows.cache_folder` walks no folder (`src/wasi_python/_platform_windows.py:427-433`): Windows has no mode bits, its owner test answers yes for every file (139's Decision 1), and the grant rule is the guard there, as 113 and 135 decided and the install page says. Reading a Windows access list on each folder of the way is a reading of its discretionary list's entries through `advapi32`, the same reading the reserved Windows line needs (`../roadmap.md:120`, a protected access list for the module cache on Windows, "likely structural"); it belongs there, with that line's own review. Nothing in this specification runs on Windows, and its rows skip there with 147's reason, "Windows has no ancestor rule; the grant rule guards it".

### 5. `_way` asks the platform, through one parameter, and stays short

`_way(folder, lstat, entries)` gains a third parameter, the platform's reader, which `_Posix.cache_folder` passes as `self.access_entries` in both of its walks. The rows never pass it; they stand in for the platform object's method (Decision 8), so `_way`'s callers are production code alone. After a folder's kind, owner and mode pass, `_way` asks `_listed_writer(str(here), entries)`: `None` when the list lets no one else change the folder, else the words of Decision 6; an `OSError` from the reader becomes the words "has an access list the runner cannot read (<strerror>)". The advice the message ends with is chosen by `_advice(root, listed)` (Decision 6). `_principal(entry)` words the principal. Reason for the split: `_way` stays one loop a reader holds whole (about 40 lines after, against 29 today and the 80-line ceiling), the entry rule is one pure function the rows can reach through the walk on every POSIX system, and the macOS reading is one method of `_Darwin`.

### 6. The warning: one text per reason, naming the folder and the principal

The walk's message keeps its shape, `f"{here}, on the way to it, {why}; {advice}"`, and `_cache_warning` raises it as today: "wasi_python: not using the module cache at <cache>: <message>". Two new reasons:

- **An entry lets another principal change the folder:** `why` is "has an access list that lets <principal> <rights>", where `<principal>` is "the user <name> (uid N)" or "the group <name> (gid N)", the name from the password or group database, or "the user uid N" or "the group gid N" where the database has none, or "a user or group the system cannot name"; and `<rights>` are the counted rights the entry grants, in Decision 1's order and `chmod +a`'s words, joined by commas. Below `/` the advice is "remove that entry with chmod -a, or set $WASI_PYTHON_CACHE to a folder of yours". So a folder with `group:everyone allow add_file,delete_child` gives: "wasi_python: not using the module cache at /Users/me/shared/cache: /Users/me/shared, on the way to it, has an access list that lets the group everyone (gid 12) add_file, delete_child; remove that entry with chmod -a, or set $WASI_PYTHON_CACHE to a folder of yours".
- **The list cannot be read:** `why` is "has an access list the runner cannot read (<strerror>)", and below `/` the advice is "set $WASI_PYTHON_CACHE to a folder of yours", as for a folder that fails its owner or mode.

**At `/`**, for either reason, the advice is a new constant beside `_ROOT_ADVICE`: "no folder can hold the cache while it is, so pass cache_dir=False to compile in memory without this warning". Reason: every cache folder is below `/` (147's Decision 2), and on macOS `/` is the sealed system volume, which no one changes from a running system, so naming `chmod -a` there would be advice no one can follow. `_ROOT_ADVICE` stays for `/`'s mode.

Reasons for the words: the warning is the embedder's one sign, so it says which folder, who, and what that one may do, in the words `chmod -a` takes back. The rows assert the texts verbatim (row 1 and row 4).

### 7. What it costs

On macOS one `acl_get_link_np` and, for a folder with a list, one call per entry and per field, for each folder on the way, in each of 147's two walks: once per flavor per process, on a miss of the process's own module table, whether the `.cwasm` is then loaded or compiled. On Linux and every other POSIX host, no system call: `_Posix.access_entries` answers `()` without one. The landing notes count the calls on the default cache's way of the build host with a counting stand-in for the reader (a count, never a time), as 147's notes counted the second walk's `lstat`s.

## Intent

After this specification, the walk of the way to the module cache on macOS reads what the mode bits cannot show: an allow entry that lets anyone but this user or root add, remove or rename in a folder on the way, or change its list, means the cache is not used, and the warning says which folder, which principal and which rights, in the words `chmod -a` takes back. The `deny delete` every macOS home carries passes, so every default cache still loads. On Linux nothing new is read, because a list there cannot grant write past the group bits the walk already reads, and a row on the Linux leg holds that. Nothing refuses a call; this is defence in depth under question 112.

## Scope

In: Decisions 1 to 10. Out:

- Linux's `system.posix_acl_access` and `system.posix_acl_default` on the way (Decision 3), and NFSv4 and SMB access lists, which the kernel does not show in the mode bits (Decision 3, question 112);
- Windows (Decision 4): its access lists on the way belong with the reserved protected access list for the module cache on Windows;
- the cache folder and the `.cwasm`: 135's presence test stays as it is;
- modelling the kernel's evaluation (the entries' order, a deny that shadows an allow, group membership): every allow entry is judged alone (Decision 1);
- an exception for a group that holds only this user, in the mode rule or in an entry: the owner's to ask for, as 135's review left it;
- a POSIX host the runner does not know by name: it reads no list, as today, and no guest runs there;
- anything that refuses a call: the cache is never used with a warning, never a failure, as 135's Decision 1 holds under question 112;
- the ancestors of the runner's other folders (its private folders, a made root): named by the runner itself, not by an argument, and judged by their own rules.
