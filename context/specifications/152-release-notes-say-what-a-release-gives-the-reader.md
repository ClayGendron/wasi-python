## The problem

The owner, 2026-10-27: "for the notes that go with the release, those need to be better. they should be like release notes that explain the value to the reader, right now ours are just a blob of text." The notes are the CHANGELOG section, cut whole. Every fact below is READ from the file cited, and the counts are EXECUTED with `awk` and `wc -w` over the line ranges named.

- **What a release's notes are.** `notes` (`release/version.py:227-233`) returns a version's CHANGELOG section from its heading to the next; `_notes` (`:466-468`) appends the verify note; the `publish` job writes that to `notes.md` and passes it to `gh release create --notes-file` (`.github/workflows/release.yml:1484-1488`); `release` puts the same text in the tag's message (`release/version.py:441`). The CHANGELOG's header says so: "A section's body is the release's notes on GitHub" (`CHANGELOG.md:3`).
- **What 0.1.1's notes say.** Sixteen entries (`CHANGELOG.md:5-27`), 2,662 words, each between 71 and 284 words (mean 165). Every one carries "(spec NNN)"; none links a page of the documentation site; no sentence says what the release gives. Ten sit under `### Changed`, and six of those change nothing an embedder sees (131's split of the platform module, 136's pins, and 138's four steps of the process, `:9`, `:12`, `:13`, `:16-18`), beside two that made calls faster (128 and 129, `:14-15`) and two that a reader must act on or should know (135's module cache, 127's wasmtime pin, `:10-11`). Under "Changed" the reader cannot tell them apart.
- **What 0.1.0's notes say.** Fifty-four entries (`CHANGELOG.md:29-98`), 6,919 words, no heading at all; every entry names its specification.
- **Where else the same text is read.** The documentation site's changelog page is one line, `--8<-- "CHANGELOG.md"` (`docs/reference/changelog.md:1`), which the snippets extension fills with the whole file (`mkdocs.yml:49-51`); the README links the file as "what each release changed" (`README.md:313`), and the README is the wheel's description on PyPI. So the same blob is the GitHub release, the site's page and PyPI's link. The public-page scans read the README and every page under `docs/` (`tests/harness/scan.py:4108-4124`), but they read the changelog page as its one include line, so the site shows specification numbers and a `context/` path (`CHANGELOG.md:3` names `context/specifications/004-alpha-releases.md`) that the scans refuse on every other page.
- **Where the text comes from.** A news file's `## Changelog` section (`context/changes/README.md:7`) takes any `- ` line under `Added`, `Changed`, `Fixed` or `Security` (`tests/harness/news.py:51`, `:113-138`). ## What the prior art does

- **wasmtime** (`../prior_art/wasmtime-v49/RELEASES.md`, Apache-2.0 with LLVM exception): each release is a heading, a "Released <date>." line, and `### Added`, `### Changed`, `### Fixed` (`:108-153`); a patch release is a list of one-line headlines, each the user-visible symptom ("Filesystem sandbox escape when renaming symlinks with trailing slashes.") followed by its advisory's link (`:1-53`). Each entry is one short sentence in the user's terms, with the detail one link away. Ours puts the detail in the entry and gives no link.
- **Rust** (`../prior_art/rust/RELEASES.md`, MIT or Apache-2.0): a version's notes are grouped by what a reader works on (Language, Compiler, Platform Support, Libraries, Stabilized APIs, Cargo, Rustdoc, `:15-102`), with "Compatibility Notes", what a reader may need to change, as a heading of its own (`:109-128`) and "Internal Changes" last (`:132`). Each item is one line whose text is the link. The heading tells a reader which items are theirs; ours puts the process and the product under one "Changed".
- **NumPy** (`../prior_art/numpy/doc/release/upcoming_changes/README.rst`, BSD-3-Clause): each pull request writes a news fragment typed by what it does for the user (`new_feature`, `improvement`, `performance`, `compatibility`, `highlight`, `:20-29`), in full sentences (`:9`); the release's notes open with a paragraph that says what the release is and its "big news" (`../prior_art/numpy/doc/source/release/2.5.2-notes.rst:7-13`), and the list of every pull request and contributor is a separate file (`../prior_art/numpy/doc/changelog/2.5.2-changelog.rst:1-25`). The reader's notes and the project's record are two documents; ours are one, written for the record.
- **pandas** (`../prior_art/pandas/.github/release_notes/minor.md`, BSD-3-Clause): the GitHub release's body is a template of four short paragraphs, what kind of release it is, a link to the full "what's new" and how to install (`:1-16`). The release page is a summary and a link.

What they share and ours lacks: an opening that says what the release is for, headings that sort changes by what they do for the reader, entries of one or two sentences in the reader's terms, and a link to where the detail lives.

## Decisions

### 1. The notes are written for an embedder who did not follow the work

A release's notes answer three questions for someone who uses wasi-python and read none of its specifications: what does this release give me, is there anything I must do, and where do I read more. Each entry says the value first, in the reader's terms, then the one fact that tells them what changed, then links the page of the documentation site that explains it. An entry names no specification, decision, review, finding or `context/` path; no module, function or file a reader cannot call or open (a private name such as `_platform.py`, a harness file); and no fuel figure, count of lines or timing unless that number is the point of the change. The voice is the one `AGENTS.md`, "Explaining things", asks of the README and `docs/`: say the fact and stop, no restated benefit, no framework named for its own sake. Reason: the owner asked for notes that explain the value to the reader, and every page the notes reach (the GitHub release, the site's changelog page, PyPI's link) is read by that reader.

### 2. One text: the news file's lines are the reader's, and the detail stays in the specification

The news file's `## Changelog` section keeps its name and its place, and its lines are now the reader's entries, in the shape of Decision 4. The project's detailed line is dropped; the detail lives where it already does, in the specification's landing notes, and the news file points there by its title, `# NNN: <title>`, which names the specification. Once `bump` has removed the news file, an entry's specification is the squash merge that added its line, `git log --diff-filter=A -S '<the entry's lead>' -- context/changes`, whose title names it. `bump` and `date` assemble these entries into `CHANGELOG.md` as today, and `notes` cuts the same section for the GitHub release and the tag, unchanged: the CHANGELOG, the site's changelog page, the release and the tag carry one text. Reason: a `## Release note` beside a detailed `## Changelog` would keep the detailed lines in `CHANGELOG.md`, and `CHANGELOG.md` is itself a public page, included whole by the site and linked from the README and PyPI, so the blob would stay in front of the same reader; it would also be a third copy of the detail beside the landing notes and the squash commit, to be kept in step by hand. One source cannot disagree with itself, and the record the project needs already exists. This departs from the roadmap's sketch, which put the reader's paragraph beside the CHANGELOG line; the sketch's purpose, the reader's notes, is kept.

### 3. Six headings, in the order a reader scans them, replace the four

The headings, in this order, each with the one-line definition `context/changes/README.md` gives:

- `### New`: something an embedder can do that they could not before (a function, an argument, a package, a host).
- `### Faster`: the same result in less time or memory, said in the reader's terms (a start, a call, an import).
- `### Security`: a hole closed or a guest's reach narrowed, with the advisory's identifier and link when one exists.
- `### Fixed`: something that did not work as the documentation says, and now does.
- `### Upgrading`: a change an embedder may need to act on (a value now refused, a default or a pin that moved, something removed), and the entry says what to do.
- `### For contributors`: the build, the tests, the release process and the documentation's own tooling, nothing an embedder sees.

They replace Keep-a-Changelog's `Added`, `Changed`, `Fixed` and `Security` in every news file and in every section from 0.1.2 on; a news file under an old heading is refused. The author chooses the heading by what the reader gets, not by what the code did: `Added` becomes New, or For contributors when nothing an embedder sees was added; `Changed` becomes Faster, Upgrading or For contributors (0.1.1's ten would have split into six For contributors, two Faster, 135 under Security and 127 under Upgrading); `Fixed` stays Fixed; `Security` stays Security. A change that both gives and asks something writes two entries, one under each heading. When two headings fit, the entry goes under the first of them in the list, so a regression restored is Faster or Fixed by what the reader gets back and a hole closed by a fix is Security; a change an embedder sees that fits none of the first five (a clearer message, a new guide) goes under New. Reason: `Changed` held ten of 0.1.1's sixteen entries and told the reader nothing about which were theirs; New, Faster and Fixed are what the owner's sketch names; `Security` keeps its name rather than the sketch's "safer" because it is the word a reader and their tooling search for when deciding whether to upgrade now, and the published sections already use it; `Upgrading` is Rust's "Compatibility Notes" in one word, placed after the changes a reader wants and flagged in the summary (Decision 5) so it is not missed; For contributors is last, as Rust puts "Internal Changes".

### 4. An entry's shape, held whenever a news file is read

An entry is one `- ` line: a bold lead of 2 to 12 words that says the value (`**Unbounded tool calls now end after an hour.**`), then the fact in one or two sentences, then a link to a page of the documentation site, `https://claygendron.github.io/wasi-python/<path>/` with an optional `#anchor`, as the line's last text. The line holds at most 60 words, counted as its whitespace-separated tokens with every link's address removed. Further links before the last (an advisory, a second page) are allowed. An entry that adds or drops a carried patch names the patch's path, `recipes/patches/<top>/<file>`, so constitution §4.1's rule holds; a path a reader can open is not detail they cannot act on. `scan.patch_errors` also reads the `## Changelog` sections of the news files beside `CHANGELOG.md`, so a pull request that adds a patch is held to name it at its own run rather than only after `bump` (a gap since the news files began, closed here because this specification already changes what that section holds and the fix is a few lines in the function the rule already runs). `tests/harness/news.py` holds the heading set, the lead, the word count and the link's form when it parses a news file; `test_the_news_files_have_their_shape` also resolves each site link to a page under `docs/` (`<path>/` is `docs/<path>.md` or `docs/<path>/index.md`; the anchor is not checked), so a link that leads nowhere is red at the pull request; it also runs `news.link_errors` over the entries of `news.reader_sections` of `CHANGELOG.md`, so a page a published note links keeps its path. `news.SITE` is the site's address, and a unit row holds it equal to `mkdocs.yml`'s `site_url`. Reason: the counts are what can be held without judgment; 0.1.1's shortest entry was 71 words and its mean 165, so 60 forces the detail out, and every model entry below fits; the voice, the private names and the figures are the reviewer's to read (Decision 8), since no regex tells a value from a mechanism.

When no page explains the change, the entry links the nearest page a reader acts from: `explanation/security-model/` for a hole closed in a pinned component (with the advisory as an earlier link), `reference/packages/` for a pin moved, `reference/defaults-and-limits/` for a bound; when none is near, the pull request adds the paragraph to a page, since a change the reader cannot read more about is a page the documentation owes. An entry that needs more than 60 words is two changes, written as two entries, or carries detail that belongs on the page it links; the bound has no allowance.

### 5. The summary is written once, at the preparation, and a dated section must have it

A section of a version `news.is_reader_version` accepts (its `X.Y.Z` above 0.1.1, so a pre-release of 0.1.2 counts) opens with one paragraph before its first heading: two to five sentences, 30 to 120 words, that say what the release gives an embedder, and, when the section has an `Upgrading` entry, a sentence that says a change may need action and what it is. The agent that prepares the release writes it into the unreleased section after `bump` and before `date`, from the news files the section holds. It and the rewrites the notes' reader asks for (Decision 8) are the hand edits of the version's section the news-file rule allows, made in the preparation pull request and nowhere else; they are reviewed with the preparation. It carries no heading: it is the first thing under the version's title on GitHub and on the site, and a "Summary" heading would add nothing. `date` refuses to date a section of a reader version that fails the reader's shape (no summary, a summary outside the bounds, an old heading, an entry out of shape), naming each fault and writing nothing; `check_errors` reports the same faults for every dated section `news.reader_sections` returns, so `check --tag` in the build job (`.github/workflows/release.yml:269-288`), `release` before it tags and `test_the_version_is_released_by_the_book` all hold it. Reason: the summary needs the whole release in view, which no single news file has, so it is written where the release is assembled; `date` is the step every release passes through on `dev`, and `check_errors` is the gate the workflow already runs on the release pull request and the tag, so no workflow changes.

### 6. A release note names no project document, by the public pages' own rule

A new rule in `tests/lint/test_writing_conventions.py`, `test_release_notes_name_no_context_document`, reads every news file's `## Changelog` section, `CHANGELOG.md`'s header (the text before its first version section) and every section of a reader version, and refuses each hit of `scan.CITATION_RULES` (`tests/harness/scan.py:3985-4018`: a specification's number, the constitution's sections, a memo, a review by date, path or kind, an owner's numbered question, a `context/` path, a finding's identifier), the same family `context_citation_hits` applies to the README and every page under `docs/`, and each name of `context/embedders.txt` (`scan.read_names`), as the README and the site are held (`tests/checks/test_rules.py:60-65`). It lives in `tests/lint/` because it is a writing rule; `quick`'s `lint` step runs it. `news.is_reader_version(version)` is true when the version's `X.Y.Z` is above 0.1.1, so a pre-release of 0.1.2 counts; `news.reader_sections(changelog)` returns the header and every section whose version it accepts, whatever other headings the file holds; `_date`, `check_errors`, the link resolution and the lint rule use these two and no other test. Reason: the notes are a public page and should meet the public pages' rule, by the same regexes so the two cannot drift; scanning only from 0.1.2 on keeps the published sections out of a rule they were not written under.

### 7. Published sections stay as they were published, and the header is rewritten

0.1.1's and 0.1.0's sections, and the alphas', are left as they are: they are the text of published GitHub releases and signed tags, and a rewrite would make the file disagree with what readers were given. 0.1.2 is the first section in the new shape. `CHANGELOG.md`'s header becomes exactly: "One section per release of the `wasi-python` artifact set and wheel, newest first. Each section is also the release's notes on GitHub. From 0.1.2 a section opens with what the release gives you, then lists its changes under New, Faster, Security, Fixed, Upgrading and For contributors, each with a link to the page that explains it. Earlier sections are kept as they were published." It names no `context/` path, and Decision 6's rule holds it. Reason: the header is the one unpublished text above the published sections, it is on the site's changelog page, and today it names a specification's path.

### 8. A reader who wrote none of it reads the rendered notes before the release

At each release's preparation, once `date` has run, a fresh agent or a person who wrote neither the summary nor any entry reads `uv run python release/version.py notes <version>` as an embedder who did not follow the work, and writes `context/reviews/<version>-release-notes-review-YYYY-MM-DD.md`: for the summary and each entry, "reads" or the rewrite it asks for, against Decisions 1, 3 and 4. The preparation pull request carries the rewrites and the review file beside the security and structural reviews. The review ends with a `## Verdict` section. The judge holds the file's presence for a released version above 0.1.1, as it holds the structural review's: `scan.release_notes_review_errors(version, reviews)`, the twin of `structural_review_errors` (`tests/harness/scan.py:432-449`), refuses a released version (`X.Y.Z`, no `aN`, `bN` or `rcN`) that `news.is_reader_version` accepts when the reviews hold no `<version>-release-notes-review-YYYY-MM-DD.md`, or hold one with no `## Verdict`, and `test_a_release_has_its_release_notes_review` calls it beside `test_a_release_has_its_structural_review` (`tests/checks/test_rules.py:249-257`) on the version `__init__.py` carries. What the notes say stays the reader's judgment. Reason: what makes a note good for a reader is a judgment the counts cannot make, so this review is the one step that holds Decision 1's voice; the project already holds its other per-release review of judgment, the structural review, by its presence; and a release whose push is delegated, as 0.1.1's was and 0.1.2's is, is where an unchecked step is most likely skipped.

### 9. Every news file of 0.1.2 is in the new shape, the merged ones converted here

The builder of this specification converts every news file on `dev` when its pull request opens, which today is 127's alone, to the model below; a news file merged before this lands that the builder's rebase brings in is converted on the same branch. A news file written after this lands meets the shape or is red at its pull request. Every branch open when this lands (144, 147 and 150 have branches today) converts its news file on its rebase, to the model's entry for it where there is one; the refused-heading message names the six headings, and `context/changes/README.md` points to the model. The drafted 144, 145 and 146 quote their news lines in the old shape in their Design sections; this specification supersedes those quotations, and their builders write the entries the model below gives for them, adjusted to what they built. 144's builder also writes an Upgrading entry if, as built, a `close()` from the event loop's thread during a `run_async` turn now waits for the ending where it used to return, since that is a call that used to return and now blocks; the preparation's summary then names it among the changes that may need action. Converting a news file re-reads its claim block at the next acceptance (`context/changes/README.md:35`), which is harmless: a claim supplies reasons and an unused one refuses nothing (`tests/harness/accept_from.py:255-295`). Reason: the owner asked that 0.1.2's notes be the new kind, and the release is assembled from every news file merged since 0.1.1.

## Intent

After this specification, an embedder who opens a wasi-python release on GitHub, on the site or from PyPI reads in a few sentences what the release gives them and whether they must do anything, then finds each change under the heading they care about, said in one or two sentences with a link to the page that explains it. The agents who build the project write that text once, in the news file, in the reader's voice, and the release assembles it unchanged.

## Design

- `tests/harness/news.py`: `HEADINGS` becomes the six of Decision 3 in their order; `SITE = "https://claygendron.github.io/wasi-python/"`; `entry_errors(line)` (Decision 4's lead, word count and last link); `_changelog` calls it for each line and names the six when a heading is refused; `summary_errors(text)` (Decision 5's one paragraph of 30 to 120 words, not a `- ` or `#` line, not the placeholder); `section_errors(body)` (the summary, the headings among the six and in order, each entry's errors); `link_errors(entries, docs)` (Decision 4's resolution, over a news file's entries or a section's); `is_reader_version(version)` and `reader_sections(changelog)` (Decision 6). Standard library only, as today, so `release/version.py` keeps loading it by its path. The module docstring shows the new shape.
- `release/version.py`: `_joined`'s order is `news.HEADINGS` through `_reader()`; `_date` runs `section_errors` on the section it is about to date when `is_reader_version` accepts the version and raises `ReleaseError` with every fault before writing anything; `check_errors` adds the same faults for every dated section that `reader_sections` returns. `notes`, `verify_note`, `bump`'s reading of news files and the `publish` job are unchanged. ### The model: 0.1.2's notes as they stand today

This is the standard every 0.1.2 news file and the 0.1.2 summary are held to. Each entry is drawn from the 0.1.2 scope (`../roadmap.md`) and the drafted 144 to 146: 147's module cache, 146's two bounds, 145's mount names (twice: what it gives under Security, what it refuses under Upgrading) and 144's sessions, and this specification's own. The last entry is 127's news file, converted.

```markdown
## 0.1.2 — YYYY-MM-DD

wasi-python 0.1.2 is for embedders who keep many guests running for a long time. Every session now ends, however and from wherever it is closed. Tool calls and mounts have bounds you can read and rely on. On a container host where another user owns `/`, the compiled module is cached again, so a start no longer compiles it first. Two changes may need action: a tool call that nothing else bounds now ends after an hour, and a mount refuses file names with `:` or `\`.

### Faster

- **Starts are fast again in containers where root does not own `/`.** In 0.1.1 the module cache was refused when another user owned `/`, so every start compiled the module first. The cache now trusts the owner of `/` as it trusts root, since that owner can already replace any file. [Where the compiled module is kept](https://claygendron.github.io/wasi-python/get-started/install/#where-the-compiled-module-is-kept)

### Security

- **A guest cannot pile up threads in your process.** A tool call that times out leaves its function running on a thread; once 64 such threads are alive in a process, the next tool call is refused, and the guest's error names the bound. [Bound a tool's time](https://claygendron.github.io/wasi-python/how-to/tools/#bound-a-tools-time)
- **A mount's paths mean the same on every host.** A path component that holds a backslash or a colon is refused with `EINVAL` on Linux, macOS and Windows alike, so a provider that stores files on disk cannot be led outside its mount. [Treat a path as a name, not a host path](https://claygendron.github.io/wasi-python/how-to/mounts/#treat-a-path-as-a-name-not-a-host-path)

### Fixed

- **`close()` inside a tool no longer hangs, and every session ends.** A `close()` from a tool or a mount's provider during `run_async` used to deadlock; it now returns at once and the session ends with its turn. A turn cancelled while queued, or still queued at exit, no longer leaves its session open. [Know how a session ends](https://claygendron.github.io/wasi-python/how-to/sessions/#know-how-a-session-ends)

### Upgrading

- **Unbounded tool calls now end after an hour.** With `deadline_s=None` and no session lifetime, a tool call used to wait as long as its tool ran; it now raises `ToolTimeout` in the guest after 3,600 seconds. Give the tool a `timeout_s` to choose another bound. [Bound a tool's time](https://claygendron.github.io/wasi-python/how-to/tools/#bound-a-tools-time)
- **A mount refuses file names with `:` or `\`.** On Linux and macOS a mount accepted them before; now every host answers `EINVAL`, as Windows always did. A guest that writes timestamped names such as `12:30.csv` into a mount should use another separator. [Treat a path as a name, not a host path](https://claygendron.github.io/wasi-python/how-to/mounts/#treat-a-path-as-a-name-not-a-host-path)

### For contributors

- **Release notes say what a release gives you.** Each change is now written for an embedder who did not follow the work: what it gives, the one fact that changed, and a link to the page that explains it. [The release process](https://claygendron.github.io/wasi-python/contributing/release-process/)
- **Upstream suites keep their pass counts under wasmtime 50.** Their fuel, last measured under wasmtime 49, is recorded again by a later release-tier run; until then only their passes are compared. [Two tiers of tests](https://claygendron.github.io/wasi-python/contributing/release-process/#two-tiers-of-tests)
```

The model's measures (EXECUTED, the same count Decision 4 makes): the summary is 87 words in five sentences; the eight entries, in the model's order, are 58, 49, 54, 59, 50, 54, 43 and 36 words, the longest lead 12 words; no line hits `scan.CITATION_RULES` or a reserved embedder name, and none names a private name.
