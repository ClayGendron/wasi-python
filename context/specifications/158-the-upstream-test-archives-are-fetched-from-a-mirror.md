## Decisions

### 1. The mirror is a release of this repository, uploaded by the owner

The two pinned archives, byte-identical to the pins, are the assets of one GitHub release of `ClayGendron/wasi-python`, tag `test-sources-2026-10-28`, title `Test sources, 2026-10-28 (not a release of wasi-python)`, published (not a draft, whose assets are not public), not marked latest, its tag on `main`'s tip. Its body names each file's origin URL, size and SHA-256, says it is not a release of the product, and says the pin is what is trusted.

Why this repository and not a separate one. Both are the owner's account, so neither adds an identity, and the bytes are trusted by the pin either way. This repository adds no repository to govern (its settings, its rulesets, its visibility, its deletion), keeps the mirror beside the pins that name it, and its download URLs are served by the same GitHub that every judge leg already reaches. What it costs is one entry in the Releases list that is not a version, which the title and body name; and `--latest=false` keeps the product's latest release where it is. A separate repository (`ClayGendron/wasi-python-test-sources`) would keep the Releases list clean at the price of a second repository with its own settings, and a reader of a pin would have to know it exists. One place wins.

Why the tag cannot start anything (READ). `release.yml` and `docs.yml` run on pushed tags matching `v*` only; `set-cache.yml` on pushes to `dev`; `accept-release.yml` on the release workflow's completion; no workflow listens for a `release` event. `release/version.py` looks up only its own `v<version>` tag, and nothing in the repository runs `git describe`. Its tag goes on `main` because `main` holds the released states and the tags (`AGENTS.md`).

Later mirrors are new releases, never new assets on an old one. A second batch is `test-sources-<date>` with its own assets, so the contents of a release never change after a line names its URL, and the rule holds if the owner turns on GitHub's immutable releases.

### 2. The mirror first, the origin second, and the pin decides

A pin that has a mirror is fetched from the mirror first and from its origin second. Each answer is hashed before it is kept: the first whose SHA-256 is the pin's is renamed into place, and the other URL is not asked. A mirror that fails (a network error, an HTTP error, or bytes that are not the pin's) falls back to the origin, with one line on standard error that names the file and why the mirror failed. When neither serves the pinned bytes, nothing is kept, and the one error names both URLs and why each failed. The verification is unchanged: the same SHA-256 from `downloads/SHA256SUMS`, so the trust in the bytes rests on the pin and not on any host.

Why the mirror first. The origin refuses automated fetches today, and the mirror is the project's. With the mirror first, a judge leg asks the origin nothing while the mirror serves, which is what the owner's rule asks of the project toward someone else's server; the origin is asked only when the mirror failed: once when it answers a challenge page (an HTTP 200 with other bytes), which is never retried, since a mismatch is not a network error; and at most three times on a network or HTTP error, as every fetch is today (`fetch()`'s three attempts, curl's `--retry 3` on a transient answer). The order changes who is asked, not what is accepted.

Why the origin stays. It is the provenance of the pin, the URL a reader checks the pin against, and the fallback if the mirror's release is ever deleted. A line keeps its origin URL first and adds the mirror after the name.

Where the mirror URL lives: as an optional third field on the pin's own line in `scripts/00_download.sh`, `tests <origin URL> <name> <mirror URL>` (and `get <origin URL> <name> <mirror URL>` for a build input, once one is mirrored). The two lines become:

```sh
tests https://foss.heptapod.net/openpyxl/openpyxl/-/archive/3.1.5/openpyxl-3.1.5.tar.gz openpyxl-3.1.5-tag.tar.gz https://github.com/ClayGendron/wasi-python/releases/download/test-sources-2026-10-28/openpyxl-3.1.5-tag.tar.gz
tests https://foss.heptapod.net/openpyxl/et_xmlfile/-/archive/2.0.0/et_xmlfile-2.0.0.tar.gz et_xmlfile-2.0.0-tag.tar.gz https://github.com/ClayGendron/wasi-python/releases/download/test-sources-2026-10-28/et_xmlfile-2.0.0-tag.tar.gz
```

Why there. It is the smallest change that covers the two archives and leaves room for more: the URL stays literal, one pin per line, as every other URL in the file is; `fetch.py` already reads its URLs from these lines, so both fetchers read one record; each later mirror is one upload and one field; and files in different mirror releases need nothing more. The scan's existing readers keep working unchanged, since `GET` and `TESTS_LINE` read the first two fields and stop, and `url_errors` finds the name at the end of either URL (READ). The two alternatives were weighed and refused. A URL column in `downloads/SHA256SUMS` would break the file's one format: `shasum -c` reads everything after the two spaces as the file's name, and `release/set_key.py`, MANIFEST's `pin` lines and `fetch.py`'s `pins()` read it as `<sha>  <name>`, so the change would reach the artifact set's MANIFEST and every reader. A `MIRROR` base URL in `scripts/steps/common.sh` and `fetch.py`, applied to a list of names, would be two copies of one value plus a list to keep equal, would bind every mirrored file to one release (which an immutable release refuses to grow), and `00_download.sh` does not source `common.sh`.

A new rule holds the field's shape. `scan.mirror_errors(download_script, repository)` in `tests/harness/scan.py` reads every `get`, `tests` or `research` line with a third field and requires it to be `<repository>/releases/download/<tag>/<name>`, where `<repository>` is the `Repository` URL of `pyproject.toml`'s `[project.urls]`, `<tag>` is `test-sources-YYYY-MM-DD` (Decision 1's dated releases, never a product release's `v` tag), and `<name>` is the line's own second field; a line with more than three fields, a second field that is a URL (a mirror written where the name goes), a mirror on another host, a mirror under another tag shape, or a mirror whose last part is not the pinned name is an error, named. So a mirror is always this project's release asset of the same file, and a typo cannot make every run fall back to the origin unseen.

An archive a forge builds on request has no file behind it; the forge makes it when asked. Twelve pins are such archives: the two on `foss.heptapod.net`, and ten under `github.com/<owner>/<repo>/archive/`, of which three are build inputs that feed the artifact set (`SheenBidi-3.0.0.tar.gz`, `libraqm-0.10.5.tar.gz` and `qhull-8.0.2.tar.gz`, read by `scripts/steps/37_plot_libs.sh`) and seven are test sources (cycler, cloudpickle, threadpoolctl, tomli-w, xlrd, xlsxwriter and pypdf's sample files). Why only two. They are the two that fail, and Heptapod is the forge 067 named as the one that regenerates archives and has changed their bytes. ### 4. One record of the mirror, two fetchers held equal by a row

The mirror URL is written once, on the pin's line in `scripts/00_download.sh`, which both fetchers read. The rule that uses it is written twice, in shell for the build's `00_download.sh` and in Python for the judge's `fetch.py`, because each runs where the other is not used: `00_download.sh` runs on a fresh build host before the build's pinned Python is unpacked, and `fetch.py` runs under uv in every judge leg, the Windows legs included. A unit row holds the two equal (Decision 7).

`scripts/00_download.sh`: `get() { # url name [mirror]` takes an optional third argument, and `tests()` and `research()` pass `"$@"` to `get`, which reads its mirror as `${3:-}`; `set -u` stops a script on an unset `$3`, so a pass-through written `get "$1" "$2" "$3"` would abort on every two-field line. With no mirror, `get` is unchanged but for its `fetched` line. With a mirror it tries the mirror, then the origin, each with today's curl command and flags (`-fsSL --proto '=https' --proto-redir '=https' --tlsv1.2 --retry 3`) into `downloads/<name>.part`, a curl failure caught rather than fatal while another URL remains; it hashes the part with `shasum -a 256` and compares it with the pin, selected by the exact-field rule of `pin_line()` (`awk` on the second field as a string, exactly one line, an error naming the file for none or two); on a match it renames the part into place, and on a miss it deletes the part and keeps the reason (`curl failed (exit N)`, or `SHA-256 <got>, the pin says <sha>`). Each value a check reads is captured into a variable or a file, never through a pipe, since `sh` has no `pipefail`. The end-of-script `shasum -a 256 --ignore-missing -c SHA256SUMS` stays as it is and checks every file again. Every fetch prints `fetched <name> from <url>` (today `fetched <name>`; `tests/unit/test_build_progress.py` reads the prefix only). A mirror failure that the origin covers prints `<name>: the mirror did not serve the pinned bytes (<why>); fetched from the origin` on standard error. Two failures exit 1 with `ERROR: <name>: <mirror URL>: <why>; <origin URL>: <why>`. The header comment says, in words, that a line may name a copy the project keeps, tried first, and that the pin decides.

`tests/upstream/fetch.py`: `GET_LINE` admits the optional third field, `^\s*(?:get|tests) (https://\S+) (\S+)(?: (https://\S+))?\s*$`. `get_urls()` returns `{name: (mirror, origin)}` for a line with a mirror and `{name: (origin,)}` for one without, in the order to try. A new `fetch_first(sha, urls, dest_dir, name)` calls today's `fetch()` for each URL in turn and returns `None` at the first that succeeds; with one URL it returns `fetch()`'s message unchanged (so `tests/unit/test_fetch_trees.py`'s rows, which read `<name>: SHA-256 …`, hold as they are); with two, a mirror failure that the origin covers prints the same standard-error line as the shell, and two failures return `<name>: <mirror URL>: <why>; <origin URL>: <why>`, each `<why>` being `fetch()`'s message after its `<name>: `. `fetch()`'s mismatch text becomes `<name>: SHA-256 <got>, the pin says <sha>` (today it says `kit.txt says` for a `downloads/SHA256SUMS` pin too, which the two-URL message would repeat; the rows read only the prefix `<name>: SHA-256`). `fetch()` keeps its signature, its three attempts on a network error and its pause, and gains one line: `fetched <name> from <url>` on standard output after the rename. `fetch_trees()` and `fetch_files()` call `fetch_first()`. The module docstring says the same in words.

### 6. The kind: build-class, and the same bytes are the proof

It changes `scripts/00_download.sh`, which is the build recipe, so it is build-class and reviewed before it is built (constitution §5.6). It changes no pin, no recipe step and no flag, and the files it lets the judge fetch are never built (Decision 3), so the product's bytes do not move. ## Intent

After this specification, a pinned file may name a copy the project keeps, and both fetchers read that copy first and the original host second. Either way, a file is kept only when its bytes have the pinned SHA-256. The two test sources Heptapod now refuses to serve are read from a GitHub release of this repository, so the pure-Python legs are green again, and they ask Heptapod nothing while the copy serves. The pins, the artifact set and every other download are as they were.

## Scope

In: Decisions 1 to 7. Out:

- changing any pin's hash, or any pin at all;
- a cache of the test sources in Actions: it would be a second copy with its own write scope to reason about (the set cache's scope is already a note in 136), it would not help a run whose key is cold, which is the first run after any pin moves, and the mirror already takes the refusing host out of the path; it is a later improvement if GitHub's own downloads prove unreliable, judged by red legs, not by guess;
- other hosts: PyPI, GitHub's archives, raw files and release assets, the Debian snapshots, GNOME, python.org, sqlite.org, sourceware.org and savannah keep their one URL; a mirror for any of them is its own reviewed change, one upload to a new dated release and one field on its line;
- `fetch.py`'s redirect policy: `urllib` follows redirects as it does today; the pin holds the bytes;
- the repository's settings (immutable releases, tag rulesets), which are the owner's;
- retiring an origin URL.
