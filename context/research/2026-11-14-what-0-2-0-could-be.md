# What 0.2.0 could be

- **Status:** research, 2026-11-14. A proposal at the owner's request ("what does wasi-python 0.2.0 look like? How can we optimize the tool and have it compete in the market better"). It commits the project to nothing: no specification, no pin, no roadmap entry. The choices are in section 7.
- **Owner:** Clay Gendron
- **Researcher:** an agent (Claude Opus), with a market-research sub-agent for the web survey. It wrote none of the code it reads. Box: one session. Nothing was built or run; only the repository and web pages were read.
- **The question:** after 0.1.5 (the Rust build pipeline with orjson and pydantic-core, unwinding panics, eight packages, the release-path fixes), what should 0.2.0 carry so the runtime competes in the market for running agent-written Python, and what should it leave out?
- **Stands on:** `2026-10-18-a-rust-core-with-js-and-python-wrappers.md`, `2026-10-22-how-the-market-describes-sandboxed-python.md` (it extends that memo and does not repeat it), `2026-10-23-a-rust-runner-against-wasmtime-py-on-speed.md`, `2026-10-27-a-starting-image-measured.md`; decision 96 in `decisions.md`; the 0.1.5 scope the owner agreed on 2026-11-14.

Labels: **READ** is a claim taken from a page that was opened, with its link, or from this repository, with its path; vendor numbers are vendor claims. **INFERRED** is the researcher's reasoning. Nothing here is EXECUTED. Pages were read on 2026-11-14 unless a date says otherwise.

## The short version

0.2.0 should turn wasi-python from a Python package into a sandbox any agent backend can embed (INFERRED):

1. **A Rust core, published as the `wasi-python` crate**, carrying the runner's limits, grants, door, tools, sessions and snapshots, with a conformance suite that requires the Python runner's `fuel_used` and outputs.
2. **An npm package on that core, through napi-rs.**
3. **A pandas-ready first call in milliseconds by default**, from a copy-on-write image of a package snapshot the release ships.

Around them: framework adapters, a public benchmark that corrects the record, and an outside security review. WASI CPython as a category has a reputation for slow starts (READ, below); wasi-python already answers it with a 12 ms start and snapshots, and 0.2.0 makes that answer the default and visible. That being usable only from Python is the bigger competitive gap is the researcher's own reading of the comparison table in section 2 (INFERRED).

What bears on 0.2.0:

- **Monty's comparison is out of date about this runtime.** Its WASI row says C extensions "need their own WASI build" and snapshotting is "no", measured 2026-09-03 on CPython 3.14.7 WASI and wasmtime 48 (READ, [alternatives](https://pydantic.dev/docs/monty/reference/alternatives/)). wasi-python has both, and session checkpoint and fork (READ, `CHANGELOG.md`). That row describes generic WASI CPython, not this project (INFERRED).
- **WASI CPython has a slow-start reputation that wasi-python already answers.** Mozilla.ai's otari has an open feature proposal for in-process code execution on Monty that dismisses "Pyodide or WASI CPython" generically for "seconds of cold start per request and no snapshotting"; it never names wasi-python, and no decision is recorded (READ, [otari #1383](https://github.com/mozilla-ai/otari/issues/1383)). wasi-python starts in 12 ms and has snapshots, so otari is a possible prospect to show the benchmark to (INFERRED).
- **Pyodide sandboxes broke in public.** Cyera's research (DEF CON 34, 2026-08-07) escaped seven Pyodide products through `ctypes.CDLL(None)`, among them n8n (CVSS 9.9) and smolagents; mcp-run-python carries CVE-2026-25905, the `js` module reaching the host (READ, [Cyera](https://www.cyera.com/research/sandcastles-not-sandboxes-how-one-architectural-flaw-exposed-seven-products), [advisory](https://advisories.gitlab.com/pypi/mcp-run-python/CVE-2026-25905/)). smolagents 1.26.0 removed its Wasm executor, with no reason in its notes (READ, [release](https://newreleases.io/project/github/huggingface/smolagents/release/v1.26.0)).
- **No agent framework lists a Wasm backend.** LangChain's Deep Agents, the OpenAI Agents SDK, smolagents, Mastra and Vercel's AI SDK list hosted VMs or Docker, and each has an interface a third party can implement (READ, [Deep Agents](https://docs.langchain.com/oss/python/deepagents/sandboxes), [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/sandbox/clients/), [smolagents](https://huggingface.co/docs/smolagents/en/reference/python_executors.md), [Mastra](https://mastra.ai/docs/sandbox/overview.md)).
- **Node cannot be the wall itself.** `node:wasi` still says "do not rely on it to run untrusted code"; no maintained wasmtime binding is on npm; exnref is unflagged only from Node 25 (READ, [Node](https://nodejs.org/api/wasi.html), the npm registry, the Emscripten pull request the sub-agent cited). So an npm package needs its own native binding (INFERRED).
- **wasmtime 51 is near:** 51.0.0-rc.1 was tagged 2026-11-05; 50.0.1 (2026-10-29) fixed five advisories (READ, [releases](https://github.com/bytecodealliance/wasmtime/releases)).

## 3. Positioning

0.2.0 should make wasi-python the sandbox an agent backend reaches for when the model's code needs `import pandas` and the team does not want to rent a VM: real CPython with the data stack, inside its own server, from Python, Node or Rust (INFERRED).

**Who it is for** (INFERRED): teams building agents into their own web backend that must run model-written analysis code on their users' files (questions over CSVs and spreadsheets, charts, reports, document extraction) and want no per-run bill, data that never leaves their server, and no Docker to operate.

**Why they would pick it** (INFERRED, from section 2):

- **Over Monty:** Monty is faster and in more languages, but runs no third-party package; wasi-python is the step up when the model writes numpy, pandas or scikit-learn.
- **Over hosted VMs:** the same capability for this workload at no per-call cost, no egress by default, nothing sent off the machine. VMs keep pip, threads and native speed.
- **Over Wasmer's SDK:** the scientific stack compiled in and judged by each package's own suite inside the sandbox, limits on by default, reproducible signed builds. Wasmer has a wider index, pip and more languages today, so this needs a measured comparison, not a claim.
- **Over boomslang:** scipy, scikit-learn and statsmodels, starts in milliseconds rather than minutes, packages on PyPI and npm.
- **Over Pyodide:** no JavaScript engine for the guest to reach and none of the `ctypes` escape class, once an outside review backs the claim.

**A line for the README and the npm page:** "Real CPython with pandas, scipy and scikit-learn, sandboxed inside your own process. Python, Node and Rust." It names the libraries, which no competitor's headline does (the Oct 22 memo, §2), and each word is true once 0.2.0 ships the Node and Rust packages.

## 4. Ranked features and optimizations

Sizes, in the project's units: S is one specification, M two or three, L a track of several with their pre-build reviews. Every size and gain is INFERRED.

| Rank | What | Why | Size |
|---|---|---|---|
| 1 | **A Rust core as the `wasi-python` crate**: `run`, limits, grants and mounts, the door and tool protocol, sessions, snapshots, displays and streamed output on the `wasmtime` crate, carrying the runner's two wasmtime fixes; a conformance suite runs the judge's jobs through it and requires the Python runner's `fuel_used`, outputs and records | the shared core decision 96 asks for, and the only way Rust and Node users get the runner's protections; the Oct 23 spike built most of a runner in 480 lines (READ) | L |
| 2 | **An npm package on that core, through napi-rs**: prebuilt for Linux x64 and arm64, macOS arm64 and Windows x64; Node 22 or later (wasmtime brings its own exception handling, so no Node 25 floor); tools as async functions; TypeScript types for every result | Node is where many agent web backends run, and nothing on npm runs untrusted Python with pandas safely: `node:wasi` disclaims it, Pyodide sandboxes were escaped, Monty has no packages (READ, section 2) | L |
| 3 | **A pandas-ready call in milliseconds, by default**: the Rust core turns a `Snapshot` into a module whose memory is mapped copy-on-write and instantiates it from wasmtime's pooling allocator; the release ships a ready package snapshot | the Oct 27 memo measured a pre-initialised module instantiating in 0.08 ms with no page fault, against about 15 ms for today's copy and 725 ms for `import pandas` cold (READ); target under 5 ms | M |
| 4 | **Framework adapters**: an OpenAI Agents SDK sandbox client, a LangChain Deep Agents `BaseSandbox`, a smolagents executor, and Vercel AI SDK and Mastra tools on the npm package | buyers meet sandboxes through these lists, and none lists a Wasm backend (READ, section 2) | S each |
| 5 | **A published, reproducible benchmark** against the field (section 6), then a note to Pydantic asking it to correct its WASI row | the comparison people quote is out of date about this runtime; constitution §4.10 already asks every number to carry its command | S to M |
| 6 | **Security evidence buyers can cite**: a page with tests showing why the Pyodide escape class cannot happen here (no `dlopen`, `ctypes` loads nothing, two imports only), and an outside review or a paid bounty before the tag | trust is the category's open wound this year; Monty's reputation rests on three public bounty rounds (READ, the Oct 22 memo) | S, and budget |
| 7 | **Parquet through pyarrow** | the most visible package gap: Pyodide, Wasmer's index and Anthropic's container carry it (READ); a large C++ build without threads | L, spike first |
| 8 | **Wasm SIMD in numpy's loops and OpenBLAS** (`-msimd128`), measured on numpy's own kernels | compute is 1.3 to 2.3 times native partly for want of SIMD (READ, performance page); the gain is unmeasured | M, measure first |
| 9 | **Smaller downloads**: compressed artifacts in the npm and crate packages, unpacked once into a checked cache | a 112 MB wheel is paid by every CI job and serverless deploy; the xz assets are 6 to 22 MB each (READ, performance page) | S |

The Python wheel keeps its frozen API either way. The recommendation is to share the conformance suite in 0.2.0 and move the wheel onto the core in 0.3 if the core holds (INFERRED; the Oct 18 memo found the gain small for Python callers).

## 5. What to cut or defer

- **The component model and WASI 0.3.** PEP 11's Tier 2 row names `wasm32-unknown-wasip3`, while its table has 3.15 on WASI 0.1 (READ, [PEP 11](https://peps.python.org/pep-0011/)); moving now re-ports every package for no gain a buyer sees (INFERRED). Revisit when CPython ships a wasip3 build.
- **A browser build.** Pyodide owns it (constitution §3).
- **pip in the guest, threads, polars and duckdb.** Each breaks the sealed set or needs wasi-threads; pyarrow stays the one data-format bet (INFERRED).
- **The Python wheel off wasmtime-py in 0.2.0.** Let the core prove itself on Node first (INFERRED).
- **Packages for their own sake.** After 0.1.5's eight, a package joins when a benchmark task or a user asks for it (INFERRED).
- **Bun and Deno as promised targets.** Best effort, Node first (READ, the Oct 18 memo).

## 6. How to measure it against the field

One scripted benchmark, kept in a research memo and re-run before each release, each number beside its command (§4.10); wall-clock stays a benchmark fact, never a test (§4.9).

| Task | What it shows | Run on |
|---|---|---|
| Empty call, cold process and warm | start cost and first compile | wasi-python (Python, Node, Rust), Monty, Wasmer SDK, boomslang, Pyodide on Node, Docker, Daytona, E2B |
| `import pandas`, a 10 MB CSV read, a groupby | the real first call for data work | everything with pandas |
| A scikit-learn fit and predict on 100,000 rows | compute against native | everything with scikit-learn, and native CPython |
| 1,000 tool round trips | the host boundary, code mode | wasi-python, Monty, hosted SDKs |
| 100 concurrent sessions | memory a sandbox, throughput a core | the in-process options |
| Cost per 1,000 runs | the bill | hosted list prices against zero plus host CPU |
| An escape suite | the Pyodide `ctypes` class, `__subclasses__` reflection, host imports | wasi-python, Pyodide sandboxes |

Targets for 0.2.0 (INFERRED, to be measured): a pandas-ready call under 5 ms from the shipped snapshot; under 50 MB of host memory per idle sandbox; Node and Python within 5% of each other on every task; a door round trip near the spike's 1 µs.

## 7. Questions for the owner

Each has a default, so a yes to all is a workable plan.

1. **0.2.0 is the Rust core plus Node, with the Python wheel on wasmtime-py?** Default: yes; the wheel moves onto the core in 0.3 if conformance holds.
2. **How the npm package carries about 250 MB of artifacts.** Bundling is what the mission's "no install step" implies; npm's size limit was not checked. Default: one package per platform holding the compressed set, checked by SHA-256 on first unpack; a first-use download only if npm refuses the size.
3. **The names** on crates.io and npm; availability was not checked.
4. **Where the framework adapters live.** §4.5 keeps embedder names out of this repository and §3 says it ships no agent or server. Default: a separate repository of adapters on the public API.
5. **pyarrow in 0.2.0, or a spike now and the build later?** Default: a spike first; it ships only if the build is clean.
6. **Budget for an outside security review or a public bounty** before the tag. Default: yes, scoped to the door, grants and the Rust core.
7. **A public comparison that names competitors**, and a note to Pydantic about its WASI row. Default: yes, once the benchmark is reproducible.
8. **The order.** Default: 0.1.5 as agreed, 0.1.6 for wasmtime 51, then 0.2.0; the core can be built beside 0.1.5, since it touches none of its files, and land after 0.1.6.

## Where it stopped

- Not checked: npm's package size limit and the free names on npm and crates.io; download counts for wasi-python and for Monty on npm and PyPI (the statistics services refused this session); whether Wasmer's SDK runs numpy; otari's final choice.
- Inferred, not measured: every "why they would pick it" line; the 5 ms and 50 MB targets; that copy-on-write images cut a sandbox's memory; that SIMD helps numpy; that pyarrow builds without threads.

## One line

0.2.0 should ship one Rust core as a crate and an npm package, with a pandas-ready first call in milliseconds by default, so that the only in-process sandbox with real CPython and the scientific stack can be embedded from Node and Rust as well as Python, and should back its claims with a public benchmark and an outside review.
