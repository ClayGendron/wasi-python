# The scope of 0.2.0: a Rust crate and an npm package, with the numbers they must hit

- **Status:** research, 2026-11-17. A scope proposal at the owner's request ("I want to work more on defining the scope of 0.2.0. I want research and data to back up our decisions. I want to focus on having it available in ts and rust", then "the research and data should be on our features and benchmarks we should hit"). It commits the project to nothing: no specification, no pin, no roadmap entry. The choices left to the owner are in section 6.
- **Owner:** Clay Gendron
- **Researcher:** an agent (Claude Opus), with a web-research sub-agent for the registry and framework survey. It wrote none of the code it reads.
- **The question:** which features the 0.2.0 Rust crate and npm package ship, each backed by evidence of need, and which measured targets they must hit, each with today's baseline and what comparable projects achieve.
- **Stands on:** `2026-11-14-what-0-2-0-could-be.md` (the direction: a Rust core, an npm package on it, a pandas-ready start; this memo turns it into scope and numbers and does not repeat its market survey), `2026-10-23-a-rust-runner-against-wasmtime-py-on-speed.md`, `2026-10-27-a-starting-image-measured.md`, `2026-11-16` weekly survey in the project files; decision 96 in `decisions.md`; `docs/how-to/embed-from-other-languages.md`.
- **Evidence:** the folder of the same name beside this memo. `harness/rust` (a Rust host on the `wasmtime` 50.0.2 crate: compile, load, instantiate, restore by copy, by `mmap` and by a copy-on-write module, sessions kept alive), `harness/js` (Node and Bun on `node:wasi`, for measurement only), `harness/py` (the Python baseline and the size measurements), and `results/` with every run's raw output. Large files (the wheel, images, compiled modules) stayed in the session's scratch folder, never committed.
- **Machine:** Linux x86_64, Intel Xeon at 2.10 GHz, 4 vCPU, 15 GiB, one cloud container. It is slower than the M1 Pro of the earlier memos: `import pandas` cold takes 1.57 s here against 0.73 s there. Compare numbers within this memo, not across machines.
- **Artifacts:** the published 0.1.4 wheel from PyPI, `wasi_python-0.1.4-py3-none-any.whl`, SHA-256 `e34d6bf4c3c7ad6fbbcf3c81a6a418cfc24eb47129e715a23a7f8076a11da079`, as PyPI lists it. 0.1.5 was not yet on PyPI when this ran.

Labels: **EXECUTED** is run and seen here, with its file under `results/`. **READ** is taken from a page that was opened, with its link, or from this repository, with its path; vendor numbers are vendor claims. **INFERRED** is the researcher's reasoning. Pages were read on 2026-11-17.

## The short version

1. **The Rust host already hits the headline number** (EXECUTED). On the `wasmtime` crate, a call that starts from a copy-on-write pandas image, imports pandas and runs a groupby takes **6.4 ms** at the median and 9.5 ms the first time. The same call costs 58 ms through today's Python runner from a package snapshot, and 1,609 ms from a cold import. An idle session after that call holds **4.7 MiB** of private memory, against 66 MiB when the image is copied in.
2. **The cost that 0.2.0 must hide is the first compile** (EXECUTED). Compiling the 110 MB snapshot binary takes 31 s and peaks at 2.3 GB of memory on this machine, in Rust and in Python alike. Turning Cranelift's optimiser off saves only 4 s and makes numpy 43% slower. So the packages should carry, or fetch, a precompiled module per platform: loading one takes 11 to 13 ms.
3. **The npm package must be a native addon, not WebAssembly in V8** (EXECUTED, READ). Node 22's own engine crashes on `import pandas`; Bun's `node:wasi` cannot even link the binary; Node documents `node:wasi` as unsafe for untrusted code; V8 has no fuel meter. A napi-rs addon on the same Rust core keeps the runner's limits, fuel counts and protections on Node, and is best-effort on Bun.
4. **Neither registry can carry the artifacts in the main package** (READ). crates.io caps a crate at 10 MB (50 MB hard cap with an exception). npm refuses uploads near 256 MiB. Measured, the set compresses to about 58 MB with zstd, and a precompiled module to about 57 MB. So the crate fetches the set by pinned hash, and npm splits it the way esbuild and Pydantic's Monty do: a small main package and one optional package per platform.
5. **Scope** (INFERRED, from the evidence below): eight features are in, framed as parity with the Python runner's core and a fast default start (section 2); browser, edge runtimes, a JavaScript-only host, Deno as a promised target, the Python wheel on the core, adapters as packages, pyarrow and SIMD are out (section 4); twelve benchmark targets are in section 3.

Three things the table shows (INFERRED from it):

- **The image copy, not the guest, is today's cost.** From the pandas image the guest's own work is 3.6 ms; the copy of 68.8 MB into fresh memory is 42 ms of page faults. Copy-on-write removes that and leaves the private memory a session actually writes, about 5 MiB.
- **A copy-on-write start does not need a module per image.** Mapping the image file privately over linear memory (`harness/rust`, `MMAP=1`) gave 7.1 ms against 6.4 ms for a module rebuilt around the image, with the same 5 MiB private per session, and no 31 s compile per image. So user-made snapshots can start this fast too. The spike maps over wasmtime's memory with `libc::mmap`; a product would do it through wasmtime's own memory hooks (the `LinearMemory` and `MemoryCreator` API, which wasmtime 51 adjusts, READ, the 2026-11-16 weekly survey), and Windows needs its own mapping call. Neither was built here.
- **The Rust host halves the fixed cost of a call** (22.8 to 10.4 ms) and removes 0.5 s from a new process's first call, which is wasmtime-py's import and its slower load path. The 2026-10-23 memo found the same shape on the M1 (READ).

## 2. Features in 0.2.0

The rule for what is in: what the Python runner already offers that an agent backend needs on every call, plus the fast start, on one Rust core that both packages wrap. Each row names its evidence.

| # | Feature | In the crate and the npm package | Evidence |
|---|---|---|---|
| F1 | **One run, with the runner's limits** | code or argv, env, stdin; fuel, deadline, memory, output bytes, open files and file calls; the result's exit code, trap, fuel used, truncation, stdout and stderr | the Python `run()` signature and its `Completed` (READ, `src/wasi_python/runner.py`); Monty's limits are the same kind (`maxMemory`, `maxFeedDurationSecs`, READ, [Monty limits](https://pydantic.dev/docs/monty/concepts/resource-limits/)) |
| F2 | **A pandas-ready start by default** | the release ships one data image (numpy and pandas imported) and the host starts every call from it copy-on-write; `snapshot: false` and user images remain | section 1: 6.4 ms against 1,609 ms; Pyodide's cold start is about 2.7 s and Cloudflare's snapshotted Python Worker 1.0 s (READ, the 2026-11-14 memo; [Cloudflare](https://blog.cloudflare.com/python-workers-advancements)); a TypeScript agent project gave up on Pyodide for pandas on spreadsheets citing a 5 to 8 s start (READ, [sql-fs #118](https://github.com/Hazzng/sql-fs/issues/118)) |
| F3 | **Package snapshots made, saved and loaded** in the Python runner's file format, so one file works from Python, Rust and Node | `makePackageSnapshot`, `save`, `load`, `snapshot:` on run and session | the 2026-10-27 memo's design (READ); Monty has `snapshot.dump` and `loadSnapshot` in its TypeScript API (READ, [Monty JS](https://pydantic.dev/docs/monty/quickstart/javascript/)) |
| F4 | **Tools over the door** | Rust closures and async functions; JavaScript async functions with a JSON schema; the gate and the tool-call caps | Monty's `externalLookup` is the same shape and has 103,207 npm downloads a week (READ, `api.npmjs.org`); the 2026-10-23 memo measured a Rust door round trip at about 1 µs against 37 to 50 µs in Python (READ) |
| F5 | **Grants and mounts, with async providers** | folders read-only or writable, and mounts served from the embedder's code, awaited in JavaScript | agent frameworks hand a sandbox files through their own calls, not a host folder: LangChain's `BaseSandbox` needs `uploadFiles` and `downloadFiles`, Mastra's `WorkspaceSandbox` an optional `filesystem` (READ, [deepagents](https://reference.langchain.com/javascript/deepagents/backends/BaseSandbox), [Mastra](https://mastra.ai/reference/workspace/sandbox.md)); a provider that blocks on Node's single thread would stall the server (INFERRED) |
| F6 | **Sessions**: turns that keep state, checkpoint and fork | `Session` in both | the Python `Session` (READ, `src/wasi_python/runner.py`); Monty's pool is session-shaped (`pool.checkout`, `session.feedRun`, READ); section 1: a kept session costs about 5 MiB private |
| F7 | **Streaming output and cancellation** | an output callback; a cancel token in Rust and an `AbortSignal` in JavaScript | Python's `on_output` and `cancel` (READ); Vercel's just-bash cancels with an `AbortSignal`, Monty's pool with a `requestTimeout`, Cloudflare's code mode with a `timeout` (READ, the sub-agent's survey of [just-bash](https://cdn.jsdelivr.net/npm/just-bash@2.14.0/README.md), Monty and [codemode](https://developers.cloudflare.com/agents/tools/codemode/api-reference/)) |
| F8 | **A conformance suite**: the judge's jobs run through the Rust core and the Node addon must give the Python runner's `fuel_used` and outputs | in CI, not in the packages | the 2026-11-14 memo's rank 1 (READ); fuel is the project's measure of work and repeats across hosts on one wasmtime (READ, `docs/explanation/performance-and-size.md`) |

**How each package is built and shipped** (INFERRED, from the READ facts in the rows):

- **The crate, `wasi-python`**, is the core on the `wasmtime` crate. It does not bundle the artifacts: crates.io caps a `.crate` at 10 MB, with exceptions up to a 50 MB hard cap (READ, [Cargo book](https://doc.rust-lang.org/cargo/reference/publishing.html), [crates.io #40](https://github.com/rust-lang/crates.io/issues/40)), and the set is 279 MB unpacked. It takes an artifacts folder, from an environment variable or the caller, and offers an opt-in `download` feature that fetches the release's assets by their pinned SHA-256 into a cache, as `ort` does for its runtime (READ, [ort's build.rs](https://docs.rs/crate/ort/1.16.3/source/build.rs)). A network fetch inside `build.rs` breaks offline and docs.rs builds, so it should happen at run time or on an explicit call.
- **The npm package, `wasi-python`**, is a napi-rs addon on the crate. napi-rs supports Node 22.13 and later, tests 22, 24 and 26, treats Bun as best effort and warns against assuming Deno (READ, [napi-rs](https://napi.rs/docs/more/support-compatibility)). It follows the per-platform pattern: a small main package with TypeScript types and one optional dependency per platform, as esbuild (26 platform packages, 11.4 MB each for Linux x64) and Monty (26.7 MB main package plus five platform packages of 37 to 44 MB) do (READ, the npm registry). The platform-free artifacts (the snapshot binary and the stdlib zip, about 58 MB with zstd) go in one shared package and are unpacked once into a checked cache.
- **Five platforms**, the set Monty ships: Linux x64 and arm64 (glibc), macOS x64 and arm64, Windows x64 (READ, the npm registry). musl (Alpine) waits for a user who asks (INFERRED).
- **An API sketch**, to be settled in the specification (INFERRED):

```typescript
import { run, Session } from "wasi-python";

const result = await run("import pandas as pd; print(pd.read_csv('/data/x.csv').describe())", {
  grants: [{ host: "./inputs", guest: "/data" }],
  limits: { deadlineMs: 10_000, memoryBytes: 1 << 30 },
  tools: { lookup: { schema, call: async (args) => db.find(args.id) } },
  signal: AbortSignal.timeout(15_000),
});
console.log(result.exitCode, result.stdout, result.fuelUsed);
```

```rust
let runtime = wasi_python::Runtime::new(wasi_python::Artifacts::from_env()?)?;
let done = runtime.run(
    wasi_python::Call::code("print(1)")
        .deadline(Duration::from_secs(10))
        .grant("/data", "./inputs", Access::ReadOnly),
)?;
assert_eq!(done.exit_code, Some(0));
```

**Later in the 0.2 line, not in 0.2.0** (INFERRED): typed results (`results=True`) and figures as PNG, `packages()` and `stats()`. They exist in Python and matter, but none blocks a first embedding, and each is a serialisation the conformance suite must pin first.

## 4. Out of 0.2.0, and why

| Out | Why |
|---|---|
| **A browser build, Cloudflare Workers, Vercel Edge** | A Worker's script is capped at 64 MiB and its isolate at 128 MB of memory, and Workers' WASI is "experimental … only some syscalls" (READ, [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers Wasm](https://developers.cloudflare.com/workers/platform/webassembly/)); the snapshot binary alone is 110 MB. No native addon runs there. The constitution leaves the browser to Pyodide (READ, §3). |
| **A JavaScript-only host** (the module in V8 or JavaScriptCore, no addon) | Node 22.23 runs `print()` but crashes with a segmentation fault on `import pandas`, with or without `--experimental-wasm-exnref` (EXECUTED, `js-hosts.txt`); its early exnref carries a 17-fix backport (READ, the sub-agent's survey). Bun's `node:wasi` cannot link the binary (EXECUTED). Node says not to rely on `node:wasi` for untrusted code (READ, [Node](https://nodejs.org/api/wasi.html)), and V8 has no instruction meter, so fuel and its parity (T9) would be lost (READ, the sub-agent found none). Node 24 and 26 were not run here. |
| **Deno as a promised target** | Deno's `node:wasi` is stubs, and napi-rs warns against inferring Deno support (READ, [Deno](https://docs.deno.com/api/node/wasi/), napi-rs). Best effort, like Bun. |
| **The Python wheel on the Rust core** | Python callers gain least (the 2026-10-18 memo, READ); the conformance suite (F8) has to prove the core first. 0.3, as the 2026-11-14 memo proposed. |
| **Framework adapters as packages** | The interfaces differ in shape: LangChain's `BaseSandbox` and Vercel's bash tool assume a shell, Mastra's `executeCommand` takes a command line, Cloudflare's `Executor` runs JavaScript (READ, the sub-agent's survey). A documented example per framework on the public API comes first; packages follow demand, outside this repository (§4.5). |
| **pyarrow, Wasm SIMD, more packages** | Unchanged from the 2026-11-14 memo: each is a build track of its own and none bears on the Rust or TypeScript surface. |
| **WASI 0.3 and components** | Unchanged from the 2026-11-14 memo. |

## 5. What the scope costs, roughly

Sizes in the project's units (S is one specification, M two or three, L a track of several), INFERRED. ## 6. Questions for the owner

Each has a default, so a yes to all is a workable plan.

1. **How a first run gets its compiled module.** (a) Ship a precompiled module in each platform package: about 140 MB a platform, first call under 1.5 s and no 2.3 GB spike. (b) Compile on first use: about 80 MB a platform, one 31 s compile per machine and version. (c) Fetch the precompiled module from the release on first use: small packages, a network step at first run. Default: (a) for npm, since serverless and small containers cannot pay the spike; (c) behind the crate's `download` feature. On Lambda, whose zip deployments have a 250 MB unzipped limit (READ, Lambda limits), (a) fits only because the packages keep everything compressed (about 135 MB, INFERRED) and unpack into a cache in `/tmp`, at about 0.5 s a file on each cold machine; an unpacked 299 MB module would not fit.
2. **The names.** `wasi-python` is free on crates.io and npm, and so is `@wasi-python/core` (READ, the registries' APIs, 2026-11-17). Default: `wasi-python` on both, with the platform packages under an `@wasi-python` npm scope, which the owner's npm account must create.
3. **The Node floor.** Default: Node 22.13 or later, tested on 22, 24 and 26, as napi-rs is; Bun best effort; Deno not promised. The addon brings its own engine, so V8's exception handling sets no floor.
4. **The Python wheel stays on wasmtime-py in 0.2.0** (the 2026-11-14 memo's first question, still open). Default: yes.

## Where it stopped

- Not built: the napi-rs addon. Its size (T10 uses the 18.4 MB bench binary as a stand-in) and the cost of a JavaScript tool call across Node-API (T7's 50 µs) are unmeasured.
- Not run: Node 24 and 26 (fetching their binaries was refused in this session), macOS and Windows hosts, the door round trip and concurrency on this machine (both cited from the 2026-10-23 memo on an M1).
- The copy-on-write start by `mmap` maps over wasmtime's memory from outside its API; it shows the cost, not the design. Windows mapping was not tried.
- The images were made by the 0.1.4 runner and restored by a host that preopens only the stdlib folder and a root; a product host must repeat the image's preopen table, as the 2026-10-27 memo found (READ).
- One machine, one container, other work idle; times are benchmark facts of it. Fuel counts repeat on any machine with the same wasmtime.

## One line

0.2.0 should ship one Rust core as the `wasi-python` crate and a napi-rs npm package with parity on run, limits, tools, mounts, sessions and snapshots, start every call from a copy-on-write pandas image, and gate the release on twelve numbers led by a pandas-ready call under 10 ms, which the Rust host here already did in 6.4 ms.
