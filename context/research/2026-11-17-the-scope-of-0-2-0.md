## The short version

1. **Starting from a copy-on-write pandas image brings the groupby under 10 ms on both hosts** (EXECUTED, section 7.1). The 0.1.4 Python runner takes 58 ms at the median when it copies a package snapshot into memory. With the same copy-on-write module, the median falls to **7.5 ms through wasmtime-py** and **6.4 ms on the Rust crate**. The crate took 9.5 ms on its first call. On the crate an idle session holds **4.7 MiB** of private memory after the call, against 66 MiB when the image is copied in.
2. **The cost that 0.2.0 must hide is the first compile** (EXECUTED). Compiling the 110 MB snapshot binary takes 31 s and peaks at 2.3 GB of memory on this machine, in Rust and in Python alike. Turning Cranelift's optimiser off saves only 4 s and makes numpy 43% slower. So the packages should carry, or fetch, a precompiled module per platform: loading one takes 11 to 13 ms.
3. **The npm package must be a native addon, not WebAssembly in V8** (EXECUTED, READ). Node 22's own engine crashes on `import pandas`; Bun's `node:wasi` cannot even link the binary; Node documents `node:wasi` as unsafe for untrusted code; V8 has no fuel meter. A napi-rs addon on the same Rust core keeps the runner's limits, fuel counts and protections on Node, and is best-effort on Bun.
4. **Neither registry can carry the artifacts in the main package** (READ). crates.io caps a crate at 10 MB (50 MB hard cap with an exception). npm refuses uploads near 256 MiB. Measured, the set compresses to about 58 MB with zstd, and a precompiled module to about 57 MB. So the crate fetches the set by pinned hash, and npm splits it the way esbuild and Pydantic's Monty do: a small main package and one optional package per platform.
5. **Scope** (INFERRED, from the evidence below): eight features are in, framed as parity with the Python runner's core and a fast default start (section 2); browser, edge runtimes, a JavaScript-only host, Deno as a promised target, the Python wheel on the core, adapters as packages, pyarrow and SIMD are out (section 4); twelve benchmark targets are in section 3.
6. **The numbers hold on wasmtime 51; the files grew about 7%** (EXECUTED 2026-11-23, section 7.8). Calls are unchanged within this machine's noise: the pandas groupby is 6.9 to 7.9 ms on the shipped 0.1.6 binary, and an empty call from the pandas image is 1.8 ms. The compile is 38 to 41 s (36 s for wasmtime 50 on the same day). A module compiled by one wasmtime is refused by the other, so every engine bump re-ships the npm platform packages. With 0.1.6's bigger binary and stdlib, a platform download is about 135 MB (unmetered module only), 161 MB (plus the binary, so a metered module compiles on first use) or 219 MB (both precompiled). Question 1's pick does not change.
7. **Eryx already ships a Rust crate, a Python wheel and an npm package** (READ by a sub-agent, 2026-11-23, section 8). It runs CPython 3.14 from a wizer snapshot, copy-on-write, and claims about 1 ms per sandbox from a factory and 1.6 to 1.8 ms per execution, with no stated hardware. It has no published pandas or scikit-learn build and needs a JSPI-capable Node (24 with a flag, or 26). wasi_python's edge is the shipped data stack, Python 3.15, Node 22, and fuel that repeats across hosts. The targets now include an empty call at or under 3 ms (T2b), crash containment (T13) and a default memory cap (T14). Section 9 orders the work into five milestones.

Three things the table shows (INFERRED from it):

- **The image copy, not the guest, is today's cost.** From the pandas image the guest's own work is 3.6 ms; the copy of 68.8 MB into fresh memory is 42 ms of page faults. Copy-on-write removes that and leaves the private memory a session actually writes, about 5 MiB.
- **A copy-on-write start does not need a module per image.** Mapping the image file privately over linear memory (`harness/rust`, `MMAP=1`) gave 7.1 ms against 6.4 ms for a module rebuilt around the image, with the same 5 MiB private per session, and no 31 s compile per image. So user-made snapshots can start this fast too. The spike maps over wasmtime's memory with `libc::mmap`; a product would do it through wasmtime's own memory hooks (the `LinearMemory` and `MemoryCreator` API, which wasmtime 51 adjusts, READ, the 2026-11-16 weekly survey), and Windows needs its own mapping call. Neither was built here.
- **The Rust host halves the fixed cost of a call** (22.8 to 10.4 ms) and removes 0.5 s from a new process's first call, which is wasmtime-py's import and its slower load path. The 2026-10-23 memo found the same shape on the M1 (READ).

The rule for what is in: what the Python runner already offers that an agent backend needs on every call, plus the fast start, on one Rust core that both packages wrap. Each row names its evidence.

**How each package is built and shipped** (INFERRED, from the READ facts in the rows):

- **The crate, `wasi-python`**, is the core on the `wasmtime` crate. It does not bundle the artifacts: crates.io caps a `.crate` at 10 MB, with exceptions up to a 50 MB hard cap (READ, [Cargo book](https://doc.rust-lang.org/cargo/reference/publishing.html), [crates.io #40](https://github.com/rust-lang/crates.io/issues/40)), and the set is 279 MB unpacked. It takes an artifacts folder, from an environment variable or the caller, and offers an opt-in `download` feature that fetches the release's assets by their pinned SHA-256 into a cache, as `ort` does for its runtime (READ, [ort's build.rs](https://docs.rs/crate/ort/1.16.3/source/build.rs)). A network fetch inside `build.rs` breaks offline and docs.rs builds, so it should happen at run time or on an explicit call.
- **The npm package, `wasi-python`**, is a napi-rs addon on the crate. napi-rs supports Node 22.13 and later, tests 22, 24 and 26, treats Bun as best effort and warns against assuming Deno (READ, [napi-rs](https://napi.rs/docs/more/support-compatibility)). It follows the per-platform pattern: a small main package with TypeScript types and one optional dependency per platform, as esbuild (26 platform packages, 11.4 MB each for Linux x64) and Monty (26.7 MB main package plus five platform packages of 37 to 44 MB) do (READ, the npm registry). The platform-free artifacts (the snapshot binary and the stdlib zip, about 58 MB with zstd) go in one shared package and are unpacked once into a checked cache.
- **Five platforms**, the set Monty ships: Linux x64 and arm64 (glibc), macOS x64 and arm64, Windows x64 (READ, the npm registry). musl (Alpine) waits for a user who asks (INFERRED).
- **An API sketch**, to be settled in the specification (INFERRED):

```typescript
import { run, Session } from "wasi-python";

const result = await run("import pandas as pd; print(pd.read_csv('/data/x.csv').describe())", {
  grants: [{ host: "./inputs", guest: "/data" }],
  limits: { deadlineMs: 10_000, memoryBytes: 1 << 30 },
  tools: { lookup: { schema, call: async (args) => db.find(args.id) } },
  signal: AbortSignal.timeout(15_000),
});
console.log(result.exitCode, result.stdout, result.fuelUsed);
```

```rust
let runtime = wasi_python::Runtime::new(wasi_python::Artifacts::from_env()?)?;
let done = runtime.run(
    wasi_python::Call::code("print(1)")
        .deadline(Duration::from_secs(10))
        .grant("/data", "./inputs", Access::ReadOnly),
)?;
assert_eq!(done.exit_code, Some(0));
```

**Later in the 0.2 line, not in 0.2.0** (INFERRED): typed results (`results=True`) and figures as PNG, `packages()` and `stats()`. They exist in Python and matter, but none blocks a first embedding, and each is a serialisation the conformance suite must pin first.

## 6. Questions for the owner

Each has a default, so a yes to all is a workable plan.

1. **How a first run gets its compiled module.** (a) Ship a precompiled module in each platform package: about 140 MB a platform, first call under 1.5 s and no 2.3 GB spike. (b) Compile on first use: about 80 MB a platform, one 31 s compile per machine and version. (c) Fetch the precompiled module from the release on first use: small packages, a network step at first run. Default: (a) for npm, since serverless and small containers cannot pay the spike; (c) behind the crate's `download` feature. On Lambda, whose zip deployments have a 250 MB unzipped limit (READ, Lambda limits), (a) fits only because the packages keep everything compressed (about 135 MB, INFERRED) and unpack into a cache in `/tmp`, at about 0.5 s a file on each cold machine; an unpacked 299 MB module would not fit.
2. **The names.** `wasi-python` is free on crates.io and npm, and so is `@wasi-python/core` (READ, the registries' APIs, 2026-11-17). Default: `wasi-python` on both, with the platform packages under an `@wasi-python` npm scope, which the owner's npm account must create.
3. **The Node floor.** Default: Node 22.13 or later, tested on 22, 24 and 26, as napi-rs is; Bun best effort; Deno not promised. The addon brings its own engine, so V8's exception handling sets no floor.
4. **The Python wheel stays on wasmtime-py in 0.2.0** (the 2026-11-14 memo's first question, still open). Default: yes.

Added 2026-11-23. Question 1's sizes are now those of 7.8 (0.1.6 on wasmtime 51): about 135 MB a platform for the unmetered module alone, 161 MB with the binary so a metered module compiles on first use, 219 MB with both precompiled, and about 90 MB compiling everything on first use. The researcher's pick is unchanged: ship the unmetered module, compile the metered one on the first call that sets fuel (7.7).

5. **Whether the copy-on-write start reaches Python users first, as 0.1.7.** The wheel can make the pandas groupby call in 7.5 ms on wasmtime-py (7.6), against 58 ms today, without the Rust core. Shipping it first puts the gain in current users' hands and proves the image, its reseeding and its cache keys on the host with the most tests, before two new hosts depend on them (INFERRED). It costs the wheel a copy-on-write module per image and the 0.1.7 release's compile. Default: yes, as milestone M1 in section 9.
6. **Which image the npm package starts from by default.** Pandas: about 135 MB a platform, numpy and pandas ready, scikit-learn still 2.8 s cold. Everything: about 180 MB unmetered (7.8), every shipped package ready in about 10 ms, from a compiled module of 115 MB with zstd against 70 MB. Default: the pandas image, which keeps T10's 140 MB, with the everything image as an optional package, since Eryx and Monty both compete on start time and the pandas call is the one buyers compare (INFERRED, section 8). This replaces the lean in 7.5, which predates the metered module and 0.1.6's sizes.

## 7. The owner's follow-up questions, answered

The owner asked, after reading the above: "How are we able to improve the performance as much? What are the trade offs? And should we start hosting the large files on GitHub and not in the package registries? What do other mature libraries do?" Pages in this section were read on 2026-11-17.

### 7.1 Where 58 ms becomes 6.4 ms

Two separate wins are at work, and they answer different questions. The copy-on-write image makes every call fast. The precompiled module makes the first call on a new machine fast. The 58 ms against 6.4 ms comparison is the first one only.

| Part of one pandas-ready call | Python runner | Rust, image copied | Rust, copy-on-write | Source |
|---|---|---|---|---|
| Put the 68.8 MB image into the new instance's memory | not separable | 41.7 ms | 0.0 ms | EXECUTED, `rust-host.txt` |
| Run the groupby | not separable | 3.6 ms | 6.0 ms | same |
| Tear the instance down | not separable | 3.1 ms | 0.4 ms | same |
| Whole call | 58 ms | 48 ms | 6.4 ms | `python-package-snapshots.json`, `rust-host.txt` |

- **About 42 ms is not copying the image** (EXECUTED). Today's runner and the copying Rust host both write all 68.8 MB into fresh memory on every call (`ctypes.memmove` in `src/wasi_python/_snapshot.py`, READ). Copy-on-write maps the image's pages instead, and the kernel copies a page only when the guest writes to it. The run gets 2.4 ms slower because it now pays for the pages it touches as it touches them, and teardown gets 2.7 ms faster because there are few private pages to free.
- **About 10 ms is the runner's own work per call, not wasmtime-py** (EXECUTED 2026-11-18, `results/python-cow.txt`; corrected from the first draft, which put it on wasmtime-py). The same copy-on-write module run through wasmtime-py by a minimal script takes 7.5 ms, against 6.4 ms on the crate. So wasmtime-py itself costs about 1 ms a call; the rest of the 58 ms against 48 ms gap is what the 0.1.4 runner does around each call (INFERRED; not broken down here).
- **The cost grows with the image when copying, and barely at all with copy-on-write** (EXECUTED). From the 240 MB everything image the runner takes 180 ms; copy-on-write takes 7.8 ms.
- **The precompiled module is the other win** (EXECUTED). Compiling takes 31 s and 2.3 GB; loading a compiled module takes 11 to 13 ms. It changes the first call in a new process or on a new machine, not the warm call.

### 7.2 The trade-offs

- **Each copy-on-write module bakes in one image** (EXECUTED). The image becomes the module's data, so each image costs its own 31 s compile and its own 326 MB compiled module. That suits one shipped pandas image, not images users make themselves.
- **The `mmap` route avoids the recompile, but leaves wasmtime's API** (EXECUTED, INFERRED). It costs 7.1 ms with no new compile. It maps over memory wasmtime owns, which is unsafe code that a wasmtime upgrade can break (51.0 changes `LinearMemory`, per the 2026-11-16 weekly survey). Windows needs another system call, which was not tried. The supported shape is a custom memory through wasmtime's own `MemoryCreator`, or a change upstream; either is work for 0.2.x, not 0.2.0.
- **Disk goes up** (EXECUTED). A mapped image must sit uncompressed: 68.8 MB on disk against a 19.8 MB snapshot file, or 240 MB against 87 MB. The packages ship it compressed and unpack it once into a cache, at about 0.5 s a file.
- **Memory goes down** (EXECUTED). Sessions share the image's pages through the page cache, so each idle session holds 4.7 MiB of its own against 66 MiB when copied. A container's memory limit still counts the shared pages once (INFERRED).
- **Isolation holds, but the image is shared** (INFERRED). A private mapping gives every call its own copy of any page it writes; no write reaches the file or another call. What the image held when it was made, every call starts with: environment, files read, and random and hash seeds. So shipped images must be made from a clean state with no user data, and each call must reseed its randomness. The runner's entropy check, a 0.1.5 review follow-up, is where that is enforced.
- **A precompiled module is native code** (READ, INFERRED). `Module::deserialize` is an `unsafe` function in the crate, because a module file runs as machine code. So wherever it comes from, it must be checked by a pinned SHA-256 before it is loaded. A compiled module also fits only the wasmtime version and the CPU features it was made for, so releases build a baseline module per platform, and wasmtime refuses a module made by a different configuration (INFERRED).
- **Caches must be keyed by content** (READ, INFERRED). The snapshot file format already records the hashes of the binary and the stdlib it was made from (`snapshot_sha256`, `stdlib_zip_sha256` in `_snapshot.py`). The module cache and the unpacked images should be keyed the same way, plus the wasmtime version and target, so an upgrade never reuses a stale file.
- **The release gets heavier** (INFERRED). Each of the five platforms needs a compiled module per release: about 31 s and 2.3 GB each, within a CI runner.

### 7.3 What mature projects do

| Project | How its big files reach users | Size per platform | Source (READ) |
|---|---|---|---|
| esbuild | Per-platform npm packages as optional dependencies; an install script only checks, and falls back to the npm registry | 11.4 MB | esbuild.github.io/getting-started |
| sharp | Moved in v0.33 from an install script that downloaded libvips from GitHub to per-platform `@img/*` npm packages with no script | 18.7 MB | sharp.pixelplumbing.com/changelog/v0.33.0, lovell/sharp#3750 |
| Biome, swc, Rolldown, lightningcss | Per-platform npm packages | 10 to 100 MB (Biome 99.7 MB) | npm registry metadata |
| onnxruntime-node | Every CPU platform in one 307.6 MB package; CUDA files downloaded at install, being "too large to be allowed in the npm registry" | 307.6 MB all platforms | npm metadata, its `install.js` |
| Playwright | Browsers fetched by an explicit `playwright install` from its CDN, host overridable by an environment variable | hundreds of MB | playwright.dev/docs/browsers |
| Prisma | Engines downloaded at install, with a mirror variable; it has since moved its engine from Rust to TypeScript, citing per-OS binaries and serverless size | | prisma.io docs and blog |
| Pyodide | Core on npm; packages fetched from a CDN on use | | pyodide.org deploying docs |
| `ort` crate | Small crate; an opt-in `download-binaries` feature fetches ONNX Runtime in `build.rs`, checked against a pinned hash per file, cached, and skipped on docs.rs | crate 0.06 MB | pykeio/ort `build/main.rs` |
| `tch` crate | System libtorch by default, then a path variable, then an opt-in `download-libtorch` feature | crate 0.24 MB | tch-rs README |

Three facts decide the npm side (READ):
- pnpm runs no dependency's install script unless it is allowed (pnpm.io/settings/build), Bun runs none outside a trusted list (bun.sh/docs/install/lifecycle), and Yarn's next major turns them off by default (yarnpkg.com/configuration/yarnrc). An install-time download would silently not happen for many users.
- sharp's stated reasons for leaving GitHub downloads: installs through package-manager mechanics only, sandboxes that forbid scripts, regions and companies where GitHub is limited, offline installs and reproducible builds, and vulnerability reporting through the package manager (lovell/sharp#3750).
- GitHub Releases allow files up to 2 GiB, 1,000 assets a release and no bandwidth limit (docs.github.com, about releases); the API allows 60 unauthenticated requests an hour per address, so a fetcher must use pinned URLs, not a "latest" lookup.

On the Rust side (READ): crates.io caps a crate at 10 MB (doc.rust-lang.org/cargo, publishing), and docs.rs builds with no network, so a `build.rs` download must be opt-in and skip when `DOCS_RS` is set (docs.rs/about/builds).

### 7.4 Recommendation on hosting

Use both, each where it fits (INFERRED, from 7.3):
- **npm:** keep the artifacts in the registry, in per-platform packages with no install script, as esbuild and sharp do. It is the only route that works under pnpm, Bun, offline mirrors and `--ignore-scripts`. At about 140 MB a platform it is larger than Biome but under onnxruntime-node's 307.6 MB, which the registry accepted.
- **GitHub Releases:** make it the canonical, attested home of every artifact (GitHub artifact attestations, verified with `gh attestation verify`). The crate's opt-in `download` feature fetches from it, by pinned URL and SHA-256, into a content-keyed cache, as `ort` does. A mirror variable covers companies that block GitHub.
- **The crate:** stays a small source crate. Artifacts come from a path or environment variable first, or from `download` when asked; never from a default `build.rs` fetch.

This keeps question 1's default: (a) for npm, (c) behind the crate's `download` feature.

### 7.5 Which packages get the speedup

The owner asked: "would we only get the speed up in pandas or every package?" A call is fast for whatever its image already imported; anything else still pays its import (EXECUTED, `results/package-coverage.txt`, Rust host, medians in ms):

| Call | No image | Pandas image | Everything image |
|---|---|---|---|
| Plain Python, `sum(range(10**5))` | 19 | 8 | 10 |
| `import numpy` and a sum | 288 | 9 | 11 |
| `import yaml, jinja2` and a dump | 220 | 110 | 8 |
| scikit-learn tree fit and predict | 4,002 | 2,828 | 122 |
| `import pandas` and a groupby | 1,257 | 6 | 8 |

- **Every call gains from the host and the precompiled module** (EXECUTED). Those parts do not depend on the image: plain Python with no image already runs in 19 ms on the crate, against 22.8 ms for an empty call through today's runner.
- **The pandas image covers numpy too** (EXECUTED), because importing pandas imports numpy. A package it did not import, such as yaml, pays about half its cold import, since the standard library parts are already loaded.
- **The everything image makes every shipped package fast** (EXECUTED). It is the image `make_package_snapshot()` makes with no names, which imports every package the set ships. Every row above lands at 8 to 12 ms, plus the call's own work (the tree fit's 122 ms is mostly fitting).
- **Its cost is size** (EXECUTED). The compiled module with the everything image is 497 MB, or 107 MB with zstd, against 65 MB for the pandas one and 57 MB with no image. Each idle session holds 5.6 MiB of its own, against 4.7 MiB.
- **A package outside the set, or a user's own code, gets no image gain** (INFERRED). It pays its normal import on every call, unless the user makes their own image. With the copy-on-write module that means a 31 s compile per image; with the `mmap` route of 7.2 it would not.

So the default image is a scope choice (INFERRED). The everything image makes every shipped package start in about 10 ms, and its compiled module is about 42 MB larger compressed than the pandas one, so each platform download grows by about that much over the 140 MB of question 1 (a). That is still under onnxruntime-node's 307.6 MB. The researcher's lean is the everything image as the npm default, since it removes the cold import that today costs 0.3 s for numpy and 4.7 s for scikit-learn, with the pandas image as the crate's smaller option. At roughly 182 MB per platform, the everything image would exceed T10’s 140 MB download ceiling for a precompiled module. Choosing it as the npm default would require either a smaller download or an explicit change to T10.

## 9. The roadmap (2026-11-23)

- **Why M1 comes first** (INFERRED). The image design, its reseeding and its cache keys are new, and wasi_python's Python tests are the deepest the project has. Proving them there first means the crate and the addon inherit a tested design rather than debug it on two new hosts at once. It also gives today's users the 58 ms to 7.5 ms gain before 0.2.0.
- **Why M2 before M3** (INFERRED). The conformance suite (F8) is what proves the Rust core gives the same results and fuel as Python; the fast start changes memory, and should be measured against a core already known to be right.

## 10. Risks (2026-11-23)

| Risk | Evidence | What the plan does about it |
|---|---|---|
| **Every wasmtime major re-ships every platform package** | modules are refused across versions (EXECUTED, 7.8); 0.1.6 already moved one major | T15: one workflow rebuilds and re-measures; caches keyed by wasmtime version; the crate's `download` feature fetches its own version's modules |
| **Eryx ships first with all three hosts** | Eryx 0.16.1 on crates.io, PyPI and npm, releases every 2 to 5 days (READ, section 8) | lead with the data stack and the pandas call; M1 puts the fast start in users' hands before 0.2.0 |
| **A runaway guest takes the host's memory** | 3.9 GB host peak at a 4 GiB limit (EXECUTED, 7.8) | T14: keep the runner's 1 GiB default on every host; document the per-session ceiling for servers that run many at once |
| **The download outgrows npm** | 219 MB a platform with both modules, about 317 MB with the everything image (INFERRED, 7.8); npm refuses near 256 MiB (READ) | question 1's pick (no precompiled metered module), question 6's default (pandas image), an optional package for the rest |
| **The first metered call is slow** | about 52 s and 2.9 GB once per machine and wasmtime version (EXECUTED, 7.8) | document it; an optional `-metered` platform package for serverless hosts with fuel limits (7.7) |
| **User images are slow to start** | each copy-on-write module bakes in one image and costs a 40 s compile; the `mmap` route is outside wasmtime's API (EXECUTED, 7.2) | ship the copy-on-write module for the shipped image only; a `MemoryCreator` route for user images in 0.2.x |
| **The image leaks state between calls** | every call starts with what the image held, including random and hash seeds (INFERRED, 7.2) | images made from a clean state; the entropy check reseeds every call, in M1 |
| **The Node addon is unmeasured** | no addon built; its size and a JavaScript tool call's cost unknown ("Where it stopped") | M4's gate measures T7 and T10 on the real addon before beta |
| **A precompiled module is native code** | `Module::deserialize` is `unsafe` (READ, 7.2) | load only files that match a pinned SHA-256; attested release assets (7.4) |
| **Release CI cost** | per platform, 40 s and 2.5 GB for the unmetered module and 52 s and 2.9 GB for the metered one (EXECUTED, 7.8) | five platforms fit standard CI runners; the metered module is built only where a package ships it |

## Where it stopped

- Not built: the napi-rs addon. Its size (T10 uses the 18.4 MB bench binary as a stand-in) and the cost of a JavaScript tool call across Node-API (T7's 50 µs) are unmeasured.
- Not run: Node 24 and 26 (fetching their binaries was refused in this session), macOS and Windows hosts, the door round trip and concurrency on this machine (both cited from the 2026-10-23 memo on an M1).
- The copy-on-write start by `mmap` maps over wasmtime's memory from outside its API; it shows the cost, not the design. Windows mapping was not tried.
- The images were made by the 0.1.4 runner and restored by a host that preopens only the stdlib folder and a root; a product host must repeat the image's preopen table, as the 2026-10-27 memo found (READ).
- One machine, one container, other work idle; times are benchmark facts of it. Fuel counts repeat on any machine with the same wasmtime.
- Not run (2026-11-23): any competitor. Eryx and Monty numbers are their own published claims, with no hardware stated; the head-to-head of section 8 waits on the owner's word to install `pyeryx`. The 0.1.6 images were made by the 0.1.6 runner on wasmtime-py 51.0.0; the crash cases of T13 were run on the harness, not the runner, and a panicking native extension was not among them.

## One line

0.2.0 should ship the Rust crate and napi-rs package with parity on run, limits, tools, mounts, sessions and snapshots. Copy-on-write is what puts the pandas-ready call under the 10 ms release target on both hosts: 7.5 ms through wasmtime-py and 6.4 ms on the crate.

Updated 2026-11-23: on wasmtime 51 and the shipped 0.1.6 binary the pandas call is 6.9 to 7.9 ms and an empty call 1.8 ms, every engine bump re-ships the platform packages, and against Eryx, which already has all three hosts, 0.2.0 leads with the data stack it ships ready: copy-on-write in Python first (0.1.7), then the Rust core, its fast start, and the npm package.
