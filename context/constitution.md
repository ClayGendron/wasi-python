## 1. Mission

wasi_python exists so that **any program that can host WebAssembly can run real Python, with numpy and pandas, inside a sandbox it fully controls, without a browser, a JavaScript engine, a kernel feature or a package install step.**

One artifact. One wall. Every platform. A few pinned releases, not every version of everything.

## 2. The goal, stated so it can be checked

A release is ready when all of these are true (the judge's goals v1.1 to v1.5 check them):

1. A statically linked `python.wasm` for `wasm32-wasip1` with CPython and its profile's packages compiled in as builtin modules is published as a GitHub release and as the `wasi-python` wheel on PyPI, with a manifest and hashes.
2. It runs under wasmtime on Linux, macOS and Windows from the same bytes, with no host directory beyond the grants the embedder gives (read-only or writable folders, which may be none), no network, no shared library and no host process.
3. Every compiled-in package imports and works; the judge's jobs for each (for numpy and pandas: a CSV read, a groupby and a CSV write) run inside it, and the results match native Python.
4. An embedder in any language with a wasmtime binding can run it by preopening the folders it grants (possibly none), binding one host function and calling one export. A Python embedder does it in one call through the wheel.
5. The whole thing rebuilds from pinned sources by a CI job anyone can run; any upstream tree differs from its pinned tarball only by the recorded, temporary patches §4.1 allows.

What a release contains, which packages its default profile carries, and the order of work are the roadmap (`roadmap.md`): the owner's living plan, changed by the owner's decision without amending this document. One principle holds for every roadmap: a profile is its own artifact set, built, judged and published, chosen by name and never assembled on a user's machine, and profiles stay few.

## 3. What this project is not

- Not a development environment. It is a drop-in, easy-to-use, sealed Python for lightweight loads: an embedder runs a program and gets its result. No pip, no venv, no package tracking. A release is one pinned set of versions. The project does not build every release of every supported package; it builds a new set when there is a reason to, and the old sets stay published.
- Not a browser Python. Pyodide owns that.
- Not a general wasm toolchain. It builds one artifact well.
- Not an application. It ships no filesystem, no shell, no agent, no server. Those are its embedders' business. A thin command that runs one program through the runner and prints its result as JSON (`wasi-python run`) is part of the runner, not a shell: it adds no power `run()` does not have (owner, 2026-10-17). A bounded session, one guest kept across several calls with an idle timeout and a lifetime, is part of the runner too, not a development environment (owner, 2026-10-17, question 19).
- Performant, not the fastest. It is correct, portable and sealed first, and it stays close to native: the penalty against native Python is measured on every release, documented, never hidden, and never the reason to break another rule. A build that gets slower than the last one without a stated reason is a regression.

## 4. Hard constraints

These are not preferences. Work that violates one is wrong even if it works.

1. **Upstream patches are few, recorded and temporary.** An adaptation is a recipe file first: a cross file, a compiler wrapper, a rename header, a stand-in module, a linker flag. Where a source change is unavoidable, the project carries it as a patch file under `recipes/patches/`, applied after the pinned tarball's hash is checked. Each patch is reviewed like any change, recorded in `MANIFEST` by its hash, named in the CHANGELOG, and matched by an upstream pull request drafted in the repository for the owner to send; it is deleted once an upstream release carries the fix. The release workflow fails on any difference from the pinned tarball other than exactly the recorded patches (question 32; built by spec 020).
2. **Every input is pinned and hashed.** Every source tarball, toolchain, tool and pure-Python dependency is a URL plus a SHA-256 in `downloads/SHA256SUMS`, verified before use. A build that fetches anything unpinned is not a build.
3. **One target: `wasm32-wasip1`.** No Emscripten, no JavaScript, no native code path, no host-specific branch. If something cannot be done inside WASI, it is left out and documented.
4. **The guest reaches the host through exactly two things:** the WASI preview1 calls and one custom import, the host door. No third import, ever. The door's raw frames are opaque to this project; what they mean is the embedder's. On top of the door the project may ship one tool protocol, through which a guest calls the host's tools, APIs and MCP servers: optional, used only when the embedder passes its tools, and gated by the embedder on every call (owner, 2026-10-17, questions 12 and 14).
5. **Embedder-neutral.** No code, name, default or test in this repository refers to a particular embedder. vfs is one consumer and gets nothing the next consumer does not.
6. **The artifact set is the product.** A plain reactor `python.wasm`, a snapshot `python.wasm`, the stdlib zip, `MANIFEST`, `SHA256SUMS`, and the licence notices of everything inside. Nothing compiled per host (`.cwasm`) is ever published. Nothing large ever lives in git.
7. **Prior art is studied, never copied.** Clones under `context/prior_art/` are read-only design input. Every line here is original. Licences are checked on clone and recorded; a project with no licence is deleted from the working set.
8. **Downloads are untrusted.** They unpack under `downloads/` and `build/`, never into the system, and execute only as build tools under the build's own control or as guests under wasmtime.
9. **Tests count, benchmarks time.** A test asserts operation counts, exit codes, bytes and equality with native results. Wall-clock and memory are benchmark facts in a research memo. A test that measures time is a bug.
10. **Claims carry their evidence.** Every number in a document has a command and an output beside it; every claim is labelled EXECUTED, READ or INFERRED. A result that was not run is not reported as run.
11. **Platform semantics are documented, not disguised.** The 32-bit default integer, the missing threads, the missing modules, the speed ratio: all stated in the README and in `python3 --version`.
12. **Licence compliance ships with the artifact.** The binary contains CPython (PSF), numpy and pandas (BSD-3-Clause), zlib and the pure-Python dependencies; their notices are inside the release and the wheel. Nothing with a licence the owner has not approved is linked in. 13. **Tooling.** `uv` only. `ruff check`, `ruff format --check` and `pytest` green on `src/` and `tests/` before any merge into `dev` for the selection its pull request runs, and on `dev` after each merge for the whole normal tier. No dependency added to `pyproject.toml` without a reason written in the specification that needs it.
14. **Git.** Commit or push only when the owner asks. Work on one specification may run in its own git worktree, outside the repository, on a branch made from `dev`'s tip, carrying one to three specifications, merged into `dev` by a pull request behind its required check and one review (§5.7); `main` moves only by the owner's fast-forward to a release pull request's acceptance (§5.5) and carries the tags. No other long-lived branch or worktree unless asked. One exception (question 70): an acceptance commit that is unpushed and breaks rule 1 may be undone with `git reset --soft`; a pushed one is reverted by a pull request. 15. **Safe by default.** Every limit has a default (memory, time, output); no channel to the host opens without an explicit argument (no folder, no network, no host function); the runtime's own files are never in a writable grant. A change that loosens a default needs the owner's decision, not only a review (owner, 2026-10-17).

## 5. How work is done

1. **The pipeline is study → research → specify → build → review.** Nothing is built that no specification describes; no specification is written on a question no research has answered; nothing lands that no review has passed. `context/README.md` holds the rules of each stage.
2. **No open questions.** A specification decides every choice it needs and says why. What cannot yet be decided becomes a placeholder research memo naming the experiment that will decide it, and the specification waits. There is no backlog of undecided things.
3. **Time boxes are real.** A research task states its box. At the box the agent stops, records exactly where it stood and why, and reports. A blocked step is skipped, not forced.
4. **Small, finished, verified.** A landing is one pull request carrying one to three specifications, green, with its landing notes written and its numbers reproduced. Half-built work is not landed; it is reported as half-built. Specifications may be built in parallel; each pull request lands into `dev`, squashed to one commit, judged and accepted once on `dev` after its merge (§5.7); each specification keeps its own news file and landing notes, and the pull request's one review reads each of them.
5. **A release is a re-run, not a project.** A new pinned set means: re-pin, re-run, re-verify, publish, and write the memo that says what changed. That must cost days, not weeks, which is why constraint 1 exists. Cadence is a scope decision the owner makes per release, never a schedule the project is bound to. A security fix in a pinned component is a reason to release: the agent prepares one and asks (owner, 2026-10-17). **The release rule** (owner, 2026-10-20): the judge has two tiers, normal and release, which together are every test of every package built; nothing is left out of both. Before a tag, the release pull request from `dev` to `main` judges both tiers on the exact commit `main` will receive and its record is accepted; the tag's own run judges both again; a release-tier failure, or a release-tier change no claim explains, stops the tag.
6. **Review is a stage, not a courtesy.** Every built change is reviewed before it lands, by a reviewer who did not write it (a fresh agent or a person), who is given the specification and the change, not the author's summary. The reviewer reads the pull request's run of the counted tests (its `ci-status` and the gather's summary), checks each acceptance criterion against its evidence, checks the change against §4 and §7, and reports ranked findings. Each finding is fixed or answered in writing before the landing; the landing notes cite the review. A finding ranked Low, or a note, is answered by the builder without another review round when its answer is in writing or touches only `context/`; a fix to code for it is read by the pull request's reviewer (owner, 2026-10-19). A Low finding that touches only `context/` may be written in by the reviewer itself, as a commit of the exact text on the specification's branch once the builder has handed the branch over; a fix to code stays the builder's (owner, 2026-10-19, the wave). A specification that changes the guest's imports or exports, the artifact set or the build recipe is reviewed once more before it is built, so a wrong design is caught before it is code. A specification that is structural (AGENTS.md: it adds a module-level mutable or lock outside the process object's module, a use of the engine's private API outside the engine seam, a platform branch outside the platform module, a test seam not on the process object, or takes a module or a function past its ceiling) is reviewed before it is built in the same way, against the structural rubric in `reviews/README.md` (owner, 2026-10-21, question 108). Reviews live in `context/reviews/`. Before each release, a fresh reviewer checks the release against the written threat model (`research/2026-10-16-a-principal-engineers-direction.md`, section 2) and the changes since the last release; the release waits on its findings (owner, 2026-10-17). Before each release a fresh reviewer also writes a structural review of `src/` against that rubric, recorded under `reviews/` beside the security review; the release waits on its High findings (owner, 2026-10-21, question 108).
7. **Pull requests into `dev`.** Builders and reviewers work in parallel on branches from `dev`. `dev` changes only by the squash merge of a pull request that passed its required check and one review by someone who did not write it. After each merge the full normal tier runs once on three systems and a job accepts its record into `context/progress/`; a red post-merge run blocks every merge but its fix or revert. `main` changes only by the owner's fast-forward to the acceptance of a release pull request from `dev`, whose check is the whole workflow, both tiers, the rebuilds and the gather's release goals, and whose review is the release's security and structural reviews. Reproducibility is proved at the release pull request, at the tag, and weekly on `dev`, not per change.

## 6. Deciding when the rules do not say

When a choice is not covered here or in a specification, the agent decides by these, in order:

1. **Does it keep the wall whole?** Anything that lets the guest reach the host by a third way is refused.
2. **Does it keep the build reproducible, with as few patches as it can?** Prefer a recipe file over a patch, a pin over a floating version, and a patch only as §4.1 allows it: reviewed, recorded, matched by an upstream pull request, and temporary.
3. **Does it work on every WASI host the same way?** Prefer the plain WASI form over the clever host-specific one.
4. **Is it the smallest thing that meets the specification?** Prefer fewer files, fewer dependencies, fewer artifacts.
5. **Would the owner recognise it as this project?** A basic, sealed, portable Python with the data stack inside, released as a few pinned sets. If the choice pulls toward a development environment, a browser runtime or an application, it is wrong.

If the choice is still open after these, it is the owner's, and the agent writes a placeholder memo and moves to work that does not depend on it.

## 7. What an autonomous agent must never do here

- Patch an upstream source tree outside §4.1: a change not carried as a reviewed patch file under `recipes/patches/` with its upstream pull request drafted, or any edit made by hand in `build/`.
- Add an import to the guest binary beyond WASI preview1 and the door.
- Fetch anything unpinned, or install a download into the system.
- Copy code from `context/prior_art/` or any other project.
- Commit, push, tag, publish a release, upload to PyPI, or make a branch or worktree beyond §4.14's, without the owner's explicit instruction for that action.
- Report a build, a run or a number it did not execute.
- Leave an open question in a specification, or a question list anywhere.
- Widen the scope past §2 and the ordered list that follows it.

## 8. One line

Build one sealed, portable Python with the data stack inside, from pinned sources with only recorded, temporary patches, prove every claim by running it, and release a new pinned set only when there is a reason to.
