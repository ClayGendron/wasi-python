## Short version

Nothing a guest, an embedder or the build can reach changed. `src/` changed by its version string alone, and recipes, scripts and pins did not change, so every row of the threat model below the release path stands as 0.1.3 left it.

The one surface that moved is the tag's upload. In 185, `pypi` signs the wheel with `astral-sh/attest-action` pinned by commit, on uv 0.13.5 pinned by checksum. It then uploads exactly the wheel and its attestation. Two new jobs, `pypi-verify` and `pypi-rehearsal`, read PyPI back with `contents: read` alone.

The design is sound:
- No new job holds `id-token`.
- `pypi` keeps `contents: read` and `id-token: write`, the `pypi` environment (tags `v*` only) and its `PYPI_PUBLISH` gate.
- Rule 20 holds `pypi` to exactly seven unconditional steps.
- PyPI itself refuses an upload whose attestation does not verify against the trusted publisher.
- No path I found puts an unattested wheel on PyPI.

The accepted residual is the one 185 names. The signer's code, the action and its hash-locked wheels, runs in the job that can mint a PyPI upload token.

**No High.** One Medium: **M1**. Every other job's inability to upload rests on PyPI's publisher list naming the `pypi` environment, and 185's Decision 9 (the owner reads that list) is not recorded yet. Four Lows: **L1**, the read-back passes when PyPI holds an extra file for the version; **L2**, the action's commit is not shown to be on upstream's tag; **L3**, the user-facing PyPI check is unpinned; **L4**, one ambiguous phrase on the release page. ## What changed, and what held

### `pypi`: the signature and the upload (READ, `release.yml:1692-1747`; `scan.py:1752-1850`; `action.yml`, `action.py`)

- **Who holds the token.** `pypi` alone has `id-token: write` among the new or changed jobs, inside `environment: pypi`. That environment deploys only from `v*` tags (`decisions.md`, S1). The job keeps `if: … ref_type == 'tag' && vars.PYPI_PUBLISH == 'true'` and gains `timeout-minutes: 20`. `pypi-verify` and `pypi-rehearsal` have `contents: read` and no environment.
- **What the signer runs.** The composite action checks for `uv` on the path. setup-uv has put 0.13.5 there, so the action's own `setup-uv` with `version: ">=0.9.12"` is skipped. The action then runs `uv run --locked --no-dev --project $GITHUB_ACTION_PATH action.py`. `action.py` globs `dist/*.whl` and gets the ambient token through `sigstore.oidc.detect_credential()`, which asks for audience `sigstore`. It signs each distribution and writes `<file>.publish.attestation`, refusing to overwrite one that exists (`action.py:182`). Its inputs reach it through `env:`, not through `${{ }}` in a script. The lock is `no-build = true` with `require-build-hashes`, so it builds nothing.
- **What the signer could do.** The job's `ACTIONS_ID_TOKEN_REQUEST_*` variables reach every step. So the action, or any of its locked wheels, could ask for an audience-`pypi` token, exchange it, and upload any file to any version of `wasi-python`. It could also sign that file as `release.yml` (INFERRED). This is 185's accepted residual. It is bounded by the commit pin, by the lock's hashes, and by the job running only on a pushed tag with the switch on. The same holds for `setup-uv` and the local `verify-artifact` action, as before 185. L1 is about seeing such a file afterwards.
- **What reaches PyPI.** Rule 20 holds `pypi` to seven steps, by kind and in order, with no `if:` or `continue-on-error:` on any of them (`PYPI_STEPS`, `scan.py:1752,1821-1828`). The staging step requires `ls dist` to be exactly the wheel and its `.publish.attestation`. The upload names `dist/*` and nothing else. `--no-attestations` and `UV_PUBLISH_NO_ATTESTATIONS` are refused anywhere in the workflow. A forged or empty attestation would be refused by Warehouse at upload, and nothing would land (INFERRED, from 185's reading of Warehouse). A wheel without an attestation cannot get past the staging step. A re-run of `pypi` after a successful upload is refused by PyPI for the duplicate file.
- **The workflow's `env:` and the root config.** `UV_LOCKED`, `UV_PYTHON` and `UV_BUILD_CONSTRAINT` reach the action's `uv run`. The checkout carries `release/` so the constraint file exists. The root `pyproject.toml` sets only a workspace and sources, and 185 found the lock runs the same from the root as from an empty folder (READ). `uv publish --no-config` reads none of it.

### `pypi-verify` and the read-back (READ, `release.yml:1749-1797`; `pypi_readback.py`)

- **What it checks.** The script reads three things. The JSON API must list the wheel named in `SHA256SUMS`, with that SHA-256. The Integrity API must hold a bundle whose publisher is `GitHub`, this repository, `release.yml` and `pypi`, with at least one attestation. The Simple API must list the file. `verify pypi` then checks the signature over PyPI's own bytes, through Sigstore's trust root. The two layers cover each other. The CLI checks the repository and the signature. The script checks the workflow, the environment and the digest.
- **How it fails.** Only a 404, a file not listed, or a 200 without JSON is asked again: six tries, 30 seconds apart, about 2.5 minutes, once per tag. A 5xx, a refused connection or a timeout fails at once (`pypi_readback.py:91-101`). JSON of the wrong shape raises, and the script exits 1. Every way it can fail ends red, and none is silent.
- **Nothing reaches `ci-status` green by a skip.** `pypi-verify` shares `pypi`'s `if:` and needs it, and `ci-status` needs both.
- **What it does not check.** That the release's wheel is the *only* file for the version (L1).

### `pypi-rehearsal` (READ, `release.yml:1799-1868`)

- It runs on every release-shaped run (`rebuild`): the release pull request into `main`, a dispatch, the weekly run and the tag. On a tag, `attest` needs it (`release.yml:1623`). So `publish` and `pypi` wait on it, and a broken PyPI path stops the tag before anything is signed.
- It holds `contents: read`. It runs the action's lock, both read-back checks on 0.1.1's wheel, and `uv publish --trusted-publishing never --dry-run` on the build's wheel with a stand-in attestation. It signs nothing and holds no token.
- On a pull request into `main` it runs code from that pull request's head with a read-only token, as every judge job does.

### Probing third-party hosts

- The read-back retries only while PyPI says our own upload is not there yet. It runs once per tag, for at most six tries. A host that is down fails at once, and a person re-runs the job later. This holds the rule.
- The weekly run now makes a handful of requests to pypi.org, files.pythonhosted.org and Sigstore's TUF CDN through the rehearsal. The weekly schedule already rebuilds from the pins at every upstream host, so this adds a few requests to an existing schedule and no retry loop (INFERRED, `ci_plan.py:538`).

## Findings, most severe first

### M1. That only `pypi` can upload rests on PyPI's publisher list, which nobody has recorded reading. Medium; the release path (READ, `specifications/185-…md`, Decision 9 and "Still to read")

- PyPI exchanges a GitHub token for an upload token when any trusted publisher registered for `wasi-python` matches it. A publisher (or a pending one) that names no environment matches any job of `release.yml` that holds `id-token`. On a tag, that includes `attest`.
- 148's history records five attempts at 0.1.1's publisher. 0.1.0's provenance names the repository's old name, `ClayGendron/wasi_python`. Decision 9 asks the owner to read the project's Publishing page and remove any publisher outside `release.yml` in `pypi`. 185's landing notes still list it under "Still to read".
- Failure: a publisher without an environment is still registered. A compromised action in `attest` (whose `actions/attest` is pinned, but which runs with `id-token: write`), or a future job that gains `id-token`, mints an upload token outside the `pypi` environment and its tag-only deployment rule. A file reaches PyPI that no step of `pypi` staged.
- **What closes it:** before the tag, the owner reads PyPI's Publishing page for `wasi-python`. The landing notes list each publisher with its repository, workflow and environment, and any other publisher is removed. The release does not wait on it, since it is a Medium, but the tag is the moment it matters.

### L1. The read-back passes when PyPI holds another file for the version. Low; the release path (EXECUTED, `p_extra_file.py`; READ, `pypi_readback.py:110-116`)

- `judge_once` looks for the release's wheel in the JSON API's `urls` and ignores every other entry.
- Failure: the accepted residual is used. A compromised locked wheel in `pypi` uploads `wasi_python-0.1.4-py3-none-manylinux_2_17_x86_64.whl` beside the real one, with an attestation of its own from `release.yml`. pip on Linux prefers the more specific tag. `pypi-verify` says `ok`, and the tag's run is green.
- **Fix:** in `judge_once`, require `urls` to name exactly the wheel `SHA256SUMS` names. Fail with `Wrong` on any other file, since an extra file is never "not there yet". Add one row to `test_pypi_readback.py`: an extra file → exit 1, naming it. This also covers a stray `.tar.gz`. A file under another version stays out of reach of a per-version read, and M1 is what narrows that.

### L2. The action's commit is not shown to be on `astral-sh/attest-action`'s own history. Low; supply chain of the release's tools (READ, `scan.py:1608-1609`; INFERRED)

- GitHub resolves `owner/repo@<sha>`, and `repository:`+`ref:` in a checkout, to a commit anywhere in the repository's fork network. A commit pushed to a fork resolves under the upstream name (an "impostor commit").
- What vouches for `39b6ce43` is that uv's own guide names it as v0.0.7 (READ, 185, *Is this the practice*). No record shows `refs/tags/v0.0.7` pointing at it. My copy of the action is a scratch folder with no git metadata and no `uv.lock`, so I could not check it either.
- Failure: a later pin bump copies a SHA from a fork's pull request. Every rule passes, since the scan holds whatever SHA is in `ATTEST_ACTION_SHA`.
- **Fix:** in 185's landing notes, record once, by hand, the output of `git ls-remote https://github.com/astral-sh/attest-action refs/tags/v0.0.7`. Say in `scan.py`'s comment beside `ATTEST_ACTION_SHA` that a new pin is checked against upstream's tag the same way. I did not run it: the brief keeps third-party hosts unprobed.

### L3. The page's PyPI check runs an unpinned tool and checks the repository alone. Low; documentation (READ, `docs/how-to/verify-a-download.md:37-39`)

- The command is `uvx pypi-attestations verify pypi --repository …`, with no version. The `gh attestation verify` command above it pins the signer's workflow and ref. This one checks the repository, not the workflow or the tag.
- Failure: a reader takes "this checks it" as the same strength as the GitHub check. It is weaker on workflow and ref. It also runs whatever `pypi-attestations` is newest on the day.
- **Fix:** write `uvx pypi-attestations@0.0.30 verify pypi …`, the version the release's lock runs, and add the sentence: "It checks that the file on PyPI was signed in this repository; `gh attestation verify` above also checks the workflow and the tag."

### L4. "the two below" points the wrong way. Low; documentation (READ, `docs/contributing/release-process.md:51`)

- `pypi-verify` is stage 8, above that paragraph. Only `pypi-rehearsal` is below it.
- **Fix:** "so that job, `pypi-verify` and `pypi-rehearsal` pin uv 0.13.5 by checksum".
