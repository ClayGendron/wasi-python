## The questions the brief asked, answered first

- **Can wasmtime-py take a `/dev/fd/N` path?** Yes. `Module.deserialize_file` encodes the path and passes it to `wasmtime_module_deserialize_file` (READ, `.venv/.../wasmtime/_module.py:76-92`). The C API turns it into a `&str` and calls `Module::deserialize_file`, which calls `open_file_for_mmap(path)`, a plain `File::open`, then maps that `File` (READ, `context/prior_art/wasmtime/crates/c-api/src/module.rs:218-232`, `crates/wasmtime/src/runtime/module.rs:471-479`, `vm/mmap_vec.rs:193-199`). So wasmtime opens by name, and the name `/dev/fd/N` works wherever the system's open of it works.
- **Does macOS `/dev/fd/N` reopen or dup?** It dups (EXECUTED): after the path was renamed over, `os.open("/dev/fd/N")` gave the checked inode; a seek on the first descriptor moved the second (a shared open file description); a private read-only `mmap` through it read the checked bytes; an `O_RDWR` open of an `O_RDONLY` descriptor was refused with `EACCES`. On Linux, `/dev/fd` is a link to `/proc/self/fd`, and opening it reopens the same inode with a new open file description (INFERRED from the kernel's documented behaviour; not run here). Either way the file mapped is the file checked. The specification's "yields the same open file" is exact on macOS and loose on Linux (same inode, not the same description); harmless.
- **One thing a descriptor does not change:** wasmtime's own documentation says the mapped file must stay unchanged for the module's life, since lazily loaded pages reflect the file's current state (READ, `module.rs:463-469`). So "the file loaded is the file checked" holds for identity; for content it still rests on the `fstat` check that no one but this user can write that inode (0600, this user's, one name, no access list). The specification has that check; it should not be read as more.
- **Windows.** wasmtime opens with `FILE_GENERIC_READ | FILE_GENERIC_EXECUTE` and share mode `FILE_SHARE_READ` (READ, `vm/sys/windows/mmap.rs:20-27`), so once it has the file no one can write, rename or delete it; the window is the check to wasmtime's open only. The specification keeps the path load with the stamp there, which is right as a floor; L10 names a cheap way to close the window there too.
- **Is `Module.deserialize(bytes)` from one read the portable path?** No, not at this size. The `.cwasm` files in this host's cache are 99 to 280 MB (EXECUTED, `ls -la ~/Library/Caches/wasi_python`). `Module.deserialize` copies the bytes into a ctypes array (`_module.py:64-70`, READ, wasmtime-py's own TODO), and wasmtime copies them again into memory it can make executable (INFERRED from `deserialize` taking a slice). That is about three copies at once, up to roughly 840 MB transient for the largest, and anonymous memory where a mapping would page in lazily and be shared. The specification is right not to use it.
- **The "one-read compile" sentence.** Its cost is stated wrongly (L5): wasmtime-py's `Module.from_file` already reads the whole file into Python bytes and compiles from them (READ, `_module.py:12-20`). Reading once and hashing those bytes costs one SHA-256 pass over bytes already in memory, and saves the second read `_artifacts._digest` makes today.
- **The ancestor rule.** Which ancestors: every prefix of the `realpath` of the call's own cache folder, up to `/` (Decision 3). Owner set: this user or root; Windows has no ancestor rule (Decision 3 says POSIX), so no Administrators SID question arises, and the reserved protected access list (roadmap line 112) is the Windows follow-up. A world-writable ancestor without the sticky bit is refused; with it, it passes. At `/tmp`: `/private/tmp` is `root wheel 1777` here (EXECUTED), so `$XDG_CACHE_HOME=/tmp/x` passes only when `/tmp/x` is this user's. On this host every default ancestor passes: `/` and `/private/var/folders` root 0755, `/Users` root:admin 0755, the home and `~/Library` the user's at 0755 and 0700, `~/Library/Caches` 0700 (EXECUTED, `ls -led`). Two gaps in the wording are L1.
- **macOS ACLs.** The specification's primary path is right and its fallback cannot work (M1).
- **Never refusing a call, and R8.** Decisions 1 and 3 never refuse for the cache's state: the cache is not used, with a warning. Decision 4 does refuse a relative `cache_dir` (H1). The warning is emitted where 113's are, inside `_module_miss`, which runs under the per-digest compile lock (`_engines.py:163-169`, READ) and never under the cache lock; L8.
