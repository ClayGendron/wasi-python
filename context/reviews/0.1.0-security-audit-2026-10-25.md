## Short version

The sandbox holds. Across 17 covered units and 135 checks (66 of them executed against the real runner and the real artifacts), no path was found from a guest to a host file outside its grants, to host memory, to the network or to a host process. Both binaries import exactly the 42 WASI preview 1 functions and the one door. The stdlib zip carries no start-up hook, link or installer. Code planted in a reused root never ran under defaults on either binary. The published 0.1.0 assets are byte for byte the accepted set and verify against their attestation. Every build input is checked against the pin table before use. The runner's own WASI shadows kept every crafted pointer inside guest memory.

Four findings survived independent verification. None is high or critical. The three confirmed ones are **low** overall (impact medium, likelihood low): each needs an uncommon embedder configuration, and none escapes the sandbox. One lead needs the owner's word to settle.

- **F1 (confirmed, low):** an `env=` entry `_PYTHON_SYSCONFIGDATA_PATH` makes a module an earlier guest planted in a reused root run on `import pandas` in a later call. Isolated mode ignores `PYTHONPATH` but not this private variable.
- **F2 (confirmed, low):** a class registered as a tool whose constructor is a `functools.partialmethod` or `partial` lets a guest frame override the bound keyword, against the documented promise that a bound keyword is fixed.
- **F3 (confirmed, low):** on wasmtime-py 49.0.0 the fuel cap under-counts C++ work that ends in a caught exception (GHSA-m63x-6p34-q65x), and the binaries reach it from plain guest Python. Fuel alone does not bound CPU until the pin moves past 49.0.1; the default deadline still bounds wall time.
- **F4 (needs validation):** the module cache's `.cwasm` is checked by `lstat` of the leaf and then opened by path, and no ancestor of the cache folder is checked, so an owner of an ancestor of the default cache folder could swap native code in. It matters only where the runner runs with another user's `$HOME`, which the owner must say is supported or not.

Two units are **deferred** and make no coverage claim: sessions and call isolation, and the limits as the runner enforces them. Their hunters ran their checks, but every attempt to write the structured result, two hunters' and the parent's own, was stopped by a safety classifier. Their evidence is in the run directory for the owner to read (below).

The hunters also returned 66 hardening notes. Several correct the project's own advisory memo of 2026-10-18: the binaries do use the exception-handling proposal, so GHSA-m63x reaches them, GHSA-p79w is avoided only because the tag count is 2, and GHSA-hw8m is unreached for a reason the memo did not give.

## Findings, most severe first

### F1. `env=` key `_PYTHON_SYSCONFIGDATA_PATH` runs code planted in a reused root on `import pandas` in a later call. Low (impact medium, likelihood low); confidence high (EXECUTED, independently reproduced on both binaries)

`findings.json` fingerprint `runner-env.sysconfig-PYTHON-SYSCONFIGDATA-PATH.loads-code-outside-import-path-rules`; detail in `FINDINGS-DETAIL.md` §1.

The security model promises that code planted in a root never runs at start-up or on import in a later call. The runner holds it with an isolated interpreter (site off, only the zip on `sys.path`, `PYTHON*` ignored) and by allowing `import_path` entries only from read-only grants. CPython's `sysconfig` reads the private variable `_PYTHON_SYSCONFIGDATA_PATH` from `os.environ` without consulting `ignore_environment` (`Lib/sysconfig/__init__.py:356-363`), and when it is set it finds and executes `_sysconfigdata__wasi_wasm32-wasi` from that folder. The runner's env check (`src/wasi_python/_limits.py:139`, `_check_inputs`) refuses only an empty key and a key with `=`; `_call.py:452` lays `env=` over `BASE_ENV` and `HOME` unfiltered; the reactor copies the environment into `os.environ` (`recipes/reactor_bootstrap.py:143`). `import pandas` calls `sysconfig.get_config_var` at import (`pandas/compat/_constants.py:21`), as scipy, scikit-learn, joblib and statsmodels do.

**Reproduced:** call 1 with a writable root writes `/data/_sysconfigdata__wasi_wasm32-wasi.py`; call 2 on the same root with `env={"_PYTHON_SYSCONFIGDATA_PATH": "/data"}` runs `import pandas` and the planted module prints to stderr, on the snapshot and the plain binary. Controls: without the entry the module did not run; `PYTHONPATH=/data` was ignored (`ModuleNotFoundError`). The guest reports `ignore_environment=1`, `isolated=1`.

**Who it reaches:** an embedder that forwards this variable, for example from a shell that sourced `scripts/python-wasi-cross` (line 25 exports it) with the CLI's `--env`, into a call on a folder an earlier guest could write. The security model's "not protected" list names only `HOME` and `PYTHONTZPATH` overrides (`docs/explanation/security-model.md:82`).

**Fix (spec 132):** refuse the key in `_check_inputs` before any work, with a message that points to `import_path`; drop it in the reactor as defence in depth; name it in the security model; a check that plants in call 1 and asserts call 2 raises `ValueError`.

### F2. A guest can override a keyword a class tool's constructor binds with a partial or partialmethod. Low (impact medium, likelihood low); confidence high (EXECUTED, three constructor shapes, through the real door, frame host and gate)

Fingerprint `src/wasi_python/tools.py:_bound_keywords:class-construction-partial-unfixed`; `FINDINGS-DETAIL.md` §2.

`tool()` promises that a keyword a `functools.partial` binds is fixed: left out of the schema, refused when a given schema names it, refused in a frame. `_bound_keywords` (`tools.py:439-474`) treats a class like any callable object: it reads `type(cls).__call__`, meets `type.__call__`, a C slot, and returns with nothing found (`tools.py:466-470`). It never reads the class's own `__new__` or `__init__`, where `inspect.signature` and the runtime find the partial. So `Tool._fixed` is empty, `_given` (`tools.py:418-423`) accepts a schema that names the keyword, and the frame refusal (`_tool_host.py:1003-1009`) never fires.

**Reproduced:** three class tools (`__init__` a `partialmethod`; `__init__` a `partial`, which Python 3.14 makes a method descriptor; `__new__` a `staticmethod` over a `partial`), each binding `role="viewer"`, under a schema naming `role`. A frame with `role="admin"` was answered `ok`, the gate received `{"q": "x", "role": "admin"}` against the documented contract, and each constructor ran with `role="admin"`. In the same run the plain-partial control was refused at `tool()` and per frame.

**Who it reaches:** an embedder that registers a class as a tool with authority bound this way and an explicit schema that leaves the keyword open. A derived schema is unreachable (`tool()` refuses a class without hints).

**Fix (spec 133):** read the class's construction path as `type.__call__` runs it (`inspect.getattr_static` for `__new__` and `__init__` through the MRO, unwrapping `staticmethod` and `classmethod`), then walk each with the existing loop; or refuse such a class at `tool()` as an unbound `partialmethod` is refused today. Rows for the three shapes in `tests/checks/test_v1_4_embedding.py` beside `test_bound_keywords_are_fixed_however_the_partial_is_reached` (line 3517).

### F3. The metered engine on wasmtime-py 49.0.0 drops the fuel of C++ work that ends in a caught exception (GHSA-m63x-6p34-q65x). Low (impact medium, likelihood low); confidence high (EXECUTED twice, independently; a standalone differential against the pinned CLI)

Fingerprint `wasmtime-49.0.0:GHSA-m63x-6p34-q65x:try_table-catch-fuel:src/wasi_python/_engines.py:_engine`; `FINDINGS-DETAIL.md` §3. Promoted from needs-validation by r04; as the skill requires, re-verified by a further independent verifier (v05) and record-checked (r05) before the promotion was applied.

The pin admits only wasmtime-py 49.0.0 (`pyproject.toml:18`, `uv.lock`), whose Cranelift fuel accounting resets to the pre-call fuel on the exceptional edge of a call inside `try_table`, so the callee's work before the throw is not counted. The advisory is fixed in wasmtime 49.0.1; no wasmtime-py carries it yet. The build compiles C++ with `-fwasm-exceptions` (`scripts/steps/55_matplotlib.sh:50,102`; `recipes/wasi-scipy.cross:44` and the other cross files) and links with it (`scripts/steps/60_link.sh:129`): `python.wasm` carries 44,791 `try_table` sites in 7,905 functions and 2 tags. Every caught C++ exception, and every `longjmp` under `-wasm-enable-sjlj`, takes that edge.

**Reproduced from guest Python:** kiwisolver's `Solver.addConstraint` catches `UnsatisfiableConstraint` after the C++ solver builds a row whose size grows with the system. One failing call is counted at about 17,000 to 19,600 fuel whether the chain has 200, 2,000 or 6,000 variables, while its wall time grows from 9.6 to 190 µs. A same-shape no-throw control is counted at 140,067 fuel per call at 200 variables and 1,552,404 at 2,000. Under a cap of 2.2e9, 20,000 failing calls on a 2,000-variable chain finished with exit 0 and 2.02e9 fuel used; the no-throw and weak-strength loops each ended `out of fuel`. The standalone WAT module: 1,101 fuel on wasmtime-py 49.0.0 against 80,001,285 on the pinned CLI 49.0.3. The under-count is about 100 times at 6,000 variables, by wall-time calibration.

**Who it reaches:** an embedder that relies on fuel as the bound (`deadline_s=None`, a fuel cap tighter than the deadline, or `fuel_used` read as an instruction count). The default 60 s deadline bounds wall time through epoch interruption, which the advisory does not affect. `SECURITY.md` lists a guest that runs past its fuel cap as in scope and names two advisories the runner handles; not this one.

**Fix (spec 127 closes it; spec 134 records it):** the pin's move to wasmtime 50 (spec 127, drafted, reviewed before build) carries the fix. Until it lands, `SECURITY.md` should name the advisory as unmitigated and the security model should say that fuel under-counts a caught C++ exception on 49.0.0; a judge check, counted in fuel only, that a failing call's fuel grows with the system as the no-throw call's does, red today as a known gap 127 closes. Disabling the exceptions proposal is not an option: the build depends on it.

### F4. The `.cwasm` checked by `lstat` is not the file wasmtime deserializes, and no ancestor of the cache folder is checked. Needs validation (no severity); the cross-user case is the owner's to settle

Fingerprint `src/wasi_python/_engines.py:_load:cwasm-checked-by-lstat-opened-by-path`; `NEEDS-VALIDATION.md`.

Spec 113 guards the cache by the grant judge (the fix) and by modes (a filter on new files), and narrows the check-to-load window with a second `lstat` (`_engines.py:233-237`). What remains: `private()` (`_platform.py:556-577`) reads the leaf alone; `Module.deserialize_file` opens the path itself; the default cache comes from `$HOME` (`_engines.py:85`, `_platform.py:534`). An owner of an ancestor of the cache folder, who is not this user, can replace the folder or the file between the check and the open, and nothing in the chain says who owns `~/Library/Caches` or `~/.cache`.

**Reproduced for one user** (EXECUTED, h04, v01, r02): a deterministic swap loaded the planted module; a blind race hit 3 times in 5,000. **Not observed:** another user owning the ancestor. The machine has a second local account but the audit held no credentials for it and would not run as another account on the owner's machine.

**The question for the owner (question 112, in spec 135):** is running the runner as root or as another user with a different user's `$HOME` or `$XDG_CACHE_HOME` (sudo keeping `HOME`, a container or CI step with a mapped home, a home on a shared folder) a supported configuration? If yes, spec 135 is a fix; if no, the security model says so and spec 135 is defence in depth. **Answered the same day** (the owner, 2026-10-25, `../decisions.md`): not supported, provided no real use a developer may want breaks; spec 135 never refuses a call (a cache under another user's folder is not used, with a warning), so it is defence in depth, after 0.1.0.

**Fix (spec 135):** open the `.cwasm` once with `O_NOFOLLOW` from a descriptor of the checked cache folder, `fstat` that descriptor for kind, owner, mode and link count, and deserialize what that descriptor holds (through a `/dev/fd/N` path on POSIX, as spec 129 reads its pipe); judge every ancestor of the cache folder as owned by this user or root and not group- or other-writable, else the cache is not used and a warning says why.

## Hardening notes (no finding; grouped; the hunters' text condensed, with the specification each goes to)

**Release workflow and CI (h10).** Release authority rests on one identity: both rulesets give the admin role `bypass_mode: always`, the environments have a tag policy but no required reviewer, and the tag-on-main check lives in the tagged commit's own workflow file (repository settings: the owner's, not a specification). The signer identity users are told to verify is stale after the rename to `wasi-python`: `release/version.py:301-303` and `docs/how-to/verify-a-download.md:20-21` name `ClayGendron/wasi_python`; the next release's attestation will carry the new name and the documented command will fail closed (**136**). The same-bytes step (`release.yml:448-457`) compares only the tarball's inner `SHA256SUMS` with the rebuilds, never the inner files against it; the judge legs close it for the binaries and the zip, not the licence files (**136**). Main-scope set caches are written by two jobs with no in-run rebuild proof; a planted entry would end red today, so denial of branch runs is the worst case (note). The PyPI trusted publisher's environment binding cannot be seen from here: the owner confirms on pypi.org that the publisher names `release.yml` and environment `pypi` (owner). The verify job resolves wasmtime from PyPI unlocked, as users do (note).

**Build inputs and the wheel (h11).** `pinned()` in `scripts/steps/common.sh:52` and the three `grep "  $wheel\$"` lookups match the name as a regular expression: on a fixture, `pinned foo.tar.gz` accepted an unpinned file because `fooXtar.gz` was pinned; no current pair collides (**136**). No meson build but HarfBuzz passes `--wrap-mode`, and libraqm 0.10.5 carries an unhashed `[wrap-git]` for SheenBidi at `master`; the recorded build resolved it through pkg-config (**136**). `scripts/assemble_artifacts.py` reads some downloads without `pinned_bytes()` (**136**). `00_download.sh`'s curl lacks `--proto '=https'` (**136**). `[build-system] requires = ["hatchling"]` is unbounded outside the hashed release constraints (note). `set_key.py verify` proves a set is whole and from this checkout's recipes, not who wrote it (note).

**The binaries and the zip (h12, h17, h18).** The snapshot's zeroed hash secret also fixes pyexpat's salt, so XML parsers on `snapshot=True` can be flooded as dicts can (**137**, the security model). `_zip._member_parts` does not refuse Windows-reserved names or names equal under case folding; the shipped zip holds none (**137**). 31 `assert __FILE__` strings and four build-config modules keep the container prefix `/wasi-python-build/` (note). The `br_table` maximum, the even tag count and the exnref liveness are measured by hand and belong in a per-build check until the pin passes 49.0.3 (**134**). The advisories memo of 2026-10-18 is out of date: the module enables exception handling (**134** adds the addendum).

**Module cache and artifact set (h04).** Open by descriptor and `fstat`; judge the ancestors (**135**). macOS ACLs are invisible to `private()`: an allow entry granting everyone write on the cache folder is inherited by every new `.cwasm` (**135**). A set given through `artifacts=` is hashed and compiled from two separate reads, so a file changed between them poisons the entry a later checked call loads (**135**). `cache_dir=""` becomes the working folder (**135**). Caches other calls named as their own `cache_dir` are unknowable to this call (documented; note).

**Door and tools (h05, h06).** `_door_answer` (`_call.py:1215-1223`) checks `memoryview(response).nbytes` and then calls `bytes(response)`; a bytes subclass with `__bytes__` returns a larger object, so `MAX_RESPONSE` is not enforced on what is written (observed: 5,000 bytes through a cap of 1,000); only the embedder's own host can cause it (**137**). The same shape lets a subclass's `__len__` run on the guest thread and disagree with the buffer copied (**137**). `_door` re-raises `wasmtime.Trap` from the whole frame, not only from `host_alloc`, so a host that raises a trap ends the call as `trapped` with its text (**137**). Unbounded re-entry of the door from a custom `host_alloc` aborts the process in wasmtime-py's trampoline; the shipped guest cannot do it (**137**, a depth guard). `_given` checks bound keywords against the root `properties` only, not a `$ref`, `anyOf` or `oneOf` (**133**). A gate that falls off its end allows (documented; note).

**Filesystem, private folders and roots (h01, h03).** The security model says the runner refuses "a grant or root over any module cache it knows of" (`security-model.md:20`), but a read-only grant over the cache is accepted, as `docs/how-to/grants.md:104` says (**137**, the sentence narrowed). `make_missing` (`_platform.py:387-409`) adopts a folder a concurrent call made and makes components at the umask's mode, so a missing root under a folder another user can write can be pre-made by that user (**137**). The runtime folders judged do not include other host `sys.path` entries (note). The set-times calls stay wasmtime 49.0.0's own, in GHSA-j2g9's range, not reachable through CPython's `utime` (note; 127 closes it). The private-folder sweep checks the lock's owner but not the folder's (**137**). `.gitignore` lists no `.env` or `*.pem` pattern (**136**).

**Guest memory and the shadows (h02, h14).** `_poll_plan` accepts misaligned pointers and unknown flag bits where wasmtime ends the run or answers `EINVAL`, and reports descriptors above 3 ready where wasmtime answers `EBADF`; no memory effect (**137**). The forwarded `fd_readdir`'s trap path is left unzeroed; `python.wasm` cannot read it (note; 127 removes the shadow). `_zeroed`'s private page is bounded on its own, not jointly with the guest's memory (note; 127 removes it). `PreparedCall.call` assigns into ctypes fields that truncate silently; every argument is below 2**32 today (note).

**Environment and loaders (h15).** `SCIKIT_LEARN_DATA` names a folder from which scikit-learn's `fetch_*` load pickles; the same shape as the documented `HOME` override (**132**, named in the security model). Every env-driven module-name selector in the zip is safe only because the import path is read-only; a regression row that plants a module and a dist-info and runs with those keys would hold it (**132**).

**Process integrity (h08).** A forked child hangs for good in `wasmtime_module_new` when the parent compiled any module through wasmtime-py directly, before the guest runs, so no deadline reaches it; the embedder's own act (**137**, documented). `_write_output` copies the whole write before the cap applies (note). wasmtime-py's `LAST_EXCEPTION` slot is process-wide (upstream's design; note). The Linux trap-handler check runs before each entry, not during a call (note).

**Positive patterns worth keeping** are listed in `REPORT.md` §5.
