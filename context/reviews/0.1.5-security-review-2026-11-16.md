## Short version

The sandbox's boundary does not move. The guest still imports the same 43 calls, `host.call` and 42 of WASI preview1's (READ, `recipes/guest-imports.txt`). The Rust library adds no import of its own. Each of its objects may import only `wasi_snapshot_preview1.random_get` outside `env`. Every such import is routed through `__wasi_random_get`, which the reactor wraps, and anything else stops the build (READ, `rust_objects.py`, `52_rust.sh` step 7). Both binaries' imports must equal the reviewed list exactly (READ, steps 60 and 80).

What 0.1.5 adds is a large build input and two new things a guest can do:
- **The build.** Rust 1.100.0 is pinned by SHA-256 from Rust's dist server. 113 crates are pinned from crates.io, each pin equal to the lock's checksum. The build runs `--frozen --offline` from an empty cargo home, with a checksum for every unpacked file (READ, EXECUTED by the units and `p_vendor.py`).
- **Panics unwind.** A panic in a PyO3 function raises `PanicException` and the run goes on. A panic in a raw C entry point, which is how orjson's are written, traps and ends the call. Either way it stays inside the guest (READ).
- **pydantic's hash keys.** In an image prepared with pydantic imported, pydantic-core's hash keys may be fixed and public. The security model says so, beside the snapshot's string hash, which is the same class (READ).

**One High: H1.** It is the owner's release gate, not a way out of the sandbox. The owner decided that if both pydantic suites have not run in the sandbox on `panic=unwind` before 0.1.5 is cut, 0.1.5 ships `panic=abort`. Those suites are deferred to 194, which has not landed, and the preparation cuts 0.1.5 with `RUST_PANIC=unwind`. No Medium. Three Lows: **L1**, the pages say "may" about pydantic's fixed keys because nobody has counted the entropy reads; **L2**, the check that pydantic-core's entropy goes through the wrap was never seen failing; **L3**, the release notes say nothing of that new limit. Every finding of the 0.1.4 review is closed. Four notes rewrites: **R1** to **R4**.

## What changed, and what held

### The host calls: entropy and clocks (READ, `rust_objects.py`, `52_rust.sh`, `reactor_main.c:76-147`, `security-model.md`)

- **Entropy.** Rust's standard library and `getrandom` import `random_get` directly, which skips the reactor's `--wrap=__wasi_random_get`. Step 52 reads each kept object's import entries, module and field, and refuses any import outside `env` except `random_get` of type `(i32, i32) -> i32`. It then defines each unresolved name ending in `::random_get` in a written C shim that calls `__wasi_random_get`. The shimmed count must equal the import entries' count, and any other unresolved name stops the step. A direct import whose symbol a link input happens to define fails the count (INFERRED from `imports_main`). Two checks are independent: the import entries refuse what wasm-ld would merge silently, and the binary's import list refuses a new field. 187's run logged `1 shimmed` (orjson and the probe); 190's spec expects two, and its count is not recorded (L1).
- **Clocks.** Rust's clocks go through wasi-libc's `clock_gettime`, which is wrapped (READ, 190's research table, "checked, Ask 3"). A direct `clock_time_get` or `poll_oneoff` would stop step 52; a unit row plants one (READ, 187's landing notes; EXECUTED, `test_rust_objects.py` passes). foldhash seeds from an address and `UNIX_EPOCH.elapsed()`, the wrapped clock (READ, 190, Decision 7).
- **What the wrap means for hash keys.** In a plain call the keys come from real entropy at first use. While an image is prepared, entropy is pinned to zeros, so keys drawn then are the same in every image of the set. The build's own snapshot pre-imports only `encodings, io, os, sys, json, csv, re, _colorize` (READ, `reactor_main.c:73`), so a default `run` draws its keys in the call. `make_package_snapshot()` imports pydantic by default (READ, `recipes/snapshot-packages.txt`). The pages say such an image "may" hold fixed keys, and one whose prelude builds a model does. Crafted JSON can then collide in a model's extra-keys map, which slows that call until its deadline (READ, `security-model.md`, `limitations.md`). This is the owner's Decision 7 (A), the same class as the snapshot's fixed string hash.
- **Faker** keeps a module-level generator, which the bootstrap now reseeds at each start from an image (READ, `reactor_bootstrap.py:106`).

### Supply chain: the build (READ, `00_download.sh`, `10_tools.sh`, `52_rust.sh`, `rust_vendor.py`; EXECUTED, units and `p_vendor.py`)

- **The toolchain.** Five tarballs a host come from `static.rust-lang.org/dist/2026-11-12/`, each pinned. Step 10 copies the folders each tarball's `components` file names, refuses an odd component name, runs no `install.sh`, and stops unless `rustc -V` and `cargo -V` print the pinned commits.
- **The crates.** Each crates.io package of `recipes/rust/Cargo.lock` must be a pin whose SHA-256 is also the lock's checksum. It is unpacked with a refusal of any member outside its folder or not a plain file, and a `.cargo-checksum.json` holding every file's SHA-256. `rust-src`'s vendored crates must match a pinned crate of the same name and version byte for byte. The lock keeps orjson's and pydantic-core's own versions but for two named raises (READ, 190's review, finding 3).
- **The build is closed.** Cargo runs `--frozen --offline` with `CARGO_HOME` holding one file, which replaces crates-io with the pinned folder and sets `net.offline`. Any `.cargo/config*` above `build/` stops the step. `RUSTFLAGS`, the wrappers and every `CARGO_BUILD_*`, `CARGO_PROFILE_*` and `CARGO_TARGET_*` are unset. Three hosts must build the same bytes (READ, 187's landing notes).
- **Carried patches.** orjson carries three: an rlib crate type, PyO3 0.30, and no global allocator, whose alignment-blind allocator would have served pydantic-core's 64-byte requests. folium carries one (a lazy `import requests`), and branca one (its tables as package data). Each has a facts sheet under `context/upstream/patches/`, and the README counts 38 (READ). `test_source_tree_matches_its_tarball` must pass for 45 trees (READ, `release.yml`).
- **What runs natively.** The crates' build scripts and proc macros run on the build host, as build tools. The build job holds `contents: read` and no secret (READ, `release.yml:299`). Notes.

### The link-map and import gates (READ, `rust_objects.py`, `60_link.sh`, `80_snapshot.sh`, `import_list.py`)

- `keep` writes an archive with only the umbrella's object and the module crates' own build-script C objects. It drops `compiler_builtins`, whose weak `round` and `sqrt` would otherwise replace wasi-libc's, and stops on any other member.
- `foreign` refuses any global name of the archive that the SDK's six runtime libraries also define. `inits` requires exactly the init functions of `modules.txt`.
- After the link, the map must show the math names from `libc.a` and the 128-bit helpers from `libclang_rt.builtins.a`. `round`, `sqrt`, `fma`, `__multf3` and `__multi3` must be named, so the check cannot pass on an empty map.
- Both binaries' imports must equal `recipes/guest-imports.txt`, one more or one fewer. Each gate is seen refusing at unit level (EXECUTED), and each rule was planted in the real file and run red (READ, 187's landing notes, "Decision 14's rules").

### New packages and the guest's new powers (READ)

- `_rust_probe` ships in both binaries. It can panic, abort its own call, or return a std `HashMap`'s order. That last one shows the guest its own call's keys, or a session's, which is one trust domain. It adds no import and no power a guest lacked.
- **Panics.** Under unwinding, std is rebuilt from `rust-src` under `RUSTC_BOOTSTRAP=1`, with the standard exception form and C++'s tag. A caught panic leaves Rust's state as the panic left it, inside guest memory (INFERRED). This is safe for the host: memory a panic corrupts is the guest's, and a trap ends only the call. Whether it is ready to ship is the owner's gate (H1).
- pytz, rich, Faker, folium, branca, xyzservices and pydantic's pure packages are zip members, read-only, and run as the guest.

## Notes (no finding)

- **The callback scanner now finds fewer getset tables** (`fb4a1bc6`). It keeps a getset table only where a static type's `tp_getset`, a `Py_tp_getset` slot or a code store at offset 124 points at it. This ended a false finding in libxml2's data.
