7. **Low: the callback pool** (Decisions 4 and 6). The libffi stand-in cannot make a closure (`ffi.callback`) or call through a function pointer (`ffi_call`, ABI mode, varargs); in API mode cairocffi needs neither but three callback types. Read is transient. Write lives as long as a stream surface. Destroy lives in every `KeepAlive`: each stream surface, each `ImageSurface` over a `data` buffer (`surfaces.py:731`) and each `set_mime_data` (`:508`). So the destroy pool, not only the write pool, caps live surfaces. A `KeepAlive` goes only when cairo calls destroy, which for a surface in a reference cycle waits for the cyclic collector: cairocffi's own tests call `gc.collect()` first (`test_cairo.py:189-215`). 128 is ample otherwise: one CairoSVG conversion holds at most one stream surface, and drawsvg's GIF frames use transient writes. Fix text: "On a full pool the stand-in runs `gc.collect()` once and retries before raising `MemoryError`. Each slot keeps its own `error=` and `onerror=`, in the decorator and the direct form. The check's 129th surface covers an `ImageSurface` over data too."
