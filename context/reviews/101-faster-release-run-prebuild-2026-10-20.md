## The draft's key finding, checked

**A cache hit cannot skip a from-source build: confirmed** (EXECUTED, read). The build shard reads the build tree, not the set: `test_source_tree_matches_its_tarball` needs the 26 unpacked trees, `test_every_compile_contracts_nothing` and `test_every_build_python_is_pinned` read the compile records and meson logs, `test_the_backend_orders_try_tables_alike` and `test_ducc0s_fft…` run the SDK's `clang` under `build/tools/`, `test_one_qhull_is_linked` reads `build/link/python.map` and `llvm-nm`, `test_the_guests_configure_results_are_recorded` reads the guest's `pyconfig.h`, and `test_recursion_raises_under_the_wasmtime_cli` runs `build/tools/wasmtime-v*/wasmtime` (`tests/checks/test_v1_5_rebuild_from_pins.py`; `paths.wasmtime_cli`). So "reuse with the build shard kept on macOS" does not exist on a reuse run. Moving the build shard to a job that always builds is the only way to keep every check on every run.

**The build shard has no metrics or facts to lose: confirmed** (EXECUTED, `acc_probe.py`): 50 goal rows in `accepted.json` (the file plus the two named nodes), all `pass`, none with `metrics`, none with `facts`.

**G2 is a real cross-host proof: confirmed** (EXECUTED, read). `plugin.py:700-714` hashes `python.wasm` and `SHA256SUMS` in `paths.artifact_dir()` when it writes the record. In a judge shard that is the unpacked `.tar.xz`. In `build-shard` it is the job's own `build/artifacts`, as long as the job sets no `WASI_PYTHON_ARTIFACTS` (L6). The gather compares both with the build job's `wasm-sha256` and `set-sums-sha256`, which the build job hashes from `build/artifacts`. Nothing is copied from an input.

**Layer 3 is stronger than the draft says** (INFERRED from the scripts). On a reuse run, the two rebuilds and `build-shard` each run all of `scripts/build.sh`: the constructor gate (step 60), `apply_patches.sh`'s drift refusal, and step 10's host-Python gate. So an input that changes only a gate's verdict also turns a reuse run red. And `MANIFEST` already hashes every tracked file under `scripts/` and `recipes/` (except `bench_*`) and every pin (except the research pins) (`scripts/assemble_artifacts.py:686-698`). So most of the key is already bytes in the set. In short: a missing key input can cause a false red, never a false pass. The key decides speed and whether the set "is this commit's", not whether the verdict is right.

## Findings, most severe first

1. **High — H1. Moving the build record to Linux makes sameness report a false suite difference at every landing** (`tests/harness/sameness.py:51` and `:144-151`; the Design table leaves `sameness.py` out). Spec 092 has landed. Its `view()` adds up the unit suite from the release record's runs whose platform starts with `darwin-`, and maps the system `build` to darwin in `SYSTEMS`. Today the build record is `darwin-arm64`, so `tests/unit/test_pins.py`'s 10 unit tests count on the darwin side. After 101 the record is `linux-aarch64`, so the release's darwin suite is 10 tests short of the lane's local darwin record. Failure: EXECUTED with `suite_probe.py`, using a release record whose build run has 10 units and own-rest has 90, against a local record with 100. With the build run on `darwin-arm64` the result is `[] []`. On `linux-aarch64` it is `["suite: {'total': 100, 'passed': 100} != {'total': 90, 'passed': 90}"]`. AGENTS.md rule 6a ejects an entry for any unexplained difference. So 101's own wave, and every wave after it, gets a difference that only a claim can explain. Fix (add to *Design* and *The checks*): "`tests/harness/sameness.py`: `view()` counts a run's suite on the darwin side when its key is the build shard's (`build/build`) or its platform starts with `darwin-`; `SYSTEMS` maps `build` to `linux` (`{"darwin": {"macos"}, "linux": {"linux", "build"}, "win32": {"windows"}}`) so `_ci_block` reads a block in `build-shard` as Linux's. Unit rows in `tests/unit/test_sameness.py`: a release record whose build run is `linux-aarch64` and a local darwin record with the same units give no suite difference; a build run missing one unit still gives one." Add `sameness.py` to the `--accept-judge` reason.

2. **Medium — M1. A tag run no longer checks its published build's own records in CI. The draft says "nothing the verdict means has changed" and "no check is retired".** (Decision 5; the owner's choice 2.) Today a tag's build shard runs on the macOS tree that built the published bytes. After 101 it runs only on `build-shard`'s Linux tree, on every run, tags included. These checks no longer see the published build in CI:
   - `test_every_compile_contracts_nothing`: the macOS compile records, and the macOS `clang -###`.
   - `test_every_build_python_is_pinned`: the macOS meson logs, `config.log`s, PATH folders, and the gate line.
   - `test_the_backend_orders_try_tables_alike` and `test_ducc0s_fft_compiles_to_one_object`: the macOS `clang`.
   - `test_one_qhull_is_linked`: the macOS link map.
   - `test_the_guests_configure_results_are_recorded`: the macOS `pyconfig.h`. `same-bytes` and G2 still prove the bytes are equal. What is lost is the check of how the published build was made, for example an unpinned host Python on the `macos-15` image that happens to give equal bytes (§4.2). The lane's darwin run at landing still covers these checks, but on the lane's machine, not on the runner image the tag builds on. Failure: a `macos-15` image update puts a Python ahead of step 10's shim. The tag's bytes equal the Linux rebuilds. The tag run passes, and no CI job reads the macOS records that would show it. Fix: put choice 2 to the owner before the build (see "Owner's choices" below), with this text in Decision 5: "On a tag, a dispatch on main and a `from-source` run, the build shard's checks see only `build-shard`'s Linux tree in CI. The published macOS tree is checked by the zero-patch step, by `same-bytes` and by G2 (equal bytes), and by the lane's darwin run at landing. The seven record checks listed in Decision 5 no longer read the published build's records in CI." Change *Intent*'s "nothing the verdict means has changed" to "the checks are the same; on a tag, seven of them read a Linux tree that builds the same bytes, not the published macOS tree". If the owner refuses, the fallback is: on source runs the build job keeps the build shard as a step (`if: needs.inputs.outputs.reuse != 'true'`), handing on `record-id` as today; `build-shard` runs only when `reuse == 'true'` (a job-level `if:` that rule 1 of spec 063 must allow for this one job); and the gather reads the build record from whichever job `set-source` names. This costs source runs their 2 to 3.5 minutes back.

3. **Medium — M2. `set-cache.yml`, the one writer to the cache every branch reads, falls under no workflow rule except the pin rule** (Decisions 7 and 12; `tests/checks/test_rules.py` runs `release_binding_errors` and `rebuild_gate_errors` on `release.yml` alone; only `test_every_action_is_pinned_by_commit` globs every workflow). Decision 12 says the `seed` job is `contents: read`, but no check holds it there. The key's `env` lines are read from `release.yml`. If `set-cache.yml`'s `env:` or its `setup-uv` version drifts, the seed builds under other values and saves the result under `release.yml`'s key. Failure: a later change bumps `UV_VERSION` in `release.yml` but not in `set-cache.yml`. Every branch then reuses a seed built with the old uv. Fix (add to *The checks*, check 2): "`scan.release_reuse_errors` also reads `set-cache.yml`: its triggers are exactly `push: branches: [main]` and `workflow_dispatch`, with no `pull_request` and no `pull_request_target`; its top-level `permissions: {}`; `seed`'s `permissions` exactly `contents: read`; `setup-uv` with `version: ${{ env.UV_VERSION }}` and `enable-cache: false`; no `${{` in a `run:`; its top-level `env:` equal, name for name and value for value, to the key's `env` lines from `release.yml`; its build steps exactly `scripts/00_download.sh` and `scripts/build.sh` with no arguments; and `actions/cache/save` comes after the step that runs `release/set_key.py verify`. Mutants: a `pull_request` trigger; `UV_VERSION` changed in one workflow only; a save before the verify."
