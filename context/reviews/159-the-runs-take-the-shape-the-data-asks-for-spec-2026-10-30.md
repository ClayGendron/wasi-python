## Findings, most severe first

1. **High: Decision 5 turns every post-merge run red and stops acceptance** (`tests/harness/gather.py:81-95`, `:324-338`, `:455-467`). With no `PLAN` after a merge, `expected_keys` expects `build/build` (EXECUTED), G3 reds every build-shard check as "collected, run in no record", and G5 reds each one `accepted.json` holds as "accepted pass, ran in no record" (READ; 55 such lines). The spec changes only `select()`. Failure: the first merge after 159 runs the normal tier green, the gather is red on G1, G3 and G5, `accept-record` never runs, and under today's rule `dev` is frozen. Fix: the specification decides how a post-merge gather treats an unselected build shard (narrowed as a pull request's is, its accepted rows carried by `--accept-from` unchanged), names `gather.py`, the acceptance code and their unit rows in Design, and adds a criterion: a post-merge gather with no build record and the build shard's accepted rows is green and its acceptance keeps those rows.
2. **High: the build shard has no tree to run on where the set is reused, and the plan cannot know** (`release.yml:183-245`, the `inputs` job). The weekly run and a branch dispatch reuse a cached set when one is cached (READ), so the build job compiles nothing and the build shard "inside it" cannot run. `reuse` is decided after the plan, so the plan's `build` cannot follow it. Failure: the weekly run sets `build`, the build job restores the cache on `ubuntu-24.04`, the gather is red on G1 every Monday and opens the issue; or a builder forces a compile on the weekly run, and the weekly comparison of the cached set with fresh rebuilds, the one 138 Decision 4 trusts cached sets on, is gone. Fix: decide one. For example, the build shard runs in the build job exactly when its compile step ran (`set-source` is `built`, already an output), the gather expects `build/build` from that output, not the plan's, and the weekly run keeps the cached set and runs the build shard in the macOS or x86-64 rebuild job. That also brings the build shard back to a post-merge run whose key moved, which is when its checks can change (INFERRED).
