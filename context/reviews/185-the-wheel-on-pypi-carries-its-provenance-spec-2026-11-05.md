## Findings, most severe first
1. **High: the workflow's top-level `env:` breaks both new uv jobs** (`release.yml:67-74`; Decisions 1, 4). Every job inherits `UV_BUILD_CONSTRAINT: release/build-constraints.txt`, `UV_PYTHON` and `UV_LOCKED`. `pypi-attest` and `pypi-verify` check out `.github/actions` alone, so the constraint file is absent, and uv reads it before it resolves anything. Failure: at the 0.1.4 tag, after `publish` has made the GitHub release, the attest-action step exits 2 with "File not found", `pypi` is skipped and 0.1.4 never reaches PyPI. The release page says a re-run cannot help and the tag is never pushed again, so the wheel waits for 0.1.5. "The job sets no `env:`" does not mean "no variable steers uv": three do. Fix: add `release/build-constraints.txt` to both jobs' sparse checkout (`sparse-checkout-cone-mode: false`, or the `release` folder), held by rule 21. The top-level env is held by K4 to `set_key.ENV`, so it stays as it is. Or set `UV_BUILD_CONSTRAINT: ""` on exactly those two steps, with rule 21 admitting only that. Then re-run criterion 2 with the full top-level env, and say in the spec that the signer runs on uv's managed CPython 3.14.2 (`UV_PYTHON`).
2. **Medium: nothing runs the new path before the tag, and a failure there costs a version** (Decisions 1, 4; `docs/contributing/release-process.md`, "Publish" and "Signing"). The release pull request and dispatches never reach `pypi-attest`, `pypi` or `pypi-verify`. Finding 1 is the kind of defect only a run finds. Failure: any further slip (a path, the action's internal step, a CDN lag beyond three minutes) is found after `publish`, with no fix but a new patch release. Fix, either or both: (a) a rehearsal on the release shape with no `id-token` and no upload. It runs `pypi-attest`'s checkout, setup-uv and the action's locked `uv run … python -I -c "import pypi_attestations, sigstore"` with the top-level env, plus `pypi-verify`'s exact command on `pypi:wasi_python-0.1.1-py3-none-any.whl`, whose provenance names `ClayGendron/wasi-python`. That exercises the lock, the pinned uv, TUF and Sigstore verification, and needs no signature. (b) Run `pypi-attest` before `publish`, beside `attest`. `attest` already signs before `publish`, so "nothing is signed for PyPI before the GitHub release exists" is not the rule today. Then a signer failure stops before anything is public. That needs `publish` to tolerate a skipped `pypi-attest` when `PYPI_PUBLISH` is off, which the spec would have to decide. Evidence that closes it: the rehearsal job green on the release pull request of 0.1.4.
3. **Medium: rule 21 does not hold that `pypi-verify` fails closed** (Decision 5, third bullet). The rule asks only that "a step runs `pypi_attestations verify pypi --repository`". Unlike `attest`, it bans no `||` or `set +e`. Failure: a retry loop written as `for i in 1 2 3 4 5 6; do … && break; sleep 30; done` with no final assertion, or `… || true`, or a digest comparison left out, or `--repository` naming another repository, passes the scan and is green on a wheel with no provenance. That is the 0.1.2 loss again. Fix: hold the step's script as a scan constant (as `CI_STATUS_PUBLISH` is), or require its words. The words: the digest read from `release-assets/SHA256SUMS` compared with the JSON API's, `--repository "https://github.com/$GITHUB_REPOSITORY"`, the `pypi:` name taken from `release-assets/*.whl`, an explicit failure after the sixth try, and no `||` outside it. Add mutant rows for each. Give both new jobs a `timeout-minutes` (the CLI's requests have no timeout).
4. **Medium: "cannot mint a PyPI upload token" rests on PyPI's configuration, which nothing records** (Decision 1, "Why a job of its own"). Warehouse refuses the exchange only if every trusted publisher registered for `wasi-python` names the environment `pypi`. 148's history records five attempts at 0.1.1's publisher. Failure: one publisher (or a pending one) left without an environment lets any of the signer's 35 locked wheels request an audience-`pypi` token and upload. Fix: before the build, the owner reads PyPI's Publishing page for the project. The landing notes list each publisher with its repository, workflow and environment, and any publisher with no environment is removed. The spec states that this is the premise.
5. **Low: the signer's uv may be installed unhashed** (Decision 2). `setup-uv@1c37ad07` (v10.3.0) checks a download against its built-in checksum table. Whether that table holds 0.13.5 (released 2026-10-22) is not shown, while 0.9.22's surely is. Fix: read the table at that commit. If 0.13.5 is absent, pass `checksum:` for the linux x86_64 archive, as a scan constant beside `ATTEST_UV_VERSION`. The pin itself is sound: 0.9.22 refuses the lock, 0.13.5 accepts it, and it is 14 days old today.
6. **Low: the AGENTS.md rule says more than the release does** (Decision 6). "The release reads each one back after it publishes" holds only for PyPI's digest and provenance. `attest` verifies before `publish`, and nothing reads `SHA256SUMS` or the GitHub attestations back afterwards. Fix: write "reads PyPI's back after it uploads, and verifies the GitHub attestations before it publishes", or build the rest.
7. **Low: the read-back can say OK on less than criterion 5 asks** (Decision 4). The CLI prints `OK` for a provenance with no bundles, and checks the workflow PyPI recorded, not `release.yml`. Fix: also read the Integrity API's JSON and require at least one bundle whose publisher is `{kind: GitHub, repository: <repo>, workflow: release.yml, environment: pypi}`. Criterion 5 then becomes the job's own check.
8. **Low: the release page's recovery for the two jobs is not written** (Decision 7: "covers the two new jobs"). Fix: say that `pypi-verify` uploads nothing and is re-run alone when a read times out. Say that a re-run of `pypi-attest` makes a new public signature. Say that when PyPI refuses the attestation, "re-run failed jobs" re-runs `pypi` with the same attestation artifact, so the fix is the next patch release.
9. **Low: name the residual of `id-token` in the signer** (Decision 1). The signer's locked wheels can mint Sigstore certificates for `release.yml@refs/tags/v<version>`, as `attest` can. GitHub's attestation store needs `attestations: write`, which the job lacks, so `gh attestation verify` without `--bundle` is unaffected. Write this in the spec, so the owner accepts it knowingly.

Judged sound (no finding): the attestation reaching `pypi` by artifact keeps rules 4, 5 and 10. It is downloaded by one guarded id, `digest-mismatch: error`, before `verify-artifact`, and `pypi` takes the wheel from its own `verify-artifact`, never from the signer, so a signer that altered the wheel only makes PyPI refuse. Rule 16 needs exactly the one exception named. The action's internal `if:`, its `$GITHUB_OUTPUT` write and its internal setup-uv (pinned `c18668ad`, skipped while uv is on the path) live in the action, not the workflow. They write no `$GITHUB_ENV` or `$GITHUB_PATH`, and inputs reach the script through `env:`, so they fit rules 11, 15, 17 and 20 in spirit. Rule 21 must keep setup-uv before the action, as drafted. `TAG_JOBS` also feeds `UNGATED` and `NOT_JUDGED_WITH`, so the two jobs need no plan gate and `accept-record` does not wait on them.

## Disposition (filled in by the author, then confirmed by the reviewer)

After this review, the owner asked how other projects do it; a survey of ten release workflows found every one signing in the upload job, and the owner chose that pattern (`../decisions.md`, "PyPI provenance comes back"). The separate `pypi-attest` job is gone: the action is a step of `pypi`. Each finding is answered on that design.

1. **High (top-level env)** — fixed, Decision 3: `pypi`, `pypi-verify` and `pypi-rehearsal` check out `release` beside `.github/actions`; rule 20 and rule 21 hold it. The spec says the signer runs on uv's managed CPython 3.14.2.
2. **Medium (nothing runs before the tag)** — fixed by (a), Decision 4: `pypi-rehearsal`, on every release-shaped run, runs the action's lock under the workflow's env with the same uv by checksum, the read-back script on 0.1.1, and `verify pypi` on 0.1.1. (b) does not apply: the signer is in `pypi`, after `publish`, as 180 placed it.
3. **Medium (read-back not fail-closed)** — fixed, Decision 5: the read-back is `release/pypi_readback.py`, unit-tested on recorded answers; `pypi-verify` runs exactly two commands held as scan constants, with `set -eu` and no `||` or `set +e`, and `timeout-minutes: 15`; the script's requests time out after 30 seconds.
4. **Medium (PyPI publishers)** — answered, Decision 9: no longer the design's premise, since the signer runs inside `pypi`; the owner is asked to read the Publishing page and remove any publisher outside `release.yml` in `pypi`, recorded in the landing notes.
5. **Low (uv unhashed)** — fixed, Decision 2: setup-uv v10.3.0's table has 0.9.22 and not 0.13.5 (READ), so `checksum: f68d291c…928f`, the release's `.sha256` and the archive's hash (EXECUTED), held as `ATTEST_UV_SHA256`.
6. **Low (AGENTS.md says too much)** — fixed, Decision 7, in the review's words.
7. **Low (OK with no bundles)** — fixed, Decision 5: the script requires a bundle with publisher `{GitHub, <repo>, release.yml, pypi}`.
8. **Low (recovery text)** — fixed, Decision 8.
9. **Low (id-token residual)** — written, Decision 1, "What it accepts", now with the larger residual of signing in `pypi`, which the owner accepted with the common pattern.

A finding of the author's since the review, for the reviewer's reading: uv 0.13.5 uploads an attestation only when it is among the files named, so `uv publish … dist/*.whl` would upload the wheel alone, without error (EXECUTED). The upload names `dist/*`, held to the wheel and its attestation by a step and by rule 20 (Decision 1).

## Verdict
Does not land yet: the High (the top-level env makes both new jobs fail at the tag) and the three Mediums (no run before the tag, rule 21 not holding `pypi-verify` fail-closed, and PyPI's publisher environments unrecorded) stand before it is built.
