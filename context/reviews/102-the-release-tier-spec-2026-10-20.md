## Findings, most severe first

1. **Medium: the four inline-cpu tests stop running on Windows and macOS** (Decision 9; criterion 4; the flags). `test_posixpath` is planned in `cpython-fs` (`tests/upstream/python/cpython-fs.txt:32`). That group runs on all three systems: `upstream-numpy-a` on Linux, `upstream-macos` and `upstream-windows` (`tests/release_shards.toml`). Its inline test reads `is_resource_enabled('cpu')` (`Lib/test/test_posixpath.py:367`, `maxusers` 1000 or 100). Decision 9 puts it in the normal group's `-i` list, so it runs only in the release tier. Decision 10 runs the release tier on Linux alone. So a test that passes on Windows today never runs on Windows again, in any tier. It runs only on Linux CI and in the lane's darwin acceptance. That breaks "every test runs in one tier" for Windows. It also means fewer checks on three systems, against AGENTS.md rule 4. The other three inline tests (`test_tokenize` and `test_unparse` in `cpython-b`, `test_unicodedata` in `cpython-c`) are Linux-only today, so for them nothing is lost. Failure: a change that breaks `posixpath` on Windows (its path rules differ there) passes every run. Before 102 that test would have failed in `upstream-windows`. **Fix text (Decision 9, criterion 4, the claim list, the flags):** "An `inline` entry is **not** ignored in its normal group. It runs in both tiers: in its normal group on every system that group runs on, doing the reduced work `cpu` off allows, and in its release group on Linux and in the release acceptance, with `cpu` on, doing the full work. This is the one case where a test id runs in both tiers. It is not a duplicate, because the work differs, and nothing leaves a system. The partition proof still holds: every `inline` entry is in its normal group's selection and in its release group's `match`. `passes` does not fall, so the `--accept-fewer-passes` flag and criterion 4's 'down by exactly the four' clause go away. Criterion 4 becomes: CPython's normal groups' JSON byte for byte as the base's, `passes` unchanged." Check 2 changes to match: no `-i` entries. Check 4 gains one fixed stream in which an `inline` id is missing from its normal group's stream; that stream is a finding.

2. **Medium: a normal acceptance writes every release-tier pass into the history as removed** (Decision 5; check 5; `tests/harness/scoreboard.py:288-292`). `accept` builds the passed set from the run's own checks. So a check the run did not run is not in the set. The probe showed this, EXECUTED: an accepted pass, deselected in the next run, stays `pass` in `accepted.json` but is listed in that history line's `passed_removed`. Decision 5 says "a normal acceptance never changes a release-tier row". That holds for `accepted.json` but not for the history. Failure: at 102's own landing, the seventeen contourpy groups' suite and class checks were passing and accepted. The landing is in the normal tier. Its history line says those passes were removed. Each later normal acceptance carries the gap, and the next release acceptance adds them back. So the append-only record (AGENTS.md rule 6) says passes were lost and found when none were. Its per-area `counts` fall by the release tier's size. Any reader of `passed_sets` (the history check, a future "since the last release" diff) sees the same false change. **Fix text (Decision 5 and check 5):** "On a normal-tier run, `accept` takes the passed set as the run's passes **plus** every release-tier check that is in the newest line's passed set and in this run's `tier_deselected`. So a normal acceptance's `passed_added` and `passed_removed` name only normal-tier changes. A release acceptance's name every change. Its `counts` count a release-tier row by its accepted status." Check 5 adds: "after a release acceptance in which release-tier check X passed, a normal acceptance's history line has X in neither `passed_removed` nor `passed_added`, and its `passed_digest` covers X."
