## 2. Concurrency soundness

### What holds (READ, with the probes marked)

- **The join.**
  - `_on_guest_thread` opens its `try` before `_start_guest`, and its `finally` is `_join_guest`.
  - `_join_guest` survives any exception raised into the home, recording it, until
    `thread.is_alive()` is false. It falls through only when an exception lands inside its own
    `except`: the abandoned path, which Decision 14 accepts.
  - The body sets `done` under `home.lock`, then runs an abandoned home's steps. `finish` decides
    under the same lock. So each step runs once, either now or after the guest.
- **Hand-offs.**
  - Some interrupts land where `serve` cannot answer the box: after `inbox.get` returned but
    before the item is stored (CPython checks for signals after a C call returns), or inside
    `_Box.answer` before its release.
  - Each such interrupt still sets `home.raised`. The guest then leaves its wait within one
    slice and raises `_Stopped`. Both are covered as Decision 15 says.
  - At most one box is in flight per guest thread. When `raised` is set by the home itself, the
    home is not running any embedder code, so no provider runs at the same time as its guest
    reads the mount table.
- **Sessions.**
  - A turn whose home is forced out keeps `busy` until its guest ends. A second turn meanwhile
    raises "a turn is already running". The session then ends "error", no store is closed under
    wasm, and the next session works (EXECUTED, `probes/abandoned_turn.out`).
  - That row is the one criterion 17 asks for and the build lacks (F4).
- **Ctrl-C and the deadline.**
  - A home that is the main thread waits in 50 ms slices (`SimpleQueue.get`, `join`). So
    `_note_ctrl_c` runs between slices, on every system, Windows included.
  - The deadline is judged by the epoch callback against the ticker's count. The outcome is the
    same as before: still "deadline".
- **Leaks** (EXECUTED, `probes/leak.out`):
  - Python threads, OS threads and RSS before → after 300 door runs, 300 turns and 60 sessions:
    (2, 24, 154,832 KiB) → (3, 25, 154,912 KiB).
  - The one extra thread is the session reaper.
- **Nested runs:** a door host that calls `run()` makes a new home on the same thread, which
  serves its own inbox while the outer guest waits on its box (READ). That is sound.

### What does not hold: F1 (EXECUTED, `probes/start_interrupted.py`, `.out`)

- **Where.** `_start_guest`'s `except BaseException` around `thread.start()` resets
  `home.done, home.thread = True, None`.
- **Why that is wrong.** `Thread.start()` makes the OS thread, then waits on `self._started`, and
  that wait can be interrupted. An exception raised there means the thread exists and will run
  the guest. The home has just forgotten it:
  - `_join_guest` returns at once;
  - `finish` runs every release step now: `store.close()`, the private root, the output keys.
- **The probe.** A stand-in `Thread.start` runs the real start, then raises `KeyboardInterrupt`.
  It prints:
  - `interrupted`;
  - `guest threads alive when run raised: ['wasi-python-guest']`;
  - `closes while wasm ran: ['MainThread', 'MainThread']`.
  The stand-in close only records. A real `Store.close()` there is the use-after-free that the
  pre-build review's `close_while_running.out` measured as SIGSEGV.
- **Who can trigger it.**
  - Under `_deferred_ctrl_c`, Python's default handler only sets a flag, so a plain Ctrl-C
    cannot.
  - An embedder's raising SIGINT handler (criterion 8's case), or `PyThreadState_SetAsyncExc` on
    a worker home, can, if it lands in the tens of microseconds while the thread starts.
- **A smaller window of the same kind:** an exception between `home.done = False` and the inner
  `try`. It leaves `done` false with no thread to end it, so the teardown never runs, and a
  session would stay busy for good.

### Notes (F7)

- `serving` is set only when the home enters `serve()`, after `thread.start()` has returned.
  Suppose a guest hands off before that, and the home is delayed more than one 50 ms slice. Then
  the guest raises `_Stopped`, and `run` raises that private exception.
  - That is improbable: instantiation alone takes milliseconds, and the home needs microseconds.
  - It is still a gap in "every hand-off answered".
- After `raised` is set, `serve` keeps running new hand-offs, and `call` posts new boxes without
  looking at `raised`. So a provider or the door host can run once more after the call has
  stopped, until the next epoch check.

## Findings, most severe first

### F1 (fix before landing): an interrupted `Thread.start()` closes the store under a running guest

- **The fault:** section 2. `_start_guest` forgets a guest thread that exists when
  `thread.start()` raises after the OS thread was made. The home then tears down the store and
  folders while the guest's wasm runs (EXECUTED: two `Store.close()` calls on `MainThread` while
  wasm ran).
- **Why it blocks:** Decision 14 and the README say the store is never torn down under a running
  guest. This is the same use-after-free, through a narrower door.
- **Fix:**
  - Make the start a handshake under `home.lock`:
    - set `home.state = "starting"` (and `done = False`) before `start()`;
    - the body first takes the lock: if the state is "cancelled" it returns at once, with no
      wasm and nothing to tear down; else it sets "running";
    - on an exception from `start()`, take the lock: if the state is still "starting", set
      "cancelled" and `done = True`; if it is "running", keep `done` false and the thread, so
      the join waits.
  - Let `_join_guest` wait on an event the body sets, not only on `thread.is_alive()`.
  - Move `home.done = False` inside the guarded region, so no exception leaves it false with no
    thread.
  - Add a unit, and a child row like my probe: a `Thread.start` stand-in that starts and then
    raises.

### F2 (fix before landing): `no-missing-stdlib-info` names README as its closer, but it is a recipe omission

  `_sysconfigdata` in the WASI build's `lib.wasi-wasm32-3.15/`, and `70_zip.sh` does not copy
