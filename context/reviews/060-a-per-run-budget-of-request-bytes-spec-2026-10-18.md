## What holds

- **The budget is checked before a byte is read (READ, EXECUTED).** `_door` calls `admit(length)` after the address checks and copies the frame only when `admit` returns `None` (`runner.py`, `_door`). Under the prototype, frames refused by the budget never reached `_ToolHost.__call__`: 60 frames of 1,000,071 bytes gave 16 reads and 44 `budget_exceeded` (P3, "after"). So frames sent after `budget_exceeded` cost only `admit` (the memo's 2.85 µs), and `max_tool_calls` still bounds how many.
- **What it counts is the cost F3 names.** Every frame `admit` lets through is parsed, whatever the answer: P1's `protocol` frames (bad JSON at the end, an unknown op) cost 0.06 to 0.24 s per MiB, and all of them are admitted, so all would spend. Counting admitted lengths, not claimed ones, is right: the judge already sends a frame that claims 1 GiB (memo, `tally060.txt`).
- **No bypass through async tools or gates (EXECUTED P3, READ).** An async tool's frame takes the same `admit` → `__call__` → `_parse` path; the prototype refused its third 400,072-byte frame exactly as for a sync tool (`[300000, 300000, 'budget', 2]`, 4 reads). A gate runs only after the parse, on an admitted frame, so a denied call has already spent its bytes (P3: `denied` with 400,071 request bytes). The raw path (`host(frame)` with nothing pending) admits in `__call__`, so it counts the same way.
- **The worst shape still holds (EXECUTED P1).** Of 17 shapes, the memo's empty objects under `Any` is still the worst, 0.317 s/MiB here. Next: `[[]]` (0.280), `{"":0}` (0.296), `list[int]` zeros (0.245), `list[float]` (0.218), unique keys under `dict[str, int]` (0.236). Invalid UTF-8 costs nothing; one long escaped string, 0.03 to 0.07. So "about 5 s here, about 10 s on the review's Mac" for 16 MiB stands.
- **The default is sound.** No legitimate path the judge drives comes near it (the memo's tally: 63,300 bytes at most through `run`). A frame is already capped at 1 MiB, and `bytes` cross as base64 (READ, `recipes/guest/host/tools.py:78`), so a 300,000-byte argument is a 400,071-byte frame (P3). A guest that sends a big dataframe through a tool must already chunk it into frames under 1 MiB; 16 MiB is 16 such chunks, about 12 MB of binary. The README's recipes send tens of bytes. The rejected 4 MiB and 64 MiB are argued correctly. I agree with 16 MiB.
- **§4.15 is read correctly (READ).** Its words: "Every limit has a default (memory, time, output) … A change that loosens a default needs the owner's decision, not only a review." This adds a limit with a default and loosens nothing, so no owner's decision is needed. The spec's paraphrase ("asks the owner only for a looser default") is faithful.
- **The failure path is consistent (READ, EXECUTED P3).** `budget_exceeded` is an existing kind in the snapshot's `outcome kinds`; the guest maps it to `ToolBudgetExceeded` (`recipes/guest/host/tools.py:37`) and keeps no "used up" state, so a later frame that fits is answered (P3: the fourth call, `b"ab"`, returns 2). The record's refusal is like `admit`'s others (`op=None`, `tool=None`, the claimed length). `stats()` keeps no per-run tool counts (READ), so it does not change. The order in `admit` (frames, then 1 MiB, then bytes) is right, and criterion 1's stand-in (d) pins it.
- **Spec 049 (READ).** The four snapshot lines match the file's format and places (`tests/public_api.txt` lines 23, 117, 138, 147). The keyword is placed last in `run` and `run_async`, the field last in `Defaults` with a default. The `TypeError` without `tools=` mirrors `max_tool_calls`. Reading the field from the `limits` that `_checked` already passes to `_check_tools` keeps one read per call, and stand-in (g) is caught by `test_set_defaults_changes_what_run_reads` (it counts `_current_defaults` calls through `run` and `run_async` with `tools=`).
- **N8 is real and Decision 8 closes it (EXECUTED P2).** On main, depth 2, 3 and 5 publish `api_key`, `limit` and `user_id`, with the secret in the descriptor; under the walk, `limit` only, with `api_key` and `user_id` fixed. The same on 3.11.14. Of the other cases, none changes: a function, a partial, nested partials, a partial subclass with its own `__call__`, a callable object, a bound method, a `MethodType` over a partial, a dict subclass with `__call__`, a classmethod `__call__`, a property `__call__`, an instance-level `__call__` (with and without a class `__call__`), `__signature__` set, `lru_cache`, `singledispatch`, `operator.itemgetter`, `operator.methodcaller`, `len` and `str.upper`. The C-slot stop is needed and sufficient for those. Cycles of one and two objects end with the walk's `TypeError`.

## Findings, most severe first

1. **F1. `list` frames cost the host in proportion to the tool list, not to request bytes, and the spec says the guest does not choose that cost. Medium; write in (a fix, or the bound stated).** (Scope's "Answer bytes"; Decision 11's *Not protected* rewrite; EXECUTED P3, P4.)
   - Each `{"op":"list"}` frame is 26 bytes. `_answer` encodes the full descriptor list again for each one, on the door's thread, holding the GIL (READ, `_answer`: `_encode(body)` per frame), and the door then copies the answer into guest memory.
   - Per `list` frame, the frame host alone (P4): 0.05 ms with 5 tools (13 KB list); 1.10 ms with 100 tools (448 KB); 4.37 ms with 300 (1.9 MB); 21.95 ms with 1,000 (10.5 MB). At the default 1,000 frames that is up to 1.1 s, 4.4 s and 22 s of host CPU, for 26 KB of request bytes, which the budget never sees. Through `run` with 100 tools and `max_tool_calls=None`, 5,000 list frames took 6.07 s of process CPU for 130,000 request bytes (P3).
   - So Scope's reason ("an answer is made by the embedder's own tool … the guest does not choose its cost") is wrong for `list`: the embedder chose the list's size, but the guest chooses how often it is encoded. And Decision 11's new *Not protected* text ("up to the call's request-byte budget") would overclaim. The same is true, to a smaller degree, of the fixed cost per admitted small frame (about 20 µs) and per refused frame (about 3 µs): both are bounded by `max_tool_calls`, and with `max_tool_calls=None` only by the deadline.
   - **Failure:** an embedder offering a large tool set (an MCP adapter in front of a big server) lowers `max_tool_request_bytes` for untrusted guests, reads the README, and believes host CPU is bounded by it. A guest spends seconds of GIL-held CPU per run on `list` frames.
   - **Fix (preferred, small, in `src/` only):** encode the list once per frame host. The body differs per frame only in `id`, so keep the encoded tools array and splice it, or cache the whole answer per `id`. A list frame then costs about a small frame's 20 µs, and `max_tool_calls` bounds it like any small frame. A unit counts `_encode` calls: one for many `list` frames. **Or, if kept out of scope:** say so in Scope with the right reason and bound (`max_tool_calls` × one encode of the list), and make Decision 11's *Not protected* and "host's cost per frame" text name both limits: request bytes by the budget, frame count (and so `list` answers and fixed costs) by `max_tool_calls`.
2. **F2. Decision 8 does not "stop where `inspect` stops" at a class: a metaclass's `__call__` still publishes a partial's bound values. Low; write in.** (Decision 8, the Intent's "however deep", criterion 4; EXECUTED P2 and P5, on 3.14.2 and 3.11.14.)
   - For a class, `inspect.signature` reads a user-defined metaclass `__call__` first (then `__new__`, then `__init__`). `_type_hints` also reads `type(cls).__call__`. The walk stops at any class (`isinstance(target, type)`).
   - Case: `class Meta(type): __call__ = staticmethod(p)`, with `p = partial(orders, user_id=42, api_key=SECRET)` and `orders`' annotations copied onto `p` (a partial has a `__dict__`); `tool(Orders)` for `class Orders(metaclass=Meta)`. On main and under Decision 8's walk: props `['api_key', 'limit', 'user_id']`, fixed `[]`, the secret in the descriptor (P2). It is N8's own class of construction (one hop, grafted annotations), so it is as unlikely as N8. But the spec sets out to close the class, and its Intent promises it.
   - **Fix:** treat a class like any other hop. Drop `isinstance(target, type)` from the stop list and let the class reach the `type(target).__call__` step, which stops at once for an ordinary class (`type.__call__` is a slot wrapper) and follows a user-defined metaclass `__call__`. P5 ran exactly that: the metaclass case then publishes `limit` only and fixes `api_key` and `user_id`, and the other 27 cases are unchanged. (A class's `__init__` or `__new__` partial needs no rule: without a metaclass `__call__`, a class's hints do not read, so `tool()` refuses it unless `input_schema=` is given, and then no default is published; P2's "class with partialmethod `__init__`" row.) Add the metaclass case to criterion 4, with a stand-in (k): the walk stops at a class (the case leaks).
3. **F3. Criteria that a wrong build could pass, or that read wrong. Low-medium; write in.** (Criteria 1 to 3; EXECUTED P3, READ.)
   - (a) **"Whatever the answer" is untested.** Every frame in criterion 1 can be a valid call. A build that refunds bytes for a frame answered `protocol`, or counts only frames that parse, passes. Add: the first 600-byte frame is not JSON (answered `protocol`, 1 parse), and `admit(401)` is still refused. Stand-in (l): no bytes counted for a `protocol` answer.
   - (b) **Criterion 3 does not catch stand-in (c) as claimed.** If the mutant checks the budget in `__call__` before `_answer`, the refused outcome still has `op is None` and the guest's output is the same; only a mutant that checks after the parse gives `op == "call"`. Criterion 1 still catches (c), so this is no hole overall, but the claim is wrong. Fix: criterion 3 counts frames read by wrapping `_ToolHost.__call__`: 4 under the budget (`[26, 400071, 400071, 75]` in P3), 5 under the default.
   - (c) **Say the wire sizes.** Three 300,000-byte arguments look like 900,000 bytes, under the 1,000,000 budget. They are 400,071 bytes each on the wire, as base64 in a `$bytes` object, so the third is refused. One sentence saves the builder and the build reviewer a doubt.
   - (d) **A zero-length frame passes every budget.** `0 + 0 > 0` is false, so with `max_calls=1, max_bytes=0`, a frame 1 of length 0 is admitted. Criterion 1 must give frame 1 a positive length. Decision 4's "0 refuses every frame" should read "every non-empty frame" (an empty frame costs one failed decode); or the rule refuses everything at 0. Either is fine; the text and the build must agree.
   - (e) **Existing calls of `_check_tools`.** `tests/unit/test_runner_tools.py:162-167` calls it with four positional arguments. The new parameter needs a default and must not take `limits`' place (keyword-only is safest). Otherwise the builder must edit a judge file to go green, which AGENTS.md rule 4 forbids without its own reason.
4. **F4. The 055 hand-off has no reader if 060 lands first. Low; write in.** (Decision 7.) 055's rule covers "every argument of `run`", but its list of "how each applies is decided here" names only 053 and 054, and its per-turn table lists `max_tool_calls` without this one. 055's builder reads 055, not 060. Fix: 060's landing adds one bullet to 055's rule list and the word `max_tool_request_bytes` to its `max_file_calls, max_tool_calls` row ("per turn, set once on the session", 060 Decision 7). That is a spec edit, not a judge change. If 055 lands first, 060's builder does the same in `Session`. INFERRED: without it, a session still gets the default per turn through `_checked`, so nothing is unsafe; only the knob is missing.
5. **F5. The 049 rules cited for the CHANGELOG. Note.** (Decisions 2, 9 and 11.) 049's exception 1 (a tighter default) is a "Changed" line; exception 2 is a "Security" line. The spec invokes both and writes only Security. Before 0.1.0 either is allowed; for the record, cite exception 2 alone (it is the honest one: the default does not "keep today's behaviour", which the minor-release rule otherwise asks of a new keyword), or add the Changed line too.
6. **F6. Decision 8 also fixes a crash on main. Note; say so.** (EXECUTED P2.) On 3.14.2, `tool()` on a `__call__` cycle raises `RecursionError` out of `inspect.signature`, which `_derived` does not catch; its docstring promises `TypeError` or `ValueError`. On 3.11.14 it is a `TypeError` from `_type_hints`. Under the walk both are the walk's `TypeError`. Name it in Decision 8 and the CHANGELOG bullet, and note that criterion 4's cycle case is "seen failing on main" by type on 3.14 and by message on 3.11.
