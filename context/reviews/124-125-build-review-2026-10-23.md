## Findings, most severe first

No High. No Medium.

### Low

**L1. The coverage measurer reads only pytest's summary line, so a red ratchet is reported as green, and its docstring says otherwise** (`tests/harness/coverage.py`, `measure()` and the module docstring). The judge turns a run red in `pytest_sessionfinish` (an accepted pass blocked, a check absent, growth, foreign steering) by setting the exit status; pytest's final summary line still says "N passed". `measure()` discards `run.returncode`, and `main()` decides on `summary_names_failures()` alone. Failure, seen: on run 39891594258 the coverage job's own `pytest.log` ends `RED: 1 accepted check(s) absent` (pytest exit 1) above "3130 passed, 50 skipped", and the job printed 91.1% and uploaded it; an accepted pass blocked on a protected need, or growth, would go the same way. Reading the summary is the right choice for a CI measurement (the ratchet's verdict belongs to the judge jobs), but the docstring's "A run that is not green exits non-zero and its numbers are not reported" is not what the code does. Fix: say it in the docstring ("a run with a failed or erroring check exits non-zero; the ratchet's verdict is the judge jobs', not this measurement's") and add a unit row that a summary of "637 passed" with a RED progress line above it is read as green, so the choice is held on purpose.

**L2. The Codecov CLI is unpinned** (`.github/workflows/release.yml`, the step "The report to Codecov"). The action is pinned by commit, but its `version` input defaults to `latest`, so each run downloads whatever CLI `cli.codecov.io` serves and runs it with `CODECOV_TOKEN` in its environment. The action checks the CLI's signature against Codecov's key, and the job has `contents: read`, no other secret and no output another job consumes, so the reach of a bad CLI is the upload token and this job's red or green. It is still the one executable in the workflow that no pin names, against the constitution's habit of pinning every input. Failure: a CLI release that changes its upload or exit behaviour turns the job red, or uploads differently, with no change in the tree to show why. Fix: add `version: v<the CLI version the branch run used>` under `with:` (the job's log names it), and name it in 124's Design.

**L3. `fail_ci_if_error: true` makes a Codecov outage a red run, and rule 6b tags only a run whose every job passed** (`release.yml`, 124 Decision 6). Decision 6 states the trade, but AGENTS.md rule 6b ("waits for every job to pass on all three systems") is not told about it, so a lane facing a red `coverage` job on the dry run before a tag has two rules that disagree in spirit: "nothing needs the job" and "every job passes". Failure: Codecov returns 5xx during the dry run on main the night of a tag; the dry run is red; the lane either re-runs the whole release workflow (about 80 minutes) or tags on a red run without a written rule. Fix (context only): one sentence in rule 6b and in 124's Decision 6: "a dry run red only in `coverage`, on an upload error the job's log shows, is re-run with `gh run rerun --job` on that job alone; it never holds the tag", or set `continue-on-error: true` on the upload step if the owner prefers a stale badge to a red run.

**L4. The wheel's growth is not recorded against the owner's 100 MB line** (125, Landing notes; `context/decisions.md` question 64: "each landing records its size"). The combined `LICENSE` is 773,726 bytes, 143,028 deflated (EXECUTED), and the branch run's wheel is 98,332,043 bytes (READ, the build job's log), 1.67 MB under 100,000,000. 125's notes record neither. Fix (context only): add to 125's Landing notes "the wheel 98,332,043 bytes on run 39891594258, about +139 KB by the combined LICENSE (773,726 bytes, 143,028 deflated); under question 64's line by 1.67 MB".

**L5. A wheel built by hand now fails the judge's wheel check, and the way round it dirties the tree** (`tests/harness/artifacts.py::wheel_errors`; `docs/contributing/building.md` "Before you build a wheel by hand"). `test_wheel_carries_the_artifact_set` runs wherever a wheel is in `dist/`. A contributor who follows the building page and runs `uv build --wheel` gets a wheel whose `LICENSE` is Apache-2.0 alone, and the check fails with "is not the combined licence". Running `release/licences.py append` first fixes the wheel but leaves the checkout's `LICENSE` rewritten: the judge's `--accept` then refuses on a dirty tree, and a careless `git add -A` commits a 774 KB `LICENSE`, which GitHub's licence detection and the README's licence badge read. Failure: the next local hand-built wheel. Fix: a `restore` command in `release/licences.py` that writes `own_licence(LICENSE)` back (it is idempotent, so it is safe to run on a clean file), and three lines on the building page: `append`, `uv build --wheel …`, `restore`. CI needs no restore: its checkout is thrown away.

**L6. The order and the set of licence files depend on the host** (`release/licences.py::parts`). `sorted()` over `Path` objects compares case-insensitively on Windows (`PureWindowsPath`), and `glob("*.txt")` matches `*.TXT` there too, while the wheel is built on macOS or Linux; the judge's wheel check runs on the Windows judge job (`own-guest`) and recomputes `combined` there. All 70 names today are lower-case `.txt`, so nothing differs now (EXECUTED). Failure: a future component file named with a capital (`SheenBidi.txt`) sorts differently on Windows and the Windows wheel check fails on a correct wheel. Fix: `sorted((p for p in … if p.suffix == ".txt" and not p.name.startswith(".")), key=lambda p: p.name)`, and a unit row with `B.txt` and `a.txt`.

### Notes

**N1. FreeType's credit is the licence's suggested sentence with `<year>` in it, not a statement.** The wheel's `LICENSE` carries FreeType's full licence, whose §2 asks the distribution's documentation for "a disclaimer that states that the software is based in part of the work of the FreeType Team" and offers a template with `<year>`. The owner chose Pillow's model, which ships the licence and no separate sentence; that is a defensible reading and Decision 1's to make. A one-line hardening at no cost: `INTRO` could add "This software is based in part on the work of the FreeType Team." so the condition is met in words and not only by reference. The owner's call.

**N2. PyPI and the 774 KB licence file.** Nothing breaks. `License-File: LICENSE` names a file the wheel carries (the builder READ it in METADATA), PyPI has no per-licence-file limit, and the deflated cost is 143 KB. `License-Expression` stays `Apache-2.0` while the file carries MIT, BSD, FTL and other texts; the components were already in the wheel under `wasi_python/artifacts/LICENSES/`, so this is not new, and Pillow does the same (`MIT-CMU`). A future SPDX expression covering the linked components is a separate decision.

**N3. Coverage of child processes is not measured.** `coverage run` measures the pytest process only; the checks that run the runner in a child Python (`tests/checks/test_v1_4_embedding.py`'s probes, started with `sys.executable -I`) add nothing to the percent. The badge therefore understates what the fast tier exercises. Out of 124's scope as written; a later change could set `[tool.coverage.run] patch = ["subprocess"]` (coverage 7.10 and later).

**N4. The rest of the commit.** No hashed build input changed (`recipes/` skipped by `tests/harness/wrap.py`, as 124's Landing notes say, and `git show --stat` names nothing under `recipes/`, `scripts/` or `downloads/`). `README.md` is the wheel's `METADATA` description; it changed, but the same text goes into all three wheels, so `same-bytes` is unaffected. Its new images are absolute `raw.githubusercontent.com` URLs, as PyPI needs.
