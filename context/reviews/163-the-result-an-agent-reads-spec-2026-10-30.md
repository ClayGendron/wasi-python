## Findings, most severe first

1. **Medium: the §4.4 amendment as drafted leaves the gate clause broken** (constitution §4.4; Decision 4; "For the owner to decide", 1). §4.4 says the protocol is "used only when the embedder passes its tools, and gated by the embedder on every call". A display frame in a call without tools breaks the first clause, which the amendment fixes. A display frame is never gated, which breaks the second unless "every call" means every tool call, and the amendment does not say so. Failure: the owner signs the drafted sentence; a later judge or reviewer reads §4.4 literally and finds ungated frames on the door. Fix text for the owner's question 1: "On top of the door the project may ship one tool protocol, through which a guest calls the host's tools, APIs and MCP servers and hands the host its displays: optional, used only when the embedder passes its tools or asks for results, every tool call gated by the embedder; a display calls nothing of the host's." My judgment on the question asked: the amendment is needed, since the letter of §4.4 does not allow display frames without tools; and it is the better road. The reserved descriptor needs no amendment by the letter (it is a WASI call, not a third import), but it is a second guest-to-host channel that a guest program can write as freely as the door, so it buys no protection against forgery and costs a second parser and bound.
2. **Medium: the door's admission cannot know a frame's operation, and the spec does not say how the two hosts compose** (`_call.py:1266`, `_door`; `_tool_host.py:858-884`, `_ToolHost.admit`; Decisions 4 and 7). `admit(length)` runs before the frame is read. If `_ResultHost.admit` calls `_ToolHost.admit`, every display frame spends a tool frame and tool request bytes, against Decision 4. If it does not, nothing says what bounds a frame before it is read, what answers one refused unread, and in which record that refusal goes. Decision 7 also leaves the guest's answer for the 1,001st record and for "no room left" unnamed; if that answer is a refusal, Decision 6's fallback prints the text, and a loop of 10,000 `display()` calls floods stdout. Failure: a builder takes either reading, and a row of Decision 12 passes on one and fails on the other; or with `output_bytes=None` a frame of any length is copied out of guest memory before anyone looks at it. Fix text for Decision 7: "`_ResultHost.admit(length)` never calls `_ToolHost.admit`. It refuses unread a frame longer than the larger of 6 × the room left (the JSON escape's worst case) and, under `tools=`, the tool request cap; the answer is `too_large` with `room`, and the refusal counts as a display record. With `output_bytes=None` the room has no bound and the frame is bounded by the guest's memory alone. After the read, `list` and `call` go to `_ToolHost.__call__`, which admits them by their length then, as it does for a raw host, so a tool frame spends tool calls and bytes exactly as today and a display frame spends neither. A display past the 1,000th record, or with no room left, is answered `ok` with `"kept": false`; the guest prints nothing and stops sending figures for the rest of the cell." Add a unit row for each sentence.
