## Findings, most severe first

### H1. A guest can plant a compiled module that a later call loads as native code in the host process. High; the runtime's own files; **0.1.0 waits on it** (EXECUTED, mine; not new in 0.1.0)

The README promises that a writable grant or `root` at, inside or above the module cache is refused, "since later calls and processes trust them" (README:1044-1048). The judge enforces that only for the cache of the call being judged. A call made with `cache_dir=False`, or with a `cache_dir` of its own, does not judge the cache that other calls and processes use.

**What I ran** (`build/secreview/probes/p50_cwasm_plant.py`, log `build/secreview/logs/p50_cwasm_plant.log`). Each step ran in a fresh process, so no module was cached in memory:

| step | the call | result |
|---|---|---|
| 0 | `snapshot=False`, `cache_dir=<C0>` | real `.cwasm` bytes of the plain reactor (239,563,920 bytes), standing in for bytes an attacker builds offline |
| 1 | `cache_dir=False`, with a writable `Grant(<D>, "/c")`, where `<D>/wasi_python` is the cache the process's `$WASI_PYTHON_CACHE` names | the guest wrote those bytes, from stdin, as `/c/wasi_python/<snapshot digest[:32]>-wasmtime49.0.0-plain.cwasm`. The judge passed the grant. The file was owned by this user with mode `0644`. |
| 2 | defaults (the cache at `<D>/wasi_python`), `snapshot=True` | `stats()`: **`compiled 0, loaded 1`**. The runner loaded the guest's file in place of the snapshot and ran it, with exit 0. |

- **Why** (READ):
  - `_walk_grants` judges `_runtime_folders(found, cache)` (`_places.py:426`, `473-512`) with the call's own `cache`. `_cache_dir(False)` is `None` (`_engines.py:67-74`), so no cache is judged.
  - `_module_miss` loads any file named `<digest[:32]>-wasmtime<version>-<flavor>.cwasm` that `private()` accepts (`_engines.py:143-149`).
  - `private()` asks only for a regular file owned by this user and not group- or other-writable (`_platform.py:535-551`). A guest writes as this user, and under the usual umask its file is `0644`.
  - The file name is public: the binary's SHA-256 is in `SHA256SUMS`, and the version is wasmtime-py's. Nothing ties the file's content to the digest in its name.
  - On Windows, `private()` returns True for any file (`_platform.py:1389-1392`).
- **What it breaks.** `Module.deserialize_file` runs the file's machine code as it finds it; wasmtime documents it as unsafe for untrusted input. A guest that writes a `.cwasm` with its own machine code, built offline against the public wasmtime 49.0.0 and the public binary, runs that code in the host process at the next call. That call is outside wasm, with the embedder's privileges, its memory and every other call's data. It is the threat model's worst class, through a promise the README states.
- **Who it reaches.** An embedder that, in any call or process, gives a writable grant or `root` at or above a module cache that another call or process uses, while that call's own cache is off or elsewhere.
  - The default caches are `~/Library/Caches/wasi_python` on macOS, `~/.cache/wasi_python` on Linux, and `%LOCALAPPDATA%\wasi_python\cache` on Windows.
  - `cache_dir=False` is the natural setting for a call that should leave nothing on disk.
  - A writable `root` at HOME is refused only when HOME also holds this package, wasmtime-py or an existing user site-packages (`_places.py:505-511`). So on a Linux server with its venv under `/opt`, `root=Path.home(), cache_dir=False` passes the judge (INFERRED from the code; not run here, since this host's venv is under HOME).
  - The same holds for two services with different `$WASI_PYTHON_CACHE`, or a `Session` with its own `cache_dir` (`_sessions.py:971`).
- **Not new** (READ): a7's `runner.py:2249` and `2294-2320` had the same rule. No earlier review tried a cache other than the call's own. The whole-surface review's N3 named the cache's weaker checks, but not this route.
- **Fix** (host-side, `src/` only, in the wheel; no rebuild):
  - **The rule.** In every call and session, judge every module cache the process could use, whatever the call's own `cache_dir`: `$WASI_PYTHON_CACHE` if set, the platform's default folder, and the call's own. Refuse a writable grant or root at, inside or above any of them, even if it does not exist yet (judge its deepest existing ancestor, as for a root still to be made).
  - **Defence in depth.** Accept a cache folder only at mode `0700` and a `.cwasm` only at `0600`; the runner makes both that way, and a guest's `mkdir` and `open` give `0755` and `0644` under the usual umask. Better still, keep beside the cache a record, written only by the runner, of each `.cwasm`'s SHA-256, and check it before deserializing. A guest that can reach the cache could rewrite that record too, so the rule above is the real fix.
  - **README:** say in *Not protected* that a writable grant over any folder of compiled modules is code execution in the host, and that `cache_dir` and `$WASI_PYTHON_CACHE` are trusted input, as the artifact folder is.
  - **Check:** steps 1 and 2 above, as a unit check that counts `stats()["loaded"]`. It is refused at step 1 for `cache_dir=False` and for a different `cache_dir`, in `run` and in `Session`.

### H2. Code planted in a reused root runs on a bare `import reportlab` in a later call when that call has no runner-made HOME. High; cross-run contamination; **0.1.0 waits on it** (EXECUTED by the helper; re-run by me)

The *Safety* policy says that "code planted in a root never runs at start-up or on import in a later call, on either binary" (README:3266-3267). reportlab breaks it.

**What ran** (`build/secreview/guest/p05c_reportlab_mods.py`, log `guest/logs/p05c.log`; I re-ran it with the same output):

| configuration | call 1 | call 2: `import reportlab` |
|---|---|---|
| a reused root with a read-only grant at `/tmp` (a mount at `/tmp` gives the same: no HOME) | writes `/~/.reportlab_mods` | **runs it**: it prints, and makes `/PWNED_MODS` in the root |
| a reused root with `env={"HOME": "/home"}` | writes `/home/.reportlab_mods` | **runs it** |
| a reused root, defaults (a fresh HOME) | writes `/~/.reportlab_mods` | does not run it |

`import reportlab.rl_config` does the same through `~/.reportlab_settings` (helper, EXECUTED, `p05_planting.py`, configurations B and C).

- **Why:**
  - `_home_folder` (`_call.py:294-316`) makes no HOME for a mount or a read-only grant at `/tmp`, as README:1249 and 1473 document. The guest then has no `HOME`.
  - The guest has no `pwd` module, so `os.path.expanduser('~/.x')` returns `'~/.x'`. That resolves against the working folder `/`, which is the writable root.
  - reportlab's `__init__` executes `~/.reportlab_mods`, and its `rl_config` executes `~/.reportlab_settings`.
  - Both came in with spec 042. The whole-surface review's addendum checklist asked that "the reportlab settings files join *Not protected*" (row 042). That was not done.
- **What it reaches.** The planted code runs inside the sandbox, but with call 2's grants, tools and door. Call 2 may be a trusted program with wider grants than call 1. That is the cross-run class the policy calls enforced.
  - The no-HOME case is not in *Not protected*.
  - The `env=` HOME case belongs to the documented item "an `env=` that overrides `HOME` … on a reused root (pdb then reads a `.pdbrc` …)". But a bare import is a much wider trigger than starting pdb, and the README even advises "pass `HOME` in `env=` if you need one" (README:1250, 1474).
- **Fix:**
  - **(a) The runner** (`src/` only, no rebuild): when it makes no HOME, set `HOME` to a guest path that no grant or root can write. One choice is an empty read-only placeholder preopened there. Then `~` never falls back to the working folder. That also covers pdb's `~/.pdbrc`, scikit-learn's and seaborn's `~/…` folders, and Pillow's `~/.fonts` (L3).
  - **(b) And/or a reportlab recipe**, build-class: a stand-in or patch so that neither file is executed.
  - **README:** name reportlab beside pdb in the `env=` HOME item, and say that a HOME the embedder points into a reused root runs reportlab's start-up files.
  - **Check:** plant both files under each HOME configuration (none, `env=`, fresh), and assert that call 2 does not run them.

### L1. A `matplotlibrc` in the working folder of a reused root steers every later matplotlib call. Low; cross-run contamination (EXECUTED by the helper, `guest/p05b_no_home.py`)
