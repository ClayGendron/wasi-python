## Short version

Read-only grants hold. A guest could not write, link, rename, truncate or re-time a file in a read-only grant or in the stdlib zip's folder, so §4.15's third clause is now met. The rules that keep writable grants away from the runtime's folders refuse every case I tried, spelling tricks included. The command line adds no power `run` lacks. The numpy patch keeps `allow_pickle=False` as the default. The 0.1.0a2 findings stay closed.

One thing blocks. Between the walk and the identity check, the runner prepares a `root` by path string, not through the folder it walked. A guest in another call that can write a folder on that root's path can redirect those preparations. In one run this deleted a host file outside every grant (S1). The fix is to do that preparation through the walked descriptor.

## Findings, most severe first

### S1. The runner prepares a `root` by path string after the walk, so a concurrent guest can redirect it outside every grant: **blocks the release** (EXECUTED)

`_walk_grants` walks `root` one folder at a time and holds the last folder's descriptor. Then `_run_checked` and `_call_deferred` prepare that root by its path string, before the identity check in `_drive`:

- `_real_dir(root_path, ("usr", "local", "lib"))` and `_real_dir(root, ("tmp",))` (`runner.py:1476`, `1557`) call `root.mkdir(parents=True, exist_ok=True)`, then `os.lstat`, `Path.unlink` and `Path.mkdir` on joined paths. Each follows a link in any component of the root's own path.
- `_open_dir(tmp)` uses `O_NOFOLLOW` on the last component only.

The identity check later refuses a swapped root, so the guest never runs on the wrong folder. But by then the host-side preparation has already been applied wherever the path pointed.

Precondition: a guest of another call, in this process or another, holds a writable grant (or root) that contains a folder on this call's root path. A root inside another call's writable root, such as a per-job folder inside a shared workspace, is that case. The README's "Not protected" item covers concurrent calls *on one root*. It does not cover nested roots, and it does not say the runner itself can be made to act outside every grant.

What I ran: a victim called `run` in a loop with `root=<arena>/sub`, while a concurrent call with `root=<arena>` changed `sub` in place. The guest used only calls the README says it can make, including creating a relative link that points out. A folder outside both roots held a regular file named `tmp`. After about 790 victim calls that file was gone: `_real_dir` had treated it as "a file a guest left in the way" and unlinked it. The victim's guest never saw that folder. Script and log: `race_root.py` and `logs/race_root.log` in `sec03/`.

Consequences on the host, outside every grant (INFERRED from the code, one EXECUTED):

- removal of a non-folder named `usr`, `local`, `lib` or `tmp` in a folder this user can write (EXECUTED for `tmp`);
- creation of empty folders with those names there;
- creation and removal of a `.home-<hex>` folder there;
- a root removed after its walk is made again by path. This was seen: most victim calls ran on an empty `sub` that their own runner had re-made.

This is the sandbox boundary in `SECURITY.md`'s scope. It is a write outside the folders the guest was given, though narrow in what it can do.

Fix (suggested): prepare the root only through the walked descriptor (`walked_root.fd`): `mkdir`, `lstat` and `unlink` with `dir_fd`, each component opened `O_DIRECTORY | O_NOFOLLOW` from the one before. Do the same for `tmp`, and use that descriptor for `HOME`. Do not re-make a missing root by path after the walk. Windows already holds every component without `FILE_SHARE_DELETE`, so this is POSIX only. Add a check that swaps the root for a link through the existing `_after_walk` seam and asserts nothing outside changes. Seen failing first on today's code, it should pass after the fix. If the owner prefers to document instead, "Not protected" must say that a guest with write access to a folder above another call's root can make the runner create and delete entries outside every grant.

### S2. The host interpreter is not among the protected runtime folders: does not block (READ, INFERRED)

`_runtime_folders` protects the zip folder, the artifact set, the module cache, and the code of `wasi_python` and wasmtime-py. The comment's reason is that later host processes run that code. The same holds for the CPython that imports them. When a virtual environment's base interpreter lives outside it, a writable grant at that interpreter's folder is not refused. Examples are uv's `~/.local/share/uv/python/…` and Homebrew's prefix. A guest could then change the host's stdlib, which the next host process runs (INFERRED; not executed, so as not to write in a real interpreter). An embedder must name such a folder writable on purpose, so this does not block. Suggested: add `sys.base_prefix` and `sys.prefix` (resolved) to `_runtime_folders`, or name the gap in *Grants*.

### S3. The patch applier clears the caller's git configuration, but not a tree's own: does not block (READ, INFERRED)

`apply_patches.sh` runs git under `env -i`, with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` and a ceiling at the tree's parent. git still discovers a repository *inside* the tree. A tarball that shipped a `.git` folder would bring its own `.git/config`, and its `.gitattributes` could change how hunks apply (INFERRED from git's discovery rules; not executed).

The tarballs are pinned by hash, and their own build systems already run as build tools. So this opens no path that the build does not already open, and the judge re-applies the patches the same way. Paths outside the tree and through links are refused by `git apply` by default and by the judge's `patch_errors` (READ). The second `touch` loop runs only after git has applied the patch.

Suggested: refuse a tree that holds `.git`, or pass `--git-dir` to an empty folder, so the header's claim ("configuration, attributes and environment cleared") holds for every source.

### S4. 0.1.0a2's F8 is still open: does not block (READ)

`artifact_dir()` still prefers `<grandparent>/build/artifacts` whenever the grandparent holds a `pyproject.toml`. That is unchanged, and it was dispositioned as a later change.

## Disposition (filled in by the author, then confirmed by the reviewer)

- **S1: fixed by spec 024** (`../specifications/024-a-root-prepared-through-its-walk.md`, its build review `024-a-root-prepared-through-its-walk-2026-10-17.md`). The root's `usr/local/lib` and `tmp` are made through the walked descriptor; the root is never made again by path. A new v1.2 check swaps the root for a link and by rename through `_after_walk`, and was seen failing on the old code (it replaced the host's `outside/usr` file with a folder). The build review re-ran this review's attack: nothing outside either root changed in 1,269 victim calls.
- **S2: fixed by spec 024.** A writable grant at, inside or above the host Python's `stdlib`, `platstdlib`, `purelib`, `platlib` and `scripts`, and the user's site-packages, is refused.
- **S3: fixed by spec 024.** The applier refuses a tree holding `.git`; no pinned tarball holds one (EXECUTED).
- **S4: unchanged, as agreed for 0.1.0a2's F8** (a later change; the artifact folder's preference is the embedder's to override).
- **S5: no finding.**
