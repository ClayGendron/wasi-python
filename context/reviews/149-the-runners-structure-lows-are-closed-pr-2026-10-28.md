## The pieces judged

- **The resolve-once tables** (READ `_platform.py:205-208`, `:828-846`, `:950-969`, `:993-1003`; `_platform_windows.py:90-96`, `:334-348`). Each fill reads the attribute once into a local, and when that is `None` builds a whole dict and publishes it in one store, then uses only its local. A reader that sees `None` does not retry: it fills itself, which is correct because resolving a C name is idempotent. Two fillers racing both resolve, each uses its own complete table, and the last store wins; nothing is lost, since neither table is ever partly visible. A fill that raises mid-build now publishes nothing, so the next call resolves again, where the old code left a partial dict. `kernel32`'s `win_api` keeps one key bound to a whole value, and its comment now says so. - **`failing` against 144's `dropped`** (READ `_outputs.py:20-34`, `:217-248`, `:251-309`, `:324-333`). A failed `os.read` marks its end; any later read of that end that does not raise (bytes, end of file, `BlockingIOError`) unmarks it. Since any failure in the fast loop raises into the slow loop, `failing` is empty whenever the fast loop answers a settle, and the slow loop names every marked end before `settled.set()` and `_end` before the ends are closed, so a turn handed back with an unread end says `truncated`. 144's `_write_output` sets `dropped` when a write that wasmtime counts as written could not be kept. The module docstring's rule, "a stream is named as truncated where a piece is lost or may be", is true of both: the callback's piece is lost, the reader's is lost (a write the stream refused) or may be (an end unread at a hand-back). `failing` is touched only by the reader thread; `_name_failing` holds the capture's own lock as `_take` already did.
