## Findings, most severe first

1. **Medium: the last delivery under an event loop waits with no bound but `loop.is_running()`** (`src/wasi_python/_outputs.py`, `_Feed.close`). When the loop's thread is blocked in `on_output` waiting for the turn, as `Session.close()` from the loop's thread is documented to do, and the last batch is not empty, the worker waits on the loop and the loop waits on the worker. Failure: under `Session.run_async`, `on_output` calls `s.close()` on its first chunk while the pipe capture's `settle()` brings bytes after the home stopped serving → the turn and the event loop hang for ever; the deadline does not end it. EXECUTED with one late piece queued just before the last delivery: "HUNG 40 s", and without the `close()` the same turn returns at its deadline; unpatched, seven runs found the queue empty at the last delivery, so the race is narrow (INFERRED reachable on Linux and macOS, where the pipe capture is used). Fix text: "Under an event loop, the last batch is posted with `call_soon_threadsafe` and the worker returns without waiting; the loop runs it before it resumes the awaiting coroutine (Decision 3). A `BaseException` it raises is kept in a holder the coroutine owns, and `run_async` and `Session.run_async` raise it after their await." A unit row drives `_Feed.close` with a loop blocked in a callback and checks that `close` returns while the loop is still blocked.
