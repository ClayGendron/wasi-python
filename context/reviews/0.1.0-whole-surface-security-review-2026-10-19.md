## Short version

The sandbox holds. Every a7 probe I re-ran gives a7's answer on `302df18`, apart from the
scratch path: the host filesystem, the slash escapes through all three linkers, the door and
its cancel, matplotlib's read-only data grant, and the async gate's `GeneratorExit`. New
hostile probes found no way out:

- A read-only grant cannot be changed through a writable root on the same filesystem. Hard
  links, renames both ways, absolute symlinks, truncate, utime and unlink are all refused (63).
  A relative symlink is made, but refused on open.
- The tool protocol refuses deep, huge, malformed and repeated-key frames before parsing them.
  A tool's exception text stays on the host.
- The guest learns nothing of the host: no host path, a fixed `uname`, one CPU, and inodes
  remapped.
- Its randomness is fresh in every call on both binaries.

**Findings.** None is critical or high. The worst two are medium:

- **S1:** a manual dry run on any branch, with an edited workflow file, can publish to PyPI.
  The `pypi` and `release` environments have no deployment-branch policy, and the
  trusted publisher cannot bind a ref. This sharpens a7's N1: no tag is needed.
- **S2:** a guest given `root=True` can still leave its private root on disk. This is a7's F1,
  re-run on `302df18`. Spec 084 closes it; it is built but has not landed.

**The low findings:**

- **S3:** an installed wheel can pick up a neighbouring `build/artifacts/`, and the set it
  loads is never hash-checked.
- **S4:** release assets can be replaced after publication.
- **S5:** the guest's string hash is 32-bit FNV, with a fixed public key on the default
  snapshot binary. That is the hash CPython dropped in 3.4 because crafted data can flood it.
- **S6:** a7's F5 to F7 and N5 (gather's checks) are still open. Spec 085 closes them.
- **S7:** GitHub's secret scanning, push protection and Dependabot alerts are off.

## Findings, most severe first

### S1. A manual run on any branch, with an edited `release.yml`, can publish to PyPI and make a GitHub release. Medium; supply chain; **0.1.0 waits on it** (EXECUTED and READ by the helper; re-checked by me)

- **The settings** (EXECUTED, `probes/supply/gh_environments.json`, re-read by me). Both `pypi`
  and `release` have `protection_rules: []` and `deployment_branch_policy: null`, so any ref
  may deploy to them. `vars.PYPI_PUBLISH` is `true`.
- **The trusted publisher** (EXECUTED, `pypi_provenance_a7.json`) binds the repository, the
  workflow file name `release.yml` and the environment `pypi`. It does not bind a ref.
- **The guards are in the editable file** (READ, `release.yml`):
  - `attest`, `publish` and `pypi` run only `if: github.event_name == 'push' && github.ref_type
    == 'tag'` (lines 964, 1024, 1089);
  - the main-ancestry check runs only for a tag (lines 62-68).

  A `workflow_dispatch` runs the workflow file from the branch it is dispatched on. So a
  `spec/*` branch whose `release.yml` drops those lines, and then a routine dry run, reach the
  `pypi` environment's OIDC token and the `release` environment's `contents: write`.
- **Why it matters now.** Since decision 98, agents push `spec/*` branches and dispatch runs on
  them. Five of the last twelve runs were on such branches (`runs.json`). Build-class
  specifications are exactly the ones that edit `release.yml`; 085 does today. Agents act with
  the owner's token (`repo`, `workflow`). The tag ruleset lets an admin bypass always. A PyPI
  version can never be re-used. So one mistake, or one prompt-injected agent, publishes an
  irreversible wheel under the project's name. a7's N1 assumed a tag push was needed. It is
  not.
- **Threat-model item:** supply chain (§2, *Supply chain*), and through it the user's host.
- **Fix (small, owner setting, no code):**
  - give `pypi` and `release` a deployment policy of custom tag pattern `v*` only;
  - optionally, add a required reviewer on `pypi`;
  - add a judge rule that reads the two policies through `gh api` in the release dry run, so a
    loosened setting turns a run red.

### S2. A guest given `root=True` can still make its private root outlive the call. Medium; disk in a root; **0.1.0 waits on it (084)** (EXECUTED; a7 F1 carried)

- **Re-run** (`probes/a7_p31d_private_root_dirfd.py 256 400`, `logs/a7_p31d_256_400.log`):
  - a guest builds a 400-deep tree through `dir_fd`, holding one descriptor at a time;
  - `run` returns exit 0;
  - `wasi-python-root-…` and its `.lock` stay in the temporary folder;
  - the next call works.
- **Why** (READ, `runner.py:915-925`). `_Private.remove` is still `shutil.rmtree(...,
  ignore_errors=True)`, which holds one descriptor per level. It fails silently past the
  process's free descriptors. The fresh HOME (`runner.py:2482-2486`) and a session's folders
  take the same path. Nothing under `src/` changed since a7.
- **Closer:** spec 084 (built at `3e28d9b`; the Windows dry run is owed). As written, it
  closes every path that a7 named (helper, READ):
  - `_remove_tree` holds two descriptors, with `O_NOFOLLOW` and identity checks;
  - a folder left behind raises a `RuntimeWarning`;
  - up to three sweeps per process retry it.

  The residue is documented: the Windows race with a concurrent writer, and a HOME past its
  2**20-call budget.
- **Fix:** land 084, then its addendum (below).

### S3. An installed wheel can load another artifact set, and no set is hash-checked when it loads. Low; the runtime's own files and cross-run contamination (EXECUTED by the helper, `probes/supply/s1_target_layout.log`; READ by me, `__init__.py:36-42, 66-88`)

- `_REPO = Path(__file__).resolve().parents[2]`. When `_REPO/pyproject.toml` exists, a
  `build/artifacts/` holding a `MANIFEST` is preferred over the wheel's own `artifacts/`.
- For `pip install --target deps` (or vendoring) inside a project, `_REPO` is the user's own
  project. The helper's probe made `proj/deps/wasi_python` with its own set and
  `proj/build/artifacts/MANIFEST`. `artifact_dir()` returned `proj/build/artifacts`.
- `find_artifacts` checks only that a MANIFEST is present. The snapshot and the plain binary
  are compiled from whatever bytes are there. The zip's copy is checked only against the source
  zip's own digest.
- **The planting path** (INFERRED, not run). Take an embedder that installed that way and gives
  a guest a writable grant at `proj/build`. The runtime-folders judge does not refuse it. It
  refuses a writable place at or above the set in use, the package and the cache, but
  `proj/build/artifacts` is not yet any of those. The guest writes a `MANIFEST`, a snapshot and
  a zip there. The next call loads them and runs the guest's code with that call's grants. That
  is code execution across calls, the threat model's worst class, though it needs an unusual
  install plus a writable grant at that exact folder.
- **Fix (small, parallel-safe, `src/` only):**
  - treat the folder as a checkout only when `Path(__file__).parent.parent.name == "src"` and
    `pyproject.toml` names `wasi-python`; or prefer the wheel's own set whenever it holds a
    MANIFEST;
  - verify the set against its `SHA256SUMS` once per file stamp before compiling it;
  - say in the README that `$WASI_PYTHON_ARTIFACTS`, and any artifact folder, is trusted
    input;
  - **check:** the probe's layout picks the wheel's own set.

### S4. Release assets can be replaced after publication. Low; supply chain (EXECUTED by the helper)

- Immutable releases are off (`{"enabled": false}`), and `v0.1.0a7` has `isImmutable: false`.
- A job in any branch's run can ask for `contents: write` and `gh release upload --clobber` a
  published asset, `SHA256SUMS` included. Users who verify the attestation with
  `--signer-workflow …@refs/tags/v<version>`, as the README says, would reject a swapped asset.
  Users who check only `SHA256SUMS` would not.
- **Fix (small, owner setting):** enable immutable releases. The publish job attaches every
  asset when it creates the release (`release.yml:1077-1083`), so it should still work
  (INFERRED).

### S5. The guest's string hash is 32-bit FNV, and the default snapshot's key is fixed and public. Low; resources and integrity of the result (EXECUTED, `probes/p44_hash_width.py`, `p40`)

- **What the guest has** (`logs/p44_hash_width.log`):
  `sys.hash_info(width=32, …, algorithm='fnv', hash_bits=32, seed_bits=64, …)`.
  - `hash('abc')` is `-1600925533` and `hash('abd')` is `-1600925532` on the snapshot, in every
    call (`p40`).
  - The plain reactor's key is random per call.
- **Why it is weak.** CPython moved from FNV to SipHash in 3.4 (PEP 456), because FNV can be
  flooded with colliding keys even under a random key. On the snapshot, the default binary, the
  key ships in the wheel, so the collisions can be computed once, offline, for every user.
  A 32-bit width makes collisions cheaper still.
- **What it reaches.** An agent program that loads attacker-shaped data into a dict or set
  can be made quadratic: CSV headers, JSON keys, a pandas index of strings. That is the threat
  model's prompt-injection adversary. The deadline and fuel bound it, and the call says
  "deadline". So the host is safe, but the agent's own call can be denied by its data.
- **Why FNV** (READ; the step that would confirm it was stopped, see the denials above). The
  spike's configure log records `checking for --with-hash-algorithm... default`
  (`context/research/2026-10-16-the-spike-that-proved-the-build/outputs/cpython-floor-logs/`).
  CPython's default falls back to FNV when configure decides that aligned access is required,
  and a cross build assumes so (INFERRED). wasm allows unaligned loads, so SipHash runs there.
- **Documented?** The README states the fixed secret (lines 122-123) as a fact. It does not
  give the consequence, and FNV is mentioned nowhere.
- **Fix:**
  - **build-class, small:** pass `--with-hash-algorithm=siphash13` in the CPython configure
    recipe; it is a configure flag, not a patch. It changes the snapshot's bytes and every fuel
    number, so pair it with 086's re-measurement.
  - **check:** `sys.hash_info.algorithm == 'siphash13'` on both binaries.
  - **README now:** one *Not protected* item. The snapshot's string hash has a fixed key, so
    data built to collide can make dict and set work quadratic until the deadline. Use
    `snapshot=False` for untrusted keys.

## Notes (no finding, or as designed and documented)

- **N1. A sub-descriptor of a read-only grant opens files for writing, but cannot write**
  (EXECUTED, `p41c`, `p41b`).
  - `os.open("secret.txt", O_WRONLY or O_RDWR, dir_fd=<the grant>)` returns a descriptor;
    every write answers EBADF. The same open by path answers 63.
  - `O_TRUNC` and `O_CREAT` answer 63 either way.
  - `os.chmod` answers 0 and changes nothing: the host mode stays `0644`.
  - Nothing on the host changes. This is wasmtime's rights model: the right is missing, not the
    open refused. It is worth a check that pins "no byte, size or time changes" for both
    spellings, so a wasmtime upgrade cannot change it quietly.
- **N2. Frames past `max_tool_calls` are still answered, refused** (EXECUTED, `p42`, `p43`).
  - At the default budget of 1,000, a guest sent 5,000 `list` frames in about a second, and
    5,010 were counted.
  - The README says `max_tool_calls` bounds each frame's fixed cost "since it bounds the frames"
    (README:1503-1504). It bounds the frames that are served; the deadline bounds the refused
    ones.
  - The cost is small, and it falls on the call's own thread. Beside a flood, a host thread
    doing pure-Python work kept 98% of its rate (`p43`). Correct the sentence.
- **N3. The `.cwasm` cache** (READ by the helper, `runner.py:3754-3806`).
  - It holds: `lstat`, the owner's uid, no group or other write, and mkstemp plus replace. The
    key is 128 bits of the binary's SHA-256 plus the wasmtime version.
  - It is weak in two ways. Only the leaf folder is checked, then opened by path. And
    `_digest` caches by (path, size, mtime_ns).
  - Both need write access to a folder the user chose, or to the artifact folder (S3). Windows
    has no check, as documented.
  - Optional: open the folder with `O_DIRECTORY|O_NOFOLLOW` and check its parents' modes.
- **N4. The publish jobs** (READ by the helper).
  - `pypa/gh-action-pypi-publish`, pinned by SHA, runs a container named by a mutable tag. So
    the bytes that hold `id-token: write` are not pinned. `uv publish --trusted-publishing
    always`, with the pinned uv, would pin them.
  - In `publish`, `GH_TOKEN` is in the environment of `uv run … release/version.py notes`.
  - Both are build-class and small.
- **N5. a7's N4 is still open.** README:367-368 says libxml2's catalog is read "only if the
  embedder grants a folder at `/etc/xml`". A guest with a reused writable root can write
  `/etc/xml/catalog` itself. Name the catalog in *Not protected*'s reused-root list, beside
  `dateutil` and `mimetypes`.
- **N6. Clean.**
  - **Workflow** (helper, EXECUTED and READ): top-level `permissions: {}`; all 52 `uses:` lines
    pinned by full SHA; no `${{ }}` in any `run:`; no `pull_request_target`; a branch push
    triggers nothing; no `secrets.*` or `continue-on-error`; caches off.
  - **Downloads:** 67 pins, all https, each re-hashed by `pinned()` before unpacking.
  - **Patches:** all 7 are hashed in MANIFEST, named in the CHANGELOG and drafted upstream;
    none touches a bound or an access rule.
  - **Licences:** no GPL or AGPL component ships. SECURITY.md has a reporting route, and
    private reporting is on.
  - **Secrets:** no secret in tracked files or in history.
- **N7. Small supply notes** (helper).
  - `pinned()` matches the file name as a regex (`common.sh:52`); `grep -F` is safer.
  - `60_link.sh:129-131` `eval`s commands from CPython's own `make -n`; that adds no trust
    beyond running `make`.
  - The wheel's `License-Expression` names Apache-2.0 alone, though it bundles PSF, BSD, MIT and
    FTL components.
  - 26 dormant `setup-uv` caches on main can be deleted.
- **N8. Process: the in-flight specifications' build reviews are not yet under
  `context/reviews/`** (helper, READ). For 073, 078, 083, 084, 085, 086, 087 and 089 they sit
  in the lane's scratchpads. AGENTS.md requires them recorded before landing, so each addendum

- **N9. The snapshot's object addresses repeat** (`p40`: `id(object())` is the same in every

## What each later package landing's addendum must check

Each addendum is one page against this review. It is written by a fresh reviewer, on the commit
that lands. The helper's per-specification notes are summarised here.

**Every landing that changes the binary, the zip or the runner:**

1. **The import list, by function, not by module.** Compare it with this review's 43
   (`p00_imports`). Any new preview1 function must be shadowed for provider numbers and counted
   by the open-file cap. 043 brings `fd_renumber` through qhull's `freopen`; 037 refuses
   `freopen` to keep it out. Re-run a7's `p30b`. Exports unchanged.
2. **Pins.** Each new or changed pin is re-hashed at use and equals upstream's published digest.
   Build-time code from sdists (f2py, meson scripts, `git_version.py`) runs only under the
   pinned host Python.
3. **Patches.** Each is in MANIFEST, the CHANGELOG and `context/upstream/patches/`. The trees
   check accepts exactly the recorded set. None touches a parser limit, a bound or an access
   rule.
4. **Native surface.**
   - Nothing native for a package declared pure.
   - Constructors and `target_features` grow only by named entries.
   - No thread can start: OpenMP, `std::thread` and pools stay gated.
   - Fuzz each new parser or recursive structure. Any new trap joins the README's list, with a
     check.
5. **Planting.**
   - Any "disk first, then the zip" read (041, 045), and any settings, cache or catalog file
     read from HOME or a root (042's reportlab settings, sklearn's and statsmodels' data
     folders), gets a reused-root probe and a line in *Not protected*.
   - Re-run `a7_p04`, `a7_p20` and `p41` (hard links from a read-only grant).
