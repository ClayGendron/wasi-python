## Feasibility on GitHub as it is

- **Rulesets today** (EXECUTED): `25363090` "main is protected" targets `~DEFAULT_BRANCH` with rules `deletion`, `non_fast_forward`, `update` and one bypass actor, `RepositoryRole` 5 (admin), `bypass_mode: always`. It has no `pull_request` rule and no `required_linear_history` rule. `25363091` protects `refs/tags/v*` (creation, deletion, non-fast-forward, update), the same bypass. The repository is public, user-owned, default branch `main`, all three merge methods allowed, `delete_branch_on_merge: false`. One collaborator: `ClayGendron`, admin; `gh` is signed in as `ClayGendron`. Environments: `github-pages`, `pypi`, `release`, each with a branch policy and no required reviewer. No deploy key, no `accept` environment.
- **`schedule` on the default branch:** works once `dev` is the default (READ, the prior-art report §7, G9); a public repository's schedule is disabled after 60 days without activity (READ, same).
- **`if: always()` aggregate over `needs` with `success`/`skipped`:** works as Wasmtime's does (READ, prior-art §4); a job skipped by `if:` reports success and a workflow-level `paths:` filter would leave the check Pending (READ, prior-art §7). Decision 2's choice is right. The required-check context is the job's `name:`, not its id; most jobs in `release.yml` carry long names (READ), so `ci-status` must be named exactly (Low 6).
- **`concurrency` with `cancel-in-progress: true` for pull requests:** works; a pending run in the group is always cancelled (READ, prior-art §7). For pushes to `dev` the spec sets nothing, so today's `release-${{ github.ref }}`, no cancel, applies: a third quick merge cancels the second's pending run (INFERRED). Acceptance "since the last acceptance" (Decision 5) absorbs that.
- **`pull_request` trigger added by a pull request:** a `pull_request` run reads the workflow from the pull request's merge ref, so step 2's own pull request runs the new trigger (INFERRED from GitHub's event model). Design step 2's "dispatched by hand ... since the trigger it adds does not exist yet" is wrong in the harmless direction (Medium 5).
- **Cache scopes:** a pull request's run restores caches from its own scope (`refs/pull/N/merge`), the base branch and the default branch, and saves to its own scope (INFERRED, GitHub's cache rules). With `dev` as default and base, `dev`'s set is readable from every pull request into `dev`, from the release pull request into `main`, and from tags. Decision 3's "the branch's own cache scope" is the pull request's merge-ref scope, not the head branch's (Low 7).
- **Squash merge with "require linear history" and "up to date":** both exist and combine (READ, docs.github.com merge methods). Each merge then puts two commits on `dev` (the squash and the acceptance), and each makes every open pull request out of date, so each open pull request re-runs its check twice per merge (INFERRED; a cost, not a defect).
- **Fast-forward merge of a pull request:** GitHub offers merge commit, squash and rebase only; there is no fast-forward method, and rebase-and-merge rewrites the commits (READ, docs.github.com "About merge methods"; community discussion 4618, open). See High 5.
- **Bypass actors in rulesets:** `RepositoryRole`, `Team`, `Integration` (a GitHub App) and `DeployKey` are the documented types (INFERRED from the REST schema as I know it; to be confirmed at the build with one `gh api` read of a ruleset carrying one). A user-owned repository has no teams; an App or a deploy key both work.
- **One approving review from a non-author:** GitHub never lets an author approve their own pull request, and every agent here acts as `ClayGendron`, the only collaborator. See High 2.
- **Who pushes the acceptance:** a push made with `GITHUB_TOKEN` starts no workflow; a push made with a deploy key or an App token does (INFERRED, GitHub's documented rule). See High 4.
