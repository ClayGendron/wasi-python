## Findings, most severe first

1. **Medium: the one step that holds "value first" is the one no check requires** (Decision 8; `tests/harness/scan.py:432-449`). Decision 4 leaves the voice, the private names and the figures to the reader of Decision 8, so the owner's request is met only if that review is written; yet nothing asks for it. The author's reason (a), that a check on a file's presence refuses a release on paperwork, applies word for word to the structural review, which the project chose to hold by `structural_review_errors` and AGENTS.md ("the judge refuses a released version without one"). 0.1.1 was released by a delegated agent while the owner slept (READ, 138's landing notes) and 0.1.2's push is delegated the same way (READ, `decisions.md:501`), so the step most likely to be skipped is the unchecked one. Evidence that closes it: `scan.release_notes_review_errors(version, reviews)`, the twin of `structural_review_errors`, refusing a released version above 0.1.1 with no `<version>-release-notes-review-YYYY-MM-DD.md` and one with no `## Verdict`; called beside it at `test_rules.py:256`; a unit row seen failing first; and Decision 8's last two sentences replaced by "The judge holds the file's presence for a released version above 0.1.1, as it holds the structural review's; what the notes say stays the reader's judgment."
2. **Medium: the model omits an Upgrading entry that its own Decision 3 requires, and Decision 9 tells 145's builder to copy it** (the model's mount entry; 145's Decision 1). 145 refuses a component with `:` or `\` with `EINVAL` on every host (READ); on Linux and macOS a mount accepted both before, so a guest that writes `2026-10-27T12:30.json` into a mount now fails. That is "a value now refused" (Decision 3's Upgrading), and the summary's "One change may need action" is then wrong. Failure: an embedder upgrades on the notes' word that only unbounded tool calls changed, and a guest that names files by ISO timestamp breaks. Fix text, in the model: under Upgrading add "- **A mount refuses file names with `:` or `\`.** On Linux and macOS a mount accepted them before; now every host answers `EINVAL`, as Windows always did. A guest that writes timestamped names such as `12:30.csv` into a mount should use another separator. [Treat a path as a name, not a host path](https://claygendron.github.io/wasi-python/how-to/mounts/#treat-a-path-as-a-name-not-a-host-path)"; the summary's last sentence becomes "Two changes may need action: a tool call that nothing else bounds now ends after an hour, and a mount refuses file names with `:` or `\`."; the measures paragraph is recounted. 144's builder should ask the same of 144's "a `close()` from the event loop's thread during a `run_async` turn now waits for the ending" (READ, `d59f2073`): a call that used to return now blocks the loop, which may be an Upgrading entry too.

4. **Low: two model entries do not yet say the value in the reader's terms** (the model, Faster and Fixed, and the threads entry). Fix text, Faster: "- **Starts are fast again in containers where root does not own `/`.** In 0.1.1 the module cache was refused when another user owned `/`, so every start compiled the module first. Threads, second sentence: "A tool call that times out leaves its function running on a thread; once 64 such threads are alive in a process, the next tool call is refused, and the guest's error names the bound."
