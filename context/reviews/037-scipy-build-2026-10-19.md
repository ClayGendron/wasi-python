## Findings, most severe first

### F1 (high; blocks the landing): the scipy behaviour checks record fuel that is not repeatable

- **What.** `test_v1_3_scipy.py`'s `_run` calls `wasi_python.run` and records `fuel_used` as the check's metric. `run` answers `random_get` from host entropy. Spec 080 found exactly this (Decision 1): such fuel moves from run to run on the plain binary, so a check that records fuel goes through the `guest` driver, which seeds randomness and steps the clock. It also showed that `PYTHONHASHSEED` does not help: the reactor's interpreter is isolated.
- **Evidence (EXECUTED).**
  - `sameness.py` between the builder's record and mine: four rows differ beyond 1e-4, all plain: `test_a_python_callbacks_exception_comes_back_through_c`, `test_a_singular_solve_raises_ linalgerror`, `test_scipy_odr_is_left_out_by_name`, `test_workers_run_serially_or_raise_as_ documented`.
  - Four runs of the singular-solve program (`probes/fuelvar.out`): plain spread 6.6e-4, and 1.2e-3 with `PYTHONHASHSEED=0`; snapshot 4.5e-5 to 5.8e-5.
- **Why it blocks.** The lane runs `sameness.py` between the reviewer's record and its own serial one, and a difference stops the landing until the check is fixed, never a re-run (spec 052, Decision 11). Later, the ratchet would find these rows "grown" at random.
- **Fix.** Either stop recording fuel from `_run` (the fuel limit still guards hangs), or run the checks through the `guest` driver with nothing writable. The Sobol gap needs nothing writable, so the first is simpler. It is a judge change: `--accept-judge` names it.

### F3 (medium): the growth reason misses the cause of the upstream groups' growth

- **What.** The accept-growth reason says every start pays about 16.5 M and every exit 1.2 to 1.5 M, and that "the rest, 0.004% to 5%" is "the same start and exit cost on longer runs (the upstream groups …)". Each upstream group is one snapshot session (READ, `upstream.py:5`). Its start and exit cost is about 1.5 M. But:
  - `numpy-core` grew 2,402,668,500 (+1.18%) with the same 9,519 passes;
  - `pandas-reshape` +234.6 M, `pandas-io-parser` +68.4 M, `pandas-io-formats` +55.2 M, `numpy-lib` +49.5 M, `pandas-internals` +37.6 M, each with the same passes;
  - `pandas-groupby` +8.07 G with one more pass, and `pandas-frame` +10.6 G with 73 more.
- **The cause I measured (EXECUTED, `probes/imp.py`).** Every import that misses the builtin table scans it, and it has 95 more entries (242 against 147). 2,000 `_imp.is_builtin` misses and 200 `find_spec` misses cost 135.8 M on this set against 85.4 M on main's: about 59% more per miss. pytest's imports do many such lookups. `gc.collect()` costs the same on both (EXECUTED, `probes/gc.py`), so the heap is not the cause.
- **The two groups with more passes (INFERRED).** `pandas-groupby`'s new pass is `sem`, which imports `scipy.stats` (`test_reductions.py:1372`, READ); a snapshot `import scipy.stats` costs 8.67 G (the landing notes). `pandas-frame`'s 73 new passes import scipy the same way.
- **Fix.** Correct the landing notes' growth list and the `--accept-growth` reason: name the builtin-table scan for the upstream groups and the long golden jobs, and scipy's own import for the two groups that gained passes. Rule 5 needs a reason that is true; 043's build review set the precedent. A note for the roadmap: this cost grows with every builtin package (044, 045, 042). A faster lookup is a later CPython-recipe question.

### F4 (medium): Sobol gives silently wrong numbers in the default sandbox

- **What (EXECUTED, `probes/probe.out`, `probe2.out`).** With nothing writable, which is every embedder call's default (§4.15):
  - `qmc.Sobol(d=2, scramble=False).random(4)` is all zeros;
  - `qmc.Sobol(d=2, seed=1).random(4)`, the default scrambled form, returns **one point repeated in every row**, not zeros as the README and the gap's reason say;
  - `differential_evolution(init='sobol')` starts from that degenerate population (it still converged on my test function);
  - `shgo(sampling_method='sobol')` dies with a confusing `QhullError` (QH6421) after the swallowed `FileNotFoundError`. Each prints "Exception ignored" to stderr and exits 0, apart from shgo. Native gives the Sobol points (EXECUTED, the oracle).
- **Judgement.** A recorded gap with a failing check, a README warning and a closer that builds next (038) is acceptable **on main**. A release that carries scipy without 038's fix is not: a wrong number with exit 0 is the worst kind of failure for an agent, and stderr is easy to miss.
- **Fix.**
  - Correct the README and both `[[gap]]` reasons: zeros unscrambled, one point repeated scrambled; name `differential_evolution(init='sobol')` and `shgo(sampling_method='sobol')`.
  - The lane records in the roadmap that no release tag carries 037 without 038's Sobol fix. The alternative is to bring 038's `0002-stats-sobol-without-a-temporary-file.patch` forward into 037 (a change to one Cython function, with its check already written).

### F5 (medium-low; Decision 14's finding): +43 MB is real; accept it, cut nothing now

- **What was measured (EXECUTED).**
  - Code section 61.28 MB against 31.90 MB: scipy's archives 20.0 MB plus its static libraries 4.2 MB (HiGHS 3.5 MB of that), OpenBLAS 5.2 MB (the link map). The largest single parts are sparsetools 3.8 MB, HiGHS 4.9 MB in all, `special` about 3.4 MB, `_flapack` 0.9 MB and ducc0 0.9 MB.
  - `name` section 13.03 MB against 2.44 MB. **Deflated it is 0.88 MB.**
  - Data 9.68 MB against 6.66 MB.
  - In the wheel: `python.wasm` 18.1 MB, the snapshot 19.8 MB, the zip 27.4 MB (stored members already deflated); 65.7 MB in all.
- **Why the estimate missed (INFERRED, agreeing with the builder).** It scaled Pyodide's `.so` files, which are size-optimized and carry no name section.
- **Stripping the name section** saves 13 MB per binary on disk (26 MB installed) but only about 1.75 MB of the wheel. The judge needs the names: the constructor check, the callback scan (051) and `same_bytes.py`'s named functions read them. Users get named frames in trap traces. Not now. A later specification could ship stripped binaries and point the judge at the unstripped link, if installed size matters.
- **`-Os` for scipy** (EXECUTED, one compile each): `bsr.cxx` code 2.27 MB at `-O3`, 2.12 MB at `-O2`, 1.56 MB at `-Os` (−31%); `csr.cxx` 2.00, 1.97, 1.73 MB (−13.5%). Across scipy that is perhaps 3 to 6 MB raw and 1 to 1.5 MB of the wheel (INFERRED), with a speed cost. ducc0 at `-Os` crashed at import (Revised at build, item 19). So not without per-module evidence.
- **The wheel's real lever (EXECUTED, INFERRED).** The reactor and the snapshot each carry the same 61.3 MB code section, 13.8 MB deflated each. The wheel holds the code twice. Each package's code costs the wheel about twice its deflated size, plus its zip members. 044, 045 and 042 at about +10 to +15 MB each (INFERRED) would reach PyPI's 100 MB within about three packages. The owner's decision on question 64 is to wait until a landing crosses it. I recommend telling the owner when 044's build measures the wheel, with this projection.
- **The snapshot's start (+9.6%).** The extra 1.44 M is the exit path (EXECUTED, above): C++ static destructors and `gotoblas_quit`. Decision 14's "within 1%" did not count them. A later reactor change could flush stdio and `_Exit` after finalization, skipping destructors that only free memory. It needs its own review. Not now.
- **Disposition.** Accept the growth, with the stated reason naming this finding. The lane's `--accept-growth` text should say "Decision 14's bound exceeded; build review F5: measured, accepted, nothing cut".

### F6 (low): the freopen refusal's stated reason is out of date, and its README sentence is inaccurate

- **The reason.** `recipes/freopen_refusal.c`, step 60's comment and Revised at build item 11 say the runner "does not watch" `fd_renumber`. Since spec 068 it does: `fd_renumber` is in `mounts.SIGNATURES` (shadowed with mounts) and in `mounts.COUNTED` (shadowed and counted without them) (READ, `mounts.py:330-393`, `runner.py:3066`). The refusal is still sound. Its true reason is that it keeps the import list as it is (the tripwire), and that qhull's file options are no use in the sandbox.
- **The README.** It says qhull's `TO <file>` "fails as an unopenable file does … the reactor refuses freopen". `TO` never reaches `freopen`: scipy passes no output file, and qhull refuses `TO` first with QH7092 (EXECUTED). `TI <file>` reaches `freopen` and fails with QH6041 (EXECUTED).
- **Fix.** Correct the three texts (with F2's choice).

### F7 (low): three bundled BSD notices are not shipped

- **What (EXECUTED, `grep` of `LICENSES/scipy.txt`; READ the sources).** scipy's `LICENSES_bundled.txt` points to notices that live in source headers ("For details, see …"). Three are compiled or packed here, and their text is not in `LICENSES/`:
  - pystreambuf (cctbx, BSD-3-Clause), in `io._fast_matrix_market`, linked into `python.wasm`;
  - Chebfun (`interpolate/_bary_rational.py`, BSD-3-Clause), shipped as bytecode;
  - getLebedevSphere (`integrate/_lebedev.py`, BSD-2-Clause), shipped as bytecode. Each licence's binary-form clause asks for the notice. scipy's own wheels ship no more than we do (INFERRED from the same `LICENSE.txt`), but §4.12 says "each ships with its notice". (L-BFGS-B's pointer names a file that no longer exists upstream; there is no notice to copy.)
- **Fix.** Add the three header notices to scipy's licence file in `assemble_artifacts.py`, or answer in writing why not.
