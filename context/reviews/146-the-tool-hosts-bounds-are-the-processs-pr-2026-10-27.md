## Judgement of the six departures

- **`timeout`, not `tool_error`:** right. The per-call cap answers `_Interrupted("timeout", False, …)` (READ, `_Bounded.__call__`), and the specification's sentence asked for both "as the per-call cap" and `tool_error`; following the shape the guest already meets gives one answer, `ToolTimeout`, for both caps, and the message names the bound.
- **The count handed through `_Bounded(abandoned=)`:** sound. The +1 is in `_abandon` and the −1 in the thread's `finally`, both under the bound's own `_lock` and both guarded by the same slot flags (`+1` only when the slot is neither `finished` nor `filled`; `−1` only when `slot.abandoned`), so each abandoned slot is counted in exactly once and out exactly once (READ). A thread that returns after its call, or its session, has ended still holds the bound through its closure and still runs its `finally`, so the count falls then; `test_the_process_count_falls_as_an_abandoned_thread_returns` drives exactly that, 64 → 63 after one host's call was answered (EXECUTED). The process lock is taken under the bound's lock and nothing under it, so it stays the leaf `_process.py`'s lock order names (READ, `_process.py:18-21`). The default, `lambda delta: 0`, keeps every existing fake-driven row out of the process count (READ). The refusal reads the count once, outside the bound's lock; that is the race the next departure records.
- **Three more files:** `_call.py` (nine lines: the counter's function and one keyword), `_sessions.py` (two keywords) and the fork row; each is what the seam needs and nothing else (READ).
- **The session's lifetime is a second guard:** agreed; with `lifetime_s` set every turn's deadline is capped, so `stop_at` is never `None` there, and with `lifetime_s=None` the bound falls to the ceiling (READ, `_Bounded.__init__`, `_sessions.py:1062`). The row drives `wait_s` on the bound directly, which is the only way to reach it.
- **The cap judged at a tool call's start:** correct as described: a tool call already running when the count reaches 64 is not refused and may still be abandoned, and two calls that read 63 at once both start, so the count can pass 64 by at most the tool calls running at that moment (READ, INFERRED). The landing notes and the pull request say so; the tools page and the defaults row do not (Low 3).
- **The bare `python3` slip:** recorded honestly; the measurement and the runs used `uv run` (READ). No finding.
