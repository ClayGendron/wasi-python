## Findings, most severe first

1. **High: the reader's `select.select` refuses a descriptor at or above 1,024, and a dead reader leaves the guest blocked where no deadline reaches it** (`129-output-is-read-from-a-pipe.md`, Decisions 3, 4 and 8: "`select.select` on the open read ends"; row R2, R8).
   Failure: an embedder that holds 1,024 or more descriptors (a server) makes a call; `os.pipe()` returns descriptors above 1,023; the reader's first `select.select` raises `ValueError: filedescriptor out of range in select()` and the thread ends; the guest fills the 64 KiB pipe and blocks inside `write(2)` in `fd_write`, a host call, where the epoch deadline, `cancel` and Ctrl-C cannot interrupt it (they stop wasm code, not a blocked system call); `release()` never runs because the guest thread never ends. The call hangs for ever, with no `trapped`. EXECUTED on this host (darwin-arm64, CPython 3.14.2) with the soft limit raised in the probe's own process: a pipe's read end moved to descriptor 1,100 by `os.dup2`; `select.select([1100], [], [], 0)` raised that `ValueError`; `select.poll()` on the same descriptor returned `[]`; `selectors.DefaultSelector()` was `KqueueSelector`. CPython's `select.select` keeps `FD_SETSIZE` (1,024) on macOS and Linux. The CLI raises its own soft limit to 10,240 (`src/wasi_python/cli.py:183–200`), so the CLI itself can hand the library such descriptors.
   Fix: (a) `select.poll()` in the drain (POSIX has it; Windows is not on this path), or `selectors.DefaultSelector`; name it in Decisions 3, 4 and 8. (b) The drain's loop body never ends the reader before the store is closed, whatever it raises: a `try`/`except BaseException` around the read and the write that drops the bytes and continues, as `_write_output` does today (`src/wasi_python/_call.py:1023–1029`), so a guest can never be left blocked by a host bug. (c) A check in the new file: a call made while the process's lowest free descriptor is above 1,024 (the check raises its own soft limit to `min(hard, 2048)` in a subprocess and holds `/dev/null` open 1,030 times, then runs a guest that writes 1 MiB) returns the 1 MiB exactly. It fails on a build with `select.select`, and would fail today only by the limit, not by the output.

2. **Medium: `close()` waits for EOF, which a forked child's inherited copy of wasmtime's write end withholds** (Decision 3, "`close()`: called after `store.close()`, which drops wasmtime's write ends and delivers EOF; it joins the reader"; Decision 2, "the only write end is wasmtime's"; row R4, R8).
   Failure: an embedder on Linux forks while a call runs on another thread (`multiprocessing` with the `fork` start method, the default there through 3.13; a pre-fork server), and the child lives on without `exec`. A fork copies the descriptor table; `O_CLOEXEC` closes at `exec`, not at fork. The child holds a copy of wasmtime's write end. The parent's `store.close()` closes its own; no EOF arrives; `capture.close()` joins the reader for as long as the child lives. Today's callback has no descriptor and no such wait. The specification's fork note (`_process.fork_used`, spec 105) refuses the child's use of the runner; it does not stop the parent's call from hanging on the child.
   Evidence that would close it: a check, POSIX only, in which the test forks a child that sleeps and then `os._exit(0)`s, and a call with 1 MiB of output made while it sleeps returns before `os.waitpid(pid, os.WNOHANG)` reports the child ended. The fix the review suggests: `close()` does not wait for EOF. After `store.close()` wasmtime holds no write end and nothing more can arrive, so `close()` asks the reader to settle (the zero-timeout drain Decision 4 already has) and then to stop, and the runner closes the read ends itself; EOF becomes a shortcut, never the condition. The same for the session's `close()`.

3. **Medium: `_platform.py` moves to about 1,480 of its 1,500-line ceiling, the change the last structural review said would be the one to watch** (Decision 8: "from 1,464 to about 1,480 lines, 20 under the ceiling"; `../reviews/0.1.0-structural-review-2026-10-21.md`, finding 5: "the next platform difference would take it over the ceiling. Under this review's ranking, that would be a High. Fix: before such a change, move `_Windows` … into a `_platform_windows.py`"; row R5, R7).
   Failure: the module stays under the ceiling by 20 lines (EXECUTED today: 1,464), so no rule is bypassed and the rules check passes; but the next platform concern after 129 crosses it, and the split the 0.1.0 review named still has no number and no roadmap line (EXECUTED: `grep -n "_platform_windows" context/roadmap.md` finds nothing). The README's ranking makes a row that moves toward Weak with no specification named to move it back a Medium.
   What closes it: a reserved specification with a roadmap line for the split (`_Windows`, `_ByHandle` and the Windows constants into `_platform_windows.py` that `_select` imports; about 350 lines), before 129 lands or as 129's stacked base. 129's text then says which.

4. **Low (written in): the thread-set check needs a warm-up call** (Decision 1, `test_a_call_leaves_no_thread_of_its_own_behind`). A process's first call starts the epoch ticker's thread, which stays (`src/wasi_python/_engines.py:298`, `p.ticker_thread`, daemon), so the sets before and after a first call differ on every system. The row now takes both sets after one warm-up call.

5. **Low (written in): the hard-exit row must write unbuffered** (Decision 1, `test_every_byte_written_before_a_hard_exit_arrives`). `os._exit` does not flush Python's buffered stdout; a guest that `print`s 1 MiB then calls `os._exit(0)` loses what the buffer held, in both captures. The row now writes with `os.write(1, …)`.

6. **Low (written in): `_process.py`'s type-checking import of `_Stream` moves with the class** (`src/wasi_python/_process.py:55`, `from ._call import _Stream` under `TYPE_CHECKING`; the Design's `_process.py` line named only the observer field). Written into the Design.

7. **Low (written in): the descriptor cost and the capture's own failures were unstated** (Decision 3). Six descriptors per live call on POSIX against none today; the library never changes limits (`context/decisions.md:177`, spec 100), so under macOS's default soft limit of 256 twenty concurrent calls take 120. An `OSError` from `os.pipe()` or a failure to start the reader is raised before any guest code with every descriptor the capture opened closed. Written in as a bullet of Decision 3.

8. **Low (written in): the settle's premise is wasmtime-wasi's synchronous `OutputFile`** (Decision 4). "Every byte written before the turn ended is in the turn's streams" holds because `OutputFile::write` is `write_all` on the calling thread (READ, `context/prior_art/wasmtime-v49/crates/wasi/src/cli/file.rs:49–52`); a wasmtime that moved file output onto a worker, as the custom stream is today, would break a turn's boundary silently. Written in, with the engine-upgrade note in `_wasmtime_ffi.py`'s docstring to carry the fact.

9. **Low (not written in; the evidence folder is the author's): criterion 6's command does not run from where the folder lives** (`context/research/2026-10-24-what-output-capture-costs/driver.py:21–23`, `REPO = HERE.parents[1]`, which from `context/research/<folder>/` is `context/`, so `SET` is `context/build/artifacts`, which does not exist; EXECUTED by reading the path and `ls`). The bare arms also need `lib/` (a stdlib folder beside the driver, not described) and `build/rust-spike-perf/work/cwasm-bare/python-snapshot.cwasm` (present here). Fix: `REPO = HERE.parents[2]`, and a line in the memo's Evidence bullet saying what `lib/` is, or the product arms alone for criterion 6.

### Notes

- **N1. Windows against POSIX, as an embedder sees it.** Both captures give the guest an `fd_write` that succeeds in full, `isatty` false, `fd_seek` refused; `Completed.stdout`, `stderr` and `truncated` are built the same way. The one difference is back-pressure: a guest past the cap on POSIX blocks until the reader drains a 64 KiB buffer, where the callback dropped at once; the guest cannot observe it, and the host's cost is a read per 64 KiB (the memo, §5.4). INFERRED; the `own-runner` shard on three systems is the check.
- **N2. The re-run, on a loud machine (two other reviewers running).** EXECUTED, 3 repeats, medians: 32 MiB in 64 KiB writes: product 216.8 ms, product-file 124.4, product-pipe 78.3 (minimums 207.4, 92.6, 63.8); 10,000 writes of 100 bytes: product 279.5, product-file 52.0, product-pipe 43.9 (minimums 263.8, 49.5, 41.7). The quiet-window ratios in the memo (155.6 against 35.9; 304.5 against 35.3) are not reproduced, but the ordering and the shape are: the pipe is 2.8 and 6.4 times faster than today's callback in the same windows. Benchmark facts, not checks.
- **N3. The alternatives were weighed.** wasmtime-py's `WasiConfig` offers `stdout_file`, `stdout_custom` and `inherit_stdout` only (READ, `context/prior_art/wasmtime-py/wasmtime/_wasi.py:103–170`; the clone is at `280ce73`, 2026-09-24, after 49.0.0 and before 50; `../research/2026-10-24-moving-to-wasmtime-50.md` §2's API diff says no class gained or lost a name in 50.0.1, so 50 offers no pipe or buffer either). A temporary file plus a reader was rejected because the cap is not live (the memo §5.2: a 1 MiB file under a 4 KiB cap, `truncated` empty; a tail reader would not stop the file growing). A FIFO is weighed in Decision 2 and kept as the Linux fallback. The pipe is the only public path with back-pressure.
- **N4. The tables match the JSON.** EXECUTED by reading `results/summary.txt` against the memo's §4.1, §4.2, §4.4, §5.3 and §5.4: every number quoted in the specification (156 to 242, 36 to 48, 35 to 42, 305 and 35, 4,096 and `("stdout",)`, 7,000 and 5,000) is in `sizes.json`, `attribute.json`, `small.json` and `cap.json`.
- **N5. 130's roadmap line is present** (EXECUTED: `context/roadmap.md:80`, "Reserved: 130, Windows reads its output from a named pipe").

## Verdict

Not fit to build yet: the reader's `select.select` fails at or above descriptor 1,024 and leaves the guest blocked in a host call where no deadline reaches it; fit to build once `poll` (or a selector) and a reader that never ends before the store is closed replace it, `close()` settles rather than waits for EOF, and the `_platform.py` split is reserved with a roadmap line.
