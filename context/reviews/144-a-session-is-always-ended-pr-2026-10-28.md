## The lifecycle, path by path

- **`close()` from a host function on the turn's thread** (READ, INFERRED): `_session_turn` takes `TAKE_TURN` under `state.lock` before any guest code, so `holder` is the worker; `close()` marks TURN to STOPPING and finds `holder == me`, returns; the turn sees `closing`, returns, `TURN_RETURNED` moves STOPPING to MARKED and claims the ending for itself in the same hold; one ending. EXECUTED by its row.
- **`close()` from the loop's thread** (READ): after `TAKE_TURN` the holder is the worker, so `close()` marks and, the phase being STOPPING, claims nothing and waits on `done`; the turn's thread ends it. Before `TAKE_TURN` the holder is the loop's thread and `close()` returns at once (departure 6; M1). Both ended once (probes 3 and 4).
- **`close()` from another thread** (READ): marks, waits on `done`; the turn's thread, or a closer after a cancel, ends it. EXECUTED by probe 3.
- **A queued turn cancelled after a concurrent `close()`** (READ): `future.cancel()` is true, the coroutine pops its entry from `live` under `live_lock` and, if it got it, runs `_release_claim`, which moves STOPPING to MARKED and claims the ending for `_CLOSER` in one hold, then starts the closer after the hold. EXECUTED by its row and probes 2 and 3.
- **`_submit` raising** (READ): the entry is popped and `_release_claim` runs directly; there is no future, so no registration, so the exit hook can never hold a second release for it. Not driven by a row; the landing notes say why, and the code is the same `_release_claim`.
- **A closer whose start raises** (READ): `_start_closer` catches a failure of the seam or of `thread.start()`, takes the thread back out of `closers`, and runs the same target on the calling thread; `_end_quietly` never raises. EXECUTED by its row (the seam) and probe 1 (`thread.start()`).
- **Exit with a turn queued** (READ): `threading._register_atexit` hooks run before `atexit`'s, so `_stop_async_calls` runs before `_sessions_at_exit`; `pool.shutdown(cancel_futures=True)` cancels the queued future synchronously; the hook then, under `live_lock`, takes out each entry whose future is cancelled, and after the lock is released runs each release once, swallowing what it raises.
