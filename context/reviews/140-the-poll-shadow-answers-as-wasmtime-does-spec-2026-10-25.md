## Is the shadow still needed after 127?

Yes. The poll shadow is spec 010's, not an advisory guard: it exists so a guest that waits keeps its deadline, since wasmtime's epoch interrupt is checked only while guest code runs (READ, `context/specifications/010-a-sleeping-guest-keeps-its-deadline.md`, Decision 1). Spec 048's advisory table names `path_rename` and `fd_readdir` only; `grep -i poll` over `context/specifications/048-the-sandbox-holds-on-wasmtime-49-0-0.md` finds nothing (EXECUTED), and over 127 finds nothing either (EXECUTED). 127 removes the two guard shadows and keeps the three counted calls as `_counted_linker` (READ, 127 line 37), so `held` is still kept after it. 140 is not moot after 127.

## High 1's mechanism, checked against the code and against wasmtime

The question 137's review left for this review: do `held`, `table` and the preopen count tell a file on a plain grant, a zip member, a preopen and a closed number apart? They do, with one change of order (finding 2) and one gap that `held` cannot see (closed stdio, finding 1).

- Every number wasmtime gives the guest comes from `path_open`, and every successful forwarded `path_open` calls `_hold` with the number wasmtime wrote at `out`, on a call with mounts or without, whatever the cap (READ, `_fs_paths.py:107-116`; `_fs_table.py:586-588`; the guard shadows `COUNTED` on every call without mounts, `_fs_table.py:13-16`). A session's table, and so its `held`, lives across turns; `new_turn` does not clear it (READ, `_fs_table.py:145-153`).
- A file on a plain grant: wasmtime answers ready, nbytes 1, for reading and for writing, even on a file opened without `fd_write` in its rights (the probe). It is in `held`, so Decision 3 answers ready. A zip member is opened the same way, on the zip's folder, a plain preopen (READ, `_call.py:193-233`; INFERRED that its answer is a grant file's).
- A preopen: wasmtime answers `EBADF` for both preopens, 3 and 4; today's shadow answers ready for 4 (the probe). The count Decision 3 needs is known: `_Files` is given `others`, the guest paths of every preopen that is not a mount's, in the order wasmtime numbers them from 3 (READ, `_call.py:472-486`, where `first = 3 + len(preopens)` already relies on that order; `_sessions.py:1010-1024`, the same). So `len(others)` is the count, HOME and the zip included; the mounts' own preopens are in `table` with `preopen=True`. The INFERRED in Decision 3 is confirmed: the count is first known in `_Files.__init__`, as `len(others)`.
- A closed number: wasmtime answers `EBADF` for a number never given (9), a number renumbered away, and a closed preopen (the probe). `_renumbered` drops `a` from `held` and `_unhold` drops a closed number (READ, `_fs_table.py:590-599`; `_fs_descriptors.py:74-79`), so each is `EBADF` under Decision 3.
- A folder the guest opened: wasmtime answers `EBADF` (the probe); Decision 3 answers ready and says so as a kept difference. Sound: no write differs, and no working program polls a folder.
- The order: a file renumbered onto preopen 3 is ready on wasmtime, and a file opened on the number of a closed preopen is ready too (the probe, number 5 reused after 4 was closed). `_renumbered` moves the file's number into `held`, so reading `held` before the preopen range gives wasmtime's answer in both. The author's INFERRED order is right, and the probe shows it must also come before 0 to 2 (finding 2).

## Each answer the specification promises, against wasmtime's

- Misaligned `in_ptr`, `out_ptr` and `nevents_ptr` end the run on wasmtime (READ, h14's `compare_wasmtime.json`). With `n == 0` and a misaligned `in_ptr`, wasmtime answers `EINVAL`, not an end (the probe): the count is checked first (finding 3).
- Unknown clock flags: wasmtime answers `EINVAL` for `0x2` (the probe) and `0xFFFE` (h14); today's shadow answers ready.
- `EBADF` for an unknown number and a preopen: as above.
- The kept `EFAULT`: wasmtime ends the run for an in-pointer past memory, aligned or not, where the shadow answers `EFAULT` (the probe), and for an out-pointer with no room (h14). Answering an errno where wasmtime ends the run lets nothing more through. Holds as a kept difference.
- Three differences the specification does not name (finding 1): `n = 4097` clocks with room for every event answers 0 on wasmtime and `ENOMEM` on the shadow (the probe); a closed stderr polled for writing is `EBADF` on wasmtime and ready on the shadow, today and after Decision 3 (the probe); and wasmtime writes the event's fields only, leaving its 11 padding bytes, where the shadow writes all 32 (h14: `changed` 25 against 36 on every answer that succeeds, READ).
