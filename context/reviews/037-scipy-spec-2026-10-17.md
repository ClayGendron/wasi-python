## What holds

- **The route is the memos' route, and its core is proven.** EXECUTED: the spec's own make line
  builds OpenBLAS 0.3.34 plus patch B with no error and the same seven warning classes as the
  memo (`-Wunused-function` 19,998 … `-Wincompatible-pointer-types-discards-qualifiers` 16), so
  dropping `-Wno-return-type` is safe. The archive is 10,866,466 bytes, SHA-256
  `761a55ed…0305c945` (smaller than the memo's 11,095,502: `-fPIC` is now dropped, 3,782 times).
  Linked whole it gives **0** signature mismatches. `make install` writes the archive,
  `openblas.pc`, `cblas.h`, `f77blas.h` and `openblas_config.h`. No builder path is in the
  archive (`strings`: 0 hits).
- **OpenBLAS's host probing does not reach the archive on one host.** EXECUTED: with `gfortran`
  removed from `PATH` and 3 make jobs instead of 10, the archive is byte-identical
  (`761a55ed…`) and `config.h` is identical. Only `Makefile.conf`'s link-only lines differ
  (`FC`, `FEXTRALIB`, `NOFORTRAN=1`, `MAKEFLAGS += -j`). READ: `config.h` carries no host fact
  (`OS_`/`ARCH_` empty, the WASM128 cache sizes, `BUNDERSCORE _`); archive members are added
  with `$^` in prerequisite order (`Makefile.tail:80`, `lapack-netlib/SRC/Makefile:634`), so
  parallelism cannot reorder them; `NUM_CORES` reaches compiles only through `NUM_THREADS`,
  which the line pins to 1; `HOSTARCH` matters only for x86_64 (`Makefile.system:207`); both
  arm64 hosts are LP64 for `getarch_2nd`. INFERRED: arm64 Linux gives the same bytes; the
  same-bytes job is the proof, and the step's archive hash localises a difference.
- **SIMD adds exactly one feature.** EXECUTED: the OpenBLAS link's `target_features` are
  today's set minus `exception-handling` and `extended-const`, plus `+simd128`. So
  `python.wasm` gains `simd128` and nothing else, as decision 29 and Decision 15 say.
- **No new import.** EXECUTED: today's `python.wasm` already imports `sched_yield`, the one
  WASI call OpenBLAS's `-include sched.h` brings. `mmap` comes from the neutral sysroot's
  `libwasi-emulated-mman.a` (present; step 10 replaces the whole sysroot, READ). §4.4 holds.
- **The `?gees_` rename reaches f2py's calls.** EXECUTED: a force-included `#define dgees_
  wasi_scipy_dgees_` rewrites both `extern void F_FUNC(dgees,DGEES)(…)` and the address taken

## Findings, most severe first

1. **[037] The golden jobs, as specified, are neither robust nor fully honest.** High: they
   will fail for reasons that are not the guest's, and some printed values check nothing.
   - **The oracle is not one pinned library.** EXECUTED (PyPI JSON): scipy 1.18.1 ships two
     macOS arm64 wheels, `macosx_12_0_arm64` and `macosx_14_0_arm64`. INFERRED from scipy's
     wheel builds: the 14.0 wheel links Apple's Accelerate, and uv picks it on macOS 14 and
     later; Linux wheels bundle scipy-openblas. So the oracle's LAPACK depends on the host's OS
     version, which nothing pins. READ: `test_goldens_reproduce_under_the_pinned_oracle` runs
     every job in `JOBS` on whatever host runs the full judge (the release build job runs it
     on macos-15; the lane on the owner's Mac). 023 handled the same problem by running its
     plot job "on the recording platform only"; 037 says nothing.
   - **`ilaver()` cannot match.** READ: the guest's is `3.12.0` (`ilaver.c:332-334`).
     INFERRED: Accelerate's LAPACK reports a different version. A golden of it compares two
     LAPACKs' release numbers, not the call.
   - **Iterative results at `k = 6` are path-dependent with default tolerances.** INFERRED:
     `solve_ivp` defaults to `rtol=1e-3`; BFGS to `gtol=1e-5`. One ulp of difference (the
     guest's numpy has no BLAS, the oracle's does) can flip one step's accept or stop decision
     and move the answer far above the sixth digit. The spec's rule, "change the input, never
     `k`", is for rounding boundaries. It does not cure this.
   - **`round(x, k)` is absolute, not significant.** READ: `format(round(x, 9) + 0.0, ".9g")`
     (`numpy_csv.py:16`). A p-value of `3e-12` prints `0`; `norm.cdf(-5)` keeps three digits.
     The numpy and pandas jobs print values near 1, where this is harmless. scipy's `t.sf`,
     `ttest_ind`, `pearsonr`, `binom.pmf` and residuals are not.
   - **The oracle may run multithreaded BLAS.** INFERRED: thread count changes summation order.
   - **Fix.** (a) Pin the oracle's BLAS: install scipy's `macosx_12_0_arm64` wheel on macOS
     (scipy-openblas, no Accelerate), for example by a uv source with a platform marker, and
     set `OPENBLAS_NUM_THREADS=1` and `VECLIB_MAXIMUM_THREADS=1` in `oracle_env`. Name the
     recording platform in each scipy `.expected`, and run the reproduce check for the scipy
     jobs on that platform only, as 023 does. (b) For `ilaver`, print only that it returns
     three integers with major 3. (c) Give every solver and integrator a tolerance at least
     1,000 times tighter than the printed precision (`rtol ≤ 1e-9`, `atol ≤ 1e-12`,
     `gtol`/`xtol`/`ftol ≤ 1e-9`). Then what is printed is bounded by tolerance, not by path.
     (d) Print scipy values with significant digits, `format(float(x) + 0.0, f".{k}g")`, not
     after an absolute `round`. Print residuals as a comparison with a stated bound
     (`residual < 1e-12`).
