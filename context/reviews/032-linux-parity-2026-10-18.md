## Is each per-system split honest?

Yes. Neither split hides a difference the mount should not have (EXECUTED, READ).

**The reads near 2**63.** I probed 10 offsets (from 2**63 − 100,000 to 2**64 − 1) by 10 iovec shapes (`[]`, `[0]`, `[1]`, `[4]`, 65,535, 65,536, 65,537, 100,000, `[0, 100000]`, `[4, 100000]`), for `fd_pread` and for `fd_read` after a seek, plus a zero-length read after a relative seek to 2**63: 234 rows per system (`edges-table.txt`). On Linux the grant and the mount agree on every read row. On macOS the grant answers 0 wherever Linux answers 28 below 2**63, and both answer 28 at and above it. So the mount now is Linux, exactly, at every point probed, including the 64 KiB step for `fd_pread` and none for `fd_read`. The source agrees (READ): `fd_read` hands the whole first non-empty iovec to `read_at_cursor_unspecified` (`p1.rs:1671-1696`); `fd_pread` reads through `FileInputStream`, whose `blocking_read` asks for `size.min(MAX_READ_SIZE_ALLOC)` (`p2/filesystem.rs:88`, `lib.rs:31`). The kernel's `rw_verify_area` refuses `pos + count` past 2**63 − 1 (INFERRED from the answers, which fit it exactly). Refusing more than macOS refuses opens nothing: there are no bytes at those offsets. Decision 6 names Linux as the reference, and acceptance 3 already says "a row that differs by system is asserted per system". The split follows that rule.

**The trailing-slash stat.** The mount keeps one rule (`folder_only and kind != "dir"` → `ENOTDIR`) for `path_open`, `path_filestat_get` and `path_readlink` (READ). On Linux, `open` and `readlink` of `a.txt/` are 54 on the grant too; only a stat differs. The split hides no guard: a stat has no side effect, and the mount answers the stricter, POSIX answer. But the difference is narrower than the commit says (F1), and that makes the case for `ENOTDIR` stronger.

## Findings, most severe first

**F1 (should fix): the README and the Decision 6 row say `os.stat`; the difference is only `lstat`.** wasmtime's `stat_at` follows the last link when `SYMLINK_FOLLOW` is set and not otherwise (`crates/wasi/src/filesystem.rs:868-872`, READ). wasi-libc's `fstatat` sets `SYMLINK_FOLLOW` unless `AT_SYMLINK_NOFOLLOW` is given (`cloudlibc/.../fstatat.c:33-35`, READ), so `os.stat` follows and `os.lstat` does not. The probe agrees (EXECUTED, `edges-table.txt`): `pstat 'a.txt/'` with lookup flags 1 is 54 on Linux's grant, on macOS's grant and on the mount; only flags 0 gives Linux's file stat. A guest program shows the same (EXECUTED, `scripts/guest_stat.py`, set `s-8d84b3b190fe9bce`, on Linux):

```
/g/a.txt/  | stat: errno 54 | lstat: ok size=13 | open: errno 54     (a grant)
/m/a.txt/  | stat: errno 54 | lstat: errno 54   | open: errno 54     (a mount)
```

On macOS all six answers are 54. So the README line "`os.stat` of a file with a trailing `/` or `/.` is `ENOTDIR` … (on Linux, a grant answers with the file's stat)" is wrong for `os.stat`: it is `ENOTDIR` on a Linux grant too. Write `os.lstat` (and `os.stat(…, follow_symlinks=False)`). The Decision 6 row and the landing notes should say "`path_filestat_get` without `SYMLINK_FOLLOW`", and the cause is then cap-std's no-follow stat, not `stat_at` as such (INFERRED from the answers; cap-std's source was not read). This strengthens the decision: Linux's own grant answers `ENOTDIR` to the same path when it follows links, so the mount gives one answer where Linux gives two.

**F2 (should fix): on Linux, the parity no longer compares any trailing-slash stat.** Both `pstat 'a.txt/'` rows are now compared on macOS only. Add `pstat 'a.txt/' following links` and `pstat 'a.txt/.' following links` (lookup flags 1) to the parity, compared on every POSIX system. They agree on Linux, macOS and the mount today (all 54, EXECUTED). Then the reference still judges the rule on Linux, and a change in cap-std's follow path would show.

**F3 (should fix): the `at >= 2**63` guard is no longer tested.** Removing it passes both tests on both systems (above). Its only own case is now a zero-length read at an offset of 2**63 or more, and there the grant answers `EINVAL` (28) on Linux and macOS alike (EXECUTED): `fd_pread` with `[]` or `[0]` at 2**63 and at 2**64 − 1, and `fd_read` with `[]` or `[0]` after a relative seek to 2**63. Without the guard the mount answers 0. Before this commit, the 4-byte rows at 2**63 covered the guard; the new end-of-read test now catches those first. Add the zero-length rows to the parity, compared everywhere. Drop `count and` (an equivalent mutant), or keep it with a comment saying it is redundant.

**F4 (minor): the 64 KiB step is asserted, not compared.** The parity compares only the 4-byte rows on Linux. The step at 2**63 − 65,536 for `fd_pread`, and its absence for `fd_read`, are hard-coded in the deliberate test from one Linux run. They are right today (EXECUTED: the probe above, and every chunk mutant fails). But if wasmtime ever changes `MAX_READ_SIZE_ALLOC`, the grant would move and the mount would not, and only a person reading the code would notice. Add the four boundary rows (`fd_pread` of 100,000 at 2**63 − 65,536 and 2**63 − 65,537; `fd_read` of 100,000 at 2**63 − 100,000 and one lower) to the parity, compared on Linux, so the reference judges them too. Keep the deliberate asserts, which hold the mount on every system.

**F5 (information): Windows.** The release's `verify` job runs this file on `windows-2025` (READ, the workflow). There, the four rows are not compared (`win32` is in neither set), and the deliberate test, which has no skip, asserts the mount's answers: 28 near 2**63, 54 for the trailing-slash stat. So the mount's answer is asserted on Windows. The Windows grant's answers are unobserved: no one has run this file on Windows yet (the earlier review's F4). I expect 0 near 2**63, as `ReadFile` past the end of a file reads nothing (INFERRED, not run). Before this commit the two read rows were compared on Windows; that comparison never ran, so no pass is lost. One sentence in the notes would make this explicit: "Windows's grant answers near 2**63 are not observed and not compared; the mount answers as Linux."

**F6 (nit): macOS gets no row for the reads.** A macOS user now sees `EINVAL` from a mount where a grant reads 0 bytes. Under Decision 6 that is a host difference (Linux is the reference), like `HOST_ROWS` on Windows, so no table row is required. A clause in the notes' read bullet ("so on macOS a mount refuses where a grant reads nothing") would say it once.

## Spec 048

The `ENOTDIR` choice agrees with spec 048 (READ). 048 Decision 1 rests on the same POSIX rule ("POSIX already requires `ENOTDIR` for a non-directory named with a trailing slash"), and its rename shadow answers 54 for `rename("f/", "x")`. 048 Decision 2 stats the source with `SYMLINK_FOLLOW` clear, the very case where Linux's grant drops the slash. But 048 trims every trailing `/` before that stat, so the quirk cannot reach it. Its criterion 2 asserts `NotADirectoryError` for a file with a trailing slash on every host. A mount that answered Linux's file stat would have been the odd one out; the mount and 048 now give the same answer to a slash on a file.
