## 1. The walk (`_walk_posix`, `_writable`, `_make_missing`)

- **Links in folders this user can write are refused, in every shape tried** (EXECUTED,
  `walk.log`): a relative link, an absolute link, a link to a link, `rel/..` after a link, and a
  link in a sealed (0555) folder that leads to a link in a writable one. A link in a sealed
  folder to a real folder is followed, as Decision 4 says. 41 links in a loop: "more than 40
  links".
- **`..` is taken after the link before it**, on the walked folders, as the kernel takes it
  (READ, `runner.py:898-901`; EXECUTED: `rel/../t` is refused at `rel`, not normalised away).
  `..` past `/` stays at `/` (EXECUTED). A relative `root` is joined to `os.getcwd()`, which the
  kernel returns resolved (EXECUTED: `t/target` and `t/target/../target/sub` walk to the right
  folders).
- **A FIFO or a file as a component** gives "is not a folder" (EXECUTED). `lstat` decides
  first, so no FIFO is opened. In the race window between `lstat` and `open`, a FIFO swapped in
  fails `open(O_DIRECTORY)` with `ENOTDIR` at once on macOS; it does not block (EXECUTED, 3 s
  guard). Linux checks `O_DIRECTORY` before it opens (INFERRED).
- **A permission-denied component** raises `PermissionError`, not `ValueError` (EXECUTED). For
  a folder with search but no read permission (0311), wasmtime itself opens a grant under it
  and the walk refuses it: the walk opens each component `O_RDONLY` (finding 6).
- **Races** (EXECUTED, `race.log`, `race2.log`; 3,100 calls against a second process that swaps
  folders in a loop). Four kinds: a middle folder exchanged for another real folder, a middle
  folder replaced by an absolute link, the final folder exchanged, the final folder replaced by a
  link. Each finished call's guest read the folder the walk had checked; I recorded the walk's
  inode for each call, and "walk checked good, guest read EVIL" never occurred. Every other call
  was refused: `ValueError` (does not exist, or passes through the link), `RuntimeError` (changed
  between its check and the call), and also wasmtime's own `WasmtimeError: failed to add preopen
  dir` and a raw `FileNotFoundError` (finding 6). A guest that reads "EVIL" did so only when the
  walk itself had checked that folder, a real folder at that path at that moment, which is what
  the README's "a read-only grant can still change if the same host files are writable
  elsewhere" covers.
- **The walk's own `fstat` check** (`runner.py:932-935`) is redundant for safety: a stand-in
  without it survives every check (EXECUTED), and the identity check compares wasmtime's open
  with the descriptor the walk holds, whatever that is. It is harmless to keep.
- **`_writable`** (READ, EXECUTED): `os.access` is in both `supports_dir_fd` and
  `supports_effective_ids` on macOS; `faccessat(fd, ".", W_OK, AT_EACCESS)` says `/` and
  `/private` are not writable and `/private/tmp` is. Two limits, both false refusals or edge
  cases, not holes:
  - run as root (uid 0), `access` says nearly every folder is writable, so every link on the way
    is refused, including macOS's `/tmp` and `/var` (INFERRED from `access(2)`; finding 9);
  - a guest makes folders with the process's umask; under an unusual umask such as 0222 a
    guest's folder is not writable by its owner, and a link a guest put in it before that would
    be followed. WASI has no `chmod`, so a guest cannot do it on its own (INFERRED; no finding).
- **Descriptors** (EXECUTED, `walk.log`, `leak.log`): 50 rounds of every walk error path, then
  140 calls mixing grants, roots, `root=False`, refusals, deadlines and a `KeyboardInterrupt`
  from the seam: no descriptor leaked. READ: `_walk_posix` closes its stack on any exception;
  `_make_missing` closes its `dup` in a `finally`; `_walk_grants` closes every walk on any
  exception; `_check_preopens` releases every walk in a `finally`; `_run_checked` closes them all
  again (idempotent) before a private root is removed.

## 2. The rules (`_judge`, `_runtime_folders`, `_chain`)

- **No host path is compared by string** (READ). Rules use `(st_dev, st_ino)` chains;
  `_runtime_folders` resolves with `realpath`, then compares identities. Only guest paths are
  compared as text, which is their nature.
- **Each Decision 4 rule, by identity** (EXECUTED, `rules.log` and the judge): a writable grant
  at the artifact set spelled in swapped case is refused ("is inside the artifact set"); at the
  zip folder in swapped case, refused; at the temporary folder, refused ("holds the runtime's
  stdlib folder"); a read-only grant inside a writable one, refused (judge). Stand-ins dropping
  "inside", "above" or "read-only inside writable" each fail two checks (EXECUTED).
- **`root=Path.home()` on a fresh machine** (EXECUTED, `rules.log`): a fresh fake home with
  `cache_dir` inside it, not made yet, is refused ("holds the module cache"), and no cache
  folder is made.
- **A missing root above a missing runtime folder is accepted (finding 1).** Decision 4 says a
  root still to be made is "above nothing". That is false when the runtime folder is also still
  to be made, inside the new root: the runner makes the root, then `_module` makes the module
  cache inside it. EXECUTED, `cache_root.log`: `root=<fresh>/a`, `cache_dir=<fresh>/a/cache`,
  neither existing. The call is accepted; the guest lists `/cache` and writes its own bytes over
  the `.cwasm`. The next process, with a different root, reports `loaded: 1` and returns
  `exit_code=42` from the guest's module: Python never ran. The same holds for
  `root=~/Library/Caches/wasi_python` (or `~/.cache` on Linux) before the first call
  (INFERRED from the same code path).
- **Reaching the zip folder, another call's root, or the lock files** (EXECUTED, READ). A
  writable grant at, inside or above the zip folder or the temporary folder is refused. A
  writable grant cannot reach another call's private root unless the embedder names it. A guest
  cannot hard-link the zip out of its read-only grant into its writable root: `os.link` gives
  `EPERM` (EXECUTED, `hardlink.log`). But a **read-only** grant at or above the temporary folder
  is allowed, and it reads other calls' private roots and stdin (finding 2).
- **The runtime's own code is not among the protected folders** (finding 4): wasmtime-py's
  package folder and, in a checkout, the `wasi_python` package, are accepted as writable grants
  (EXECUTED, `rules.log`), and so is a project folder holding `.venv` when the artifact set comes
  from `$WASI_PYTHON_ARTIFACTS` (EXECUTED, `venv.log`).

## 3. The identity check (`_check_preopens`, `_siphash13`, `_wasi_ino`)

- **Before any guest code** (READ, `runner.py:1627-1629`): it runs in `_drive` after the
  cancel test and before `linker.instantiate(store, module)`, so before any start function.
  wasmtime opened every preopen earlier, inside `preopen_dir` (READ, wasmtime `ctx.rs:302`), and
  holds it after.
- **Every preopen, in wasmtime's order** (READ, EXECUTED): preopens are added stdlib, root,
  grants, and checked `3 + i` in the same list. A probe that checks the list reversed is refused
  ("grants[2] at /g2 changed"), so the order is load-bearing and right (`check.log`).
- **The formula** (READ): wasmtime v49 hashes `(dev, ino)` on POSIX and
  `(dwVolumeSerialNumber, nFileIndexHigh << 32 | nFileIndexLow)` on Windows with
  `DefaultHasher` (`filesystem.rs:353-372`, `filesystem/unix.rs:107-118`,
  `filesystem/windows.rs:85-91`), as the runner does. The unit test pins it per OS (EXECUTED on
  macOS). The SipHash is the public algorithm, written fresh; nothing is copied from the C
  versions in `prior_art` (READ, INFERRED).
- **A passed deadline gives "deadline"** (EXECUTED, `check.log`): with the check slowed past
  `deadline_s=0.05`, the call returns `trapped == "deadline"`, `exit_code None`, and the door is
  never called. With `cancel` set during the check: `"cancelled"`. No check covers either
  (finding 7).
- **Fuel** (READ): the check runs while the store holds `UNMETERED`; `set_fuel(fuel)` comes after
  the guest's instantiation, so `fuel_used` cannot count the check module. EXECUTED
  (`fuel.log`): five calls each with and without the check give overlapping ranges
  (82.24–82.34 M and 82.30–82.35 M); the guest's own clock noise is far larger than the check,
  so this only agrees with the READ.
- **The seam `_after_walk`** is `None` in production (EXECUTED) and is read once per call. It
  runs after the walk, with every walk held, before any work.
- **Real swaps are caught** (EXECUTED, `check.log` and the judge): a middle folder (the
  author's check), the final folder, and a root, each swapped through the seam, raise
  `RuntimeError` before the guest runs; the door count stays 0.

## 4. The zip folder

- **One copy per process** (EXECUTED, `zip.log`): sixteen threads making their first call at
  once all import `json`; there is exactly one `wasi-python-zip-*` folder and one lock file.
- **Locked like spec 016's folders** (READ, EXECUTED): it is a `_Private`, its lock held for the
  process's life. Another process's first call (its sweep) leaves it alone (`swept: 0`, folder
  still there). A killed process's zip folder is swept by the next (the judge's changed spec 016
  check; the "sweep ignores zip-" stand-in fails it).
- **Stamp check and re-copy** (READ, EXECUTED): a changed copy is replaced before the next call
  (the author's check; its stand-in fails). A removed `python315.zip` is re-copied (EXECUTED).
- **The folder itself removed by the host is never recovered (finding 3).** EXECUTED: after
  `rmtree` of the zip folder, every later call in the process raises `FileNotFoundError` from
  `mkstemp`. A temporary-folder cleaner (systemd-tmpfiles' age rule, macOS's periodic clean of
  `/var/folders`) does this to a long-idle server.
- **Removal at exit** (READ, EXECUTED): `_release` calls `_remove_zips`; the stand-in without it
  fails four checks.
- **The fork child forgets them** (READ, EXECUTED, `fork.log`): a child that exits normally
  after `os.fork` leaves the parent's zip folder alone; with the reset removed, the parent's
  next call raises `FileNotFoundError`. No check covers this: the fork check's child leaves by
  `os._exit` (finding 7).
- **Windows re-copy** (READ): every guest open on Windows drops `FILE_SHARE_DELETE`
  (wasmtime `filesystem/windows.rs:148-151`, `filesystem.rs:949`), so `os.replace` over a zip that
  a running guest has open fails with `PermissionError`. The old `_place_checked` handled that
  case; `_copy_zip` does not (finding 3).
- **Coarse timestamps** (READ): the old code trusted its stamp only where `ctime` had
  sub-second precision; the new stamp check has no such guard. Only the host can change the
  copy, so I note it without a finding.

## 6. Windows (READ and INFERRED; nothing run)

- **`_ByHandle`** matches `BY_HANDLE_FILE_INFORMATION`: one DWORD, three FILETIMEs (six
  DWORDs), then serial, size high/low, links, index high/low; 52 bytes (READ).
- **Handles are closed on every path** (READ): `_win_open` closes on a failed
  `GetFileInformationByHandle`; `_walk_windows` closes all held on any exception; a missing tail
  keeps the held handles in the returned `_Walked`; `_identity_of` closes at once;
  `_check_preopens` and `_run_checked` close before a private root is removed.
- **Sharing with wasmtime's own open** (READ): wasmtime opens a preopen with `GENERIC_READ` and
  share `READ | WRITE` (`primitives/windows/fs/dir_utils.rs:86-96`). The walk's handles ask only
  `FILE_READ_ATTRIBUTES`, which sharing does not check, and share `READ | WRITE`, which admits
  wasmtime's read. So the preopen succeeds (INFERRED). wasmtime itself already holds each
  preopen without delete-sharing for the whole call, so the walk's handles add nothing during
  the guest's run; they are closed before the guest is instantiated. A guest's deletes inside a
  grant need no delete access on the grant folder. A concurrent call's walk can make another
  guest's rename of a held folder fail for a moment (INFERRED; benign).
- **Spellings** (READ, INFERRED): `abspath` keeps 8.3 names, which open fine component by
  component; each component's identity comes from its handle, so nothing compares spelling.
  `splitdrive` handles UNC and `\\?\` anchors. `realpath` is used only for the runtime's own
  folders. Every reparse point is refused, so OneDrive's cloud folders and Windows container
  layers would be refused too (finding 5).
- **What `verify (windows-2025)` runs** (READ, `release.yml:234-243`): the v1.1, v1.2
  portable-and-sealed, v1.3 and v1.4 checks, `test_runner_sweep.py` and
  `test_runner_grants.py`. So Windows runs the identity formula (with a grant under the real
  `%TEMP%`), the rules on made-up chains, the raw read-only rows, and the v1.4 grant, no-root and
  `HOME` checks. It runs no junction refusal (`test_the_walk_judges_links` is POSIX-only), no
  read-only Python rows, no bad-grant check and no swap check: those are in
  `test_v1_2_hostile_guest.py`, which `verify` does not run (finding 5).

## Findings, most severe first

1. **High. A root still to be made, at or above a module cache still to be made, is accepted,
   and its guest writes the native code the next process runs** (`runner.py:1336-1338`,
   `1133-1134`; spec Decision 4, "above nothing").
   Failure (EXECUTED, `cache_root.log`): `run(prog, root="<fresh>/a",
   cache_dir="<fresh>/a/cache", stdin=payload)`, neither folder existing. The call is accepted;
   `_module` makes the cache inside the new root; the guest overwrites the `.cwasm` with its
   stdin. The next process (another root) gets `stats() == {'compiled': 0, 'loaded': 1,
   'written': 0}` and `Completed(exit_code=42, …)` from the guest's module. With a crafted file
   this is native code on the host. Real triggers: `root=~/Library/Caches/wasi_python` on a
   fresh Mac, `root=~/.cache` or `~/.cache/wasi_python` on a fresh Linux box or container, or any
   `WASI_PYTHON_CACHE` under a missing root. The spec sentence came from the second
   confirmation and is wrong in this case: a folder not made yet holds nothing until the runner
   makes the cache in it.
   Fix: make the decision after the make. Either (a) make the module cache (`_private(cache,
   is_dir=True)`) before `_walk_grants`, so it always exists when judged; or (b) after
   `_make_missing`, re-run `_judge` with fresh `_runtime_folders`, and on refusal remove only the
   components it made (by descriptor, deepest first). Change Decision 4's sentence to match, and
   add a check: a missing root above a missing cache is refused and makes nothing.
2. **Medium. A read-only grant at or above the temporary folder reads other calls' stdin and
   private roots, and the README no longer warns of it** (`runner.py:1141-1149`; README "Not
   protected").
   Failure (EXECUTED, `tempread.log`): call A runs with `stdin=b"CALLER A's SECRET INPUT"` and
   waits in the door; call B in the same process runs with `grants=[Grant(tempfile.gettempdir(),
   "/t")]` and prints `CALLER A's SECRET INPUT` from `/t/wasi-python-…/stdin`. Before 017 the
   only way was `root=`, and the README said never to grant it; that line was removed because
   writable grants there are now refused.
   Fix: refuse any grant, read-only too, at or above the temporary folder (it holds every call's
   private folders and stdin), or restore the warning for read-only grants and say "calls share
   nothing" depends on it.
3. **Medium. The shared zip folder has no recovery** (`runner.py:1172-1180`, `1190-1205`).
   Failure (EXECUTED, `zip.log`): the host removes `wasi-python-zip-…` while the process lives;
   every later call raises `FileNotFoundError` from `mkstemp` until the process restarts. Before
   017 each call made its own copy, so a temp cleaner could not break a process. On Windows
   (READ), a re-copy while any concurrent guest has the zip open raises `PermissionError`, since
   wasmtime opens guest files without `FILE_SHARE_DELETE`; the old `_place_checked` caught that.
   Fix: if the folder is gone (or not a folder), drop the entry, `remove()` the old `_Private`,
   and make a new one under `_zip_lock`; on Windows, accept a `PermissionError` from the replace
   when the file in place still hashes right. Add a check that removes the folder between calls.
4. **Medium-low. The runtime's own code is not protected, and the `.venv` claim is
   conditional** (`runner.py:1347-1361`; README *Grants*; CHANGELOG).
   Failure (EXECUTED, `rules.log`, `venv.log`): writable grants of wasmtime-py's package folder
   (`_libwasmtime` lives there) and of a checkout's `src/wasi_python` are accepted; so is a
   writable grant of a project folder holding `.venv` when `$WASI_PYTHON_ARTIFACTS` points
   elsewhere. A guest that writes there runs native or Python code in the next host process.
   These are the runtime's own files in §4.15's words.
   Fix: add `Path(wasmtime.__file__).parent` and `Path(wasi_python.__file__).parent` (and the
   folders of a custom `Artifacts`' three files, not only the manifest's) to `_runtime_folders`;
   or answer in writing why three folders suffice and reword the `.venv` claim.
5. **Low-medium. Windows' walk is untested where it differs, and refuses more than links**
   (`tests/unit/test_runner_grants.py:164`; `runner.py:1076-1080`).
   Failure (READ, INFERRED): `verify (windows-2025)` never makes a junction, so the refusal of a

   that renames a held folder during a walk and expects it refused; a README sentence on reparse
   points.
6. **Low. Refusals outside the documented types; one false refusal** (`runner.py:903-931`;
   README "refused with `TypeError` or `ValueError`").
   Failure (EXECUTED, `walk.log`, `race.log`): a folder with search but no read permission
   raises `PermissionError`, though wasmtime opens the grant under it; a component that vanishes
