## Short version

The sandbox holds. Every probe from the a4 review gives the same answer on a6. That covers the
host filesystem, the slash escapes through all three linkers, the mounts, the limits, the
leftovers and the door's cancel.

matplotlib's data grant is read-only, sits at one fixed path inside the runtime's own
`/usr/local/lib`, and no embedder grant, mount or import-path entry can be placed there. A
hostile guest tried 21 ways to change it, alone and three at once. The tree on the host did
not change by one byte or one mode bit.

Pillow and FreeType parse untrusted bytes inside the guest only:
- a 1.6-gigapixel PNG bomb stops at Pillow's own limit;
- with that limit lifted by the guest, it stops at the 1 GiB memory cap with `MemoryError`;
- 1,500 corrupted fonts gave 1,201 renders and 299 `RuntimeError`s, and no trap.

A provider's `OSError` (spec 061) crosses as its errno alone. No message, filename or class
name crosses, and no provider code runs during the mapping.

The release workflow after 057 passes all 18 of its scan rules, and it reads as the rules say.
Every new pin is re-hashed at use. Four of them equal upstream's published hashes.

Async tools run on the embedder's loop under `run_async` and on a private loop under `run`.
Every way a call can end cancels the coroutine before `run` returns. The a4 review's F2 holds
on the async path: across about 3,300 tool runs under race, none started on a call already
answered. The request-byte budget (060) has a safe default, 16 MiB, checked from the length
before any byte is read, and nothing the helper tried got past it. The a4
confirmation's N8 is closed.

One small new finding (F1): an async gate that raises `GeneratorExit` lets the call through.
Only the embedder's own gate code can raise it, so it is not a way in for the guest, but it
breaks the "a broken gate fails closed" contract.

Nothing found blocks a6. The two known gaps stay open, and are recorded below with their
owners. The descriptor cap is due before 0.1.0 final. The unpinned host `python3` turns out to
be wider than noted: it also writes FreeType's configuration headers (F2, low).

### matplotlib's data grant (EXECUTED, `probes/p20_mpl_data_grant.py`, `logs/p20_mpl_data_grant.log`)

- **Read-only.** From a guest with `root=True`, each of these got `PermissionError` 63:
  - `open` for write, `r+b` and append; `truncate`; `mkdir`; `rmdir`; `unlink`; `utime`;
  - `rename` inside the grant, out of it to the root, and into it from the root (`rename` and
    `replace`);
  - `link` both ways between the grant and the root; `symlink` into the grant;
  - `..` and `../..` from the grant, and `..` through `dir_fd`;
  - a create and an unlink through `dir_fd`.
- **`chmod` returned without error.** It changed nothing: the host tree's digest, file modes
  included, was the same before and after. WASI has no `chmod`, so the guest's call does not
  reach the host (INFERRED from the digest).
- **Unchanged on the host.** I hashed the private `mpl-data/` tree (every name, mode and file
  hash) after a first hostile run. It was the same after a second run, and after three hostile
  runs at once. The folder and its parent are `0700`.
- **A fixed path, and no collision.** The guest sees the data at
  `/usr/local/lib/python315.zip/matplotlib/mpl-data`, and matplotlib's `get_data_path()`
  agrees. `_guest_path` refuses every path at or under `/usr/local/lib` (READ,
  `runner.py:1205`). These were each refused with `ValueError` before any work:
  - a grant at the data path, read-only or writable;
  - a grant at `/usr/local/lib/python315.zip`;
  - a mount at the data path;
  - an import-path entry under it.
- **A writable grant at `/usr/local` is allowed, and cannot shadow the data.** The guest made
  `lib/` in that host folder through `dir_fd`. `/usr/local/lib` still listed only the zip:
  wasi-libc resolves the longer preopen first. A `makedirs` toward the data path got 63.
- **The extraction itself** (READ, `_extract_data`, `_member_parts`): the inner archive comes
  from the private copy of the zip after its SHA-256 check. A member that is absolute, holds
  `..`, `\` or `:`, or is not a regular file or folder is refused. Each file is written to a
  temporary name and moved into place, and links are removed, never followed. The inner archive
  is our own build output, hashed in `SHA256SUMS`, so this is defence in depth.

### Pillow and FreeType on untrusted bytes (EXECUTED, `probes/p21_image_font_bombs.py`, `logs/p21_image_font_bombs.log`)

The build compiles Pillow's `_imaging`, `_imagingmath` and `_imagingmorph` with zlib only, so
the image decoders are Pillow's own C (PNG, GIF, BMP, TIFF without libtiff, and so on). There
is no `_imagingft` (READ, step 55). Fonts are read by matplotlib's `ft2font` through FreeType
2.14.3, which is built without PNG, brotli or bzip2 (READ, step 37).

The images were made on the host and granted read-only:

| case | result |
|---|---|
| PNG of 40,000 × 40,000 (1.5 MB on disk, 1.6 G pixels), Pillow's default limit | `DecompressionBombError` at `open` (limit 178,956,970 pixels) |
| the same, the guest sets `Image.MAX_IMAGE_PIXELS = None`, default 1 GiB cap | `MemoryError`, exit 1, no trap |
| the same through `matplotlib.image.imread` | `MemoryError` |
| a 9,000 × 9,000 PNG (81 M pixels), under `memory_bytes=64 MiB` | `MemoryError` |
| the same under the default cap | loads |
| `Image.new('RGBA', (40000, 40000))` | `MemoryError` |
| `fig.text(…, fontsize=1e5)` and `savefig` | FreeType refuses the size (`invalid pixel size`) |
| `figure(figsize=(1000, 1000))` and `savefig` | `MemoryError: std::bad_alloc` |

- **The host stayed bounded.** The probe process's peak RSS was 1,144 MiB across all cases: the
  1 GiB guest cap plus the runner (a benchmark fact, not a test).
- **The guest is the adversary, so Pillow's limit is not a control.** The guest can lift it.
  The memory cap is the control, and it held.
- **FreeType fuzz.** Six runs, each loading 250 mutated copies of `DejaVuSans.ttf`. Each copy
  had 1 to 64 random bytes changed, and a fifth were also truncated. Each was set to a size,
  shaped and drawn. Totals: 1,201 drawn, 299 `RuntimeError`, 0 traps, and every run exited 0.
- **What a parser bug could do.** A memory-safety bug in FreeType or Pillow is a bug inside
  wasm linear memory. It can corrupt that guest's own state, or trap it. It cannot reach host
  memory, because wasmtime bounds every access (INFERRED: this is the sandbox's design, and
  the fuzz found no trap to show either way).

### Async tools and gates (053) and the byte budget (060) (EXECUTED by the helper; F1 re-run by me)

- **Which loop.** Under `run`, an async tool runs on a private loop on its own thread. Under
  `run_async`, on the embedder's loop (the loop ids match). A sync `run()` called inside a
  running coroutine works, on a private loop. The gate's verdict, the arguments and the encoding
  are handled on the work thread; only the awaitable is posted to the loop (READ,
  `tools.py:1488-1560`). A blocking `async def` holds the embedder's loop under `run_async`: the
  embedder's own code, as the README's *Async tools* says.
- **Cancellation** (`a1_async_loop_cancel`). `timeout_s`, the deadline, `cancel=` and a
  `run_async` task's `cancel()` each cancelled the coroutine before `run` returned. No effect
  after any of them, and no "never awaited" or "Task was destroyed" message. A tool that swallows
  its cancel lands its effect later (this review's N8).
- **The a4 review's F2, on the async path: holds.**
  - A gate that allows 1.5 s late: no tool ran in any of the 12 combinations of
    {`run`, `run_async`} × {sync tool, async tool} × {timeout, deadline, cancel}
    (`a2_async_late_gate_races`).
  - Races with gates sleeping 0 to 90 ms: 1,632 tools ran, 468 calls answered abandoned, 0 late
    starts, 0 starts after `run` returned. A gate that swallows its cancel and then allows
    (`a2c_stubborn_gate`): 0 late runs, and 0 late starts in 1,647 race runs.
  - The probe catches the defect: with the guards replaced by ones that ignore the abandoned
    mark, 12 of 12 ran late (`a2d_stubborn_gate_standin`).
- **Exceptions** (`a3_async_exceptions`). An async tool or gate raising `RuntimeError`,
  `KeyboardInterrupt`, `SystemExit`, `CancelledError` or a custom `BaseException` reached the
  guest only as "failed (internal error)" or `denied`. Nothing escaped `run`, `run_async` or the
  embedder's loop. A token and a path in the message stayed in the host's record. The exception
  is `GeneratorExit`: F1.
- **Isolation between runs** (`a4`). Four concurrent `run_async` calls each saw only their own
  `contextvars` value; a tool's `set` changed neither the next call's view nor the embedder's.
- **The byte budget** (`b1_byte_budget`, `b2_boundary`). The door calls `admit(length)` before
  it reads the frame (READ, `runner.py:3192`). Forty 1 MiB frames of each kind were counted:
  worst-shape calls (sync and async tools), padded `list` frames, malformed JSON and unknown
  tools. Each gave 16 admitted, then 24 `budget_exceeded`, with no tool run. Frames over the
  1 MiB cap are `too_large` and spend nothing. A budget of 1,000 admitted 600 + 400 bytes and
  refused the next byte.
- **The a4 tool probes, re-run** (`a4rerun/`): every difference from the a4 logs is a 056 fix
  (F1's bound keywords gone, frame 25 `invalid_arguments`, no tool run after `run` returned).
  Nothing else moved.

### Spec 061: a provider's `OSError` (EXECUTED, `probes/p22_errno_061.py`, `logs/p22_errno_061.log`)

A read-only mount whose provider raises on `stat`, `read`, and in the middle of a listing. Each

- **Mapped** (no fault recorded, the secret in neither output nor `repr(done)`):

- **Faults** (EIO 29 to the guest, a `FileFault` on the host): an errno of 9999, `True`, an

## Findings, most severe first

### F1. An async gate that raises `GeneratorExit` allows the call, and the tool runs. Low; does not block; fix with a check, ideally in a6 (EXECUTED)

The README says: "A gate that raises anything else refuses too, and the record keeps its
fault." That holds for a sync gate. It does not hold for an async gate that raises
`GeneratorExit` or a subclass of it.

**What I ran** (`probes/p24_gate_generatorexit.py`, `logs/p24_gate_generatorexit.log`; the
helper found it first, `tools-probes/a4_async_ceiling_context.log` case 1):

| gate | raises | outcome | the tool |
|---|---|---|---|
| sync | `RuntimeError`, `GeneratorExit`, a subclass | `denied`, the fault recorded | not run |
| `async def` | `RuntimeError` | `denied` | not run |
| `async def` | `GeneratorExit`, a subclass | **`ok`, no fault** | **ran** |
| a `def` returning a coroutine | `GeneratorExit`, a subclass | **`ok`, no fault** | **ran** |

- The same for a sync tool and an async tool, and under `run_async`.
- An async *tool* that raises `GeneratorExit` is answered `ok` with the value `None`. A sync
  tool that raises it is answered `tool_error`, with the fault recorded.

**Why** (READ, `tools.py:1740-1763`, `1729-1731`, `1500-1516`). `_ToolLoop._wrapper` awaits
the gate's or the tool's awaitable, and re-raises `GeneratorExit` without keeping it
(`except GeneratorExit: raise`). Its `finally` sets `ended`. `_ToolLoop.run` then sees `ended`
with no `post.error` and returns `post.value`, which is still `None`. `_Work` reads `None` from a
gate as "allow" (line 1502, then the verdict tests), and from a tool as its result (line 1525).

**What it breaks.** Spec 053's Decision 6 says "any other exception, a BaseException
included, is a fault", and Decision 7 says "anything else fails closed" (helper, READ). The
README's gate item says the same.

**Who can trigger it.** Only the embedder's own gate or tool code, by raising `GeneratorExit`.
A guest cannot raise an exception inside a gate. I found no ordinary way for an `async def` to
raise it by accident either:
- a closed coroutine swallows it;
- a task cancelled at the call's end gets `CancelledError`;
- a loop closed under a pending gate is past `_proceed`, which already stops the tool (spec 056).

So this is a broken promise about the embedder's control, not a way in for the guest. But the
gate is the control §4.4 names, and "fails closed" is its contract. The two paths disagree:
sync fails closed, async fails open. The result's integrity (asset 4) suffers too: the record
says `ok` for a tool that raised.

**Fix** (host side, `tools.py` only, in the wheel; no rebuild). Mark the post finished only
after `await post.awaitable` returns. In `_ToolLoop.run`, if the post ended with neither a
value marked nor an error, raise a `RuntimeError("the awaitable ended without a result")`. The
gate then fails closed (`denied`, fault recorded), and the tool answers `tool_error`. Leave the
wrapper's own close path as it is. The helper's simpler variant, `except GeneratorExit as e:
post.error = e; raise`, also covers this case; either is fine if the check passes.

**Check:** the table above as a parametrised unit row, for three gate forms (`async def`, a `def` returning a coroutine, an object with an async
`__call__`), with `GeneratorExit` and a subclass, under `run` and `run_async`. Each must give
`denied`, a recorded fault, and no effect. The same rows for an async tool must give
`tool_error`.

### F2. The rebuild runs an unpinned host `python3` that writes FreeType's configuration headers. Low; does not block (EXECUTED and READ by the helper)

writes a version header. The helper found a second use, which matters more (`supply/`, the main
tree's meson logs, read only):

- **FreeType's meson** resolved `find_program('python3')` to the host's
  `/Library/Frameworks/Python.framework/Versions/3.10/bin/python3`
  (`build/freetype-build/meson-logs/meson-log.txt:112`). I re-read the log: meson itself runs
  on the pinned `build/tools/python/bin/python3` (line 2), but `find_program` finds the host's.
- **What it runs:** `extract_libtool_version.py`, `parse_modules_cfg.py` (which chooses the
  modules compiled in, written to `ftmodule.h`) and `process_ftoption_h.py` (which writes
  `ftoption.h`). These shape the compiled FreeType.
- **HarfBuzz** runs `gen-hb-version.py` through its `#!/usr/bin/env python3` line
  (`build/harfbuzz-build/meson-logs/meson-log.txt:909-911`).

**Why it does not block.** Each script is a fixed text transform of pinned tarball input. The
three hosts already build the same bytes with different `python3` versions, and same-bytes in
the release fails on any difference (INFERRED, from 059's three-host agreement and the
`same-bytes` job). A hostile or broken host `python3` would have to change all three hosts' runs
the same way to slip past.

**What is wrong.** §4.2 says a build that runs anything unpinned is not a build. The
interpreter is a tool the pins do not cover, the rebuild's tools step does not print its
version, and spec 023 does not list it.

**Fix:** put a `python3` in `build/tools/…/bin`, first on `PATH` for steps 37 and 55, that runs
the pinned `$HOSTPY`, so both `find_program` and `env` resolve to it. Print `python3 --version`
in the rebuild's tools step. Add a check that each meson log's `python3` is that shim.

## Notes (no finding, or as designed and documented)

- **N1. The descriptor gap, measured on default arguments** (EXECUTED,
  `probes/p23_descriptors.py`, `logs/p23_descriptors.log`). No grant, no root, no tools. The guest opened the data grant's
  `matplotlibrc` read-only in a loop. Each open is a host descriptor.
  - With the process's soft limit at 1,048,576, the guest held 122,869 descriptors. Then it got
    EIO (29). macOS's per-process ceiling is `kern.maxfilesperproc` 122,880. The system-wide
    `kern.maxfiles` is 245,760, so one guest held half the machine's file table.
  - With the soft limit at 65,536, the guest held 65,525.
  - **While it held them, the embedder's own thread failed.** Its `os.listdir("/dev/fd")` and a
    `subprocess.run` both raised `OSError` errno 24 (EMFILE).
  - All were released when `run` returned (9 open afterwards). The guest's own call ended
    cleanly, exit 0.
  - The zip's grant gave the same path since 0.1.0a1 (INFERRED: the same read-only preopen of a
    host file). The data grant is a second such path, not a new class.
  - The README's *Not protected* states this. The owner decided a cap for 0.1.0 (decision 92,
    spec 068: default 1,024, `EMFILE` past it). See *Known open items*.
  - **For spec 068:** the guest sees EIO, not EMFILE, when the host's table is full. With a cap,
    the guest should get `EMFILE` from the runner, before the host's table is touched.
- **N2. The release environments are unprotected, by the owner's choice** (EXECUTED, read-only
  `gh api`; READ, decision 97).
  - `pypi` has no protection rule and no deployment-branch policy, and `PYPI_PUBLISH` is `true`.
    `release` does not exist yet.
  - So a workflow edited on any branch and dispatched could reach PyPI's trusted publisher.
    Pushing such a branch needs the admin's rights, the only account.
  - A deployment policy of tags `v*` on both environments would close this without a human
    step. Worth raising when question 97 is revisited.
- **N3. The rulesets do not constrain the agent** (EXECUTED; READ, decision 94).
  - Both rulesets let the Admin role bypass, `always`. The only collaborator is the owner's
    account, and the agent pushes as it ("Bypassed rule violations" on each push).
  - So they stop accidents by anyone else, and there is no one else. They are not a control on
    the release path. No status check is required until spec 064.
  - The repository's `sha_pinning_required` is false. The judge enforces pinning in the
    repository, so setting it is optional hardening.
- **N4. Spec 061 lets a host-backed provider tell the guest more** (INFERRED from `p22`). A
  provider that lets a host call's `OSError` escape now answers its errno: `ENOENT`, `EACCES`,
  `ENOTDIR`, `ENAMETOOLONG`. Before 061 the guest saw EIO for all of them.
  - Inside the provider's own base, that is what POSIX tells any program, and it is the
    intent.
  - It matters only for a provider that resolves outside its base, which a4's F5 already
    covers (README, "A path is a name, not a host path"). Then the guest could tell an
    unreadable host file from an absent one.
  - Suggest one clause in that README paragraph: an escaped host `OSError` is now an answer,
    so containment must come before the host call.
- **N5. `os.chmod` on a read-only data file returns success** (EXECUTED, `p20`). It changes
  nothing: the host tree's digest, modes included, was the same afterwards. A guest that checks
  its own `chmod` is told a lie. This is not a security matter.
- **N6. Two README sizes are stale.** *Safety* and *Not protected* both speak of "its 11 MB
  stdlib zip folder" (README lines 2362 and 2379). The folder now holds the 22 MB zip and about 9.6 MB of
  data: 31 MB on disk (EXECUTED, `du -sh` of a live `wasi-python-zip-*` folder). It matters to
  an embedder who sizes a temporary volume.
- **N7. The font cache's trust is documented, and nothing worse is reachable** (READ, spec 023
  Decision 7, README *matplotlib in the guest*). A shared, writable `MPLCONFIGDIR` lets one call
  choose the fonts a later call parses. `p21` shows what a hostile font can do: raise
  `RuntimeError` or exhaust its own memory. A planted `matplotlibrc` with
  `backend: module://x` imports only what the sealed import path holds (INFERRED).
- **N8. A stubborn async tool still lands after `run` returns** (EXECUTED by the helper,
  `tools-probes/a1_async_loop_cancel.log`). A tool that swallows its cancel lands its effect
  2 s later. That is the README's *Abandoned tools*, for a tool that had started. Its loop
  thread is counted, and was gone 2.5 s later. As designed.
- **N9. No process-wide ceiling on abandoned tools, for async as for sync** (EXECUTED by the
  helper, `tools-probes/a4_async_ceiling_context.log`). The per-run quota of 4 holds: 30 calls to
  a cancel-ignoring tool gave 4 timeouts, then 26 answers of "4 earlier tool calls are still
  running". Four concurrent `run_async` calls left 21 tool threads and 16 runner tasks on the
  embedder's loop, all gone 4.5 s later. This is a4's N5, unchanged and documented. A guest
  cannot make a tool ignore its cancel (INFERRED).
- **N10. Answers are not counted by the byte budget** (EXECUTED by the helper, `b1` (d)). Each is
  capped at 16 MiB, and `max_tool_calls` bounds how many. 500 `list` frames against 300 tools
  copied 72 MB into the guest for 0.07 s of host CPU, since the list is encoded once. The README
  says so. As designed.
