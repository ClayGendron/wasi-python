## Findings

### F1 (should fix, small): the `a.txt/../b.txt` grant answer on Windows can be asserted, and should be

The commit asserts only the mount's 0 for `a.txt/../b.txt` on Windows, because the grant's
answer was not observed (the run stopped at the row before). Dropping an unobserved assertion is
honest; nothing accepted is lost, as this assertion has never passed on Windows. But the answer
is not a guess. cap-std's Windows `manually::open` pops `a.txt` at the `..` exactly as it pops
`missing` (it never looks at what the component is), so the path becomes `b.txt` before any
lookup. That is the same code path the dry run EXECUTED for `missing/../a.txt` (answer 0). The
grant's answer on Windows is 0, READ, with the sibling row as its observation.

Asserting it costs one line and keeps the test symmetric: on Windows
`both(lambda r: r.open(3, "a.txt/../b.txt")[0]) == (0, 0)`. If the reading were wrong, the next
dry run would say so; that is what the dry run is for. Leaving it out means the Decision 6 row
"`a.txt/../b.txt` not observed" stays open indefinitely, since nothing will ever observe it.

Suggested change: assert `(0 if windows else 54, 0)` on the second row too, and say READ
(cap-primitives v4.0.3 `manually/open.rs`, the `#[cfg(windows)]` block in `Context::new`) in the
comment, the Decision 6 Windows row and the landing note.

### F2 (should fix, wording): the landing note names the wrong mechanism

The note says the Windows answer follows because "Win32 path handling collapses `..` before the
file is looked up; cap-std's Windows code was not read". On Windows, cap-std opens one component
at a time, so Win32 never sees the `..`. The collapse is cap-std's own (`#[cfg(windows)]` in
`manually/open.rs`), written to imitate Win32. The conclusion holds; the stated cause should be
cap-std, READ. The test comment says only "resolves `..` by text", which is right.

### F3 (nit): the docstring's rule and the new per-system row

The test's docstring says the grant's answer "is asserted where it does not depend on the host".
The first `..` row now asserts a host-dependent grant answer, per system. That is fine (both
answers are observed facts, and the file already does per-system rows in `SYSTEM_ROWS`), but the
docstring could say "or per system where it does". Optional.

### F4 (nit): `sys.platform == "win32"` beside the file's `POSIX`

The file's other system splits use `POSIX = os.name == "posix"`. The new code uses
`sys.platform == "win32"`. They are equivalent on the three systems that run the judge. Using
`not POSIX` would match the rest of the file. Optional.

### O1 (outside this diff, for the lane): the mount deadline check is sensitive to load

`test_a_mount_keeps_its_deadline_and_cancel[deadline]` runs the guest with `deadline_s=0.05`.
The deadline is measured by the epoch ticker, which counts wall-clock time. The provider holds
the guest at its third `stat` for 20 ticks. When the host is heavily loaded, start-up up to the
first `os.stat('/work/x')` can take longer than 50 ms. The run then ends "deadline" with 0
provider calls, not 3. It failed 3 of 5 times alone at load average 174 (EXECUTED). It does not
depend on this commit, which changes only `tests/unit/test_runner_grants.py`, the README and the
spec. It is not a finding against 579571e. The lane should judge the exact commit on a quiet
machine, as AGENTS.md 6a already requires. The check's dependence on load should become its own
item, against spec 032's acceptance 6 or the progress harness. AGENTS.md says "tests count
operations, never wall-clock", and this check's 50 ms budget is wall-clock.
