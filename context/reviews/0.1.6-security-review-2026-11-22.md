## Short version

0.1.6 closes a hole and opens none. The hole was wasmtime's. On Windows, a name such as `./C:canary` reached the current folder of drive C, outside every folder a guest was given. The runner hands every path call on a host folder to wasmtime unchanged. So every call on Windows was reached, even one with no grant, through the runtime's own read-only folders. 0.1.6 moves to wasmtime-py 51.0.0, whose engine refuses a `:` in any path on Windows.

What I checked:
- **Every route a guest name takes to the host.** A name either goes to wasmtime unchanged, where the fix lives, or to the runner's own `_resolve`, which has always refused `:` and `\` for its mounts. No route lets the runner build a host path from a guest name itself (READ).
- **The check.** Its safety assertions are unconditional and come before the errno table. The twin allowance admits only an errno, never a success, so it cannot hide an escape (READ).
- **The other eight advisories.** None is reachable, as the documents say. The empty-write one rests on the pre-build reviewer's read of wasmtime's source, which I did not repeat (READ).
- **The GC switch.** It narrows what the engine accepts and opens nothing.
- **The `rmdir` fix.** A slash-named `rmdir` on a mount still meets the rule against removing a folder above a nested preopen (READ, EXECUTED).
- **Provenance.** Nothing that makes or proves a release changed (EXECUTED).

**No High, no Medium. Five Lows.**
- **L1:** the runner does not refuse a wasmtime-py below 51 at run time, so an install that skips dependencies keeps the escape silently.
- **L2:** the advisory draft's only "inferred" for writes sits in the notes that are deleted before it is published.
- **L3:** "the artifact set's bytes are unchanged" is not quite true: the manifest changed.
- **L4:** the security model calls the exception heap "small", which no run measured.
- **L5:** 0.1.5's open L1 and L2 are named nowhere in the roadmap. This one is `context/` only.

## What changed, and what held

### GHSA-f2pq-268w-886c: every way a guest names a host path (READ, `_fs_paths.py` whole; `_fs_descriptors.py`)

- **No mount in the call.** Every `path_*` call goes to wasmtime's own implementation. The fix is in that implementation (READ, the memo's §2: commit `486e6db`, present at `v51.0.0`).
- **A mount in the call.** The runner shadows the ten path calls. For a descriptor the table does not hold, each forwards the guest's pointer and length unchanged: `path_open` (through `_forwarded_open`), `path_filestat_get`, `path_filestat_set_times`, `path_readlink`, `path_create_directory`, `path_remove_directory`, `path_unlink_file`, `path_symlink`, and `path_rename` and `path_link` when both sides are wasmtime's (READ). So wasmtime's colon rule sees the same bytes it would see with no runner between.
- **The look before an open.** `_look` asks wasmtime's own `path_filestat_get` about the guest's path. Under 51 that is refused for a colon, and the open that follows is refused the same way (INFERRED, from the forwarding).
- **The runner's own extra calls.** `_wasmtime_folder` (`fd_fdstat_set_rights`, `fd_allocate`) names no path. `_wasmtime_writable` forwards `path_create_directory` with an empty path (READ).
- **A rename or link across a mount and a grant.** `_across` reads both paths but forwards neither. It answers EBADF, EPERM, EINVAL or EXDEV itself (READ). No guest name reaches the host this way.
- **A mount's own descriptor.** `_resolve` refuses `\0`, `\` and `:` with EINVAL on every host before any provider call (READ, `_fs_paths.py:74`). `test_a_mount_refuses_a_name_a_host_could_reinterpret` holds it (READ). That is why the drive check skips `/m`.
- **Descriptor calls** (`fd_*`) name no path. Those the runner shadows forward the descriptor number, or serve a mount from the table (READ, `_fs_descriptors.py`).
- **Links.** A link whose target holds a drive may be made on a writable grant on Windows. Every call through it is refused (READ, the check; EXECUTED by the runs as recorded). A link left in a grant is the host's to follow or not, which "What is not protected" already says (READ, `security-model.md:83`).

So the escape is closed on every route, both with and without a mount. Both routes are parametrized in the check (`mounted`), on four kinds of call (`none`, `read-only`, `writable`, `root`) (READ).

### The check, and the twin allowance (READ, `test_a_drive_prefixed_name_stays_in_its_folder`)

- **The safety assertions are unconditional, and they come first.** On every system the canary's secret must not appear in the child's output, and the guest's reads and `readlink` buffers are part of that output. The canary's bytes and `st_mtime_ns` must equal what was written, and its `st_atime_ns` must differ from the guest's value. The working folder must hold exactly the canary and its folder, and that folder must be empty. `temp` must be empty, and `tmp_path` must hold exactly five names. None of these is inside a branch, and all of them come before the errno table (READ). So the check fails first on wasmtime 50 whatever the errnos, as the pull request's reviewer also inferred.
- **What the drive reaches.** The child runs with `cwd` set to the canary's folder. The drive it names is `cwd.drive`, so a drive-relative name resolves to exactly that folder (INFERRED from Windows's rule that a process's current folder is its drive's current folder). An escape that wrote rather than read would show in the listing of `cwd`. A hard link into the grant would answer `"ok"` and fail the table.
- **The twin allowance cannot hide an escape.**
  - On Windows a colon row passes in two ways only. It answers its spelling's refusal (EPERM for a name that begins with the drive, ENOENT otherwise). Or it answers an **integer** equal to its twin's integer.
  - An escape answers `"ok"` or `["ok", data]`. Neither is an integer, so no allowance admits it.
  - An escape that did harm and then returned an errno would still trip the unconditional assertions above.
  - What the allowance gives up is the errno's exactness where the folder refuses first. That is a parity loss, not a safety loss.
  - The link rows that follow a made link must be integers. A row that makes a link must be `"ok"` or an integer (READ).
- **One edge, a Note, not a finding.** The check probes the canary, a name that exists. An engine that leaked whether a host name exists only through an errno would pass the check if that errno happened to equal the spelling's refusal. wasmtime 51 refuses the colon before any host call (READ, the advisory's fix as the memo gives it), so no such oracle exists.
- **What ran** (READ, 202's landing notes): red on wasmtime-py 50.0.1 in the Windows leg, all eight items, each with the canary's secret in the output. Then green on three systems in runs 45040897479, 45045772454 and 45047186479 as far as the safety assertions go, and wholly green in 45048766529. Every correction of the errno table touched the table alone.

### The GC switch (READ, `_engines.py:144-153`; EXECUTED, `test_the_engines_refuse_gc_types`)

- `cfg.wasm_gc = False` is set in the one function that makes the runner's two engines, before `wt.Engine(cfg)`. No other `Config()` exists in `src/` (EXECUTED, grep). The judge's three mirrored engines set it too (READ).

### The slash-named `rmdir` on a mount (READ, `_fs_paths.py:458-498`; EXECUTED, the mount units)

- Before: an `rmdir` of `e/` took the `folder_only` branch and answered EINVAL after one `stat`, so it never removed anything. Now an `rmdir` whose last real component is neither `.` nor `..` falls through. It meets `_above` (EBUSY when a nested preopen lies under it), then the provider's `rmdir` of the plain path, then `_follow` (READ).
- `_resolve` has already refused a name that equals or lies under a nested preopen (EPERM) and any climb above the descriptor (READ). So the rule against removing a folder above a nested preopen holds for every spelling that now reaches the provider. The unit row `rmdir above a nested preopen, slash-named` answers 10, EBUSY, with one `stat` (EXECUTED).
- `last` is taken past trailing slashes (`rstrip("/")`), so `e/./` and `e/.//` still answer EINVAL. That was the pull request review's High, fixed and re-probed over 21 spellings (READ, its second round). The write parity's rows pass (EXECUTED).
- **A Note:** `_path_rename`'s `lasts` still splits without `rstrip`, so `rename("e/./", …)` is not treated as a name ending in `.`. It is unchanged since 0.1.5, and `_above` and the own-subfolder rule still bound it (READ). It is a parity question, not this release's.

## Findings, most severe first

### L1. The runner does not refuse a wasmtime-py below 51 at run time. Low; an embedder's engine (READ, `_wasmtime_ffi.py:131,174-215`; INFERRED)

- The fix is in the engine. `pyproject.toml` requires `wasmtime>=51,<52`, but nothing checks it at run time. `_wasmtime_ffi.check` refuses only a wasmtime-py that lacks a private name, and `PIN` appears only in that error's text (READ).
- wasmtime-py 50.0.1 has every name the seam reads (the memo's §4: 51 changed no name the runner reads), and `Config.wasm_gc` is an older wasmtime-py property than 50 (INFERRED; the probe set it on 51 only). So 0.1.6 very likely imports and runs on 50.0.1 (INFERRED, not run here).
- Failure: some environments skip the dependency resolver: `pip install --no-deps`, a frozen or vendored tree, or a lock file kept from 0.1.5 with only `wasi-python` bumped by hand. On Windows these run 0.1.6 on the vulnerable engine with no warning. A user who reads "0.1.6 closes the escape" believes it closed.
- **What to change:** for this release, R3 below. Then a later specification gives `_wasmtime_ffi.check` a floor: it refuses a wasmtime-py outside `PIN`, or at least one below 51.0.0, with the same `ImportError`. The seam's bump steps would then keep the floor in step with `PIN`.

### L2. The advisory draft's only "inferred" for writes is in the notes that are deleted. Low; documents (READ, `advisory-draft.md`, Impact and "Notes for the owner")

- The Impact says: "Through a writable folder, or with `root=True`, it can also create, change, rename or remove them." The next sentence reports the reads that ran. The note "that a writable folder or `root=True` could also write outside is inferred from the same resolution, not run" is under "delete before publishing".
- Failure: the published advisory gives reads and writes the same footing, and anyone who reads it cannot tell which was seen. The claim is very likely true, since it is wasmtime's own advisory's scope, and it errs on the side of warning. So this is Low.
- **What to change:** in the Impact, after that sentence, add: "That follows from the same flaw; only reads were run here." No other document needs it: `SECURITY.md`, the security model and the notes say "could", and keep reads and writes in separate clauses.

### L3. "The artifact set's bytes are unchanged" is true of the binaries and the zip, not of the set. Low; documents (READ, the notes' summary; the roadmap's 0.1.6 "Built"; 202's landing notes)

- The landing notes record `python.wasm`, the zip and the snapshot as byte-identical to 0.1.5's. The set's `SHA256SUMS` differs (`c4fb24f6…` against `8fdd3282…`) because `MANIFEST`'s three `pin` lines now name 51.0.0. `AGENTS.md` names the manifest as part of the artifact set.
- Failure: readers compare `SHA256SUMS` across releases (`AGENTS.md`). One told "the artifact set's bytes are unchanged" who finds the manifest's hash changed has been told something false about a security release. That reads like tampering.
- **What to change:** R1 in the notes. In the roadmap's "Built" line, "The artifact set is byte-identical to 0.1.5's" becomes "Its binaries and zip are byte-identical to 0.1.5's; `MANIFEST` names wasmtime 51.0.0."

### L4. The security model calls the exception heap "small". Low; documents (READ, `security-model.md:74`)

- No run measured that heap's size, and the probe compared on and off, not the size. "Small" also suggests a bound that the page does not give. Whether the call's memory cap covers wasmtime's GC heap is not recorded anywhere I read.
- **What to change:** "wasmtime still keeps a heap for exception objects, as it did before." Or, if someone measures it, say what bounds it.

### L5. 0.1.5's open L1 and L2 are named nowhere in the roadmap. Low; `context/` only (EXECUTED, grep of `roadmap.md` and `decisions.md`)

## Notes (no finding)

- **The existence oracle.** Above, under the check: the check would not see a leak through an errno alone. wasmtime 51 refuses before any host call, so there is none to see.
- **wasmtime 51's new budget trap.** A single write above 64 KiB to the custom stream now traps in the C API, and the runner uses that stream on Windows. WASIp1's `fd_write` asks `check_write` first and writes in parts (READ, the memo's §4). `test_one_large_write_arrives_whole` writes 8 MiB in one call and passes on three systems, on both captures (READ, 202's landing notes). A trap would end only the call.
- **The `pread` difference.** A zero-size `pread` past `2**63` answers EINTR on a grant under wasmtime 51 and EINVAL on a mount. The mount's answer is the safer one, since an EINTR invites a retry loop that the deadline still bounds. It is recorded as a deliberate difference (READ, 202's Decision 3d).
- **Other drives.** The check names only the working folder's drive. Windows keeps a current folder for every other drive in hidden `=D:` variables, and wasmtime's rule refuses a colon whatever the letter (READ, the memo). The advisory's workaround paragraph rightly says that narrowing every drive's current folder is not a fix.
- **Timing.** wasmtime's advisory has been public since 2026-11-19, so 0.1.5's Windows users have been exposed to a known flaw for three days. Publishing the repository advisory with 0.1.6, as the draft's notes plan, is right.
