## Short version

The sandbox holds on every row a guest can reach. The new surface, a starting image an embedder makes, saves and loads, holds under hostile input:

- the `.wpsnap` reader refuses every damaged or crafted file I made, 28 kinds, never decompressing past the size its header names, and a zlib bomb stops at that size plus one byte; one of the 28 is refused with the wrong exception type (L3);
- a file that is a link, has two names, is readable by others, or is a FIFO, socket or folder is refused, and a FIFO does not block the load;
- a crafted image whose hash matches its header runs as a hostile guest does: it traps or exits, and the host process goes on;
- a snapshot is never saved or loaded where a live call may write, and no later call is granted writing at or above a remembered snapshot folder;
- an image binds to its set: another snapshot binary, or `memory_bytes` below the image, is refused before any work.

The 0.1.1 Medium is closed. A guest's open of a FIFO, socket or device in a grant now answers `ENXIO` at once, in 25 cases, and a session with such a turn closes in 0.01 s (EXECUTED, 143).

**No High and no Medium. 0.1.2 does not wait on this review.**

**The Lows:**

- **L1, closed by `797a5e77`.** The security model page said nothing of a saved snapshot, and two sentences of the how-to promised more than the code keeps. The preparation branch's docs commit fixes both, and it ships with the release.
- **L2.** A load holds three copies of the image at its peak. A 4 MiB file can name a 4 GiB image. The how-to now says three (`797a5e77`); the code fix to two copies may follow.
- **L3.** A header nested deeply enough raises `RecursionError`, not `SnapshotMismatch`.
- **L4.** On macOS a snapshot's way is held to owner and mode alone. 141 reads the access lists on the way to the cache, not to a snapshot. 141 records this as its follow-up.
- **From 0.1.1's release path**, 148 (in #49) closes L2, L4, L5's `edited`, DL1, and L6's token, container, SECURITY.md and umask parts. I read its code in the delta read and found no new finding. ## What changed, and what held

### A special file in a grant (143; EXECUTED, `p03_fifo.py`, `p03b_fifo_dirflags.py`, 0.1.1's set)

The host made a FIFO, a link to it and a Unix socket in a granted folder. Each case ran in a child process the driver kills at 25 s, with `deadline_s=3`.

| the guest | answer |
|---|---|
| `open('/g/fifo','rb')`; with `O_NONBLOCK`; through a host link; through a link the guest made; after the guest renamed it | `ENXIO`, at once |
| `open(..., 'wb')` on a read-only grant and on a writable one; `O_WRONLY \| O_TRUNC`; `O_RDWR \| O_CREAT`; `O_WRONLY \| O_APPEND`; `O_NOFOLLOW` | `ENXIO` |
| `O_SYNC`, `O_DSYNC`, `O_RSYNC` (forwarded without a look) | `ENOTSUP`, wasmtime's own, before its open |
| `O_CREAT \| O_EXCL` (forwarded without a look) | `EEXIST` |
| `O_DIRECTORY` with `O_CREAT`, `O_EXCL` or `O_TRUNC` (forwarded without a look) | `EINVAL` |
| `O_DIRECTORY`; `os.listdir` | `ENOTDIR` |
| the socket; `/dev/null`, `/dev/zero`, `/dev/tty` through a read-only grant of `/dev` | `ENXIO` |
| `os.stat` of the FIFO; a regular file beside it | answered as before |
| `os.mkfifo`, `os.mknod` | `AttributeError`: the guest cannot make one |
| a `Session` turn opening the FIFO, read-only and writable | `ENXIO`; `close()` returned in 0.01 s |

So every open that wasmtime takes to its host open is looked at first. The ones forwarded without a look are refused by wasmtime before it opens anything, as `_looked_at` (`_fs_paths.py`) says. The residue is a host process, or another call writing the same grant, that swaps a name between the look and the open. The security model now says so (READ, `security-model.md:80`).

### A saved snapshot (150; EXECUTED, `p01_wpsnap.py`, `p02_live_writable.py`, 157's set)

`p01` made a snapshot of three lines (40 MiB, 10.5 s), saved it (mode 0600), loaded it and ran from it (`b'1\n'`, the same `image_sha256`). Then it loaded crafted copies.

| the file | `Snapshot.load` |
|---|---|
| another first line | `SnapshotMismatch` |
| the image's hash changed in the header | `SnapshotMismatch` ("does not match its hash") |
| the body cut in half; the zlib trailer cut | `SnapshotMismatch` ("ends before") |
| one byte past the stream; a second zlib stream after it | `SnapshotMismatch` ("bytes past its stream") |
| `format` 2 | `SnapshotMismatch` ("saved by a newer wasi-python") |
| `format` 0, `"1"`, `true` | `SnapshotMismatch` ("damaged header") |
| `codec` `"zstd"` | `SnapshotMismatch` |
| `image_bytes` not a page multiple; 4 GiB + 64 KiB; `true`; negative | `SnapshotMismatch`, before any decompression |
| `image_bytes` 4 GiB with the 40 MiB stream | `SnapshotMismatch` ("ends before"), after 40 MiB |
| `image_bytes` one page more, or one page less, than the stream | `SnapshotMismatch` |
| `home` other than `/tmp/.home-snapshot`; `guest_paths` a string; a field missing | `SnapshotMismatch` |
| a header that is a list, not JSON, has no newline, or passes 17 MiB | `SnapshotMismatch` |
| a 5,000-digit integer in the header | `SnapshotMismatch` (Python's digit limit is a `ValueError`) |
| a header of 200,000 nested arrays | **`RecursionError`** (L3) |
| a zlib bomb: one page named, 1 GiB of zeros in a 1 MiB stream | `SnapshotMismatch` in 0.00 s, no growth of peak memory |
| mode 0644; a link; two names | `PermissionError` |
| a FIFO at the name | `PermissionError` in 0.00 s: opened non-blocking, refused by `fstat` |
| a socket at the name | `OSError` (`EOPNOTSUPP`, 102): refused, by another type |
| a folder at the name | `PermissionError` |

READ, the order of checks in `_read` (`_snapshot.py:343`) and `_header_origin`: the first line; the header line, read to at most 17 MiB + 1; its JSON; every field's kind, `bool` excluded from the integers; `format`, then `codec`; `home`; `image_bytes`, a page multiple from 64 KiB to 4 GiB; then the stream, decompressed with `max_length` at most one byte past the declared size, so a bomb never grows `out` past it; then the trailing bytes; then the hash. The hash is integrity, not authenticity: whoever writes the file writes the header too. Authenticity rests on `open_owned` alone, which is why L1 matters.

**A crafted image runs as a hostile guest does.** `p01` loaded two images whose header hash was made to match: all zeros, and random bytes, each 40 MiB. From `run`: the zeros trapped `indirect call to null`, the random bytes exited 70 (the reactor's refusal of an unprepared instance), each in 0.01 s. From a `Session` turn: `indirect call to null`, and `memory out of bounds`. The process went on, and `stats()` counted 5 restores. READ: `_restore` (`_snapshot.py:490`) refuses an image shorter than the fresh memory, grows through the store's limit, reads `data_ptr` after the grow, checks `data_len` equals the image's length, then one `memmove`. An image holds linear memory only: no global, table or code. So it can steer the binary's own code and nothing else, with the call's grants, door and tools. That is a guest's reach, and the reason the file is trusted as code.

**The set binding.** A header naming another snapshot binary: `check()` and `run` raise `SnapshotMismatch` before any work. `memory_bytes` of 4 pages against a 640-page image: `SnapshotMismatch` before any work (EXECUTED, `p01`).

**Live calls and the folder registry** (`p02`, 157's set). A session held `shared` as a writable grant.

| the act | result |
|---|---|
| `save` into `shared`, the session idle | `PermissionError` (names the grant) |
| `save` into `shared/inner` | `PermissionError` |
| `save` into `shared` while a turn blocks in a door call | `PermissionError` |
| `save` and `load` after `close()` | accepted |
| a later `run` with a writable grant at `shared`, above it, or `root=shared` | `ValueError` before any work |
| a later `run` with a writable grant inside it, or read-only at it | runs, exit 0 |
| `save` into a 0777 folder | `PermissionError`; nothing left behind |
| `save` into a 1777 folder | accepted, as `/tmp` is (sticky: no one else may rename or remove the file) |
| an access list a new file inherits, on the folder | `PermissionError` for the temporary file, which is removed (`p04`) |

**What the registry cannot know** (`p07_guest_rewrite.py`, 157's set). An earlier process saved `app/snap.wpsnap`. This process, before it saved or loaded anything in `app`, ran a guest granted `app` writable. The guest opened the file `r+b` and wrote another valid snapshot's bytes over it. The file stayed this user's, at 0600, with one name. `Snapshot.load` accepted it, and a call from it printed the planted code's value. A new file the guest wrote was 0644 under umask 022 and was refused. This is 150's stated limit (Decision 8: "Another process that never saved or loaded the file cannot know it"). It is also the reason for L1.

**The load's memory** (`p02`). A 522,424-byte file naming a 512 MiB image of zeros raised the loading process's peak resident memory by 1,537 MiB: three copies. That is L2.

### L1. The security model page says nothing of a saved snapshot, and two sentences promise more than the code keeps. Low; documentation; the runtime's trusted files (EXECUTED, `p07`; READ)

- **What a saved file is.** An image runs as the embedder's own code in every call made from it, with that call's grants, door and tools. A guest that can rewrite the file once gets its code into every later call, past the session and call boundaries the sandbox otherwise keeps.
- **What the code keeps.** `open_owned` refuses a file another user could have written. The process registry refuses a guest writing a folder this process has already saved or loaded in. Nothing can refuse a guest that wrote the file before this process knew the folder, in this process or another, since the guest writes as this user (`p07`).
- **What the pages say.**
  - `docs/explanation/security-model.md` lists "the module cache's contents" under *What is not protected* (`:92`) and has no line for a saved snapshot. The page is where a security-minded reader looks.
  - `docs/how-to/snapshots.md:82` says "In this process the runner keeps the two apart both ways" and "Another process cannot know the file". The first holds only for a folder this process saved or loaded before the guest ran; `p07` is this process.
  - `docs/how-to/snapshots.md:67` says `load` "reads only a file that only you can write … in a folder no other user can change". On Windows, `open_owned` checks only that the file is not a link or junction and has one name (`_platform_windows.py:463`); it reads no owner and no access list. The reference page says the like for the module cache (`docs/reference/artifacts.md:70`), but not for a snapshot. On macOS the folder's access lists are not read either (L4).
- **Why Low.** It needs the embedder to grant a guest writing over a folder that holds its own snapshot, which the how-to tells it not to do. The code does what specification 150 decides.
- **Fix, before the tag:** one bullet under *What is not protected*, beside the module cache's: "**A saved snapshot's file**, if a guest or another user could write it before you load it. Its image runs as your code in every call made from it. Keep it where no guest is granted writing, in this process or any other; on Windows the runner checks only that it is no link." In the how-to, "In this process, once it has saved or loaded a snapshot in a folder, the runner keeps the two apart both ways", and the Windows clause. Documentation only, so no delta read is owed.

### L2. A load holds three copies of the image at its peak, and the header names the size. Low; resources (EXECUTED, `p02`; READ, `_snapshot.py:398-416`)

- `_image_of` asks `decompress` for up to the whole image in one call, appends that `bytes` to a `bytearray`, then copies the `bytearray` into `bytes`. A 512 MiB image raised peak memory by 1,537 MiB. The how-to says "A load holds the image twice while it reads" (`snapshots.md:132`).
- The header can name up to 4 GiB, and zeros compress about a thousandfold. So a file of about 4 MiB can cost about 12 GiB at its load (INFERRED from the 512 MiB measurement). `load` takes no memory limit, and the image's size meets `memory_bytes` only at a call.
- **Why Low.** Only a file `open_owned` accepts gets that far: this user's, 0600, one name. Whoever can write it has this user's power already, or is a guest the embedder let write there (L1).
- **The words are fixed by `797a5e77`:** the how-to now says "A load holds up to three copies of the image at its peak". The code fix below may follow 0.1.2.
- **Fix:** decompress with `max_length=SLICE` per step into a preallocated `bytearray(size)` through a `memoryview`, so the peak is two copies. Optionally, a `max_bytes=` on `load`. A unit row that loads a 64 MiB image under a `tracemalloc` peak assertion would hold it.

### L3. A header nested deeply enough raises `RecursionError`, not `SnapshotMismatch`. Low; robustness (EXECUTED, `p01`; READ, `_snapshot.py:350`)

- `json.loads` of 200,000 nested arrays raised `RecursionError: Stack overflow … while decoding a JSON array`. `_read` catches `ValueError` only.
- The how-to's "load, else make" recipe catches `FileNotFoundError` and `SnapshotMismatch`, so a service would crash on such a file instead of making a new snapshot.
- **Why Low.** As L2: the file must pass `open_owned` first.
- **Fix:** catch `RecursionError` beside `ValueError` at `_snapshot.py:351`, with a row in `tests/unit/test_snapshot.py`. Or refuse a header whose first byte is not `{` before parsing, which a format-1 header always is.

### L4. On macOS, a snapshot's way is held to owner and mode alone. Low; follow-up recorded by 141 (EXECUTED, `p04`; READ, 141's `_platform.py:658`)
