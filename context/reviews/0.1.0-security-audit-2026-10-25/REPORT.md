## 2. Security posture

The sandbox's core promises held under adversarial review. Across 17 covered units and 135 checks (66 of them executed), no path was found from a guest to a host file outside its grants, to host memory, to the network or to a host process; the two shipped binaries import exactly the 42 WASI preview1 functions plus the one door; the stdlib zip carries no start-up hook, link or installer; code planted in a reused root did not run on either binary under defaults; the release workflow's artifact handoff, tag-on-main check and attestation bind the published assets to the accepted set byte for byte; every build input is verified against the in-repo pin table before use; and the runner's own WASI shadows (file calls, directory listing, rename guard, poll) kept every crafted pointer inside guest memory.

Three confirmed findings and one unresolved lead survived independent verification. All three confirmed findings are **low** overall severity: each needs an uncommon embedder configuration, and none escapes the sandbox. Two break explicit documented guarantees inside the embedder's process (a tool-registry keyword that a guest can override; an environment key that lets planted code run in a later call). The third is an upstream wasmtime 49.0.0 defect that the shipped binaries reach: the fuel cap under-counts C++ work that ends in a caught exception, so fuel alone does not bound CPU until the pin's floor moves past 49.0.1. The unresolved lead concerns the module cache being checked by name and opened by path, which matters only when a lower-trust user owns an ancestor of the default cache folder. The hunters also returned 66 hardening notes, several of which correct the project's own advisory memo of 2026-10-18.

### 3.1 env= _PYTHON_SYSCONFIGDATA_PATH makes a module planted in a reused root run on `import pandas` in a later call

- **Fingerprint:** `runner-env.sysconfig-PYTHON-SYSCONFIGDATA-PATH.loads-code-outside-import-path-rules`
- **Severity:** low overall. Likelihood low: Requires the trusted embedder to pass a private, underscore-prefixed CPython variable naming a guest-writable folder on a reused root; plausible mainly when forwarding a cross-build shell's environment, which the project's own wrapper sets. Impact medium: Crosses the call-to-call boundary the policy promises: an earlier, lower-trust guest's code runs in the later call with that call's grants, door, tools and stdin. It stays inside the wasm sandbox and does not reach the host.
- **Confidence:** high. The source path is complete in the build tree and the shipped zip, and the verifier reproduced the effect independently on both binaries, with a no-env control and a PYTHONPATH control that did not run the planted code.
- **Lower-trust principal:** A guest in call 1 with a writable root writes one file at /data/_sysconfigdata__wasi_wasm32-wasi.py; the embedder's later call on the same root, with env={'_PYTHON_SYSCONFIGDATA_PATH': '/data'}, runs a program that only imports pandas, and the planted module runs.
- **Description:** The security model promises that code planted in a root never runs at start-up or on import in a later call, on either binary. The runner holds this with an isolated interpreter (PyConfig_InitIsolatedConfig, site off, only the stdlib zip on sys.path, PYTHON* variables ignored) and by allowing import_path entries only from read-only grants with nothing writable under them. CPython 3.15's sysconfig reads the private variable _PYTHON_SYSCONFIGDATA_PATH from os.environ without consulting sys.flags.ignore_environment, and when it is set it finds and execs `_sysconfigdata__wasi_wasm32-wasi` from that folder with PathFinder and exec_module. The runner lays env= over BASE_ENV and HOME with no key policy beyond emptiness and '=', and the reactor copies that environment into os.environ. So when an embedder passes this variable (for example forwarded with the CLI's --env KEY from a shell that sourced the project's own scripts/python-wasi-cross, which exports it) naming a folder in a reused root, a file an earlier guest wrote there runs in the later call on a plain `import pandas`, which calls sysconfig.get_config_var at import. Verified on both the snapshot and the plain binary. The documented not-protected list names only env= overrides of HOME and PYTHONTZPATH; it does not name this code-loading variable, and the 'Writable grants and imports across calls' item covers an import_path the embedder grants writable, which the runner would refuse for a folder served by the root.
- **Root cause:** sysconfig._get_sysconfigdata (Lib/sysconfig/__init__.py:356-363, shipped as sysconfig/__init__.pyc in the stdlib zip) loads code from os.environ['_PYTHON_SYSCONFIGDATA_PATH'] regardless of isolated mode, and the runner's env check (_limits._check_inputs, line 139) rejects only empty keys and keys containing '=', so the import_path rules (_places._check_import_path) are never applied to this code-loading folder.
- **Intended behaviour:** Every folder the guest's interpreter loads code from is subject to the import_path rules (a read-only grant with nothing writable under or above it), or the runner refuses or drops an env= entry that would load code from elsewhere, as isolated mode already ignores PYTHONPATH.
- **Source location (trace):**
   1. `src/wasi_python/_limits.py:139` (entrypoint, _check_inputs): The embedder's env keys are checked only for emptiness and '='; _PYTHON_SYSCONFIGDATA_PATH passes (called from runner.py:581).
   2. `src/wasi_python/_call.py:452` (propagation, _instance): wasi.env is BASE_ENV, HOME, then env= laid over them, unfiltered; the session opening does the same at _sessions.py:999.
   3. `recipes/reactor_bootstrap.py:143` (propagation, run): The reactor clears os.environ and copies the WASI environment into it for the program (the session setup does the same at line 240).
   4. `build/pandas-3.0.6/pandas/compat/_constants.py:21` (propagation, module level): `import pandas` calls sysconfig.get_config_var('HOST_GNU_TYPE') at import time.
   5. `build/Python-3.15.0/Lib/sysconfig/__init__.py:360` (propagation, _get_sysconfigdata): Reads _PYTHON_SYSCONFIGDATA_PATH from os.environ with no ignore_environment check (the zip's compiled sysconfig carries the same constant and no ignore_environment reference).
   6. `build/Python-3.15.0/Lib/sysconfig/__init__.py:343` (sink, _import_from_directory): PathFinder.find_spec(name, [path]) then spec.loader.exec_module(module): the module the earlier guest planted in the reused root runs.
- **Conditions:**
   - system_configuration: The trusted embedder passes env containing _PYTHON_SYSCONFIGDATA_PATH naming a guest folder that an earlier call could write (a reused root, a writable grant or a writable mount), for example forwarded from a cross-build shell with the CLI's --env _PYTHON_SYSCONFIGDATA_PATH.
   - data_state: An earlier, less trusted call on the same root or writable folder left `_sysconfigdata__wasi_wasm32-wasi.py` there.
   - user_interaction: The later program imports pandas (or another package that reads sysconfig config vars at import), or calls sysconfig.get_config_var(s).
- **Reproduction (target-native, bounded):** see FINDINGS-DETAIL.md §1. Observed: The guest reports sys.flags.ignore_environment=1 and isolated=1. Without the env entry, import pandas printed ok and the planted module did not run. With env={'_PYTHON_SYSCONFIGDATA_PATH': '/data'}, import pandas printed ok and stderr held 'PLANTED-V03' on both the snapshot and the plain binary. The PYTHONPATH=/data control failed with ModuleNotFoundError, so isolated mode does ignore the documented variable but not this private one. The verifier did not test other packages; the hunter's record also reports scipy, sklearn, joblib and statsmodels.api.
- **Smallest source fix:** Refuse env keys that make the guest interpreter load code from a folder, at least _PYTHON_SYSCONFIGDATA_PATH, in _limits._check_inputs before any work, with a message pointing to import_path; add a regression check that plants the module in call 1 and asserts that call 2 with the entry raises ValueError. As defence in depth the reactor bootstrap can drop the key from os.environ, as isolated mode drops PYTHONPATH. Name the variable in the security model's not-protected or refused list either way.

### 3.2 A guest can override a keyword a class tool's constructor binds with a partial or partialmethod

- **Fingerprint:** `src/wasi_python/tools.py:_bound_keywords:class-construction-partial-unfixed`
- **Severity:** low overall. Likelihood low: It needs an uncommon registration shape the embedder chooses: a class as a tool whose constructor binds authority with a partial or partialmethod, plus an explicit schema that leaves the keyword open or names it. Impact medium: Where that shape is used, untrusted guest code replaces an authority value the embedder bound, such as a role or user id, the constructor acts with it, and the gate is shown arguments the documentation says it never holds. That is a confused deputy inside the embedder's process against an explicit documented guarantee; it does not escape the sandbox or reach other tools.
- **Confidence:** high. Independently reproduced end to end through the real door, frame host and gate for three constructor shapes on Python 3.14.2, with the plain-partial control refused in the same run, and the source walk at tools.py:466-470 explains the result exactly.
- **Lower-trust principal:** Untrusted guest code in wasi_python.run(tools=[...], gate=...) sends a raw tool-protocol frame through _host.call naming a keyword the embedder bound in the tool class's constructor.
- **Description:** tool() promises that a keyword a functools.partial binds is fixed: it is left out of the schema, refused when a given schema names it, and refused in a frame. For a class registered as a tool, _bound_keywords goes from the class to type(cls).__call__, which is type.__call__ (a C slot), and returns with no fixed keywords. inspect.signature and the runtime both go into the class's own __new__ and __init__. So when __init__ is a functools.partialmethod, when __init__ is a functools.partial (a method descriptor on Python 3.14), or when __new__ is a staticmethod over a functools.partial, the bound keyword is not recorded in Tool._fixed. tool() then accepts a given schema that names the keyword, and the per-frame refusal in _ToolHost._call_answer never fires. Under an explicit schema that is open, has additionalProperties true, or lists the keyword, a guest frame naming the keyword reaches the constructor, and the guest's value replaces the embedder's bound value, because a partial lets call-time keywords override bound ones. The gate's ToolCall.arguments also carries the keyword, although the documentation says arguments never hold a keyword a partial binds. The same registration path is already refused for a callable instance whose __call__ is a partialmethod, so the class case is a gap in an intended control, not an unhandled design choice.
- **Root cause:** _bound_keywords (src/wasi_python/tools.py:439-474) treats a class like any other callable object: it reads type(target).__call__ and returns at the C-slot check (tools.py:466-470). It never reads the class's own __new__ or __init__, where inspect.signature and type.__call__ find the partial. So Tool._fixed is empty. The two checks that rely on it, _given (tools.py:418-423) and the frame refusal (_tool_host.py:1003-1009), let the bound keyword through.
- **Intended behaviour:** A keyword bound by a partial or partialmethod on a class's construction path (its __new__ or __init__, found through the MRO, through staticmethod or classmethod wrappers, nested partials and __wrapped__ links) is in Tool._fixed, or the class is refused at tool() as an unbound partialmethod already is. tool() then refuses a given schema that names the keyword, and a frame that names it is answered invalid_arguments without the gate or the constructor running.
- **Source location (trace):**
   1. `src/wasi_python/_call.py:1263` (entrypoint, _door): Untrusted guest code calls the imported host::call door; after admit, the frame bytes are copied out of guest linear memory and handed to the tool frame host.
   2. `src/wasi_python/_tool_host.py:1000` (propagation, _ToolHost._call_answer): The args object is checked against the tool's explicit schema; an open schema ({"type": "object"}), additionalProperties true, or a properties map naming the keyword accepts role.
   3. `src/wasi_python/_tool_host.py:1004` (propagation, _ToolHost._call_answer): The bound-keyword refusal tests each argument against t._fixed, which is empty for the class tool, so role passes.
   4. `src/wasi_python/tools.py:469` (propagation, _bound_keywords): At registration the walk reached type.__call__, a C slot, and returned no fixed keywords without reading the class's __init__ or __new__.
   5. `src/wasi_python/_tool_host.py:232` (propagation, _Work.__call__): The gate receives a deep copy of the arguments with role in it, contrary to the documented contract.
   6. `src/wasi_python/_tool_host.py:258` (sink, _Work.__call__): t.fn(**args) calls the class; type.__call__ runs the partial-bound __init__ or __new__, whose keyword merge lets the guest's role replace the embedder's bound role.
- **Conditions:**
   - system_configuration: The embedder registers a class (a type whose metaclass __call__ is type.__call__) as a tool, with __init__ that is a functools.partialmethod, __init__ that is a functools.partial (Python 3.14 makes it a method descriptor), or __new__ that is a staticmethod over a functools.partial, binding an authority keyword such as a role or user id.
   - system_configuration: The tool's explicit input_schema lets the keyword through: no properties (open), additionalProperties not false, or a properties map naming it, which tool() refuses for every other binding shape. A derived schema is not reachable: tool() refuses a class without an explicit schema for lack of hints.
   - authentication_level: The attacker is the untrusted guest code, or the model driving it, which can send any frame through the door.
- **Reproduction (target-native, bounded):** see FINDINGS-DETAIL.md §2. Observed: Each of the three class tools answered ok with value {"q": "x", "role": "admin"}; the host log shows the gate received {"q": "x", "role": "admin"} and each constructor ran with role='admin'; the record's outcome was ok. Without role the constructor ran with the bound role='viewer'. Tool._fixed was [] for all three, inspect.signature showed '(q, *, role='viewer')', and tool() accepted a schema whose properties name role. In the same run the control's user_id=1 frame was answered invalid_arguments ('unknown argument user_id') with neither the gate nor the handler running, and tool() refused a schema naming user_id. A callable instance whose __call__ is a partialmethod is refused at tool(), so only the class construction path is unguarded.
- **Smallest source fix:** In _bound_keywords, when the target is a class, read its construction path as type.__call__ runs it: inspect.getattr_static(cls, '__new__') and inspect.getattr_static(cls, '__init__') (MRO included), unwrap staticmethod and classmethod through __func__, and then walk each member with the same loop the function already uses (partial keywords collected, nested partials and __wrapped__ followed), treating a partialmethod as its .func plus .keywords rather than refusing it. Do this whatever the metaclass __call__ is: a Python metaclass __call__ that delegates to super().__call__() still runs __init__ with the guest's keywords, and the hunter's patch skips that case (in the verifier's run it returned [] for such a class, where inspect.signature shows only (*a, **k)). A simpler fail-closed alternative is to refuse at tool() any class whose __new__ or __init__ is a partial or partialmethod, as an unbound partialmethod is refused today. Add to test_bound_keywords_are_fixed_however_the_partial_is_reached a class with a partialmethod __init__, a 3.14 partial __init__ and a staticmethod-partial __new__, under an open schema and under a schema naming the keyword, expecting refusal at tool() or invalid_arguments with neither gate nor constructor called.

### 3.3 Metered engine on wasmtime-py 49.0.0 drops the fuel of C++ work that ends in a caught exception (GHSA-m63x-6p34-q65x), so guest Python can run far past its fuel cap

- **Fingerprint:** `wasmtime-49.0.0:GHSA-m63x-6p34-q65x:try_table-catch-fuel:src/wasi_python/_engines.py:_engine`
- **Severity:** low overall. Likelihood low: Needs an embedder that relies on fuel as the bound (deadline_s=None, or a cap far below the deadline, or fuel_used for accounting); the default 60 s deadline bounds wall time. The guest side is easy: plain Python reaching a caught C++ exception. Impact medium: The documented fuel limit does not bound CPU: roughly 100x under-count at N=6000 by wall-time calibration, growing with N, and a 2.2e9 cap let a loop of 20,000 failing calls run where the same-shape no-throw loop ran out of fuel within a few hundred calls. Impact is CPU denial of service and wrong instruction accounting; no sandbox escape.
- **Confidence:** high. Reproduced twice, independently, through wasi_python.run on the shipped artifacts: per-call fuel stays flat across a 30x range of N while wall time grows about 19x; a same-shape no-throw control is counted 7.5x to 79x more fuel per call at comparable wall time and runs out of fuel under the cap the failing loop finishes under; and the engine defect matches the advisory in a standalone differential against the fixed CLI. Not run on a fixed wasmtime-py (none exists), so the true per-call cost of the failing call is inferred from wall time.
- **Lower-trust principal:** An untrusted guest Python program run by an embedder through wasi_python.run with a fuel cap and deadline_s=None.
- **Description:** The runner meters calls with fuel on a wasmtime-py 49.0.0 engine. Wasm exceptions and Cranelift are left at their defaults. That is GHSA-m63x-6p34-q65x's affected configuration; the fix is in wasmtime 49.0.1, and no wasmtime-py release carries it yet. On the exceptional edge of a call inside try_table, 49.0.0 resets fuel to what remained before the call, so all the work the callee did before throwing is not counted. The compiled-in C++ packages are built with -fwasm-exceptions, so every C++ catch is such an edge. Guest Python reaches one directly: kiwisolver's Solver.addConstraint (py/src/solver.cpp in the pinned 1.5.1 tarball) calls the C++ solver inside try and catches kiwi::UnsatisfiableConstraint, which the solver throws after building a row whose size grows with the system. Measured twice, independently, through wasi_python.run on the shipped artifact set (fuel given, deadline_s=None): one failing addConstraint is counted as about 17,000 to 19,600 fuel whether the chain has 200, 2,000 or 6,000 variables, while its wall time grows from about 9.6 to 190 microseconds. A same-shape control that adds and removes a consistent required equality on the same chain end (no throw) is counted as 140,067 fuel per call at 200 variables, at the same 9.6 microseconds of wall time as the failing call, and 1,552,404 fuel per call at 2,000 variables. The same-shape no-throw control and the pure-Python control are counted at roughly 9 to 15 billion fuel per second of wall time (the weak add/remove loop at about 21 to 29 billion); the failing calls at 6,000 variables are counted at about 0.9 to 1.0 hundred million per second, so their fuel is under-counted by roughly 100 times, an estimate from wall time since no fixed wasmtime-py exists to count them exactly. Under a cap of 2.2e9 fuel, 20,000 failing calls on a 2,000-variable chain (about 1.2 s of loop) finished with exit 0 and about 2.02e9 fuel used; the same-shape no-throw loop and the weak-strength add/remove loop each ended 'out of fuel' under the same cap, the no-throw one after at most about 364 calls of the 565 million fuel left after setup. The engine defect also reproduces with a standalone WAT module: 100 rounds of a 100,000-iteration callee that throws count as 1,101 fuel on wasmtime-py 49.0.0, but need 80,001,285 under the pinned wasmtime CLI 49.0.3. A finite deadline_s (the default is 60 s) still bounds wall time through epoch interruption, which the advisory does not affect. So the cap is lost only where fuel is the bound an embedder relies on: deadline_s=None with fuel, a fuel cap tighter than the deadline, or fuel_used read as an instruction count. In the guest case observed, the under-count per call grows with the size of the system the guest builds; the advisory's 'exponential' amplification is its own claim for arbitrary wasm and was not shown from guest Python.
- **Root cause:** pyproject.toml pins wasmtime>=49,<50 and uv.lock resolves it to 49.0.0, whose Cranelift fuel accounting resets to the pre-call fuel on the exceptional edge of a call inside try_table. _engine sets consume_fuel on the metered engine and leaves wasm exceptions enabled. The build compiles C++ with -fwasm-exceptions and links python.wasm with it, so every caught C++ exception (and, by the same lowering, every longjmp under -wasm-enable-sjlj, not separately demonstrated) takes that edge. The runner carries no mitigation for this advisory, though it carries its own fixes for two later wasmtime filesystem advisories.
- **Intended behaviour:** A fuel cap bounds the guest's executed instructions, and fuel_used counts them, whatever path the guest's code takes, including C++ exceptions caught inside a compiled-in package. run()'s docstring calls fuel 'a cap on the guest's executed instructions', and SECURITY.md lists a guest that runs past its fuel cap as in scope.
- **Source location (trace):**
   1. `src/wasi_python/runner.py:115` (entrypoint, run): wasi_python.run takes an untrusted guest program (argv) with fuel and deadline_s; deadline_s=None means no wall-clock limit, so fuel is the only CPU bound.
   2. `scripts/steps/55_matplotlib.sh:102` (propagation, kiwisolver _cext build): kiwisolver's seven C++ files are compiled with CXX_EH (line 50: -fwasm-exceptions -mllvm -wasm-use-legacy-eh=false -fexceptions), so the extension's catch of kiwi::UnsatisfiableConstraint around solver.addConstraint is a try_table catch. recipes/wasi-scipy.cross line 44 sets the same flags (plus -wasm-enable-sjlj), and the numpy, pandas, matplotlib, plot-libs and sklearn cross files also pass -fwasm-exceptions for the other C++ packages.
   3. `scripts/steps/60_link.sh:129` (propagation, link): python.wasm is linked with -fwasm-exceptions; the hunter counted 44,791 try_table in 7,905 functions.
   4. `uv.lock:1049` (propagation, wasmtime pin): wasmtime resolves to 49.0.0 (installed in .venv), inside the advisory's affected range.
   5. `src/wasi_python/_engines.py:122` (propagation, _engine): cfg.consume_fuel = metered; wasm exceptions and the compiler are left at their defaults (epoch_interruption is also on, line 123).
   6. `src/wasi_python/_call.py:618` (sink, _drive): store.set_fuel(fuel) sets the instruction cap; fuel_used is read at line 511 through _fuel_used (line 554). On 49.0.0 both miss callee work that unwinds to a try_table catch.
- **Conditions:**
   - third_party_dependency: wasmtime-py 49.0.0 (wasmtime 49.0.0, Cranelift), the only version the pin admits today.
   - system_configuration: The embedder passes fuel and relies on it as the bound: deadline_s=None, a fuel cap much tighter than the deadline, or fuel_used used for accounting. With the default 60 s deadline, wall time stays bounded.
   - data_state: The guest runs code that reaches a caught C++ exception (or longjmp) in a compiled-in package after material work; kiwisolver's unsatisfiable addConstraint is one plain-Python way.
- **Reproduction (target-native, bounded):** see FINDINGS-DETAIL.md §3. Observed: Proposer's run, failing addConstraint, fuel per call / wall per call: N=200 18,619 / 9.8 us; N=2000 18,112 / 59 us; N=6000 17,162 / 190 us. Independent re-run (fresh guest and host scripts): N=200 18,744 / 9.6 us; N=2000 19,581 / 58 us; N=6000 18,357 / 184 us. Setup fuel (N:0:none): 79,699,507; 1,635,065,251; 15,271,669,312. Same-shape no-throw control (ok): N=200 140,067 / 9.6 us; N=2000 1,552,404 / 127 us. Weak add/remove: N=200 950,942 / 44 us; N=2000 65,972,562 / 2.29 ms. ### Door and tools

- src/wasi_python/_call.py:1215-1223 _door_answer checks memoryview(response).nbytes, then calls bytes(response). For a bytes subclass with __bytes__, bytes() returns a different and larger object, so MAX_RESPONSE is not enforced on what is written. Observed: with MAX_RESPONSE patched to 1000, the guest received 5000 bytes (door_probe_output_run2.txt, bytes_subclass_over_max). A real answer of 2 GiB or more would also be truncated to i32 by wasmtime-py's Val.i32 when it is passed to host_alloc, while the bound check uses the full Python length. The effect stays inside guest memory, and only the trusted embedder's own host can cause it. Fix: convert first, then check, by doing data = bytes(response); if type(data) is not bytes: data = bytes(memoryview(data)); then if len(data) > MAX_RESPONSE: return None.
- src/wasi_python/_call.py:1277-1281: when __bytes__ returns a bytes subclass, its __len__ runs on the guest thread, not on the home thread, and can disagree with the buffer that memory.write copies. Observed: the out length was 1 while 3000 bytes were written past a 1-byte allocation (len_lies). The effect stays inside guest memory, and only the embedder can cause it. - src/wasi_python/_call.py:1243-1246 re-raises wasmtime.Trap and WasmtimeError from the whole frame, including from the host function itself, not only from host_alloc. - src/wasi_python/_call.py:1263: bytes(memory.read(...)) copies a raw host= frame twice, as a bytearray and then as bytes, so a frame as large as guest memory costs the embedder's process about twice the guest memory cap for a moment. Read straight into one bytes object.
- _given (src/wasi_python/tools.py:417-423) checks partial-bound keywords only against the root properties. ### Guest memory and the runner's WASI shadows

- src/wasi_python/_call.py:1082-1137 (_poll_plan) says it answers 'as wasmtime 49 answers it', but it accepts misaligned in_ptr/out_ptr/nevents_ptr, which wasmtime ends the run for, and unknown subclockflags bits, which wasmtime answers EINVAL for. The sibling mount shadows end the run for both through _fs_memory._ends. Checking alignment (in_ptr % 8, out_ptr % 8, nevents_ptr % 4) and flags & ~ABSTIME, and answering as wasmtime does, would remove the difference. It has no memory effect: all writes stay inside the checked ranges.
- src/wasi_python/_call.py:1099-1106: any descriptor other than 0-3 (fd 4 and up, including preopened folders, numbers that do not exist and 0xFFFFFFFF) is reported ready with nbytes 1, where wasmtime answers EBADF for a descriptor that does not exist or a folder. The rule hard-codes fd 3 as 'the preopened root', but a real run preopens more than one folder. This is a difference in answers only: no host resource is touched and nothing outside the event region is written.
- src/wasi_python/_call.py:1159: the out_ptr bound uses 32*n, not 32*len(events), so a call that would write fewer events than subscriptions still needs room for n. That is stricter than wasmtime and safe, and is recorded here only so a later change does not 'fix' it into a weaker bound.
- The trap path of the forwarded fd_readdir is left unzeroed. When a guest buffer crosses the end of memory, or `used` is out of bounds, wasmtime 49.0.0 writes whole entries (their padding from uninitialized host memory) and then traps. The guard runs only on errno 0, so nothing zeroes those entries. _shared then records the stop and returns EIO. The guest stops at its next function entry or loop header, so python.wasm cannot read the bytes. A hand-written wasm guest could read and fd_write them in straight-line code before that check: wasmtime's own fd_write is not shadowed and does not consult call.stopped. A crafted guest is outside the project's stated threat model, and the padding read zero on this host. Optional fix: zero [buf, buf+min(length, memory.size-buf)) in _fd_readdir when the forward raises, before re-raising.
- _zeroed grows the stat trampoline's private page up to the guest memory's size. The store limiter's memory_size applies to each linear memory, so this second memory is bounded by memory_bytes on its own, not jointly with the guest's. Pages are reserved lazily and only the listing's bytes are touched, so resident growth equals the listing, which wasmtime already holds on the host. Joint accounting would make memory_bytes a whole-store bound.
- PreparedCall.call assigns into ctypes c_int32/c_int64 union fields, which truncate out-of-range Python ints silently. Every computed forward argument is below 2**32 today. An explicit range assertion in PreparedCall.call would turn a future unit slip (a 64-bit length forwarded as i32) into an error instead of a wrapped pointer.
- The path_open forward reads the new number at `out` without a fits check. It relies on wiggle having written `out` on errno 0, and wasmtime-py's clamping read would raise struct.error, a stop, otherwise. A fits check would make the invariant local.

- Every env-driven module-NAME selector in the zip (MPLBACKEND module://, QT_API, LOKY_PICKLER, MPMATH_SAGE/SAGE_ROOT, MPMATH_NOGMPY, USE_SYMENGINE, SYMPY_GROUND_TYPES, NETWORKX_* backends via entry points, SCIPY_ARRAY_API, PYTHONBREAKPOINT, PYTHON_DOM, PY_SAX_PARSER, _PYTHON_SYSCONFIGDATA_NAME) is safe only because the import path is the read-only zip plus read-only import_path entries and site is off. A regression test that plants a module and a dist-info in a writable root and runs with these keys (as h15_check.py does) would pin that, so a later change that put a writable folder or a .pth-processing site on sys.path is caught.
- A runner fix for the sysconfig finding that filters only _PYTHON_SYSCONFIGDATA_PATH covers every sysconfig variant (NAME alone reaches only the zip), but does not cover SCIKIT_LEARN_DATA-style folder keys; a runner-level rule (refuse or warn on env values that name a writable root, grant or mount for keys known to select code-bearing folders) would be the general control if the project wants one.

### Process integrity

- Fork refusal keys off wasi_python's own engine only (_engines._engine sets fork_used). When a parent compiled any module through wasmtime-py directly, a forked child's run() hangs for good inside wasmtime_module_new waiting on the parent's rayon compile pool (observed: fork_foreign.log, fork_foreign_sample.txt). The hang comes before the guest runs, so no deadline or Ctrl-C ends it. The fork is the embedder's own act and no guest can cause it, so this is not a finding. Document it, or refuse a child whenever the parent had made a wasmtime Engine.
- _write_output copies the whole write with ctypes.string_at before _Stream.write applies the cap, so a guest past its output limit still costs one host copy per write, as large as the write. Copying only the room left would make the cap bound this work too.
- wasmtime-py's LAST_EXCEPTION slot is process-wide. The runner's host functions never raise into it, so a process that runs only wasi_python is unaffected. But if the embedder's own wasmtime-py host function raises at the same time as a wasi_python guest traps, the runner's Func.__call__ paths (the run export, _initialize, host_alloc) can pick up that foreign exception and raise it from run(). This is upstream's design.
- The Linux trap-handler check runs before each entry, not during a call. If a tool, host or provider replaces wasmtime's SIGSEGV or SIGILL handler during a call (for example with faulthandler.enable()), a guest trap later in that same call ends the process. The guest can choose when to trap, for example with an out-of-bounds read through numpy as_strided. Re-checking in the epoch callback or after each hand-off home would close the window.
- _wasmtime_ffi.check verifies only that the private names exist, plus the arity of two binding records. It does not check behaviour such as Caller invalidation, Func._func layout or trampoline exception handling. The wheel admits any 49.x release while CI pins 49.0.0 through uv.lock. A version-equality warning, or a behavioural self-test at import, would catch a 49.x patch that changes one of these.

### Positive patterns worth keeping

- Every root and grant is walked component by component with no-follow opens from a held descriptor, links in user-writable folders are refused, and the preopen's inode identity is re-checked after wasmtime opens it (`src/wasi_python/_platform.py`, `_places.py`).
- Every WASI call the runner serves masks each guest pointer to 32 bits and checks it against the memory size read at entry before any read or write; the door re-reads the memory size after `host_alloc`; padding bytes are written as zeros (`_fs_memory.py`, `_call.py`).
- The guest's interpreter starts isolated: `site` off, only the stdlib zip on `sys.path`, `PYTHON*` variables ignored, `safe_path` on; planted `sitecustomize`, `.pth`, `pyvenv.cfg` and stdlib shadows never ran (`recipes/reactor_main.c`).
- Tool frames are admitted by length before being read, parsed by a bounded JSON parser, validated against a closed schema, and gated fail-closed; a plain partial's bound keyword is refused at registration and per frame (`_tool_host.py`, `tools.py`).
- Every build input is pinned by SHA-256 in the repository and re-verified in the step that extracts it; the carried patches were read in full and change only what their names say; tools install only from hashed wheels offline.
- The release workflow has `permissions: {}` at the top, every action pinned by commit SHA, no `${{ }}` inside any `run:` script, artifact handoff by numeric id with digest mismatch as an error, two rebuilds that must agree byte for byte, a tag-on-main check, and an attestation whose subjects are exactly the published assets; the published v0.1.0 assets equal the accepted set and repack deterministically.
