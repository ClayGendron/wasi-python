## 1. Module cache: the .cwasm checked by lstat is not bound to the file wasmtime deserializes, so a lower-trust owner of an ancestor of the default cache folder can swap in its own native code

Fingerprint `src/wasi_python/_engines.py:_load:cwasm-checked-by-lstat-opened-by-path`.

### Description
The runner loads a .cwasm (native code) only when private() finds the cache folder and the file owned by this user, with no group or other bits and one link. Each check is an lstat of the leaf by its full path. wasmtime-py then reopens the file by the same full path (Module.deserialize_file, which passes the path to the C API), and the runner afterwards compares a fresh lstat stamp (dev, ino, size, mtime) with the first one. No step checks the ancestors of the cache folder, and the check and the load are not bound to one descriptor. A principal that can rename entries in any ancestor can point the path at its own folder only while wasmtime opens it, and restore it before the stamp re-check. The planted module is then cached in the process and used as python.wasm. The default cache is chosen by the runner from $HOME (or $XDG_CACHE_HOME on Linux), so a process whose HOME belongs to another user, such as root under a sudo that keeps HOME, places the default cache under a folder that other user owns. A guest is not the lower-trust principal here: the grant judge refuses a writable grant at, inside or above any module cache folder, ancestors included, so the remaining principal is another OS user (or process identity) that owns or can write an ancestor. The verifier reproduced the identity mismatch on one OS user: with a deterministic schedule the checked file was inode 222410199 and the opened file was the planted inode 222410200, and _module returned the planted module with no warning. With a blind external swapper (renamex_np RENAME_SWAP in a loop, no hook in the runner), 3 of 5000 in-process load attempts returned the planted module, the first of them with no RuntimeWarning in that attempt; 4367 of the 5000 attempts did raise a 'not using the module cache' warning. The cross-user case and the deployment that creates it were not observed. Context that limits the effect: when the user whose HOME is kept holds unrestricted sudo, that user already has root and no boundary is crossed; the effect matters where that user is lower trust than the runner's user, for example a sudo rule restricted to one command, a container or CI step running as another uid with a mapped home, or HOME set to a shared folder another user can pre-create entries in.

### Claimed root cause
private() (src/wasi_python/_platform.py:556-577) and the post-load stamp check (src/wasi_python/_engines.py:237) bind the trust decision to path names, by lstat of the leaf, while the load (src/wasi_python/_engines.py:233) reopens the file by path and follows any link in its ancestors. Nothing checks that every ancestor of the cache folder is owned by this user or root and not writable by others, and the .cwasm is not opened once with no-follow and deserialized from that verified descriptor (for example by reading it from the checked descriptor into Module.deserialize, or by checking the ancestry). The default cache path is derived from $HOME without checking that $HOME belongs to this user.

### Exact blockers
- The cross-user case was not observed. This macOS machine lists a second local account (uid 502), but the audit holds no credentials for it and no non-interactive root, and running as another account on the owner's real machine is outside the execution boundary; uid 501 is in the admin group, so its own sudo with HOME kept would cross no boundary. The verifier's evidence uses one user in both roles, where the swapper already owns the cache folder and needs no race, so it shows the identity gap but not a crossed boundary.
- Whether a supported deployment runs the runner as one user with a $HOME (or $XDG_CACHE_HOME) whose ancestors another, lower-trust user can rename entries in is a deployment fact outside source. /etc/sudoers on this machine is root-only (0440), and sudo -V run by a non-root user prints only versions (sudo 1.9.17p2), so whether this host's sudo keeps HOME could not be read; it would not settle the deployment question in any case. Source anticipates such processes (_platform.py:545) and the documentation names only cache_dir, $WASI_PYTHON_CACHE and the artifact folder as trusted input, so neither settles it.
- The blind race was measured only in-process with a tiny module (3 of 5000 attempts on darwin-arm64); a real runner process loads its module once per process, and the per-process success rate with the real snapshot-sized .cwasm across two users was not measured.

### Affected boundary
private(): owner, mode 0700/0600, link count, no reparse point

### Bounded local plan
On a disposable macOS or Linux VM with users alice and root, never on a real cache: (1) as root with HOME=/home/alice (Linux: sudo --preserve-env=HOME, or a sudoers env_keep HOME for one test command; macOS: check sudo -V output for HOME in env_keep) run wasi_python.run(['-c','print(1)'], snapshot=False) once so root makes its 0700 cache and .cwasm under alice's ~/.cache (or ~/Library/Caches). (2) As alice, put a serialized module of another wasm, made by the same wasmtime 49.0.0 engine configuration, at /home/alice/planted/<same .cwasm name>, mode 0644, and a link /home/alice/.cache/swaplink -> /home/alice/planted. (3) As alice, loop an atomic swap of ~/.cache/wasi_python and ~/.cache/swaplink (Linux renameat2 RENAME_EXCHANGE, macOS renamex_np RENAME_SWAP), re-planting the file whenever it changes. (4) As root, start N fresh processes, each calling run() once and printing wasi_python's process().counts and whether the call failed for missing exports or printed the planted module's behaviour, with RuntimeWarnings captured. Record the count of processes that loaded the planted module and whether each raised a warning. The single-user deterministic and blind schedules are in agents/v01-cache-swap/artifacts/evidence/v01_swap_harness.py.
