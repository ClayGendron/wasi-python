## Findings, most severe first

1. **Medium: `prepare` runs again after a first `prepare` that returned non-zero, and so do `run` and `turn`** (`recipes/reactor_main.c`, `reactor_prepare`'s refusal test; `docs/how-to/embed-from-other-languages.md`, step 1). Decision 4 makes an image "once per instance, and before anything else", and the embedder's page says `prepare` refuses "a second time"; but the refusal tests `preparing || prepared || run_called || turned || shut`, and a prelude that ends with a status other than 0 clears `preparing` and never sets `prepared`. Failure, EXECUTED through the judge's driver on the local set: `prepare("x = 1\nraise SystemExit(3)")` returns 3, then `prepare("print('second prepare ran')")` runs, prints, and returns 0, leaving an instance that is now `prepared` and whose image holds the failed prelude's state: `prepare("x = 1\nraise SystemExit(3)")`, then `prepare("y = 2")` returning 0, then a call from that image of `-c print(x, y)` prints `1 2`; and after `prepare("raise ValueError('boom')")` returns 1, `run()` returns 0. An embedder in another language who retries a setup that failed (a missing file, a bad import path) on the same instance gets a 0 and an image with the failed attempt's state in it: the checkpoint of a guest's run that the specification puts out of scope. Fix: refuse `prepare` when any earlier `prepare` reached Python (a `prepare_called` bit set beside `preparing`, never cleared; it also stops `end_function` being overwritten without a decref), decide whether `run` and `turn` also refuse after a failed `prepare` (recommended: yes, as after a trap, since the host is told never to image it and the instance has run code under pinned entropy), add the case "after a failed prepare" to `test_prepare_refuses` (seen failing on this head first), and say in step 2 of the docs "discard an instance whose `prepare` returned anything else". Evidence that closes it: that row, green on the run.
2. **Low (context, committed by the reviewer): two departures were missing from the landing notes.** `_MAIN_NAMES` keeps the double-underscore names (the code, rightly; Decision 3's text says otherwise), and the byte-for-byte baseline was a rebuild of steps 60 to 90 over the main tree's earlier objects, not a build from the pins, and its log prints three hashes, not MANIFEST's. I added a departure bullet for the first and reworded the baseline sentence, with the `cmp` I ran: the saved `build/157/set-before/` equals 0.1.1's four files.
3. **Low: the embedder's page does not say that the making call's argv puts folders on the import path for the setup alone** (`docs/how-to/embed-from-other-languages.md`, "Start each call from a starting image"). `prepare` puts each argv entry after the first that begins with `/` on `sys.path` while the code runs and removes it after, with the importer cache's entries; an embedder whose setup imports its own module has no way to learn that from the page. Fix text, after step 1: "The instance's argv entries after the first that begin with `/` are on `sys.path` while the setup runs, and are gone after it; a call that imports more from such a folder passes it in its own argv."
4. **Low: the self-check's Windows box is unchecked, and criterion 3 names the label `ci:full`, which the pull request does not carry.** Fix: once the run ends, read the Windows legs and check the box; add `ci:full` if the plan did not run the macOS legs for the recipe paths, or say in the pull request that it did.
