## Short version

The wall holds. No guest reached a host file, the network, a process, another call's data or host memory. Every deadline held, including waits, `atexit`, `__del__`, `sys.excepthook` and door loops, with twelve hostile calls at once. Memory and output caps held. Three things block the release: a guest can make `run` raise by using up the host's file descriptors (a code fix); and two things the README says nothing about, a default call's unbounded disk use and links out of a granted root that host code follows (document them). The owner must also answer one conformance point in writing: §4.15 says the runtime's files are never in a writable grant, and the stdlib zip is.

## Findings, most severe first

### F1. A guest that uses up the host's file descriptors makes `run` raise — **blocks the release** (EXECUTED)

`SECURITY.md` puts "anything a guest does that makes `wasi_python.run` raise" in scope. The guest opens one file over and over until the host refuses, then exits normally. `run` then raises `OSError: [Errno 24] Too many open files`, the guest's output is lost, and the stdin scratch directory (`$TMPDIR/wasi-python-*/stdin`, holding the caller's input) is left behind.

```python
# guest
import os
open("/f", "w").close(); fs = []
try:
    while True: fs.append(os.open("/f", os.O_RDONLY))
except OSError as e: print("opened", len(fs), "then", e)
```

With the soft `RLIMIT_NOFILE` lowered to 256, 1024 and 4096 (1024 is Linux's usual default), all three runs raised. The traceback ends in `tempfile.TemporaryDirectory`'s cleanup (`shutil._rmtree_safe_fd_step`, `os.open`), and the count of `wasi-python-*` scratch folders went from 28 to 29. The next call in the same process worked.

Cause (READ, `runner.py:443-457` and `375-381`): the `with tempfile.TemporaryDirectory()` that holds stdin is left inside `_instance`, while the store, and so every descriptor the guest opened, is still open. The store is closed later, in `_call_deferred`'s `finally`.

Fix: close the store (or at least release the guest's descriptors) before removing the scratch folder, or remove the scratch folder in a way that cannot raise. Then add a check with a lowered `RLIMIT_NOFILE` in a subprocess. The README's "Not protected" line about file descriptors should stay, but it must not cover `run` raising.

### F2. A default call can fill the host's temporary disk, and the README does not say so — **blocks the release until documented** (EXECUTED)

A call with no `root` writes into a private folder under `tempfile.gettempdir()`. Nothing caps its size. The guest below wrote 2,048 MiB in 2.18 s, 0.92 GiB/s on this machine:

```python
import os
b = os.urandom(1 << 20) * 32
with open("/fill", "wb") as f:
    n = 0
    while n < (2 << 30): n += f.write(b)
```

At that rate the default 60 s deadline allows about 55 GiB (INFERRED from the measured rate). This machine had 20 GiB free, so one default call could fill its system volume (INFERRED). A full temp volume hurts every process on the host, not only the embedder. The folder is removed after the call, but only after the damage is done.

The README says "a call that names no limit still has one" and, under "Not protected", lists only "disk use in a granted root". The private root is not a granted root, so a reader is told nothing. §4.15 lists memory, time and output as the limits, so a missing disk cap is not a breach of the constitution; the missing sentence is a breach of §4.10 ("claims carry their evidence") and of the threat model's own "claims that go beyond the evidence" paragraph.

Fix for this release: under "Not protected", say that disk use is unbounded in **any** root, the private one included, and that an embedder who needs a cap should point `tempfile.tempdir` (or pass `root`) at a size-limited volume. A real cap is a specification for later.

### F3. Links a guest leaves in a granted root lead host code out of it — **blocks the release until documented** (EXECUTED)

In a granted root the guest can create a relative link that climbs out. The guest cannot follow it, but the embedder's own code can, and embedders read results from the root and stage inputs into it.

```python
# call 1, run(["-c", guest], root=root) with root = <scratch>/roots/r1
import os
os.symlink("../../secret.txt", "/result.txt")
os.symlink("../../victim.txt", "/input.csv")
```

Then, in the embedder: `(root / "result.txt").read_text()` returned `HOST-SECRET-TOKEN`, a file outside the root; and `(root / "input.csv").write_text("a,b\n1,2\n")` overwrote `victim.txt`, a file outside the root. With `../` steps up to a home directory, the same move reads a key or writes a shell start-up file (INFERRED). For the AI use case this matters: a framework that hands a result file back to the model hands it a host secret.

The README's Enforced bullet says "no symbolic link out (refused at creation or on open)". That is true from the guest's side only. "Not protected" lists planted data and concurrent calls, but not this. A call without `root` is not affected: its root is removed and nothing is read from it.

Fix for this release: document under "Not protected" that a guest can leave links (relative, climbing out) in a granted root, that host code reading or writing there must not follow links (`O_NOFOLLOW`, or `os.lstat` first), and reword the Enforced bullet to "the guest cannot follow a link out". Removing or refusing links when a call ends is a later specification.

### F4. §4.15 says the runtime's files are never in a writable grant; the stdlib zip is — **owner's written answer needed before the tag** (READ)

§4.15, added on 2026-10-17: "the runtime's own files are never in a writable grant". The runner places `/usr/local/lib/python315.zip` inside the guest's writable root (`_place_stdlib`, `_place_private`), and the guest can rewrite it during its run. The README documents both consequences ("a program damaging its own stdlib zip during its own run"; "concurrent calls on one root … the stdlib zip included"), and the threat model names the cure (the zip inside the binary or read-only). The practical risk in 0.1.0a2 is small: a private root's zip harms only its own call, and a reused root's zip is replaced before each call. But the release does not meet the letter of a hard constraint that §4 says makes work "wrong even if it works". The owner should record either an exception for the alpha line or a plan; no code change is asked of this release.

### F5. The second-host gate does not cover the wheel — does not block (READ)

`same-bytes` compares the set's `SHA256SUMS` with the arm64 Linux rebuild, and `verify` checks the tarball's files against it. The wheel is built in the `build` job from the same `build/artifacts/`, but nothing outside that job checks that the wheel's `wasi_python/artifacts/*` hash to the set's `SHA256SUMS`. In `verify` the `wheel` need is allowed to be blocked. A compromised macOS build job could ship a wheel whose `python.wasm` differs from the attested tarball, and the wheel would still be attested (INFERRED). Suggested fix: in `same-bytes` (or `verify`), unzip the wheel and `cmp` its artifacts' hashes with the set's `SHA256SUMS`.

### F6. Private roots and stdin files outlive a process that dies mid-call — does not block (EXECUTED)

This machine's `$TMPDIR` held 37 `wasi-python-root-*` folders (11 MB each, with the zip and a `tmp/.home-*`) and 28 `wasi-python-*` stdin folders, all dated 04:11–05:42 today, before this review began. Their cause was not determined; a killed or aborted process skips the `finally` blocks (INFERRED). They hold whatever the guest wrote and whatever the caller passed as `stdin`. Suggested fix: name it under "Not protected" (a killed process leaves its root and stdin in the temp folder).

### F7. A stack overflow is reported as an unhelpful `trapped` string — does not block (EXECUTED)

`sys.setrecursionlimit(10**8)` and unbounded recursion end with `Completed(exit_code=None, trapped='error while executing at wasm backtrace:', …)`; `json.loads("[" * 200000 + …)` the same. The embedder can still tell the run was stopped (`exit_code` is `None`), so result integrity holds, but it cannot tell why. `_first_line` takes wasmtime's heading instead of the trap's cause.

### F8. An installed package can prefer a nearby `build/artifacts/` — does not block (READ, INFERRED)

`artifact_dir()` uses `Path(__file__).resolve().parents[2] / "build" / "artifacts"` whenever that grandparent holds a `pyproject.toml`. In a normal virtual environment the grandparent is `lib/python3.X`, so nothing changes. With `pip install --target lib/` inside a project, the grandparent is the project, and a `build/artifacts/MANIFEST` there wins over the wheel's own set (INFERRED, not executed). A guest given that project as its root could plant a runtime that later calls load. Since such a guest could already change the vendored host code, this is not a new escape. Suggested fix: use the checkout path only when the package is not installed from a wheel (for example, when no `artifacts/` sits beside it).

### F9. Entropy in the snapshot — no finding (EXECUTED)

`random`, `tempfile` names and `numpy.random` differ between calls on the snapshot; only the string hash secret is fixed, as documented.

### F10. On Windows the `.cwasm` cache is trusted wherever it is — does not block (READ)

`_private` answers `True` on Windows for any `cache_dir`. The default is under the user's profile, which is fine. An embedder who passes a shared `cache_dir` (or sets `WASI_PYTHON_CACHE`) on Windows would load native code another user wrote. A sentence in the docstring or README is enough for now.

## Interactions between the specs

- **Stop (011) × deadline waits (010):** EXECUTED. Waits in `poll_oneoff` (sleep, select, `sleep(0)` loops) and door loops all ended at the deadline with twelve calls sharing one epoch ticker. READ: `call.stop` sets the epoch deadline to 0 through the caller's context, so a stopped call traps at its next function entry with nothing raised through wasmtime-py.
- **Limits (013) and inputs (014) × defaults (006):** READ. `DEFAULTS` is validated by the same `_check_limits`; `_UNSET` keeps `None` meaning "no limit". No input I found removes a limit. Inputs are checked before any work, so a bad input leaves no root behind.
- **Snapshot × plain reactor:** EXECUTED. The escape probe gives identical answers on both; entropy differs only in the documented hash secret. READ: `__wasilibc_reset_preopens()` after Wizer means the snapshot rebuilds its preopen table from the runtime's.
- **Host door × concurrency:** see the table. I did not run a host function that blocks; a host's own slowness is out of scope by `SECURITY.md`.

## Verdict

**Release after fixing the listed blockers:**

1. F1: `run` must not raise when a guest has used up the host's descriptors (code and a check).
2. F2: the README's "Not protected" names disk use in every root, the private one included.
3. F3: the README names links a guest leaves in a granted root, and says host code must not follow them; the Enforced bullet's wording is narrowed to the guest's side.
4. F4: the owner records, in writing, how §4.15's third clause applies to the stdlib zip in 0.1.0a2.

F5 to F10 do not block. Each should be answered in writing or scheduled.

## Disposition (filled in by the author, then confirmed by the reviewer)


1. **F1 — fixed.** `_instance` now closes the store first, which releases every descriptor the guest opened. Only then does it pop the output keys and remove the stdin scratch folder, with `shutil.rmtree(..., ignore_errors=True)`, which cannot raise.
   - The new v1.2 check, `test_a_guest_that_uses_up_host_descriptors_cannot_make_run_raise`, runs a child process with `RLIMIT_NOFILE` at 256. It requires exit 0, the guest's own "refused" line, and an empty temporary directory.

   - The guest sees WASI's errno 29 (`EIO`) for the refused open.
   - The CHANGELOG names the fix.
   - Windows skips the check (no `RLIMIT_NOFILE`).
2. **F2 — documented for this release.** The README's "Not protected" list now names disk use in any root, the private one included. It gives the order of magnitude and says to point `tempfile.tempdir` or `root` at a size-limited volume. A real disk cap is a later specification.
3. **F3 — documented for this release.**
   - The Enforced bullet now says the guest cannot *follow* a link out, and can still create a relative one.
   - "Not protected" tells host code to open a granted root's files with `O_NOFOLLOW`, or to check `os.lstat` first.
   - Removing or refusing such links at the end of a call is a later specification.
4. **F4 — the owner's written answer** (2026-10-17, asked and answered in the session).
   - The answer: release, with an exception for the alpha line. It is recorded under §4.15: until typed grants land, the stdlib zip may sit in the guest's writable root, verified and replaced before every call.
   - The typed-grants specification ends the exception.
   - The README's "Not protected" list names it.
5. **F5 — accepted for a later change.** The wheel's artifacts are not compared with the set's `SHA256SUMS` outside the build job. The next release-workflow change adds a `cmp` of the unzipped wheel in `same-bytes`. It does not block.

7. **F7 — accepted for a later change.** A trap whose message has a generic first line, such as a stack overflow, will be named by its trap code.

**Author's answer to F11** (the confirmation's new finding): taken before the tag.
