## Short version

The sandbox holds. The guest found no way to the host's filesystem, network or processes. It found no way out of a grant, a root or a mount, and no way to write where nothing writable was granted. The two wasmtime 49.0.0 advisories are closed by the runner's own guards. I tried eleven spellings of the trailing-slash rename, plus the other path calls, through all three linkers. None moved or reached a host folder.

Mounts behave as specified. They have no host path behind them. `..`, absolute paths, nested preopens, links and renames across preopens are all refused. The staging bound and the file-call limit hold.

A cancel in the door is named, and leaves nothing running or behind. The tool protocol gates and counts every frame a hostile guest can send. Only registered tools can be called, and host errors stay on the host.

**One thing blocks.** `tool()` accepts a `functools.partial` on purpose. But it turns each keyword the partial binds into an optional parameter. The bound value becomes the parameter's published `default`. So a credential or user id bound with `partial` is sent to the guest, and the guest can override it (F1). The fix is small and on the host side only.

Two more tool findings should be fixed soon, ideally in the same change:

- a gate that says yes late still runs the tool, after a timeout or a cancel, even after `run` has returned (F2);
- a guest can spend its whole deadline as host CPU, holding the GIL, for almost no fuel, by sending large frames (F3).

The rest are low or notes.

## Findings, most severe first

### F1. A keyword bound with `functools.partial` is published to the guest and can be overridden by it. High; **blocks the release** (EXECUTED)

`tool()` supports `functools.partial` on purpose (spec 031 line 86, `_is_async`, `_doc`). `_derived` builds the schema from `inspect.signature(fn)` (`tools.py:410`). For a partial, that signature lists each bound keyword as a keyword-only parameter, with the bound value as its default. `_derived` then makes it an optional property and writes `"default": <bound value>` (`tools.py:426-438`). A partial's keywords can be overridden by the caller, so the bound value is not fixed either.

What I ran (`probes/p08_tools_partial_and_late_gate.py`, log beside it):

```python
def orders(user_id: int, api_key: str) -> list[str]: ...
mine = tool(functools.partial(orders, user_id=42, api_key="sk-live-SECRET"), name="my_orders")
```

- The schema sent to the guest: `{'user_id': {'type': 'integer', 'default': 42}, 'api_key': {'type': 'string', 'default': 'sk-live-SECRET'}, ...}`.
- In the guest, `inspect.signature(tools.my_orders)` printed `(user_id: int = 42, api_key: str = 'sk-live-SECRET')`.
- `tools.my_orders(user_id=7)` returned user 7's orders.
- `stubs()` would put the same defaults into a prompt (READ, `tools.py:1843-1860`).

**Failure scenario.** The README tells embedders to "pass capabilities, not services… each closing over that caller's authority". An embedder does that with `partial(orders, user_id=request.user.id, api_key=KEY)`, the usual Python idiom, instead of a closure. A prompt-injected guest then reads the key from its own descriptor. It can also call the tool as any user: the tool becomes a confused deputy, acting for the guest with authority the guest should not have. This touches asset 1 (the embedder's secrets) and asset 2 (other users' data).

**Scope.** Only bound keywords whose hint maps to JSON are exposed. A bound connection object is refused loudly ("hint … is not one tool() maps"), so the dangerous case is exactly the scalar credential or id (READ, `tools.py:421-423`, `471`).

**Fix (suggested).** In `tool()`, refuse a partial that binds keywords (walk nested partials). Or drop those names from the schema, and drop any guest key that names one, so the bound value is always used. Never write a bound value into `default`. Add a check: a partial bound with `user_id=42` either is refused, or has no `user_id` in its descriptor and answers `invalid_arguments` to a frame that sends one. No rebuild is needed: `tools.py` is in the wheel, not in the artifact set.

### F2. A gate that allows late still runs the tool after its call timed out or was cancelled, after `run` has returned. Medium; does not block, fix soon (EXECUTED)

The gate and the tool run in one `_Work` on the tool's thread (`tools.py:1309-1331`). When the call times out or is cancelled, `_Bounded._wait` answers the guest and marks the call abandoned (`tools.py:1485-1516`). But nothing between the gate's yes and `t.fn(**args)` checks that mark.

What I ran (same script): a gate that takes 0.6 s, a tool with `timeout_s=0.1`. The guest got `ToolTimeout` and the run returned. Then `gate allowed` and `TOOL RAN` were both logged 0.47 s after `run` returned. The helper saw the same under `cancel=`: the run returned `"cancelled"`, and the tool ran later (`tools-probes/p8_late_gate.log`).

**Failure scenario.** The gate is a human or policy approval, and the tool is `transfer(amount)`. The embedder cancels the request, or the guest retries after `ToolTimeout`. The approval arrives and the first transfer runs anyway, after the request is over.

The README's *Abandoned tools* covers a tool that has *started* ("its effect may still land"). A call still at its gate has not started, so this case can be avoided.

**Fix.** Check the abandoned mark after the gate returns and before the tool runs. If the call was already answered, skip the tool and record that. One check, beside F1's.

### F3. A guest can spend its whole deadline as GIL-held host CPU through frame validation. Medium-low; does not block (EXECUTED by the helper)

Each frame up to 1 MiB is parsed and validated in Python on the door's thread. That cost the host about 0.27 to 0.65 s per frame on this Mac, even for a frame that names an unknown tool (`tools-probes/p4b_cpu_notrace.log`, `p6_flood_profile.log`). Re-sending one prepared frame costs the guest almost nothing. 20 frames cost about 28,000 fuel (against a 152 M baseline), 27 s of wall time and 8.9 s of process CPU. Meanwhile another host thread's p99 wake-up gap rose from 17 ms to 42 ms (`p5_flood.log`).

The frame budget does not bound this. With the defaults, 1,000 frames × about 0.4 s is far beyond 60 s, so the deadline is the only bound. Under `run_async` with several workers, several such guests contend with the event loop. The README states per-frame work, but not the per-run total.

**Fix options:** a per-run budget of request bytes, checked in `admit` before the bytes are read; or a lower default `tool_calls`; or, at least, the per-run cost stated in *Tools* and *Not protected*.

### F4. The signing job trusts whatever artifact is named `release-assets` when it runs. Low; does not block (READ, INFERRED)

`same-bytes`, `verify`, `attest`, `publish` and `pypi` each download the artifact by name (`release.yml:166-185, 247-250, 325-328, 357-360, 383-386`). The build job's artifact id or digest is never passed on and checked. A malicious input used only on a Linux rebuild host could swap that artifact before `attest` runs. Candidates are a Debian `.deb`, the Linux wasi-sdk or a Linux wheel. Such an input is pinned by hash, and would itself have to be malicious. It would need the Actions runtime token, for example through a background process reading a later upload step's environment. Then `same-bytes` would compare the attacker's files with each other, and `attest` would sign them. This was already true for the arm64 rebuild; the new x86_64 job (spec 040) widens it.

**Fix:** output `artifact-id` and a digest list from `build`. Download with `artifact-ids:`, and check `sha256sum` against that list in `attest` before signing.

### F5. Provider paths keep `\`, `:` and Windows device names as written. Low, a documentation gap; does not block (EXECUTED)

`_resolve` treats only `/` as a separator. A provider receives `/..\..\outside\secret` and `/C:\Windows` verbatim (`p02`: `rw seen`). That is correct for a namespace. But a provider that maps paths onto a host folder with `os.path.join` or `Path` on Windows would climb out of its own base. On Windows, a component with a drive even discards the base. The README calls these paths "normalized" and does not warn about this. The spec's use cases (a database, an object store) make host-backed providers likely.

**Fix:** one README sentence: a component may hold any character but `/` and NUL, and a provider backed by a host folder must refuse `\`, `:` and device names, or resolve the path and check it stays inside its base.

Mitigated: every use goes through `pinned()`, which re-hashes the file and refuses a name with no pin (`common.sh:48-54`). Suggest exiting 1 when `VERIFIED != PINS`.
- **N2. `wasmtime>=49,<50` admits 49.0.0, which carries both advisories.** The runner's guards stand in for the fix, and they hold (rows above). An embedder that installs `--no-deps` and drives the artifacts with its own wasmtime does not get the guards. Worth one README line.
- **N3. The release path's human controls cannot be seen from the repository.** Spec 029 is a process aid. `publish` (with `contents: write`) has no protected environment. Branch and tag protection cannot be verified from the repository. `setup-uv`'s cache is probably on by default in build and publish (INFERRED). Suggest rulesets on `main` and `v*`, an environment on `publish`, and `enable-cache: false`.
- **N4. `ToolCall.arguments` holds only what the guest sent, not the defaults.** A gate that reasons about effective values must fill defaults itself. Not documented. A gate returning `None` allows (documented).
- **N5. Abandoned tool threads have no process-wide ceiling** (4 per run; EXECUTED by the helper: 16 after four runs, back to 0 once they ended). Documented, with the reason.
- **N6. Write amplification, the walk after a deadline, a provider that blocks.** As spec 034 and the README say (EXECUTED above).
- **N7. 0.1.0a2's F8 (a3's S4) is unchanged.** `artifact_dir()` still prefers a checkout's `build/artifacts` (READ, `__init__.py:56`). Dispositioned as a later change.

### F4 and a4's PyPI publish (2026-10-18, the coordinator's question)

My recommendation is to publish a4 to PyPI now, with F4 open, and then yank 0.1.0a3 and publish the advisory. **F4 does not block a4's PyPI publish.**

The two risks are not the same size:
- a3 stays PyPI's newest version for as long as a4 waits. a3 carries a confirmed high-severity sandbox escape on macOS (GHSA-m9f7-9w4p-gv38). It is executed, and it is reachable by any guest with a writable grant or root.

A cheap check, which the owner can make before yanking a3: the wheel's and the assets' SHA-256 on PyPI and the GitHub release must equal the `SHA256SUMS` and wheel hash printed in the `build` job's log for the tag's run. That closes F4's window for this one release by hand.
