### Exit paths of `run()` and `Turns`

- **Guest returns, exits, traps, or wasmtime errors:** these fall through to the tail, which
  releases once in the `finally`.
- **`BaseException` inside the `try`** (for example Ctrl-C): `_release`, then `raise`. The tail
  is never reached, so the release happens once.
- **`HostLitter` from `watch.after()`:** the `finally` releases, then the `HostLitter`
  propagates.
  - `litter.remove` never raises (READ: `unseal` tolerates failures, `rmtree` uses
    `ignore_errors`, a leftover only goes to stderr). So a release error cannot mask the
    `HostLitter`.
  - Only a raising `store.close()` could mask it. It would still be chained as `__context__`.
    I know of no case where it raises (INFERRED).
- **Does the watch see the run's own `lib`?** Yes. `Watch(ordered)` is built after
  `_place` + `seal`, with `lib` as a read-only grant whose inventory is compared. `after()`
  runs before `_release`.
- **`Turns.close`:** `_release` once per call. `Turns` does not seal its `lib` (it is outside
  089's scope), and `litter.remove` on an unsealed or missing folder is harmless. A second
  `close()` is harmless too (READ).
- **Paths outside the `try`:** see L1.

## Findings

### B1 (blocks landing): 089's row `test_a_runs_stdlib_folder_is_unsealed_after_a_voided_run` fails on the batch tip

- **What fails:** `assert libs and litter.sealed_leftovers(work) == []` gives
  `AssertionError: []`.
- **Why:** on 089 alone, `lib` outlives the run (unsealed). In the batch, `_release` removes it,
  so `work.glob("run-*/lib")` is empty.
- **Who saw it:** the lane's fast tier in the same worktree has one `F` at 47%
  (`build/lane-fast.log`, line 23), consistent with this row.
- **Why it was missed:** "For the lane" resolves only `guest.py` and does not name this row.
- **Fix, in the batch's merge:** the row states the batch's behaviour, which is stronger: after a
  voided run the stdlib folder is gone, so nothing is left sealed.

  ```python
  assert not list(work.glob("run-*/lib")), "a voided run's stdlib folder is removed (spec 083)"
  assert litter.sealed_leftovers(work) == [], litter.sealed_leftovers(work)
  ```

  Rename it to match if wanted (for example `…_is_removed_after_a_voided_run`), and fix its
  docstring.
- **This does not weaken the judge.** "Gone" implies "unsealed", and the row was added by 089 in
  this same batch. The lane names it in the landing notes as part of the merge's resolution.
- **Re-review:** a one-row delta look is enough, if the change is exactly this.

### L1 (Low): exits between the seal and the `try`, and between the `try` and the watch, skip `_release`

- **Before the `try`:** `litter.seal(lib)` runs about 100 lines before it. Anything that raises
  in between skips the release:
  - `Watch(ordered)`'s `HostLitter (before the run)`;
  - `mpl_data_dir`'s new N1 refusal;
  - a `preopen_dir` or `define_func` error.
- **After the `try`, before the watch:** `store.get_fuel()` and `Result`'s `read_bytes` can
  raise too.
- **What is left:** `lib` stays, sealed on POSIX, and the store stays open, until
  `guest_workdir`'s `litter.remove` at session end. A kill before then leaves it sealed.
- **The before-run `HostLitter` is a real path.** On Windows and as root, the drop check's
  non-binding branch takes it on every run. On Windows nothing is sealed, and `set_wasi` has not
  run yet, so no handle is open. The copy is removed at session end.
- **Not new in shape:** 083's `except BaseException` covered only the `try`, and 089 alone's
  unseal `finally` covered only the watch.
- **Fix when convenient:** one `try`/`finally` from `litter.seal(lib)` to the return, so every
  exit releases once. Decision 3's "at most one per worker" would then hold without exception.

### L2 (Low): the session-start line calls a live judge's sealed stages "left by a killed judge", and its recovery would break that judge

- **Observed (EXECUTED):** each of my single-node runs printed `host litter: 20 sealed folder(s)
  … left by a killed judge (first: …/guest-mcjz_rox/mpl-data-0)`.
- **Whose they are:** those folders belong to the lane's fast tier, running now in the same
  worktree (`pytest -n 3`, pid 38201, started 19:59:28; folders created 20:00 to 20:01).
- **The risk:** following the printed recovery (`chmod -R u+w build/harness` then `rm -rf`)
  while that judge runs would destroy its live stages.
- **Fix:** word it as "left by a killed judge, or held by one running now in this worktree; clear
  them only when no judge runs here". Optionally print it only when the count is non-zero for
  folders older than the session's start.

### N1 (note): on Windows, a `lib` that cannot be removed is now named on stderr

- 083's reviewed `_release` was silent. `litter.remove` makes five immediate tries, then writes a
  stderr line.
- With `store.close()` first, the handles should already be gone. If they are not, the release
  dry run shows a stderr line, never a failure.
- No action. Worth a glance in the next Windows dry run's log.
