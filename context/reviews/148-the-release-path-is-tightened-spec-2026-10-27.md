## The PyPI provenance: A, B or C

I recommend **A**: accept the loss of PyPI's PEP 740 provenance object. The project's proof of origin is the GitHub attestation over the wheel's digest, and it verifies the very bytes PyPI serves: `gh attestation verify` on a wheel fetched from PyPI checks the same SHA-256 the `attest` job signed (INFERRED; the verify page documents the command, and no page claims PyPI's provenance, EXECUTED grep of `README.md`, `SECURITY.md` and `docs/`). PyPI still records that the file came through this repository's trusted publisher (INFERRED). **B** puts a signing tool and its dependency tree (Sigstore's client and what it pulls) into the one job that holds `id-token`, with pins of its own, which is a larger surface than the finding removes and more bytes than uv. **C** keeps an unpinned container image holding `id-token`, the finding itself. A is reversible: when uv makes attestations itself, one flag on the pinned tool restores the object with no new dependency.
