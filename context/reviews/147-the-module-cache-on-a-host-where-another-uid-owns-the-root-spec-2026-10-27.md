## The questions the brief asked, answered first

1. **Is the trust argument sound?** For `/` itself, yes, in every case tried; for a folder below `/`, yes on `/`'s own file system and no past a mount point, which is M1. The argument has two halves that the specification treats as one. Exempting `/` from the owner test is sound everywhere: on a writable `/` its owner can `chmod` it and rename any entry, so it already decides where every path leads; on a read-only `/` no one can rename an entry of it; and below a mount the owner of `/` cannot rename the mount (`EBUSY`), so it cannot redirect the way past it either (INFERRED). Trusting `/`'s owner on a folder *below* `/` adds nothing on `/`'s own file system, since that owner could already rename an ancestor of it, but past a mount point its only power over a folder is owning it, which is today's "another user's" case exactly (INFERRED). The specification names that case and rests it on the `/etc` argument, which needs a writable `/` as well as a setuid program; a read-only root with a writable volume for the cache is the common hardened container shape, and there the argument does not hold at all (M1).
2. **What today's code answers, and what Decision 1 would** (EXECUTED, `build/147-review/probe_way.py`, cache at `/home/runner/.cache/wasi_python`, `/home/runner` and `.cache` this user's at 0700). Cloudflare's shape, `/` 2346 at 0755 and `/home` 2346: today refused at `/` ("is another user's (uid 2346)"), 147 used. `/` 2346 at 0555 (not writable by its owner): today refused, 147 used, which is right, since an owner may `chmod` without write permission. `/` 2346 at 0777: today refused for its owner, 147 refused for its mode. `/` 2346 at 1777 (sticky, world-writable): today refused, 147 used, right, since a sticky `/` lets only an entry's owner, `/`'s owner and root rename. `/` root's and `/home` 2346: refused by both, at `/home`, so nothing is trusted below a root-owned `/`. `/` 65534 and `/home` root's: today refused, 147 used. `/` and `/home` both 65534: today refused at `/`, 147 refused at `/home`, so the overflow uid is trusted on `/` alone, as Decision 1 says. ## Findings, most severe first

1. **M1. Past a mount point, trusting `/`'s owner adds it, and the reason given for leaving that open is half right** (Decision 1, "Below a mount point"; the predicate's rule 2) — On `/`'s own file system the owner of `/` could already rename an ancestor of any folder below, so trusting it there adds no one. Past a mount point it cannot rename the mount (`EBUSY`), so its only power over a folder there is owning it, which is today's "another user's" refusal; the specification rests that case on the `/etc` argument, but that argument also needs a writable `/`, and on a read-only root (the hardened container shape, a writable volume for the cache) it fails whatever setuid programs exist, which the bullet does not say. Its reason for not closing it, "Reading `st_dev` would not close it, since a bind mount keeps `/`'s device", holds only for a bind mount of `/`'s own file system: every other mount (a volume, a tmpfs, a bind mount from the host) has a device of its own, and the walk already holds `st_dev` in the stat it reads, so the check costs no system call. Failure: a read-only `/` owned by uid R, a volume at `/home` whose root R owns at 0755, the cache below it in this user's 0700 folders: the walk passes `/home` (INFERRED from the predicate), yet a process running as R can rename `/home/runner` away and put another folder at its name, which is the swap the way check exists to rule out. The leaf checks still stand behind it (the cache folder and the `.cwasm` must be this user's, read through the checked descriptor), so R plants nothing of its own (INFERRED); what is lost is the way check's own guarantee, which is the guarantee this decision claims to keep. **Fix text for Decision 1's predicate:** rule 2 becomes "it is another user's: `here` is not `/`, and `owner(st)` is neither `e` nor `0`, nor `r` on a folder whose `st_dev` is `/`'s, where `r != 65534`"; the code line becomes "refused for its owner when `here != here.parent and not _this_users(st) and owner(st) != 0 and not (owner(st) == r != _OVERFLOW_UID and st.st_dev == root_dev)`", with `root_dev` read from the walk's first step beside `r`. **For the mount bullet:** "**Below a mount point.** The owner of `/` cannot rename a mount point (`EBUSY`), and on a read-only `/` it can neither rename an entry nor replace `/etc`, so past a mount its only power over a folder is owning it. So it is trusted below `/` only on a folder on `/`'s own device (`st_dev`, from the stat the walk already holds); a folder on another device that it owns is refused as another user's, as today. A bind mount of `/`'s own file system keeps `/`'s device and is not told apart: that remainder is named, not closed." **For row 1:** "(d) `/` and the folder above the cache that uid, the folder above with a stand-in `st_dev` of `/`'s plus one: not used, the warning names the folder above. Red today: it names `/`."
