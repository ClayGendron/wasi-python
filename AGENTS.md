# Project guidance for Claude Code

## What this is

A statically linked CPython for `wasm32-wasip1` with numpy and pandas compiled in as builtin modules, built from pinned sources as a few releases rather than a build of every version of every package. The product is the artifact set (`python.wasm`, the snapshot, the stdlib zip, the manifest) and the small `wasi_python` wheel that carries it. Read `context/constitution.md` first: it is the mission, the goal and the hard constraints, and it governs this file. Then `README.md` and `context/README.md`.

## Rules that bind all work

- **Upstream patches are few, recorded and temporary** (constitution §4.1, amended 2026-10-17). An adaptation is a recipe file under `recipes/` first (a cross file, a compiler wrapper, a rename header, a stand-in module). An unavoidable source change is a patch file under `recipes/patches/`, reviewed, hashed in `MANIFEST`, named in the CHANGELOG, with its upstream pull request drafted under `context/upstream/patches/` for the owner to send, and deleted once upstream releases the fix. `scripts/steps/apply_patches.sh` applies them, and the release fails on any difference from a pinned tarball other than exactly the recorded patches (spec 020).
- **Every input is pinned by URL and SHA-256** in `downloads/SHA256SUMS` and verified before use. Downloads are untrusted: they unpack under `downloads/` and `build/`, never into the system, and run only as build tools or under wasmtime.
- **uv only.** `uv run …`, `uv sync`; never a bare `python` or `pip`. `ruff check`, `ruff format --check` and `pytest` stay green on `src/` and `tests/`.
- **Prior art is studied, never copied.** `context/prior_art/` holds shallow clones, git-ignored and read-only. Read, grep, cite, describe; every line of code here is ours. Check the licence right after cloning and record it in `context/prior_art/README.md`. Building a dependency from its released source is not copying.
- **Tests count operations, never wall-clock.** Cold-start and speed numbers belong in a research memo as benchmark facts.
- **Artifacts never live in git.** `*.wasm`, `*.cwasm`, `*.zip` and the build trees are ignored; hashes and sizes are recorded in the memo or the manifest.
- **Nothing lands unreviewed.** A built change is reviewed by a fresh agent or a person who did not write it, given the specification and the diff, before it lands; the review is the pull request's review file, `context/reviews/NNN-<slug>-pr-YYYY-MM-DD.md`, committed after the last code commit and cited in the landing notes, and `ci-status` checks for it (from step 3 of spec 138). Findings are fixed or answered in writing first.
- **Structure is reviewed, not only behaviour** (spec 108; the design review `context/research/2026-10-20-a-design-review-of-the-runner.md`). A specification is **structural** when its change to `src/` adds a module-level mutable or lock outside `_process.py`, a use of wasmtime-py's private API outside `_wasmtime_ffi.py`, a platform branch (`sys.platform`, `os.name`, `platform.system()`) outside `_platform.py`, a test seam that is not on the process object, or takes a module past the size ceiling or a function past 80 lines. Its Kind line carries the bold word **structural**, and it is reviewed before it is built, as a change to the build recipe is (constitution §5.6), against the eight-row rubric in `context/reviews/README.md`. The rules checks of specs 103 to 108 hold the letter of this; the review holds its spirit. Before every release, a fresh agent writes a structural review of `src/` against the same rubric, `context/reviews/<version>-structural-review-YYYY-MM-DD.md`, beside the security review; the release waits on its High findings, and the judge refuses a released version without one.
- **Code speaks for itself** (the owner, 2026-10-20). A code file (`src/`, `tests/`, `scripts/`, `release/`) names no specification, memo, review, finding ID or `context/` path (in comments and docstrings; the judge reads `context/` as data): its comments and docstrings give the reason in words, and the number lives in the specification that cites the file. A `context/` document may cite and link code files. `src/` is cleared by spec 107 and held by its check; `tests/`, `scripts/` and `release/` by spec 109. A page under `docs/` and the README name no specification, question, decision, wave or review number, no `context/` path and no name from `context/embedders.txt`; the judge's scans read them whole (spec 122).
- **Commit or push only when asked**, with pushes to a pull request branch allowed once the owner has asked for the specification to be built. A specification is built on a branch made from `dev`'s tip (`spec/NNN-<slug>` by convention, in a worktree outside the repository if you like) and merged into `dev` by a pull request (constitution §4.14); no other long-lived branch or worktree unless asked. Only the owner pushes `main`. Never `git checkout`, `git restore` or `git stash` a file that carries uncommitted work.
- **All project knowledge lives in this repo** under `context/` (the agents' memory) and `docs/` (what we tell users); no out-of-repo memory.
- **Every package runs its own tests in the release** (spec 063). A specification that adds a package adds its suite's groups under `tests/upstream/` and to a shard in `tests/release_shards.toml`, or says in `tests/upstream/packages.toml` why not yet; the judge checks it.

## Working autonomously

How an agent works here alone, drawn from the ports that converged (`context/research/2026-10-16-how-autonomous-ports-were-run.md`), and since 2026-10-25 through pull requests into `dev` (`context/specifications/138-pull-requests-into-dev-and-the-judge-runs-where-it-is-needed.md`). The judge is `uv run pytest`; its scoreboard is the progress signal (`context/specifications/002-the-progress-harness.md`). Two branches carry the work. `dev` is the default and integration branch; it changes only by the squash merge of a pull request. `main` holds released states and the tags; only the owner pushes it.

A change goes through nine steps.

1. **Orient from the scoreboard, not from memory.** Start every session with `uv run pytest -m "not slow"`. Read its last twenty lines: the count per goal, the failures, the ratchet, and the `next:` line. Then read the specification you are on. The fast tier's last measured time is in `docs/contributing/first-change.md`, labelled with its date; the `quick` job's joins it once that job is measured.
2. **Pick work by what it unblocks.** The `next:` line names the prerequisite that blocks the most checks. Work on the specification that provides it, once the owner has asked for it to be built.
3. **Write the check before the code.** A new behaviour gets a check (or a gap entry naming its closer) first. A new failure mode, once seen, becomes a check, so it cannot come back. Iterate locally on the fast tier, and run a slow check you are changing alone by its node id. The full judge runs in CI, not on your machine.
4. **Branch from `dev`.** Make the branch from `dev`'s tip (`spec/NNN-<slug>` by convention), with one to three specifications on it. A worktree is your convenience, not a rule. Bring the branch up to date by rebase (`gh pr update-branch --rebase`), never by a merge commit: the head is what the judge reads.
5. **Open a pull request with its news file.** Push the branch and open a pull request into `dev` (`gh pr create --base dev`). A change that is not documentation only carries its news file, `context/changes/NNN-<slug>.md`: its CHANGELOG line, the README rows it adds or moves, and its claim block. The pull request's description is its self-check: the author named (session or name), every new check seen failing first, the Windows legs read, every gap naming its closer, the news file present. The pull request template, `.github/PULL_REQUEST_TEMPLATE.md`, holds these from step 6 of spec 138.
6. **Read `ci-status` and the gather's summary.** The run is chosen by the changed paths: `quick` always; the product's own shards on Linux and Windows from the cached set unless the change is documentation only; macOS, the upstream groups or the merge-grade set when the paths, the label `ci:full` or a `citest:full` commit line ask for them. Read `ci-status` and the gather's summary in the job summary (`gh pr checks`, `gh run view <id>`). A red line is fixed by a new commit on the same branch. No run is dispatched by hand for a change. A specification is built once its pull request's `ci-status` is green; its landing notes name the run id.
7. **One review, its file committed last.** A fresh agent or a person who did not write the change reads the specification, the diff and the pull request's run, and dispatches no run of its own. It writes `context/reviews/NNN-<slug>-pr-YYYY-MM-DD.md` in the template of `context/reviews/README.md`. There is no confirmation round: the author answers in the pull request, a code fix is a new commit on the same branch, and the reviewer reads it and signs again. The review file is the branch's last commit, after the final code commit. A Low that touches only `context/` the reviewer may commit itself. The pre-build review stays where constitution §5.6 requires it (the guest's imports or exports, the artifact set, the build recipe) and for a structural specification.
8. **Merge when green and the review says "Lands".** The builder merges its own pull request with `gh pr merge --squash` once `ci-status` is green and the review's verdict begins "Lands"; the owner's instruction to build the specification is the instruction constitution §7 asks for. No merge into `dev` while a release pull request runs, or while `dev`'s last post-merge run is red, except the fix or a revert. Only the owner pushes `main`.
9. **The post-merge run accepts.** Each merge runs the full normal tier once on three systems. When its gather is green, a job writes the record into `context/progress/` (`uv run pytest --accept-from`, with the reasons from the news files) and pushes one acceptance commit to `dev`. A red post-merge run means `dev` is broken: the author of the merged change fixes forward the same day or reverts, and nothing else merges until `dev` is green. The local `uv run pytest --accept "<reason>"` stays for a machine that must accept without CI; it is not part of the normal flow (`context/progress/README.md`). A release is a pull request from `dev` to `main` whose check is the whole workflow; the owner moves `main` to its acceptance and tags it.

Until step 3 of specification 138 lands (written 2026-10-25, removed by that step), the old acceptance rules hold: `ci-status` and the post-merge run arrive with its step 2, and the news files, the review check and the accept job with its step 3; before step 2 a code change is judged by a dispatch of the release workflow on its branch, as before; until step 3 a merge into `dev` is accepted locally by the owner's agent with `--accept` as today (`context/progress/README.md`, "Local acceptance"), the CHANGELOG line goes under the one unreleased section by hand, and a context-only merge needs no acceptance.

These hold at every step.

- **Never weaken the judge to get a pass.** Do not edit a check, a golden output, `tests/known_gaps.toml`, the upstream suites' allowances (`tests/upstream/*.toml`, `tests/upstream/expected/`, CPython's plan `tests/upstream/python/`) or `context/progress/` to turn a run green. Changing the judge is its own change, with a reason, and the review sees the judge-hash line.
- **No pass is lost quietly.** A run that loses an accepted pass is red; no reason clears it. On a pull request, fuel or bytes that grow, fewer upstream passes and a check moved between tiers are listed under `GROWTH` with the reason the news file gives, and are not red. At acceptance each needs its reason: the news file's claim block, or locally `--accept "<reason>" --accept-growth "<why it grew>"`. New passes never pay for a lost one.
- **Two strikes, then write it down.** After two failed attempts on one hypothesis, stop. Record where you stood and why in the memo or specification, and move to work that does not depend on it.
- **Commit only what you mean.** Before every commit, read `git diff --cached --stat`: a `git mv` or an earlier `git add` stays staged and rides along. A commit on `main` is green on its own; when two pieces of work share the tree, check the commit in a clean clone. A pull request's branch carries one to three specifications and nothing else.
- **Keep output short.** Logs go to files under `build/`; a failure is one line with its reason.
